# Texture format index: every value the library can emit

Release IRIX 6.5.30m, `libGLcore.so`, all six IP30 and IP35 builds (o32, N32, 64-bit) and the patch 4103 builds. Names are the routine names from the N32 library's debug information. Addresses are N32 (`usr/gfx/arch/IP30ODSY32/libGLcore.so`); the other builds are listed under "Other builds".

The index is the six-bit field in bits 25:20 of word 1 of a level descriptor (blocks 0x280 + level, [buzz.md](../buzz/README.md#level-descriptor-words-blocks-0x280--i)). The library picks it from the GL internal format and never from the texel data. Four routines turn it into everything else the library knows about the format. They read no context and call nothing, so each was run in the MIPS interpreter for every input (`retools/tools/odsy/texfmt_sweep.py`, output in `libglcore/runs/texture-format-index-sweep.txt`): 

| Routine | Address | Maps | Entry |
|---|---|---|---|
| `ChooseSuitableBuzzTexObjFormat` | 0xd9cfdc0 | GL internal format to index | [entry](../../software/opengl/libglcore-odyssey-reads.md#texture-format-class-codes-and-the-mipmap-fill-in) |
| `CalcTexelSizes` | 0xd9d01d0 | index to six component widths and a size code | same section |
| `ChooseSuitableBuzzTexModeBaseFmt` | 0xd9cfc80 | index and GL internal format to a 3-bit class | same section |
| `GetImageFmtEnumFromBuzzTexFormat` | 0xd9cfbd0 | index to the pixel class of [pixel-paths.md](../buzz/pixel-paths.md) | same section |

The words around the index (level-table entries and the bits the library writes, per-axis wraps, the environment block, the texture colour table, 3D levels) are in [texture-state.md](texture-state.md).

## The table

Grades follow the repository rule. Each row's "selection", "widths" and "pixel class" columns are **established**: the routines were read in full and every input run. The component names in the widths column (which output is R, G, B, A, luminance or intensity) are **inferred** from which GL formats land on the row. Two facts hold for every row and are **unknown**: how the board packs the texel (bit order, whether a 12-bit value sits in 16 bits), and whether the board treats the index as a layout code or as an opaque number. The allocator sizes storage by the size code (`2 << c` bytes per texel, `AllocateGfxMemForTexture`, **established**), which is a unit the allocator uses, not a measured packing.

Widths are in bits, in the order the routine writes them: R, G, B, A, L, I. Component bits is their sum. "Class" is the 3-bit value `ChooseSuitableBuzzTexModeBaseFmt` returns: 1 alpha, 2 luminance, 3 luminance-alpha, 4 intensity, 5 RGB, 6 RGBA (names **inferred** from the formats that give each; the board's use of the value is **unknown: no shipped software or published source shows it**; silicon test: bind one texture with fixed texel data and sweep only the class field of mode word 4 (bits 25:23) over the six values the routine returns, one value per drawn frame, sample it on a flat quad with modulate off and read the fragment colour back, to see which components each class feeds from the texel). Where a row has two classes, the first is for the listed RGB-family formats and the second for the RGBA-family ones.

## Who writes the field

Three routines store the index into a descriptor word. The scan was every use in the N32 library of the mask for bits 25:20 (`lui 0x3f0`) and of the shift that places a field at bit 20; a store built another way would not show. The odyssey.so X module and the kernel's odyssey.a have no `lui 0x3f0` and no 0x10ebc operand word. The writers:

- `__glOdysseyTextureActivate` (0xd9d1f90): two loops, one for the primary levels (the field at 0xd9d216c) and one for the detail levels (0xd9d23dc). Each takes the per-level record's index at texture-object offset 1364 + 68 x level, which `AllocateGfxMemForTexture` (0xd9d03b0) filled from `ChooseSuitableBuzzTexObjFormat`.
- `DownsampleTextureThruHW` (0xd9d11a0), field at 0xd9d14b8: the same record, to render the next mipmap level on the board.
- `__glOdysseyImageMovePixelsTexture` (0xd9bbff0), field at 0xd9bc338: the index comes from `__glOdysseyImageCalcTexObjFormats` (0xd9beda0), a table from the pixel class of the source image: class 0 gives 0, 1 gives 2, 2 gives 4, 3 gives 8, 4 gives 9, 5 gives 10, 6 gives 11, 7 gives 12, 8 gives 13, 9 gives 16, 10 gives 17, 11 gives 18, 12 gives 33, 13 gives 32, 14 gives 48, 15 gives 49, 16 gives 4 and 17 gives 10; 18 and above fail. **Established** (the routine's 416 bytes read, every class run).

The detail-texture format test in `__glOdysseyValidateTexture` compares level-0 indices only, so `GL_RGBA4` and `GL_RGB4` count as one format for it.

## Index 12 is RGBA4444 storage; the RGB reading is the class

Both statements are right, because the library sends two different fields for one texture:

1. **Storage index** (level descriptor word 1 bits 25:20). Index 12 is always the 4/4/4/4 layout of `CalcTexelSizes` and pixel class 7, "RGBA 4/4/4/4". Four GL formats select it (`GL_RGB2_EXT`, `GL_RGB4`, `GL_RGBA2`, `GL_RGBA4`) and so does `GL_R3_G3_B2`, which the library stores in this layout and not in the 3/3/2 layouts 6 and 7. Established.
2. **Class** (mode word 4 bits 25:23, [BUZZ.h](../buzz/BUZZ.h) TEXMODE4). `ChooseSuitableBuzzTexModeBaseFmt` returns the class from the index and the GL internal format the application named: for an alpha-capable index (12, 13, 17, 18, 32, 33, 49) it returns 5 (RGB) when the format is `GL_R3_G3_B2`, 3, `GL_RGB`, or `GL_RGB2_EXT` to `GL_RGB16`, and 6 (RGBA) for any other format. So a `GL_RGB4` texture carries index 12 and class 5, a `GL_RGBA4` texture index 12 and class 6. Established; the calls are at 0xd9d2264 and 0xd9d247c in the activation routine, which stores the result through `sll 0x17` into the object's mode word at +180 and at 0xd9d13fc in the mipmap builder (stored at context +0x7cd4, shadow TEXMODE4).

So a template that pairs index 12 with an RGB component set was built from an RGB-family internal format: the index says "4/4/4/4 storage", the class says "no alpha". It is the combination (index, class), not a different meaning of 12. There is no host-transfer meaning of 12 that differs from the texture meaning: in the move path index 12 comes from pixel class 7 and the class stored is a constant 6 (the routine ORs 0x03000000 into the word at 0xd9bc298), so a 4444 pixel source always arrives as RGBA. In the pixel path 12 is not a pixel class; the pixel class that index 12 maps to is 7.

What stays **unknown**: the meaning of TEXMODE4 bits 25:23 on the board (the library only stores them; **Test that settles it:** a published texture-unit description of the activation field, since no shipped code reads the bits back); what an RGB-family upload puts in the unused 4-bit alpha field of index 12 (the library's host-conversion path was not traced for this; **Test that settles it:** trace the host conversion that packs an RGB-family upload into index 12 and read what it stores in the alpha nibble); whether the board forces alpha to 1 for class 5. That class 5 is "RGB, alpha 1" is **inferred**.

## The class and index pair, the size code and the booked size

Three questions the table raises. All three were answered from the N32 library (IRIX 6.5.30m, `IP30ODSY32`) by reading the writers and the callers; the board's own behaviour is unknown in every case and is said so.

### Does anything check the class against the index?

Short answer: **unknown for the board**. **Established** that no software on the reference install checks it, and that the library itself sends pairs the texture path never produces.

Every store of the index (word 1 bits 25:20, mask `0x3f0` at bit 20) and of the class (TEXMODE4 bits 25:23) in the N32 library, by instruction scan of the whole extracted assembly (`lui 0x3f0`, `lui 0x380`, the shifts by 0x14 and 0x17):

| Writer | Index | Class | Pair |
|---|---|---|---|
| Activation, primary levels (0xd9d1f90) | store 0xd9d217c, from the level-0 record's index for every primary entry | selector call 0xd9d2264 on the level-0 index and level-0 GL format, stored to the object's mode word at 0xd9d22ac | Always a pair the class selector returns for that index. **Established**: the code was read in full. |
| Activation, detail levels | store 0xd9d23ec, from each detail level's own record | selector call 0xd9d2484 on the detail object's level-0 record, stored to the detail object's own mode word at 0xd9d24b4 | The detail object's word is never copied to the board; the validation routine copies only the bound primary object's mode word (load 0xd9d2cbc, store 0xd9d2cd8), so the class that reaches TEXMODE4 is the primary's. A detail level whose own index differs from the primary's level-0 index (the format test compares level 0 only) would pair with the primary's class. Whether a caller can build such a chain: **unknown** (not traced). |
| On-board mipmap builder (0xd9d11a0) | store 0xd9d14cc, from the level's index with 0 mapped to 4, 1 to 5 and 8 to 10 (the index is loaded at 0xd9d1244; the branches at 0xd9d1248 and 0xd9d1250 give 4 and 5, the select at 0xd9d1268 to 0xd9d1270 gives 10) | selector call 0xd9d1404 on that mapped index, stored at 0xd9d1428 | A selector pair for the mapped index. **Established.** The mapping reads an alpha texture's source level as luminance. It is **inferred** that the alpha and luminance twins (0 and 4, 8 and 10) therefore describe one stored layout, since the same bytes are sampled under both indices. |
| Pixel-to-texture move (0xd9bbff0) | store 0xd9bc34c, from the pixel class table (0xd9beda0) | the constant `0x03000000` (class 6), 0xd9bc288 to 0xd9bc298, for every pixel class | Class 6 with whatever index the table gives. **Established.** |
| X server start-up (`odyssey.so`, default hardware set-up, 0x15c6d50 to 0x15c6d6c) | none: no level descriptor is sent there | class 6 in the shadow word at +348, sent in block 0x016 at 0x15c6d9c | Class 6 with whatever index the board already holds. **Established** for the class store; that no descriptor is sent there is **inferred** from an operand scan of the module. |

The move also computes the natural class for its index, the second output of the table routine (class 1 for pixel class 0, 4 for pixel class 1, and so on), and never reads it: the output slot is cleared at 0xd9bc004 and its address passed at 0xd9bc17c, and the routine has no other reference to it. **Established.** So for the indices whose class selector value is not 6 (every index except 12, 13, 17, 18, 32, 33 and 49) the move sends a pair the texture path cannot produce. Reachable examples, **established** from the code that builds the move's source object (`ImageChainValidateScratchBufferFormats`, 0xd98f810 to 0xd98f9a4, which stores four pixel-class and size-code pairs: class 12 with size code 2, class 10 with 1, class 17 with 0 and class 5 with 0): pixel classes 5 and 17 both give index 10 (12-bit luminance), whose selector class is 2, and the move sends class 6 with it. That this chain step is reached was not traced; the code that selects each of the four cases was not traced.

Nothing else reads either field. The kernel driver, IP30 build: its context-restore routine replays block 0x016 (header 0x11c16, seven operands at shadow offsets 332 to 356, `odsy_ctxsw.o` 0x1004 to 0x105c) and the 64 level descriptors (header `0x10e80 | i`, three words each from shadow +360 + 12 i, 0x1acc to 0x1b1c) as plain loads and stores with no mask or compare. No object of `odyssey.a` has `lui` with 0x380, 0x3f0, 0xfc7f or 0xfc0f in a texture context (the one `0x380` in `odsy_init.o`, at 0x2940, sits inside `odsyInitInterrupts`, and the shifts by 0x14 in `odsy_ctxsw.o` pick vertex-attribute slot selectors). **Established** for the IP30 objects of this install; the IP35 and patch 4103 objects were not rescanned (**inferred** the same). The transform microcode takes vertex data and parameter memory ([buzz_isa.md](../../ucode/buzz_isa.md)) and has no instruction that reads class-1 raster blocks; that it never sees these fields is **inferred**. No library or driver reads the state back to check it, and nothing tests an error status after sending it.

What the board does with a pair the table does not contain (class 1 with index 17, or class 6 with index 10): **unknown: no shipped software or published source depends on it** except the one case above, where the library relies on the board accepting it. Routes tried: every writer in the library (above), the X module, the kernel objects, the microcode documentation, the published patents (texture cache and texel sizes only). Nothing in software settles it.

The library's own move path sends class 6 with index 10, a pair outside the activation table, so the library relies on the board accepting at least that pair (**inferred**: it assumes that step runs on a working board). The library takes the stored layout and component widths from the index, and the component set the texture environment sees (alpha, luminance, luminance-alpha, intensity, RGB, RGBA) from the class. The class cannot be derived from the index: index 17 is sent with class 5 for `GL_RGB8` and with class 6 for `GL_RGBA8`, and the same four bytes are stored. A discriminating test on a board sends the pair (class 6, index 10) and checks that the write is accepted and a nearest sample of a known 12-bit luminance texel returns the same value in the colour components; the alpha of such a sample is **unknown**.

### Do bits 31:30 mean the same for the pixel-to-texture move?

Short answer: **yes as a quantity, inferred; unknown as board behaviour**. The field is the log2 of the bytes per texel the buffer holds, minus 1 (0 for 2 bytes, 1 for 4, 2 for 8), in both paths.

- Texture path, **established**: word 1 bits 31:30 take the level record's size code (object +1368 + 68 level), the `c` of `CalcTexelSizes` for the index (0 for indices 0 to 15 and 48, 1 for 16, 17, 18 and 49, 2 for 32 and 33; see the table). Stores at 0xd9d2194 (primary, level-0 record for every primary entry) and 0xd9d240c (detail, each detail level's own).
- Move path, **established**: word 1 bits 31:30 take the source buffer object's word at +40 (`lw` at 0xd9bc2e4, shift at 0xd9bc2f8, store 0xd9bc308). The buffer descriptor is the layout the texture upload builds for its destination (`LoadTextureFromHost`, 0xd9d08a0): the upload stores the record's size code (record +4) at the same +40 and +44, `CalcPixelModePixelFormat` of it (0xd9d0390: 1 when the code is 1, else 0) at +48, the pixel class from the index at +52 (call at 0xd9d0b40), the level's tile pitch at +28 and the width and height at +32 and +36. The move's offset helper reads +44 and +48 the same way.
- Value agreement, **established** for the cases that store the field: the four pixel-class and size-code pairs of the scratch-buffer routine above agree with the table (class 12 is index 33 with code 2, class 10 is index 17 with 1, class 17 and class 5 are index 10 with 0), and the window description (`__glOdysseyImageDescribeWindow`, 0xd989710 to 0xd989b34) stores to +40 the base-2 logarithm of a context value minus 1, the same form; that the value is the window's bytes per pixel is **inferred**. Not every routine that builds a move source (the stack descriptors in the colour-matrix, depth, stencil and convolution steps, and the host-image conversion) was read, so that the field equals the index's size code for every object is **inferred**.
- Difference: the texture path takes one value per level from the format, so every primary entry carries level 0's code. The move takes it from its own source object and writes it into descriptor slot 60 (block 0x2bc, `0x00010ebc`), which the on-board mipmap builder also uses for its temporary source descriptor (0xd9d1468 to 0xd9d14cc).

The library derives bits 31:30 from the index in both paths. Whether the board reads the field as a size, as a layout selector or ignores it is **unknown** **Test that settles it:** a published description of the level descriptor's top bits, or a texture upload that sets them differently from the size code (none ships); see the next section for what the library sends elsewhere.

### Does anything on the board side depend on the booked bytes per texel?

Short answer: **yes**. The booked size is not library-side accounting. It reaches the board in four ways, and in one of them (3D uploads) the board's packing has to agree with it.

1. **Placement, established arithmetic.** The allocator (0xd9d03b0) sends the kernel a 72-byte request whose byte 1 is `2 << c`. The kernel's object constructor (`odsy_pmm.o` `odsy_mm_obj_new`, 0x2bc4) accepts only 2, 4, 8, 16 and 32, stores the size as the tile count times (depth plus its offset), shifted left by a table entry (0 for 2 bytes, 1 for 4, 2 for 8, 3 for 16, 4 for 32; `.data` +0 of `odsy_pmm.o`, read at 0x2d84 to 0x2da4), and the extent search (`mm_check_enode`, 0x6248) aligns the start to 2 shifted left by the table entry units and keeps objects of different element sizes out of one 32-unit block. The extent's start times 32 is the per-level value the library puts in word 0 bits 28:0. The kernel stores the extent's start times 32 as the object's board address, and the library's per-level values (word 0 bits 28:0) come from these objects; that link is **inferred** (the library's reference routine was not followed into the kernel's table), as is the board reading word 0 as an address (the level descriptor entry). If both hold, the per-level addresses the board receives depend on the booked bytes.
2. **Word 1 bits 31:30 are the size code.** The same `c` that is booked as `2 << c` is sent (above). **Established.**
3. **3D texture uploads, established library side, inferred board side.** For a 3D texture the upload computes each slice's offset itself: slice number times the record's tile count (record +16, rounded up to a power of two by the allocator at 0xd9d0784 for depth 2 or more) times `2 << c`, times 256, divided by 16 (0xd9d0ce8, 0xd9d0d3c, 0xd9d0dd8 and the loop step at 0xd9d0dec), and passes it as the destination object's offset (+24) in the unit of word 0. So the library stores slice k at k times a stride that uses the booked bytes. Activation sends word 2 bits 11:0 as the base-2 ceiling of the slice tile count (0xd9d21ec to 0xd9d224c, 3D targets only) and nothing else about the slice stride. For the board to find the slice the library wrote, its slice stride must be 2^word 2 tiles times the tile size of the index, and that tile size must be 256 texels times the booked bytes per texel (512 bytes for code 0, 1024 for code 1, 2048 for code 2). That the board derives its stride this way is **inferred**; it is the only reading under which an upload and a later sample agree. The same arithmetic fixes the kernel's unit: the library's per-tile step of 32 address units at 2 bytes per texel equals the kernel's start times 32 per tile, so the kernel's extent unit is one 16 by 16 tile at 2 bytes per texel (the kernel's own failure message counts "2Bpp tiles"). That the address unit is 16 bytes (as the DMA header divides by 16) and the tile is 16 by 16 texels are **inferred**.
4. **The on-board mipmap builder sends it again.** It writes the destination level's render-target words at context +0x969c to +0x96a4 with the size code at bits 12:10 and again at bits 15:13 (0xd9d15fc to 0xd9d1634) and the "4-byte" flag from `CalcPixelModePixelFormat` at bits 9:7 (0xd9d15e0 to 0xd9d15e8). **Established.**

What the booked size does not determine: the pitch. Word 1 bits 11:0 come from the width in 16-texel tiles rounded up to even and never from bytes (0xd9d20b0 to 0xd9d2110). So the board must know the bytes per texel from the index, and the library's booking is only a bound on it.

Evidence that booked bytes are an upper bound and not the packing:

- ICC formats (indices 48 and 49), **established**: activation computes the pitch from half the width, rounded up to a tile (0xd9d21b0 to 0xd9d21dc), while the allocator has no ICC case and books tiles for the full width. The board sees half the tile count the allocation holds.
- Image scratch buffers, **established** creation: the library books them at 8 bytes per pixel with kind 6 (0xd988ca8, 0xd988ccc, 0xd988dd8, 0xd988e04), while the size codes stored on the move's source object are 0, 1 or 2 (above). That the move's source objects live in those buffers is **inferred**.

So for 2D textures the software needs only self-consistency: upload and sample both go through the board with the same descriptor, and packing no larger than the booked bytes cannot overlap a neighbour. For 3D textures the booked bytes are a contract, as in item 3. Nothing else observes the 2D layout, so the board may pack tighter than the booked bytes there, but not for 3D. The packing of the board's 8-, 12- and 24-bit formats inside the booked 2 or 4 bytes stays **unknown**. Discriminating test for 3D: upload two slices of a 3D texture of index 17 and sample slice 1 with the third texture coordinate; the result must come from the second upload, and must not if the board's slice stride is not 2^word 2 times 1024 bytes.

## Sampler word 4: the context-kept field (bits 22:18 and bit 0)

`__glOdysseyValidateTextureState` (the merge and store at 0xd9d2cd0) builds word 4 of block 0x016 from the texture object's word with the context's own bits merged in under the mask 0x007c0001 (`BUZZ.h`, TEXMODE4). The context's copy is the shadow word at +0x7cd4 (31956). Every one of the 71 stores to that word in the N32 library was listed and its masks and constants read (the Odyssey GL driver attribute state assembly unit, the Odyssey GL driver image API assembly unit, the Odyssey GL driver image chain assembly unit, the Odyssey GL driver image move assembly unit, the Odyssey GL driver image utility assembly unit, the Odyssey GL driver texture assembly unit). Together they give three independent pieces, all **established** as what the library writes.

| Piece | Bits | Written by | Value |
|---|---|---|---|
| Colour-table enable | 0 | `glEnable` and `glDisable` of `GL_TEXTURE_COLOR_TABLE_SGI` (0x80bc) in `__glOdyim_Enable` (the store at 0xd957548) and `__glOdyim_Disable` (0xd95e728), which also set and clear bit 31 of the enable word at +0x700; `RenderFunc_Lut` (0xd991188) sets it for a pixel-transfer table; the attribute pop copies it back from bit 31 of +0x700 | 1 while the table is on |
| Table format code | 22:20 | `__glOdyim_ColorTableSGI` and `__glOdyim_ColorSubTable` after storing a table for target 0x80bc (the stores at 0xd98da0c and 0xd98e0d4), and `RenderFunc_Lut` (0xd9911a8), each from the format code that `__glOdysseyStoreLUT` (0xd9c3c50) keeps with the table | 0 until a table is stored, then 1 for `GL_ALPHA`, 2 for `GL_LUMINANCE`, 3 for `GL_LUMINANCE_ALPHA`, 4 for `GL_INTENSITY`, 5 for `GL_RGB`, 6 for `GL_RGBA` (a stored format of 0 counts as `GL_RGBA`; the table records start at 6) |
| Image-step flag | 18 | the default state block of every image transfer (`0x03640000`); the steps that build their own word 4 set it again, together with bit 14 (0x4000), except six stores listed under "Bit 14" below, which set 14 alone and rely on the default block | 1, together with bit 14 in the stores that set 14 |

Bit 19 is set by no store; bit 21 and 20 are only ever written as part of the 3-bit code. So the values the library can put in bits 22:18 are 4 times the code (0, 4, 8, 12, 16, 20 or 24) with bit 18 added in the image steps: 0, 1, 4, 5, 8, 9, 12, 13, 16, 17, 20, 21, 24 or 25. The four values the table lists (0, 20, 24, 25) are a subset: 20 is an RGB table (code 5), 24 an RGBA table (code 6), 25 an RGBA table with an image step's bit 18.

What selects each: the table's internal format sets the code, never the texture object, and the code outlives `glDisable` (the disable case clears bit 0 only), so a disabled table keeps its code in the word. The image steps save the application's word (`__glOdysseyImageSaveUserBuzzRasterState`) and put it back (`__glOdysseyImageLoadBuzzRasterState`, the store at 0xd9c2058) after the draw, so bit 18 is set only while an image step draws; the board sees it in the stream of that draw. The image steps leave bits 22:20 and 0 as the application's context holds them, except `RenderFunc_Lut`.

Grades: the setters and values are **established** (read in full for the table writers and the image steps' `or` constants; the stores that take a register mask are covered by the same save and restore, **inferred**). That bit 0 is "lookup through the texture colour table" and that the code names the table's channels is **inferred** from the enumerant and the code's own enumeration (the code 6 and 5 cases are the only two with an alpha channel and without one). Whether bit 18, bit 14 and the code change the board's lookup is **unknown: no shipped software or published source depends on it**. Next route: a trace of the board's behaviour with a known one-channel table, which no software evidence can replace.

### Bit 14: is it ever written without bit 18?

Short answer: **no write sends bit 14 without bit 18 to the board; six stores set bit 14 without setting bit 18 themselves, and bit 18 is already set when they run.** All 71 stores to the context's word 4 (the `sw` to +0x7cd4, found by an instruction scan of the N32 `.text`, not by text search) were classified. Bit 14 (`ori 0x4000`) is set by 26 of them and cleared by none (no mask in any of the 71 covers 0x4000), and all 26 are image-chain steps. **Established** for the stores named below (N32 IP30 build).

Stores that set bit 14 together with bit 18 in the same instruction sequence (0x40000 is `lui 0x4`): `RenderFunc_ScaleBias` 0xd9969c0; `RenderFunc_ScaleBiasForSignedTypes` 0xd9981f4; `RenderFunc_ScaleBiasGfx` 0xd999cbc; `RenderFunc_ColorMatrix` 0xd99b8a8, 0xd99bda4, 0xd99c67c; `ConvolutionDenormAndScale` 0xd99cfec, 0xd99d16c, 0xd99d524, 0xd99d918, 0xd99dc4c; `ConvolutionClampToZero` 0xd99def4, 0xd99dffc, 0xd99e1c4; `AddConvolutionBorders` 0xd99e614, 0xd99e9e4, 0xd99ee88, 0xd9a062c; `__glOdysseyRenderFunc_DownloadColor` 0xd9a4064, 0xd9a49fc.

Stores that set bit 14 without bit 18 in their own constants:

| Routine | Store | Sets with bit 14 |
|---|---|---|
| `RenderFunc_Convolve` | 0xd992a3c | bit 28; wrap fields cleared; minification code 1 and magnification code 1 |
| `RenderFunc_FastConvolve` | 0xd9933e4 | as `RenderFunc_Convolve` |
| `RenderFunc_Convolve24BitMode` | 0xd993e3c | as `RenderFunc_Convolve` |
| `RenderFunc_ConvolveResidue` | 0xd99597c | as `RenderFunc_Convolve` |
| `RenderFunc_ConvolveResidue` | 0xd995cf8 | bit 16 |
| `RenderFunc_ColorMatrix` | 0xd99c2c4 | bit 16 |

None of those six has a mask that touches bit 18 (their masks cover only the 0x3000, 0xc00, 0x300, 0xe0 and 0x1e fields), so each leaves bit 18 as it found it. What it finds is bit 18 set. These routines run only as operations of an image transfer (the only static caller of `__glOdysseyImageChainCreate`, 0xd98eb90, is `__glOdysseyImageXfer`, 0xd9892d0, which also runs the operations), and `__glOdysseyImageXfer` loads the library's default state block into the live words before the chain runs (`__glOdysseyImageLoadBuzzRasterState` with argument 0, called at 0xd989330 to 0xd989340; its word 4 store is 0xd9c2058). The default block's word 4 is `0x03640000` (`__glOdysseyImageInit`, 0xd988ae0, run under `retools/tools/odsy/glcore_probe.py`; [pixel-paths.md](../buzz/pixel-paths.md) holds the block), which has bit 18 set and bits 22:20 equal to 6. **Established** for the default value and the load; **inferred** that the library's start-up has run `__glOdysseyImageInit` before any transfer (not traced for every entry path). So the "image-step flag" is set from the start of every transfer and again by the steps in the first list, never cleared by any of them.

Outside image transfers the context's word 4 never carries bit 14: every step saves the word and puts it back at exit, and the texture-object merge (`__glOdysseyValidateTextureState`, 0xd9d2cd8, mask `0x007c0001`) takes only bits 22:18 and 0 from the context's copy and the rest from the object, whose word has no bit 14 writer (the object's word at +0xb4 is stored only by the wrap, filter, offset-flag and activation setters, which edit bits 28, 25:23, 17, 13:8 and 7:1).

*Software expectation.* Every draw the library sends is consistent with refusing bit 14 without bit 18, and equally with accepting it. **Unknown** what the board does with bit 14, or with bit 18, in a sampler word: no shipped software or published source depends on it (route: a board measurement). *Test:* run a convolution step's word sequence (bit 14, bit 28 and bit 18 from the default block) and check the draw completes.

## Placement of stored-border levels and 3D slices, at any size

The 16-texel offset and the "15 slices" of the captured 2x2x2 volume follow from three routines, read in full: the allocator `AllocateGfxMemForTexture` (0xd9d03b0), the loader `LoadTextureFromHost` (0xd9d08a0; its border adjustment is at about 0xd9d0980 to 0xd9d09a0) and the activation loop `__glOdysseyTextureActivate` (0xd9d20b0 to 0xd9d2254). `retools/tools/odsy/texlevel_layout.py --check` restates the arithmetic and reproduces the captured pitch, slice exponent, stride and first slice of the 4x4x4 stored-border volume, the 2x2x2 zero-border volume and pfCity's 128x128x64 volume. All three sizes below are the level's stored size, border included. **Established** as library arithmetic; that the board reads the stored data the way the library places it is **inferred**.

1. **Origin.** With a border b, the allocator asks the kernel for an object whose image starts (16 - b) & 15 texels from the object's start on each axis (15 for b = 1, 14 for b = 2), so the interior begins on the 16-texel tile boundary. The loader applies the same shift to every upload on each axis the target has (z for 3D, y for 2D and 3D, x always): destination = offset in the stored image - b + 16. A whole-image upload has offset 0, so its first texel is at 15 and the interior at 16. With b = 0 nothing shifts (the zero-border volume's boxes start at 0). The shift does not depend on the image size. The allocator takes a border per axis and only shifts when the S border is non-zero; in the captured calls all three are the one GL border value (whether the three can differ is unchecked: the border arguments of `TexImage` were not traced in full).
2. **Row pitch** (level word 1 bits 11:0), in 16-texel tiles: round up to even `ceil((W - 2b) / 16) + 2b`, where W is the stored width and the +2b is the two border tiles (zero without a border). The allocator forms 2b + round-up-even(ceil((W - 2b) / 16)), the same number. A result of 4096 is stored as 1. Examples: W = 4, b = 1 gives 4; W = 514, b = 1 gives 34; W = 17, b = 1 gives 4.
3. **Slice tiles.** One slice holds pitch x (ceil((H - 2b) / 16) + 2b) tiles; the height term is not rounded to even. For a depth of 2 or more the allocator rounds that count up to a power of two, S; for a depth of 1 it keeps the count. Level word 2 bits 11:0, written for 3D targets only, is the base-2 logarithm of the slice tile count rounded up (0 for a count below 2); it equals log2 S for depth 2 or more.
4. **Slice stride.** The loader places slice z of the stored volume at address unit (z + (16 - b) & 15) x S x (2 << c) x 16, where c is the format's size code (0, 1 or 2 for 2, 4 or 8 bytes a texel; table above). With the activation word 2 equal to log2 S this is `(32 << c) << word 2` units. The datasheet's "64 << word 2" is the c = 1 case. For the captured stored volume: S = 16 (12 tiles rounded up), c = 1, stride 0x400, first slice at 15 x 0x400. For pfCity: S = 64, stride 0x1000. For a 2-byte format the same shape strides 0x200 and for an 8-byte format 0x800.
5. **Object size.** The kernel books the object as the slice tile count times (depth + offset) (`odsy_mm_obj_new`, above), so the 15 leading slices are inside the booking.

The rule is exact for the shapes reproduced above and was derived, not fitted, from the arithmetic; it extends to other sizes and to mip levels because each level has its own record and object. What is **inferred** beyond the library: that the board's slice stride is the one the library's uploads imply (the only reading under which a later sample finds the upload), and the 15-slice offset as a board property rather than a library convention (no register carries it).

## ICC formats: the primary-level pitch

For the internal formats 0x8466 and 0x8467 (board indices 48 and 49) the activation loop takes a separate branch (0xd9d21b0 to 0xd9d21dc; the dispatch on the level record's internal format is at 0xd9d219c to 0xd9d21a4). **Established** (loop read in full, in the N32 build):

- Half width, rounded up: h = (W + 1) / 2 using the full stored width. The border is not subtracted.
- Tiles = (h + 15) >> 4.
- Then the common ending: add 2 when the level has a border, round up to even, store 4096 as 1.

So the pitch is round-up-even(((ceil(W / 2) + 15) >> 4) + 2b). Examples with no border: W = 64 gives 2, W = 17 gives 2, W = 512 gives 16, W = 1024 gives 32. The allocator has no ICC case and books the full width (above), and the detail-level loop uses the ordinary rule (it neither subtracts the border nor halves the width). For a 3D target the slice exponent uses the height term of the ordinary rule with this pitch. Whether the half width is the board's real row length is **unknown** (see "How an ICC level's texels are packed" below); the earlier reading of it as the real row length, from the booking bound argument, is withdrawn.

### How an ICC level's texels are packed in board memory

Short answer: **unknown: no shipped software or published source depends on it.** Silicon test: load one 16-texel tile through the ordinary upload path with each texel set to a distinct known value, draw a quad that samples the tile with nearest filtering for formats 48 and 49, and read the frame to learn which stored element each texel comes from and how the two texels of an element are ordered. Nothing in the library or the kernel driver packs texels for these formats, so the packing is a board property that no software shows. What software does show (N32 IP30 build):

- **No library routine forms an ICC texel.** There is no 5/6/5 packing or pairing routine. The immediates 0x8466 and 0x8467 occur only in 0xd9cfdc0 (internal format to index), 0xd9d2040 to 0xd9d2048 (activation), 0xd9d3240 (internal format check) and 0xd9d3650 (host format and type check) in the whole `.text` (an instruction scan, not a text search). **Established.**
- **The upload is the ordinary pixel-transfer path.** `LoadTextureFromHost` (0xd9d08a0 to 0xd9d0e04) has no ICC case. It calls `__glOdysseyImageXfer` with the host format and type and a destination description whose pixel class comes from `GetImageFmtEnumFromBuzzTexFormat` (0xd9cfbd0): 14 for index 48 and 15 for index 49. For ordinary host formats `__glOdysseyImageCalcXferWriteParams` (0xd9bd800) returns the same 24-byte record for destination classes 14, 15 and 10 (the RGBA8 class) and a different one only for class 12 (run under `retools/tools/odsy/glcore_probe.py`'s machinery for `GL_RGBA` and `GL_RGB`, bytes and shorts). So the library sends plain components to a destination it calls class 14 or 15 and gives it no ICC-specific record. **Established.**
- **Host data in the published compressed layout has no direct route.** `0x8466` and `0x8467` pass the host format check with unsigned short data only (0xd9d39cc to 0xd9d39d8), but the transfer parameter routine returns the refusal record (first byte 0) for them for every destination class from 0 to 17 and every integer type (72 combinations run). The download step then takes its host-conversion fallback (0xd9a3ebc to 0xd9a5110): the target comes from `__glOdysseyImageCalcSuitableHostFormatForDownload` (0xd9ac1f0), RGBA with unsigned short for classes 14 and 15, and `__glOdysseyImageConvertHostImage` (0xd9a9e10) has no case for a source format of 0x8466 or 0x8467 (the size routines give one element of 2 bytes a group, 0xda11ee0 and 0xda120b0). What the converter writes for that input was not traced: **unknown**. So no software path here moves published block data to the board as blocks.
- **The activation pitch is not the published block's density.** The extension that defines the formats (SGIX_icc_texture in the Khronos registry) lays host data out as 4 by 4 blocks: 64 bits for `GL_R5_G6_B5_ICC_SGIX` (a 32-bit field of 2-bit indices, then two 16-bit R5G6B5 colours) and 128 bits for `GL_R5_G6_B5_A8_ICC_SGIX` (that block, then a 32-bit alpha index field, two 8-bit alphas and 16 unused bits): 4 and 8 bits a texel. The activation pitch (half the width in 16-texel tiles, 0xd9d21b0 to 0xd9d21dc) with the booked element size (2 and 4 bytes, `CalcTexelSizes` size codes 0 and 1) spends 8 and 16 bits a texel, twice the published density, and the allocator's full-width booking four times. **Inferred** arithmetic from the published layout and the library's numbers. "Two texels to each booked element" fits the half-width pitch; the published block fits a quarter-width pitch, which the library never sends. Which the board does is **unknown**. **Test that settles it:** a published description of the texture unit's row-length derivation from the pitch field, or an ICC upload in a shipped diagnostic whose pitch and data size can be compared.
- **Order of texels within an element: unknown.** The published layout puts the first 2-bit index in the high bits of the first byte and orders indices bottom to top, left to right; that is the host layout of the extension, not a board fact, and the library never builds it.

**Is the primary level read consistently with its upload?** Unknown. The upload side halves nothing (no ICC test between 0xd9d08a0 and 0xd9d0e04); the activation of the primary level halves the width. Whether the board's write path and sampler path derive one row stride for index 48 and 49 from the descriptors they get is a board property. **Unknown**; no software route remains.

**Detail levels.** **Established:** the detail-level loop (0xd9d2254 to 0xd9d2478) uses the ordinary rule for the same object: `(W + 15) >> 4` rounded up to even, with no ICC test, no border term and no halving (0xd9d242c to 0xd9d2458), and stores the level's format index in bits 25:20 as the primary loop does (0xd9d23d8 to 0xd9d23ec). So one ICC object is described to the board with a half-width pitch for its primary levels and a full-width one for its detail levels. That the board reads the two consistently is **unknown** **Test that settles it:** a published description of how the texture unit forms an ICC level's row length from the pitch field; with one board rule for index 48 and 49 they cannot both describe the same density.

*Software expectation.* The library treats an ICC level as ordinary 2-byte (index 48) or 4-byte (index 49) elements, with a row length of the pitch the descriptor carries, and expects the same layout for upload and sample; it never sends the published block layout. *Test:* upload an 8 by 8 level of index 48 through a class 14 destination and sample texel (5, 3): the sample must come from the same address as the texel uploaded at (5, 3); a board that used a different row stride for the upload and the sample would fail.

## The offset code (level word 1 bits 28:26) and the offset flag pair

Two separate questions: **whether the library ever sends code 2**, and **whether the sampler's two offset flags can disagree**.

**Code 2.** Level word 1 bits 28:26 have two writers. The activation loop never writes them. `DownsampleTextureThruHW` (0xd9d11a0) stores a code of 2 only when the level record's word at object +1372 equals 2 (the code store at 0xd9d1484), and that word is the result of `CalcPixelModePixelFormat` (0xd9d0390), which returns 1 for size code 1 and 0 otherwise; the allocator is its only writer (the store at 0xd9d0618), so the downsample path's test of that word against 2 (0xd9d1a50 to 0xd9d1a5c) never holds and it stores 0. **Established.** `__glOdysseyImageMovePixelsTexture` stores `__glOdysseyImageCalcTexOffset` (0xd9bef40), whose full body (296 bytes, read) maps the source object's words at +44 and +48 to 0 for (0,0), (0,3), (0,4), (1,1), (2,0) and (2,6), to 2 for (2,2) and to a GL error for every other pair. **Established.** The builders of those two words that were traced give only pairs that map to 0: texture-upload buffers store the size code at +44 and a 0 or 1 at +48 ((0,0), (1,1), (2,0)); `ImageChainValidateScratchBufferFormats` (0xd98f810) stores (2,0), (0,0), (1,1) and (0,0); `ImageChainOpCreateScratchImage` stores (0,0); the window description (`__glOdysseyImageDescribeWindow`) stores 3 at +44, which would fail the check if it reached the move. Not traced: the stack descriptors built in `RenderFunc_ReadbackColor`, `RenderFunc_ColorMatrix`, `RenderFunc_PixelTexture` and the host-image conversion, some of which can reach the move. So code 2 is the move's only possible output besides 0, and no traced path produces it: **inferred** unreachable in the shipped software, not excluded. Whether the board treats 1 to 7 differently from 0 is **unknown: no shipped software or published source depends on it**.

**The flag pair.** Sampler word 4 bit 28 (clear when the level-0 border is non-zero) and word 6 bit 24 (set then) are complements wherever the texture code writes them: `SetTexOffsetValues` (0xd9d2660), which `__glOdysseyValidateTexture` calls on every validation, writes both from the level-0 border; `DownsampleTextureThruHW` writes both together (word 6 bit 24 set at 0xd9d13dc and word 4 bit 28 clear, or the reverse at 0xd9d1a4c). `InitTextureObject` starts the object with both clear, but the validation always runs before the object reaches the board, so that start state is not sent. **Established.** Outside the pixel-to-texture move, which writes neither, the pair can disagree: the convolution steps `RenderFunc_Convolve24BitMode` (word 4 stored at 0xd993e38) and `RenderFunc_ConvolveResidue` (0xd995978) (and, by the same constants, the other convolution steps' word 4) build word 4 with bit 28 set whatever the bound texture's border is, and their border-colour update keeps the top byte of word 6 as the context holds it (mask 0xff000fff then 0xfffff000), so a bound texture with a border leaves bit 24 set too. The context's old values come back when the image step finishes (`__glOdysseyImageLoadBuzzRasterState`). **Established** for the two steps named, **inferred** for the others from the shared constants. What the board does with both set, or with both clear, is **unknown: no shipped software or published source depends on it**; a board that took the offset from bit 28 alone, or from bit 24 alone, would agree with the library everywhere except those convolution draws.

## How large one texture can be, and where it starts

Read 2026-11-10 from `odsy_pmm.o` of the 6.5.30m IP30 `odyssey.a` (`odsy_mm_obj_new` 0x2bc4, `odsy_mm_reserve` 0x45d4, `odsy_mm_reserve_texture` 0x48c4, `mm_init_freespace` 0x50c, `mm_check_enode` 0x6248, shift table at `.data` +0).

- **established.** The kernel has no constant byte limit for one texture. The object constructor rejects a request whose texel size is not 2, 4, 8, 16 or 32 bytes, whose first extent (request +16) is zero or above 65536, or whose second or third extent (+20, +24) is zero. A booked size beyond the tile pitches the caller supplied is also rejected. Those checks bound shape, not bytes.
- **established.** The byte limit comes from the reservation. The object's size is its slice bytes (extent one times extent two times the texel size) times its depth, rounded up to 16 KB from 16 KB up. `odsy_mm_reserve` fails the object when the board-wide reserved total would pass the figure at manager record +4904, which `mm_init_freespace` sets to the host-locking warning level plus the board budget (the board's memory in megabytes shifted to 512-byte units, less the reserved start) minus 0x700000. `odsy_mm_reserve_texture` then adds a per-share-group test: the new group total plus the largest competing totals (scratch, the other texture kind, the pixel-buffer figures) must stay within the board budget at +4856. So the largest single texture is what remains of the board's memory after the other classes' largest holders; no fixed figure applies. For a 128 MB board with nothing else resident the ceiling is below 128 MB by the reserved start and the competing minimums; the exact number depends on the reserved start at board record +216, which this pass did not trace to its value.
- **established.** Start alignment: the texture's start in board memory is rounded up to 2 shifted left by the shift-table entry for its texel size, in extent units (an extent unit is 16 by 16 texels at 2 bytes, 512 bytes). The table maps 2 bytes to 0, 4 to 1, 8 to 2, 16 to 3 and 32 to 4, so the alignment is 2, 4, 8, 16 and 32 units, which is 1, 2, 4, 8 and 16 KB. Two objects with different texel sizes are also kept out of the same 32-unit block (16 KB), at either end.
- **unknown.** The exact byte ceiling on a 128 MB board. The test that settles it: read, on a board with the shipped driver attached, the manager record's budget (+4856), reserved start (board +216) and the four competing figures and subtract; or request textures of growing size and note the first refusal.
