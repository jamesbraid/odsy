# Numeric formats in the geometry and raster path

What number format each stage of BUZZ uses between the host's vertex words and the pixel the rasteriser stores, and how well each is known. Four questions, one section each. Labels follow [AGENTS.md](../../AGENTS.md): **established** (read from a binary, a stored frame or a published document, with the address or the source), **inferred** (a reasoned reading) and **unknown**. "Vendor simulation" means a frame stored by the board's field diagnostics, drawn by the vendor's C simulator of the board; [raster.md](raster.md) explains why it is evidence for the board's rules and not a board measurement.

Published sources used: the VPro porting guide (007-4271-001), SGI's white paper "Benefits of VPro Graphics Architecture with 12-Bit Component Support" (J13937), and US 6,259,460, US 6,417,858 and US 6,104,415 ([published-sources.md](../../references/documents/published-sources.md) sources 1 to 3, 5 and 6). Addresses are in the 6.5.30m N32 `usr/gfx/arch/IP30ODSY32/libGLcore.so` unless another file is named.

## Summary

| Stage | Format | Grade | Where it ends |
|---|---|---|---|
| Vertex position, normal, texture coordinate, colour sent by the host | IEEE single, or raw integers that the board converts; doubles narrowed to single on the host | established | the command word, see 1 |
| Transform, lighting arithmetic | 32-bit floating point; lighting uses limited-precision approximations | established (published) | internal widths unknown, see 2 |
| Perspective divide | reciprocal of w, then multiplies by it | established (vendor simulation) for the order, inferred for the width | see 2 |
| Clipping to the frustum | no geometric clip on the board; library clips in float only near w = 0 | inferred / established | see 2 |
| Position at the rasteriser | window x, y snapped to a 1/256 pixel grid by truncation | established as a bound (vendor simulation), inferred as the exact rule | see 3 |
| Edge equations | floating point, mantissas shifted to one exponent per edge | established (published), widths unknown | see 3 |
| Slopes, gradients | not sent by the host; formed inside the chip | unknown | see 3 |
| Colour interpolation | 12-bit modules | established (published) for the width, inferred for the arithmetic | see 4 |
| Depth interpolation | floating point, perspective-corrected barycentrics | established (published), inferred for this board | see 4 |
| Texture coordinate interpolation | divided per pixel, exact where a coordinate is constant | inferred | see 4 |

## 1. Vertex data from the host

- **established.** Immediate-mode senders write a word whose opcode names the data type and then the operands. The float forms are single-precision. `__glOdyim_Vertex3f` (0x0dace840, 32 bytes) stores `0x8080cc03` and three floats and returns, with no test. `__glOdyim_Vertex3d` (0x0dace7c0, 44 bytes) converts each double with `cvt.s.d` before the same store, so the width on the wire is 32 bits even for a double-precision caller. The same holds for the display-list copies (`__glOdylc_Vertex3d`, 0x0d9dd530, narrows then stores).
- **established.** Integer forms are stored raw: `__glOdyim_Vertex3i` (0x0dace8c0, 56 bytes) stores `0x8080cc02` and the three 32-bit integers it was given. It builds floats with `cvt.s.w` for another path but does not store them. `__glOdyim_Color4ub` (0x0dad4e80, 36 bytes) stores `0xc580d00f` and the four byte values unscaled (0 to 255), and the other colour and normal integer forms are the same shape ([words.md](words.md)). So integer to float and normalisation of byte, short and int colours and normals is the board's work. **inferred**: the board normalises as OpenGL does; no read shows the scale.
- **established.** The opcodes come in pairs, low bit 1 for the float form ([buzz.md](README.md), [tokens.md](tokens.md), [words.md](words.md)). Floats: Vertex2, 3, 4 `0x8080c801`, `0x8080cc03`, `0x8080d005`; normal `0xc180cc19`; texture coordinates `0xc380c41f`, `0xc380c821`, `0xc380cc23`, `0xc380d025`; colour `0xc580cc0e` (RGB), `0xc580d015` (RGBA), index `0xc580c407`; the four-float clipped-vertex slots `0xc680d02f` to `0xc980d032`. Integers: Vertex `0x8080c800`, `0x8080cc02`, `0x8080d004`; colour `0xc580cc08` to `0xc580cc0d` and `0xc580d00f` to `0xc580d014`.
- **established.** One non-vertex record carries floats. The ten-operand record `0xcf80a92f` holds four floats from the context and the destination corners (x, y, z) as floats, ahead of a Vertex2 at 0, 0 ([pixel-paths.md](pixel-paths.md)). What the ten floats set on the board is **unknown**.
- **established.** Window coordinates the library produces carry a fixed 6144 bias (viewport adjust at context offsets +0xe4c and +0xe50, set in `__glOdysseyCreateContext`, 0x0d96c610), so the library's window coordinates are GL window coordinates plus 6144; the combined matrix subtracts the two words from the viewport centre (`__glOdysseyValidateMatrixComb`, 0xd9e2f90; [raster.md](raster.md), "Vertex pre-clip in the library"), which would cancel the shift for the board's rows (inferred) ([pixel-paths.md](pixel-paths.md)).
- **unknown.** Whether the board's front end reads denormals, NaN or infinity as written. The patent says NaN and infinity become the largest value in the front end (US 6,417,858); register 0x26 holds a maximum exponent for w, 127 at start-up ([ucode/buzz_isa.md](../../software/ucode/buzz_isa.md)). **inferred**: the internal float has a bounded exponent. Settled by sending a w of 2^100 and 2^127 through a one-triangle stream and reading the frame.

## 2. Transform, clip and perspective divide

Which side does what.

- **established (published).** The porting guide: "VPro does not have a full geometry engine. Instead, there is a simple transform engine that runs at a very high clock rate", and the chip "implements the full geometry pipeline, including transformation, lighting, and clipping". The white paper: "the VPro XFORM unit computes in 32-bit floating point", with a footnote that for lighting "certain limited-precision approximations are used", whose accuracy "is variable depending upon the input data". The footnote is about lighting only; the transform of positions is stated as 32-bit floating point with no qualification.
- **established.** The transform is a microcode program the host uploads (`buzz_xform.bin`, 96-bit instructions, [ucode/buzz_isa.md](../../software/ucode/buzz_isa.md)). The host computes the combined matrix in the library (`__glOdysseyValidateMatrixComb`, 0x0d9e2f90) and sends it as floats: the x and y rows are scaled by the viewport scale and offset, so the board's dot products give window x and y before the divide; the z row is mapped through the depth range into the eye-linear 0 to 2S range ([raster.md](raster.md), Depth range); the w row is the clip-space w. The viewport multiply is therefore done in the same float arithmetic as the matrix product.
- **established (vendor simulation).** For the unlit points, lines and triangle programs (routines 214, 224, 234) the output stage forms 1/w from the w dot product (code 0x2b) and multiplies the x and y products by it (codes 0x46, 0x26). Replaying that order reproduces the stored frames. Those frames also bound the reciprocal: x arrives as exactly 470.0 when the reciprocal is rounded to nearest single precision, and one step low (469.99997, a reciprocal truncated to 23 bits) fails 26 and 28 pixels unless the rasteriser snaps coarsely first. So the divide is not a truncated 23-bit reciprocal; the pair (reciprocal accuracy, position snap) is bounded and not separated ([raster.md](raster.md), Position precision).
- **inferred.** The patent describes a three-stage engine: a vector stage forming four dot products per clock with a fused multiply-add, a scalar stage with look-up tables (arc-sine, exponent, inverse square root, negate), and a stage that divides x, y and z by w (US 6,417,858). The shipped microcode shows the vector and scalar structure ([published-sources.md](../../references/documents/published-sources.md) source 1).
- **inferred, weakly.** The vector unit's sum keeps 22 fraction bits below its leading one and rounds down at least at 2^17. This rests on one routine, the spot-light interpolation (routine 792, [ucode/buzz_isa.md](../../software/ucode/buzz_isa.md), Precision). It would make the datapath slightly narrower than IEEE single, which the white paper's "limited-precision approximations" footnote would allow for lighting; it does not show the position path.
- **unknown.** Internal exponent and mantissa widths of the registers, the rounding of the fused multiply-add, the table sizes of the scalar stage. Not in any shipped file or published text. Settled by running chosen operands through the board's transform and reading the output words, which the host cannot do (no routine reads a transform result back); a captured frame of a stream with operands chosen near the rounding boundary would bound it.
- **Clipping.**
  - **established (library).** The host clips in float only for vertices that cross w = 0 or come near it, and only with `GL_SGIX_vertex_preclip` enabled (off by default): the guard limits are |w| below 0.0625 and window x or y beyond 8192 times |w| (`__glOdyim_Vertex3f_smallw`, 0x0dacf440; `_mag`, 0x0dad06c0). The library's own clipper then sends the clipped polygon as clip-space Vertex4 floats (`0x8080d005`). User clip planes 6 and 7 are added for an interior depth range ([raster.md](raster.md)).
  - **inferred.** The board does no geometric frustum clip. US 6,259,460 says frustum clipping is "effectively performed by the recursive subdivision rasterization", and the microcode consumes the clip-space z with no compare. Near and far cuts are per-pixel kills in the raster pipeline, the same mechanism as user planes.
  - **unknown.** The board's coordinate limit before precision is lost (the library's 8192 and 1/16 are its margin); where exactly the far kill sits ([raster.md](raster.md)).

## 3. Raster setup

- **established.** The host sends no slopes, gradients or edge equations. The per-primitive numeric words it sends are the vertex and attribute words of section 1, the combined matrix rows and the polygon-offset block 0x058. The set-up values are formed inside the chip. That is a statement about the sender set read in [words.md](words.md) and [tokens.md](tokens.md); a sender outside the scanned files would not show. The formats of slopes, gradients and edge equations are therefore **unknown** from software.
- **established (published).** US 6,259,460, the raster unit: the parser "snaps vertices to grid"; a vertex denormaliser receives floating-point vertices one primitive at a time; the line-equation block "calculates the edge equation signed floating point distances for each of 4 corners of the largest recursive subdivision region (4K by 4K) against each of the 3 edges", with mantissas denormalised so the four corner distances of an edge share one exponent, "12 mantissas, but only 3 unique exponents", and a signed floating-point area that goes to a reciprocal block. The subdivider produces distances at each level by averaging the corners of the level above. Applies to this chip (source 3 of [published-sources.md](../../references/documents/published-sources.md) matches the chip's blocks at high confidence): **inferred** for V10 and V12, since the patent describes the architecture and names no board revision.
- **unknown.** The mantissa width of those distances, the grid the vertices snap to ("the grid is not stated"), the width of the reciprocal of the area. The twelve mantissas are twelve values (four corners times three edges), not a width.
- **Subpixel precision.** **established as a bound (vendor simulation)**: the stored points, lines, triangle and alpha frames accept truncation of window x and y to 1/16 pixel or finer and rounding to 1/256 or finer; rounding to 1/128 moves 22 pixels of the large points frame. **inferred (vendor simulation, one frame)**: truncation toward minus infinity to 1/256 pixel for both coverage and interpolation; only the small checkerboard frame separates it (rounding to nearest 1/256 moves 5 pixels, truncating to 1/128 moves 6, to 1/512 or 1/1024 moves 3, no snap moves 4). Eight subpixel bits is therefore the best-supported figure; **unknown** whether the board's grid is the simulator's.
- **Slope.** **established as a bound (vendor simulation)**: if a line's minor coordinate is stepped from the first end by a fixed-point slope, the stored line frame needs more than 10 fraction bits (rows at 6, 8 and 10 bits fail by 20, 18 and 12 pixels; 12 and 14 bits pass; 11 was not run). The slopes in that test are 0.8 and 0.5. Exact arithmetic on the snapped ends also passes, so the frame does not require a stepped slope at all.
- **Coverage and ties.** **inferred** (US 6,259,460): coverage subdivides to the subpixel and tests the signs of the edge distances; an edge value of exactly zero is resolved by consulting the neighbouring pixels of the quad so that one primitive owns a shared subpixel. **not tested** by any stored frame ([raster.md](raster.md)).
- **What would settle the formats.** A trace of the chip's internal edge registers (none is host-visible), or stored diagnostic frames with steep slopes, long edges (near 4096 pixels) and vertices on a fine grid so that slope truncation shows. The vendor streams in the field diagnostics are all gentle; none is known to settle it.

## 4. Span interpolation

- **Colour.** **established (published)**: shading uses "eight identical 12-bit Bilerp Modules" configured to give four 12-bit colour components (or one 24-bit monochrome component) for two fragments per clock, from perspective-corrected barycentrics (US 6,259,460). The white paper and the porting guide state that the whole pipeline runs at 12 bits per component or greater from geometry through rasterisation, and the transform unit's lighting colours have 12 bits per component. **inferred**: colour iterates in 12 bits. The stored 8-bit frames convert as floor(256 c) limited to 255 (**established**, vendor simulation, [raster.md](raster.md), Colour as stored; round(255 c) and floor(255 c) both fail thousands of pixels). The perspective-corrected colour model leaves 1070 of 13934 pixels one step off in the blend frame, and no tried arithmetic (8 to 20 bit barycentrics, 10 to 16 bit weights, 12-bit vertex colours, 10 to 16 bit intermediates) removes the residue, so the exact interpolation arithmetic is **unknown**. The residue behaves as if a value below 0.5 reads 1/16 of an output step high (**inferred**, fit only).
- **Depth.** **established (published)**: the depth bilerp has two sub-blocks, "3 floating point inputs, 2 32-bit floating point perspective-corrected barycentric coordinates, and a single floating point output" (US 6,259,460). **inferred** for this board: depth is interpolated in 32-bit float with perspective correction, in eye-linear space. **established** for what the host sees: the depth plane is read back as a 24-bit word, bits 23:18 exponent, bits 17:0 mantissa with an implied one, value (1 + m/2^18) x 2^(e - 31) ([raster.md](raster.md), The depth word; `__glOdySpanFloatToEyeZ24`, 0x0d9a6d80, truncates the low five bits of an IEEE single to make it). That the plane holds exactly these bits is **inferred**; how the board rounds when it stores a float depth into the word is **unknown**. The porting guide states depth is kept in an internal floating-point format and is faster to read through the host's conversion.
- **Texture coordinates.** **established**: the transform program outputs s, t and r each times 1/w, plus 1/w as its own word, and the window x, y and z ([raster.md](raster.md), Texturing). **inferred (vendor simulation, small checkerboard)**: each pixel's coordinate is the plane of s/w divided by the plane of 1/w, evaluated exactly enough that a coordinate equal at all vertices reaches the sampler unchanged; summing weighted vertex values in double precision moves 111 pixels. **established (published)**: an "address reformatter (float to fixed)" precedes the level-of-detail, address and cache units (US 6,259,460), so the texel address is fixed point; its integer and fraction widths are **unknown**.
- **Level of detail.** **established** for the host registers: bias, minimum and maximum are 14-bit two's complement with 8 fraction bits (block 0x013, [tokens.md](tokens.md)); the detail-weight table index is 1/32 of a level and the weight is 12 bits ([BUZZ.h](BUZZ.h)). **unknown**: the width of the computed fraction and of the filter weights and sub-texel position; the patent names a "texture tree filter" without widths. Every stored texture frame uses nearest sampling, so none constrains them.
- **Stored colour and blend widths.** Blend constants are 12 bits ([11:0]) and blending is done at 12 bits per component (white paper); fog colour is two 12-bit values per word and the fog function coefficients are 12-bit signed with 8 fraction bits ([tokens.md](tokens.md)). **established** for the register widths.

## What is graded

- Graded as hardware formats: 32-bit IEEE operands from the host; 32-bit float transform with a reciprocal-and-multiply divide that is not truncated to 23 bits; no geometric frustum clip on the board; window position snapped by truncation to a 1/256 grid (the stored frames accept 1/16 or finer truncation); 12-bit colour modules; float perspective-corrected depth; the 24-bit exponent-and-mantissa depth word as the host reads it; 8-fraction-bit LOD fields.
- Not graded, so **unknown**: edge-equation, slope and gradient widths; internal float widths and the rounding of the transform's multiply-add; table function sizes; how depth rounds into the stored word; texel address, sub-texel and filter-weight widths; the exact colour interpolation arithmetic.
