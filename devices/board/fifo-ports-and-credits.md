# The command windows, flow-control credits and a writer that holds none

Release IRIX 6.5.30m, IP30 and IP35 kernel objects, the N32 `libGLcore.so`, the VPro patch 4103 and 4104 builds, and the IRIX 6.5.7 standalone graphics library read from the IRIX source tree (`irix-6.5.7/stand/arcs/lib/libsk/graphics/ODYSSEY/odsy_flow.h`, `odsy_flow.c`, `odsy_internals.h`, `odsy_tport.c`, `odsy_init.c`), restated in our words. Labels: **established** (whole routine, table or source passage read), **inferred** (reasoned, with the reasoning), **unknown** (routes tried, and what would settle it). A fact about one host does not fill a gap in the other. Written for a driver author who feeds the board from a host that is not IRIX.

## Which window each sender writes (what differs between +0x100000 and +0x110000)

| Sender | Window it stores command words to | Basis |
|---|---|---|
| Every kernel routine (textport, clip, context switch, DMA kick, microcode load, set-up) | board +0x110000 | **established**, [board-registers.md](board-registers.md) "FIFO ports and windows"; no kernel object stores to +0x100000 or +0x120000 |
| `libGLcore.so` of 6.5.30m, all three ABIs | user address 0x10000, which is board +0x110000 | **established.** `__glOdyim_Vertex3f` (N32 0x0dace840, 32 bytes) loads `lui 0x1` and stores `0x8080cc03` and three floats through it with no other base; `__glOdyim_Color3f` (0x0dad4300) does the same with `0xc580cc0e`; `ValidateHardware` and `__glOdysseyClear` store through the same constant. The user offset to board offset map is the 8-row table of `gf_OdsyMapGfx` ([buzz/README.md](../buzz/README.md) section 9) |
| `libGLcore.so` of patches 4103 and 4104 | user address 0x4000, which is board +0x120000 | **established**, [board-registers.md](board-registers.md) "The 0x120000 window" (4101 or 4231 constant-address stores per build) |
| `libGLcore.so`, all builds | stores nothing to board +0x100000 as commands | **inferred** from the two rows above: no command word is stored at a user address below 0x4000 in any build. The library does keep its own state at user addresses 0x1010 (the current context pointer, stored by make-current), 0x1018 (a word set to 2 after every setter and compared with 1 at the top of every entry point, which raises GL_INVALID_OPERATION when it reads 1) and others up to 0x17a8; those addresses fall in the first user page, which `gf_OdsyMapGfx` maps to board +0x100000. See "Open" below |

What the board does differently per window: **unknown.** No shipped software sends different ids to different windows, so no id filter can be read from software:

- **Accepted ids.** The context-select block 0x050 is stored only by the kernel (`gf_OdsyPcxSwap`, `odsyRestartContext`; a scan of the libGLcore and X module listings for its `ori 0x850` finds none), the DMA kick (`0xe01`, two doubleword stores, [dma/README.md](../dma/README.md)) is built only in the kernel's `odsy_DmaRegion_DoTransfer` and `odsyDMAOp`, and the class-0 pair `0x340`/`0x341` only by the kernel's replay and start-up. Everything else the kernel sends, the tag block 0x25a (86 sites in 20 binaries, including libGLcore's glGet read-back), block 0x258, the sequencer words, matrices, attributes and primitives, user code sends through its own window. So the observed split is by sender, and a user window refusing block 0x050, the kick or the 0x340/0x341 pair is neither shown nor excluded. **inferred:** a miniport that keeps those three in its kernel half and sends draw, state and sequencer words from the ICD matches shipped practice.
- **Context owner and privilege.** The board's notion of the current context is selected by block 0x050 with the slot in bits 18:12 and the save doorbell at +0x118000 ([buzz/README.md](../buzz/README.md) section 4), both stored by the kernel through +0x110000 into the same stream the user words travel in. The kernel's replay after a lost context resumes mid-primitive by sending its own words through +0x110000 *behind* the user's, which only works if both windows feed one in-order queue. **inferred**: one queue. Whether +0x100000 and +0x120000 feed it too, or a separate queue, is **unknown**.
- **Who gets +0x110000.** `gf_OdsyMapGfx` (6.5.30m IP30 `odsy_map.o`, read in full; `odsy_attach.o` `gf_OdsyAttach` has the same split on IP35) maps +0x100000 and +0x120000 for every client and the other six windows, including +0x110000, only when bit 5 of the client's flag word at +4 is set. **established.** The one store that sets bit 5 is in `gfxioctl` (`gfx.o`, the case for generic request 110, which first calls through the owner's operation table slot at +96 with arguments (client, 0, -1), then ORs 0x20 into the flag word at +4 under the display lock). Which user program sends request 110, and what slot +96 is: **unknown** (a scan of every `li ...,110` in libGLcore, the X module and `libgl.so` finds only character compares in `getenv` handling). So +0x110000 is a per-client grant, not a fixed kernel-only port, and 6.5.30m `libGLcore.so` stores to it directly. Whether the hardware itself treats the kernel's and a user's stores differently: **unknown**.

### Host flow control covers both +0x100000 and +0x110000, and not +0x120000

- **established.** The 6.5.7 standalone library's flow header defines the host-side match for flow-controlled stores as board offsets 0x100000 to 0x11ffff (its comment states that offsets 0x10xxxx and 0x11xxxx match and 0x12xxxx, anything from 0x200000 and anything below 0x100000 do not), and `odsy_init.c` passes `hw | 0x100000` with mask 0x1ffff to the credit allocator. `gf_OdsyInitialize` of 6.5.30m IP30 (`odsy_init.o`, the `gfx_flow_alloc` call, read in full) ORs 0x100000 into the board's PIO base and passes 0x1ffff as the mask (`lui 0x10`; `lui 0x1` with `ori 0xffff`), 2048 bytes of credit (256 doublewords, one credit per doubleword) and a 10000 ns timer: the same arguments as the source. The IP35 call passes the PIO base plus 0x100000 and plus 0x110000 (a range start and a second address), a credit value taken from a global shifted left by 3, and a timer of 100000; its credit-range convention was not decoded, so the +0x120000 statement below is for IP30 only.
- **inferred (IP30).** A store through the +0x120000 window is outside the host's credit accounting. Why patches 4103 and 4104 use it, and whether the older libraries rely on that, is **unknown**.

## Overflow: what a store to a full FIFO does, and what the unit of the level is

There are two FIFOs in series, and the earlier pages mixed them.

- **The input FIFO of the front end ("in" block): 256 doublewords. established (IRIX source).** The 6.5.7 internals header (`irix-6.5.7/stand/arcs/lib/libsk/graphics/ODYSSEY/odsy_internals.h`) sets the depth at 256 doublewords, the size of the input FIFO in the front end's "in" block, and builds the poll from that depth: the gate before a burst of n doublewords is `level <= 256 - 2 - n`, with the level the flow-count field of the levels register. The header's own simulation branch gives the field as bits 15:7 of the register at 0x1068 (mask 0xff80) and the display FIFO as bits 6:0 (mask 0x7f), so the level is **bits 15:7 of the word at +0x106c, counted in doublewords**. This settles the unit that [board-registers.md](board-registers.md) ("The 0x106c readers") and [interrupts-fifo-reset.md](interrupts-fifo-reset.md) left unknown, and moves "level unit: words" there to **established: doublewords**. The host credit window (2048 bytes, 256 doublewords) equals this FIFO's depth, so the credits are slots in the "in" block, not in the memory FIFO.
- **The memory FIFO: 32,768 words, no wrap protection. established (IRIX source).** The header says in as many words that there is no wrap-around protection for the memory command FIFO and that its physical high-water mark must leave room for the "in" block's 16 cache lines and about two more for the stages between "in" and the next block. The skid is `2 * 256 + 0x40` = 576 words, so the high mark is 32768 - 576 = 32192 and the low mark three quarters of it, 24144: exactly the values `odsyInitCfifo` stores. The source gives the four set-up commands a role each (tile count, low water mark, high water mark, bypass disabled), so 0x6b1 = size in 512-byte tiles, 0x6b3 = low water (24144), 0x6b2 = high water (32192) and 0x7b5 = 1 = bypass off remain **inferred** from the match of values and order; the roles support that reading, but the command ids are in a header not held here.
- **What a store to a full "in" block does: unknown.** Nothing shipped stores past the credit limit. The only software-visible overflow outcome is flag 27 (in the teardown mask 0x39f02587), **inferred**. Routes tried: both kernels, the PROM, the 6.5.7 library, the diagnostic reference 108-0314-003 (searched by an earlier pass for the flags, not for this). **What would settle it:** a published description of the front end's input handling when credits are exhausted or off.
- **What a store to a full memory FIFO does: wraps over unread data, per the source's statement that nothing protects it.** **inferred** for the effect (the source says only that no protection exists); the flag 27 reading above is the likelier visible symptom.

## A writer that holds no credits: is it safe on IP30 and IP35

- **Shipped practice for console traffic. established, both hosts.** `odsy_tpinit` (`odsy_tport.o`, drain loop at +0x16a8 on IP30 and +0x1634 on IP35, both read in full) waits for bits 15:7 of +0x106c to read 0, pulses +0x1084 as 0, 1, 0, stores 0 to +0x1074 and 1 to +0x107c (flow control off, no credit counted), runs `odsyInitCfifo`, replays the 4165-word stored stream and sends the textport state. None of the textport draw routines of 6.5.30m (`odsy_color`, `odsy_sboxfi`, `odsy_pnt2i`, `odsy_cmov2i`, `odsy_drawbitmap`, `ODSY_SET_GC`) loads +0x106c; only `odsy_mapcolor` polls a level, and that is the display FIFO. So the kernel's own console path sends its bursts (36 word stores in `odsy_sboxfi`, up to 135 across the paths of `ODSY_SET_GC`) with flow control detached and no command-FIFO poll, on IP30 and on IP35; the IP35 `odsy_tport.o` shows the same single reader of +0x106c. The 6.5.7 library it descends from did poll before each burst (gate of 10 to 100 doublewords).
- **Larger credit-less traffic. established as software practice, once:** the 12,291-word microcode load after +0x6b* set-up, sent by `odsyInitCfifo` inside `odsy_tpinit` with flow control off and no level check, 48 times the "in" block's depth. It cannot overrun the memory FIFO (it is 37.5% of 32768) and the "in" block drains as the writer goes. That the front end never lost a word in that load on shipped hardware is **inferred** from the textport working afterwards, since nothing reads the program back.
- **What no shipped software does:** stream beyond the memory FIFO's depth with credits off, or poll nothing and send a burst longer than the "in" block. Whether the host or the board stalls, drops or errors then: **unknown.**
- **inferred rule that matches both shipped practices and the source's conservative form:** before each burst of n doublewords, read +0x106c and wait while bits 15:7 exceed 254 - n (5 microsecond polls, as the library did); keep the bursts between polls under 8048 words (the memory FIFO's low-to-high span) and the whole stream outstanding at less than 32192 words by also gating on status0 bit 17 (below low water) as the public OpenBSD driver does ([buzz/README.md](../buzz/README.md) section 11), whose bursts are a few dozen words. A store posted by the CPU may still be in the host chip when the level is read; reading the level back after the last store of a burst (a load from the same widget orders it behind the posted stores) is the cheap guard, **inferred** from the detach sites' read-back of +0x106c after the +0x107c store ([board-registers.md](board-registers.md) "Detach read-backs").
- **What IP35 changes. established as a difference of mechanism only:** the credit source is a Bedrock-side register block (`buzz/README.md` section 1), the board-side registers and values are the same, and the flow-off store (+0x107c = 1) is the same. Whether a credit-less writer can hang a Bedrock PIO queue that a HEART queue tolerates: **unknown**; the public OpenBSD driver was not read for IP35 attachment (its `odyssey.4` page and attach glue were not initialised in this checkout), so no real-board run is cited for IP35.
- **Registers a miniport needs for credits, from the kernel's attach code.** IP30: HEART `fc_mode` at +0x40 of the HEART base (bit n+8 enables processor n, the two-bit field at 2n+10 holds n), credit counters at +0x60 + 8n, address match at +0x50 + 8n, timer limit +0x48 (the registers are the host chip's, see [kernel/kernel-flow-control.md](../../software/kernel/kernel-flow-control.md)), plus the board's +0x1074 and +0x107c (detach). The field layout of +0x1074 is **established** from the 6.5.7 header: timeout bits 9:0, coherent bit 10, GBR bit 11, credit target number bits 16:12, destination id bits 20:17, display flow-control enable bit 21, mode bits 24:23 (1 for the Octane host chip, 2 and 3 for the Origin family, 0 disabled). The 6.5.30m kernel builds `(interrupt target << 17) | 0x800000 | (target number << 12) | 0xc8` (`gf_OdsyInitialize`, [kernel.md](../../software/kernel/kernel.md)): destination id, mode 1, target number and a timeout of 200 ticks of 100 MHz, with coherent, GBR and display enable zero as in the source. IP35 registers: [buzz/README.md](../buzz/README.md) section 1 (an interconnect register block at `.lit8[0]` + 768, 776, 784 + 40 per processor slot), whose field layout is **unknown**.

## Open

- **What the first user page (board +0x100000) is.** libGLcore stores a 64-bit pointer and a state word there at fixed addresses, which a command port would not hold, while the kernel maps it with the same call as the command window. Readings: board-resident scratch memory the board does not interpret; or memory-like behaviour the board gives that page. Not settled. Routes tried: `gf_OdsyMapGfx`, `gf_OdsyAttach`, the library stores. **Would settle:** a published description of the 0x100000 window, or the diagnostic reference's address map. An ICD should not store anything there.
- **Cache attribute 0 against 2** on the windows: [buzz/README.md](../buzz/README.md) section 9.
- **Byte lanes** of 32-bit and 64-bit stores from a little-endian CPU: see the next section; the host chip's behaviour for a little-endian processor is still unknown.

## Byte lanes: what a little-endian CPU changes

All shipped software here runs on a big-endian R10000, so nothing below was run with the other order. Host-chip facts come from the chips repository (`devices/crosstalk/packets.md`, `platforms/ip30/reset-byte-order.md`, `platforms/ip35/dual-boot.md`, `devices/r14000/README.md`).

- **established. The command port is one address, not a growing window.** Every one of 548 stores made through a `lui 0x1` base in the four API listings of the N32 6.5.30m library (`software/opengl/asm/ODYSSEY.IP30.N32_M4.O/ody_{v,c,n,t}api_asm.s`: 397 `sw`, 123 `swc1`, 28 `sd`) uses displacement 0, for example `__glOdyim_Vertex3f` (0x0dace840: the vertex word, then three floats, all at offset 0). The kernel's stores are 32- or 64-bit at the same single offset ([board-registers.md](board-registers.md) "FIFO ports and windows"). The two kick words ([../dma/README.md](../dma/README.md)), the five set-up doublewords and every display-FIFO store are `sd` with the id or header in the high word and the operand in the low word.
- **established. What the widget is told about the host.** The kernel writes widget +0x24 with bit 9 set ([board-registers.md](board-registers.md) 0x24). The shared widget header names that bit the system-endianness select, and HEART's status word has a bit 8 named for big-endian (`irix/kern/sys/xtalk/xwidget.h` `WIDGET_SYS_END`; `irix/kern/sys/RACER/heart.h` `HEART_STAT_BIG_ENDIAN`, IRIX 6.5.7 source). The sense of the bit is stated only for sibling chips (Bridge and XBridge specifications: 1 = big, 0 = little, reset 1), so for this widget it is **inferred** that 1 means big and that a little-endian host clears it. What the widget changes when it is clear (DMA byte numbering, the lane of its own register reads): **unknown**.
- **inferred. The CPU side.** A 64-bit store puts register bits 63:0 on the system bus unchanged in either mode, so a command pair or display-FIFO word built as (high word, low word) arrives the same from both. A 32-bit store at an address that is 0 mod 8 uses data bits 63:32 in big-endian mode and 31:0 in little-endian mode, and the reverse at 4 mod 8 (the R10000 manual prints one worked example; the general rule is an extension of it, as chips records). If the host chip and the crossbar carry the data lanes unchanged, which no document held says, then:
  - a 32-bit store to the command port at offset 0 reaches the board on the low half from a little-endian CPU, where shipped software always puts it on the high half. A little-endian driver that wants the shipped lane stores each word at port +4, or sends pairs as one `sd`. Whether the front end accepts a command word on the low half alone: **unknown**, since no shipped store does it.
  - 64-bit display-FIFO stores and the kick pair need no change.
- **unknown. Host memory the board reads or writes.** The DMA entry header and page list ([../dma/README.md](../dma/README.md)), the tag halfword and the save record are all laid out and read by the kernel as big-endian 32-bit words and a big-endian halfword (`lw`, `lhu`). Whether the board numbers their bytes in big-endian order whatever the host, or follows widget bit 9, is not in any shipped code. The Crosstalk rule that data bytes are numbered from the most significant end in big-endian mode and from the least significant in little-endian mode is established for the Bridge specification only.
- **Routes tried.** Both kernels, the PROMs, the 6.5.7 standalone library, the public IRIX headers for HEART and the widget block, the chips repository's host-chip pages (no HEART or Bedrock text on a little-endian processor; the Octane's mode word source is itself unknown). **What would settle it:** a HEART or Bedrock description of a little-endian processor's data lanes, or a published VPro widget specification giving bit 9's sense.
