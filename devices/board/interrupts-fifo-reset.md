# Interrupts, command FIFO credits and reset: graded readings

Release IRIX 6.5.30m. Builds: the IP30 and IP35 `odyssey.a` (`odsy_init.o`, `odsy_intr.o`, `odsy_flow.o`, `odsy_retrace.o`, `odsy_tport.o`, `odsy_ctxsw.o`), the IP30 boot PROM image, the IP30 standalone diagnostic monitor, and the published documents named per entry. Every offset is in the member or image named. **Established** is a whole routine or whole sequence read; **inferred** is a reasoned reading, with the reasoning; **unknown** has the routes tried, so that a reader who needs a value can choose one and document the choice.

The entries answer one question each, so a reader can tell which part of a behaviour rests on software and which part is a free choice.

## Interrupts

### The flags handler: one pass, acknowledged at the board

- `odsyFlagInterrupt` (`odsy_intr.o`, offset 0x1ac, 916 bytes, IP30 and IP35 alike): **established.** It loads the flags word at +0x1014 and the enable word at +0x1034 once, ANDs them, runs the low-water routine first when bit 9 is set, tests the remaining bits in a fixed order (logging or acting on each), and as its last step before returning stores the pending set to +0x101c. It contains no loop and no re-read of +0x1014, and it makes no access to any host-interrupt register. So the handler acknowledges at the board, once, and it relies on the board to raise a new delivery for anything that becomes pending afterwards.
- **Inferred:** the board must deliver one interrupt for each rise of (flags AND enables) from zero. The reasoning is the single pass above; nothing in the shipped code shows what the board does on the way down.
- **Unknown: whether the board sends anything when (flags AND enables) falls to zero.** Routes tried: both builds of the handler, the low-water and high-water routines, the reset and disable routines (all of them only store to the board), and the PROM and standalone images (they never enable a flag). Whether the host interrupt controller's pending bit needs a clearing write from the board depends on who clears it first, which no Odyssey object shows. Nothing in the software depends on a clearing write from the board.

### Flags raised while their enable is clear

- **Inferred:** a flag raised while its enable bit in +0x1034 is clear is held in +0x1014, and enabling it afterwards raises the interrupt. Two readings give this. First, the handler's teardown test is made on the raw flags word, before the enable mask is applied (`odsyFlagInterrupt`, the test against 0x39f02587 after the per-bit chain), which only makes sense if masked flags stay latched. Second, the high-water routine (`odsy_flow.o` `odsyHiwaterInterrupt`, offset 0xcc) clears flag 9, and when status bit 17 is already set it stores 0x200 into +0x1014 itself, then enables flag 9 through +0x1034, then returns. The low-water routine that wakes the sleeping writer runs only from that interrupt, so the enable of an already-set flag has to interrupt.
- **Unknown, the three routed sources (bits 18:16 of +0x1044): whether a source raised while its enable bit is clear is dropped or held.** No shipped code writes one of the three bits alone, in the kernel, the PROM or the standalone monitor (see the next section), so no shipped path raises a source in that state. Whether the board drops it stays unknown.

### Bits 18:16 of +0x1044: the PROM images

Earlier readings of these bits did not scan the PROM images. Both IP30 images carry a copy of the driver's reset routine: the PROM at flash offsets 0x48830 to 0x48cc0 and the standalone monitor at 0xbfc40 to 0xbfed0. **Established** by reading both sequences in full: each stores +0x1044 exactly twice, both stores of zero (the PROM at flash 0x48a0c and 0x48c70; the monitor at 0xbfc58 and 0xbfebc), and neither image sets a bit of the register. The PROM text console takes no interrupts. So no shipped code of any kind writes one of bits 18:16 alone, so no shipped code of any kind writes one of bits 18:16 alone. A routed source is silenced only by the all-clear store.

- **The assignment, unknown:** which of bits 18:16 enables the retrace, DMA-done and software-sync sources is not shown by the binaries read here; the three handlers are numbered 3, 2 and 4 in `buzz/README.md` section 6, and a guess that the bits run in the order retrace, DMA, software sync from bit 18 down has no evidence behind it. A read of the enable path of each handler in `odsyInitInterrupts` would settle it.
- **Unknown from the shipped binaries, which bit is which.** No binary separates the bits (all three are set together, cleared together). What would settle it is the same as before: a board with one bit cleared at a time.

### The retrace handler and +0x10d4

- `odsyRetraceHandler` (`odsy_retrace.o`, 716 bytes in both builds): **established.** Once per retrace interrupt it loads the 32-bit word at +0x10d4, XORs it with the driver's kept copy (record +28528) to get the set of window ids whose bit changed, then walks window ids 0 to 31. It stores the swap mask to +0x10b4 and 0 to +0x10bc (under a driver state flag), forces a swap that has waited more than 300 retraces, wakes video-sync waiters, and finishes by running the DMA tag check. It acknowledges nothing at the board.
  Build: `6.5.30-media/usr/cpu/sysgen/IP30boot/odyssey.a(odsy_retrace.o)`.
- **Inferred:** a set bit i of +0x10d4 says window id i is showing the second buffer, and the bit toggles when the board latches a pending swap for that id at a vertical retrace. The basis is the pairing with the set port +0x10c4 and clear port +0x10cc and the XOR against a kept copy. Which polarity is the first buffer rests on that pairing only.
- **Unknown:** what starts the retrace interrupts (the timing generator's start is the last write of the timing load, +0x2481 = 1, but no code shows the board's reaction), whether one arrives for every frame, and the jitter. The counter the handler keeps is one per interrupt with no field test; the compiled timing tables of all 71 formats carry the one candidate output (`VINT`) once per frame, so if `VINT` drives the retrace interrupt, a two-field format raises one per frame (**inferred**, weakly; no register routes it): [retrace-field-or-frame.md](../../software/kernel/ip30/readings/retrace-field-or-frame.md).

## Command FIFO and credits

### FIFO depth and level unit

- **Inferred (shipped values): the depth is 32,768 words (128 KB).** The five stored registers are inferred to be the FIFO's base, its size in 2-bytes-per-pixel tiles, a low-water mark, a high-water mark and a bypass switch. The shipped values fit that reading exactly: `0x6b1` = 256 tiles of 128 words is 32,768 words; `0x6b2` = 32192 is 32,768 - 576; `0x6b3` = 24144 is exactly three quarters of 32192 (4 x 24144 = 3 x 32192 = 96,576). The arithmetic is the only support: no 6.5.30 code reads the registers back, so the roles stay inferred. (The 6.5.7 library's flow header supplies the formulas behind those numbers; see "Taking the board back" below, which moves the pairing to strong inference.) The two builds and the IP30 PROM's copy of the set-up (flash 0x486a8 to 0x48700; the standalone monitor loads the same constants at 0xbf8f4 to 0xbf940) send the same values.
- **Unknown:** whether the depth is the same on every board. The diagnostic reference (108-0314-003, memory tests) says the FIFO's data normally resides in SDRAM, so its size is a share of board memory. The porting guide (007-4271-001, "Command FIFO and Context Switching") says only that the FIFO holds about a millisecond of commands. **Test that settles it:** check whether the set-up routine's size register (0x6b1) store sits behind any branch on the board's strap or size word, in both builds and the PROM copy; the values were read as identical constants in all three (above), so the same depth is the shipped behaviour, but a board-dependent path was not looked for.
- **Level unit: established, doublewords, for the +0x106c bits 15:7 level of the 256-doubleword input FIFO** ([fifo-ports-and-credits.md](fifo-ports-and-credits.md)); the water marks 0x6b2 and 0x6b3 are in words of the memory FIFO (inferred above). The diagnostic reference's error text "Timed out waiting for CFIFO level to drop below <num> words" is about the memory FIFO's marks. That a doubleword store counts two follows from the host credit unit (one credit is an 8-byte doubleword, established in `gfx_flow.o`).
- **Established, arithmetic:** the host credit window is at most 256 credits (2048 bytes, 512 words) on both builds (`gfx_flow_alloc`), and the high-water poll and the hold work in credits, not in FIFO fill. A FIFO of 32,768 words is 64 times the window, so the window, not the FIFO, limits a writer that the board keeps up with.

### Credit return: when, and the 64-store rule

- **Inferred, the hardware shape:** a credit returns when the board takes a word into its FIFO, not when it has run the work. The FIFO holds about a millisecond of commands (published) and the window is 100 to 256 doublewords, so on a real board the window, not the FIFO, limits the writer, and a credit waits only for the store and its acknowledgement to cross the interconnect. No published figure gives that round trip. The software holds the writer only from the high-water mark (32,192 words) until the level falls below the low mark, which is what a board that has genuinely fallen behind would cause.
- **Crediting at entry into an unbounded FIFO:** if credits are never owed, the counter never falls below the driver's bias, which is the same as crediting at entry into an unbounded FIFO. That agrees with the inferred hardware shape whenever the real FIFO is deeper than the window, which the arithmetic above makes certain for the shipped drivers. It differs only in not holding a writer that outruns a slow board, which is a timing difference that IRIX sees only as a slower writer.

### Full FIFO

- **Inferred:** software avoids filling the FIFO by credits and descheduling; a board-side overflow is a flagged fatal error (flag 27, and the teardown mask 0x39f02587 contains bit 27).
- **Unknown: what a store to a full FIFO does** (is it refused, held in the interconnect, or lost). Routes tried: the two kernels, the PROM and the diagnostic reference. The host processor interface's hold on a store when credits run short is described in the interface's own header comments (write-ready withdrawn below the bias); that is a host-side mechanism, not a board one. **Test that settles it:** a published description of the board's input FIFO overflow handling (the flag-27 path above is the only software-visible consequence); no shipped code stores past the credit limit.

### Water marks, status bit 15 and flag 25

- **Established:** the register names of status bit 15 ("above high water"), bit 17 ("below low water"), bit 16 (empty), flag bit 25 and flag bit 9 are in the driver's decode tables (`odsy_init.o` data tables). The kernel never tests bit 15 and masks flag 25 at start-up (`odsyInitInterrupts`, IP30 offset 0x275c, the enable chain clears bit 25).
- **Inferred:** `0x6b2` is the physical high-water mark and `0x6b3` the physical low-water mark, both in words of FIFO fill, and bit 15 and flag 25 compare the fill against the high mark, bit 17 and flag 9 against the low mark. Basis: the arithmetic above and the status-bit names. The 576-word margin below the FIFO's size would be room for words already in flight when the high mark is reached; that reading rests on the arithmetic only, and no shipped code tests it. What the board does at the marks (the comparison it makes, level or edge) is **unknown**.
- **Inferred, what follows for the host:** because the low mark (24,144 words) is far above anything the host window can queue, status bit 17 reads set whenever the board is keeping up. The high-water routine's path then finds bit 17 already set, raises flag 9 itself and enables it, and the low-water routine releases the hold at once. The writer sleeps for real only when the board has fallen 24,144 words behind.
- **Unknown:** hysteresis between the marks, whether flag 25 and flag 9 are level or edge, and the interrupt latency. **Test:** published sources first (the diagnostic reference 108-0314-003 on the FIFO flags and thresholds); if it is silent, a board capture that polls status bits 15 and 17 and flags 9 and 25 while the host fills the FIFO past the high mark and lets it drain below the low mark, with the board's clock noted for latency. Nothing in the shipped code reads the flags between the marks, so no binary read settles it. The capture needs a physical board and goes through the project's proposal step before it is run.

### FIFO set-up registers and 0x7f0

- **Established, value, order and count:** `odsyInitCfifo` stores, in this order, `0x6b0 = 0`, `0x6b1 = 256`, `0x6b3 = 24144`, `0x6b2 = 32192`, `0x7b5 = 1` (IP30 `odsy_init.o` 0x230c, IP35 0x2bc8; the pool of doublewords is read from the code), then the doubleword `0x7f0 = 1000000000` after the microcode load. The IP30 PROM's FIFO set-up (flash 0x48620 to 0x4882c) builds and sends the same six doublewords in the same order, with the memory-protect command in front, `0x7f0` last (flash 0x487f0). So the values are the same in the kernel, the PROM and both hosts.
- **Established:** nothing reads back any of the six registers, in the kernels, the PROM or the monitor.
- **Established, the start-up program is 12,291 words sent with no level check.** After the 0x7b5 store and the 2 ms wait, `odsyInitCfifo` sends three header words (`0x2e008380`, `0x2600807f`, `0x27008000`), then a loop (IP30 `odsy_init.o` 0x2494, outer count 2048) of six stores per record, 12,288 words, each store followed by a `sync` and none preceded by a read of the FIFO level (+0x106c) or of status0. The host credit window is at most 512 words (above), so the board takes or holds most of the program as credits come back. Flow control is attached before the program and `odsyInitInterrupts`, which routes the water-mark interrupts, runs after it ([kernel.md](../../software/kernel/kernel.md), order inside `gf_OdsyInitialize`). The IP35 routine sends the same 12,288 words (kernel.md, IP35 section); the IP30 loop is the one read here. **Inferred:** a FIFO shallower than the program would have to drain while it loads; the inferred 32,768-word depth is more than twice the program. No shipped software states the depth, so this does not bound it.
- **Inferred, `0x7f0`:** a hardware sync timeout counted in board clocks, 10^9 clocks; its expiry raises flag bit 1 (named SYNC_TIMEOUT in the driver's flag table, which is in the teardown mask). Basis: the flag name and the value alone. **Unknown:** the board clock rate and what a sync that times out does besides the flag. The stock drivers never sync for long enough to need the timeout.
- **Unknown, `0x7b5`:** the value 1 is stored last in the set-up; its role (leaving a bypass mode) is a reading of the value alone. Whether any 6.5.30 path stores it with another value: none stores `0x7b5` but the set-up. **Test:** search the microcode disassembly (`software/ucode/disasm/buzz_xform.lst`, `buzz_ucode_kernel.lst`) for an instruction that reads state selected by 0x7b5, and look up 0x7b5 in the diagnostic reference; a board run that stores 0 instead of 1 and checks whether the command FIFO still drains would settle the bypass reading.
- **Established, what the software needs from these stores:** the PROM's text console and the kernel's textport both draw after these stores with no read-back, so a board that merely stores them keeps both working. The kernel's flow-control attach follows the stores and is independent of them: its bias and window are fixed per platform.

## Reset and initialisation

### The widget request timeout, offset 0x28 (+0x2c as a 32-bit access)

- **Established, no shipped writer:** neither `odsyReset` (IP30 `odsy_init.o` 0x1c04; IP35 0x23e0) nor the IP30 PROM's copy (flash 0x48830 to 0x48cc0; the helpers it calls for the clock and memory set-up and for the 0x100c pulse were not scanned) nor any other member of either `odyssey.a` stores to widget offset 0x28 or 0x2c. The scan covered every load and store through the board's register base in all members of both archives for constant displacement 40 and 44; none exists. Generic crosstalk code in the kernel was not scanned.
- **Established, a value was read from a real board:** a published verbose boot of a four-processor deskside Tezro with a V12 (forum post "Tezro IO9/Configuration Oddities", 22 July 2022, https://forums.irixnet.org/thread-3613.html) prints, from the base-I/O PROM's Odyssey sanity diagnostic and before any kernel runs, `XT_REQ_TIMEOUT = 0x000fffff`, `XT_INTR_DST_HI = 0x00000000`, `XT_INTR_DST_LO = 0x00000000` and `FLCTL_CONFIG = 0x0001c000`.
- **Inferred, as a reset value:** 0x000fffff. Nothing shipped writes the register, and the same 20-bit all-ones default is the documented reset value of the request timeout of other crosstalk widgets. The register is read-write: the diagnostic reference (108-0314-003, "Register Test") says its walking-zero and walking-one test covers `XT_REQ_TIMEOUT` (printed pages 11 and 12). That only the low 20 bits are writable is **inferred** from the width of the value and the sibling widgets.
- **Unknown:** what the timeout does (no code reads it) and the register's state after a link reset.
- Cross-reference: the same capture names `FLCTL_CONFIG` with the value 0x0001c000. The print does not give the offset. The driver's flow-control configuration word is at +0x1074 and carries the credit target number in bits 16:12; 0x1c in those bits is the transaction number the driver packs into the interrupt words. Which offset the name stands for is left to the entry that owns +0x1070 and +0x1074.

### The kernel's and the PROM's reset sequences

`odsyReset` and the PROM's copy store, in this order after the clock and memory set-up: +0x103c = all ones, +0x101c = all ones, then zero to +0x1044, +0x104c, +0x1054, +0x105c, +0x1074, +0x107c, +0x108c, +0x109c, +0x10a4, +0x10ac, +0x401c, +0x4024, +0x402c, +0x4034, +0x403c; then +0x4044 and +0x4014 with the master widget id; zero to +0x404c, +0x4054, +0x405c, +0x10bc; all ones to +0x10cc; and at the end zero to +0x34, +0x1044, all ones to +0x103c, zero to +0x1074, the pulse 0, 1, 0 on +0x1084, all ones to +0x101c, zero to +0x5c. **Established**, both images read in full. The reset never stores to +0x1034 (the enables are cleared through +0x103c), +0x1014 (the flags are cleared through +0x101c), +0x28, any command-FIFO word, or any drawing register.

### Board reset pulse, +0x100c

- `odsyLowLevelReset` (`odsy_init.o`, IP30 build, 980 bytes): **established.** One form stores 0x200 to the register (offset 0x1acc), waits 1,000,000 microseconds and never writes 0 back to the register: the zero stores at 0x1ab4 and 0x1ae4 go to the driver's shadow word in the board record (record offset 34216). The other stores 0x16d (built as 0x100, 0x40, 0x20, 0x8, 0x4, 0x1; the store is at 0x1b0c), waits 200,000 microseconds and does write 0 to the register (0x1b24). The form chosen depends on a field of the host chip's identity word (a revision above 4 takes the 0x200 form). The IP35 build has only the 0x200 form. This replaces the earlier statement that the timings were not re-checked.
  Build: `6.5.30-media/usr/cpu/sysgen/IP30boot/odyssey.a(odsy_init.o)`.
- **Established:** `odsyLowLevelReset` is called at the start of `odsyReset`, which then stores every register listed above and sends no drawing state. So a driver run does not depend on any state surviving the pulse.
- **Unknown:** which state a pulse clears. A board that clears all its state on a pulse is consistent with the driver; one that keeps state is too. **Test:** on a board, store distinctive values to the registers the driver can read back (the strap and status word at 0x106c and the flag words), pulse 0x100c and read them again; the registers the host cannot read back are not settled by this and stay unknown. Needs a physical board and the proposal step.

### Reset values of drawing state

For each item the software reads below, the point is the same: the board's reset value is unknown, and the shipped software sends the state before any drawing that depends on it.

- **Draw mask (block 0x024, 0x10424).** **Unknown** reset value. the kernel's textport sends the mask before every primitive (the text-port state set-up routine, `odsy_tport.o` 0x30: the word 0x10424, then the context's mask word, 12 or the caller's value), the buffer-select push (`odsy_drawable.o` 0x744) sends it and is run by the bind and the swap path, and the kernel's state replay after a lost context sends block 0x024. By inference, the X server sends it before the first draw, because its per-screen copy is compared against the new value and an all-zero copy never equals a real mask (3, 12 or 15); the copy's initial value was not traced. So no shipped code draws on the reset mask.
- **Colour mode (the select words 0x22008000 / 0x23008002 for RGB and 0x22008001 / 0x23008003 for index).** **Unknown** reset value. **Established:** the kernel textport's colour routine sends the index form before every fill (`odsy_color`, `odsy_tport.o` 0x9b8), and the public OpenBSD console driver sends the RGB form before its fill. **Inferred** from the X server's constant sites that its fill routines send one or the other before drawing. No shipped path relies on the reset mode. The four select words and their register numbers and values are in `generated/c/buzz.h` (`BUZZ_SEQ_WORD_COLOUR_*`).
- **Current colour index.** **Unknown** reset value. No shipped path draws in index mode without an index word, and the hardware shadow's initial content is whatever the kernel's reset leaves in host memory. GL's own initial index is 1.
- **Depth function, write masks, clip rectangles.** **Unknown** reset values. The kernel's drawable bind pushes the clip words (block 0x204b with the full and empty rectangles) and the context restore replays the depth function and masks; the library validates its state before the first draw. A reset value of these is unobservable to IRIX. **Test:** none from the shipped binaries, since nothing reads these values back; a board capture that draws once after a reset with no state sent, using a drawing that depends on each value in turn, would show them, and needs the proposal step.
- **First switch-in after board start replays everything.** `gf_OdsyStart` (`odsy_init.o`, IP30 build, 144 bytes) stores 127, the "no context" slot, into the board record's current-slot word at +820, and `gf_OdsyPcxSwap` (`odsy_ctxsw.o`) takes its full-replay path when that word is 127 or 0, or when the incoming context's saved word at +564 is zero: it calls `odsyRestoreXform`, `odsyRestoreRaster`, `odsyRestoreGfe` and `odsyRestartContext` in that order (labels 0x908 and 0x90c). **Established**, both routines read in the paths named. So the first context the kernel switches in sends the transform, raster and geometry-engine state wholesale, and no shipped path relies on the board's reset values of that state.
  Build: `6.5.30-media/usr/cpu/sysgen/IP30boot/odyssey.a(odsy_init.o)`.
- **Lighting constants and geometry program memory.** **Unknown** reset content. **Established:** the program memory is loaded before use, by the 12,288-word program of `odsyInitCfifo` and later by the microcode download, and the library loads lighting constants before a lit draw.
- **Depth plane contents.** **Unknown**; the depth-clear word is unknown (grades table). Nothing reads depth before a clear in the shipped software, so the software does not depend on it.
- **Back-end entries (display tables, colour map, cursor, DAC, clock).** **Unknown** reset values. **Established:** the kernel writes every display mode, the cursor control word and the scanout entries itself during board start; the cursor's own reset is graded separately.

## Context switch inside a primitive

- The context switch and restart routines (`odsy_ctxsw.o`): **established.** `gf_OdsyPcxSwap` and `odsyRestartContext` both test the saved primitive type, the low four bits of the saved word at +128, against 11 (`andi 0xf; sltiu 11`): a type below 11 is an open primitive, which `gf_OdsyPcxSwap` drops with the words 0x10444 and 0; a type of 11 or more means none, and `odsyRestartContext` then uses 15. The member also holds eleven restore walkers, named `restorePoints`, `restoreLines`, `restoreLineLoop`, `restoreLineStrip`, `restoreTriangles`, `restoreTriStrip`, `restoreTriFan`, `restoreQuads`, `restoreQuadStrip`, `restorePolygon` and `restoreRect`, one for each type 0 to 10.
- **Inferred:** the board saves an open primitive of every type 0 to 10 (points through polygon and the rectangle form), because the kernel has a replay path for each; the order of the walkers matches the OpenGL primitive numbering used by the library. A board that reported an unsupported switch and saved "idle" for polygon and rectangle forms would refuse behaviour the kernel's replay paths expect. Which of the saved words the board writes for each type is **unknown** (see the attribute replay entry in the datasheet).

## A command cut short

Question: what the board does when the word stream stops inside a command, for example when a bug check stops a CPU between two stores of one multi-word command. Labels: **established** is code or source read in full, **inferred** is reasoned from it, **unknown** names what would settle it. Sources: the IP30 6.5.30 `odyssey.a` members named below, the IP30 `gfx.o`, and the 6.5.7 standalone graphics library that the kernel's textport is built from (`stand/arcs/lib/libsk/graphics/ODYSSEY/odsy_tport.c`, `odsy_flow.c`, `odsy_flow.h`, `odsy_init.c`; it is the same source as `odsy_tport.o`, but an older build than the kernel objects, so each use below says which one was read).

- **Framing, established (existing pages).** A command is a class-1 word whose COUNT field gives the operand words that follow; there is no terminator and no per-command length elsewhere ([BUZZ.h](../buzz/BUZZ.h), command words). The kernel and the user windows take plain 32-bit word stores in store order. So a command that stops short leaves the front end holding a header whose operands have not arrived.
- **No shipped software completes or abandons a cut command, established.** The kernel's exits from a client that may be mid-command are `gf_OdsySuspend`, `gf_OdsyResume`, `gf_OdsyReleaseGfxSema` and `gf_OdsyExit` (`odsy_sched.o`, IP30). All four read in full. Suspend and release detach the flow-control credit object (store 1 to +0x107c, one read of +0x106c, `gfx_flow_detach_me`); resume attaches it again; exit takes the board semaphore, waits for the busy word, then finishes DMA, detaches memory objects and unmaps regions. None of the four bodies stores a word to either FIFO window. Their callees can, however. `gf_OdsyExit` calls `odsyMMdetach`, and a static call walk (`jal` targets across the IP30 objects) reaches `odsy_mm_obj_xfr_bs` and `odsyDMAOp` through `odsy_mm_sg_destroy`, `odsy_mm_grp_destroy`, `odsy_mm_obj_destroy`, `odsy_mm_decommit` and `mm_release_extent`; `gf_OdsyDestroyDDRN` reaches the same two. Both store through the kernel FIFO port (+0x110000), and the transfer in `mm_release_extent` is conditional on a flag that was not decoded, so whether an exit sends a DMA command is **unknown**. If it does, it appends a whole new command behind the cut one; it does not finish the cut one. A scan of every IP30 kernel object for the high-half constant of the kernel FIFO port finds stores in the context-switch, clip, DMA, memory-manager transfer, set-up, textport, microcode-download, mapping and drawable members. (A scan and a static walk, not a read of each body; indirect calls are not followed.)
- **What the kernel does when the stream stops draining, established.** `odsyHiwaterInterrupt` arms `odsyFifoTimer`, which sets a 15 second watchdog (1500 ticks in the 6.5.30 object; `ODY_FIFO_TIMEOUT` is `15*HZ` in the 6.5.7 source). If the FIFO has not recovered, `odsyFifoTimeout` calls `odsy_teardown` and logs "CFIFO timeout" ([kernel.md](../../software/kernel/kernel.md), `odsy_teardown`). The source comment on the timeout handler says it is for a pipe that "is not draining". `odsy_teardown` kills every graphics thread on the board (**established**: the 6.5.7 source sets the scan's signal to `SIGKILL`, the 6.5.30 object passes 9, and `SIGKILL` is 9 in the IRIX signal header) and every later entry point refuses work until `odsyReset` runs. The teardown does not call `odsyReset` itself. The reset follows only if the killed threads include the board manager, whose exit runs `GfxUnmanage` and `cn_init` (item 7 below); that the kill reaches the manager is **inferred**. So IRIX's only answer to a stream it cannot finish is to kill the board's users and refuse work, and a reset comes after that by the manager's exit. The context-switch, glGet, memory-manager and DMA waits have their own 15 second watchdogs (`ODSY_CTXSW_TIMEOUT_INTERVAL` and its siblings in the 6.5.7 `odsy_internals.h`, IP30 objects `odsy_ctxsw_timeout` and the others named in [kernel.md](../../software/kernel/kernel.md)); each ends in the same teardown.
- **Hardware outcome, unknown.** No shipped code, source or published document says whether the front end waits indefinitely for the missing operands, times out, or treats the next header as an operand. Routes tried: the kernel's exit, suspend and teardown paths (above), the 6.5.7 library (it only polls the FIFO level with no limit; the poll macro's comment says a timeout routine "will have to reset gfx"), and the two board-side timers found (below), whose roles are not shown. The diagnostic reference 108-0314-003 was searched for the FIFO flags by an earlier pass (above) and was not re-read for this question. Nothing shows either board-side timer to be a parser timer, and nothing shows otherwise. The flow-control configuration word at +0x1074 has a 10-bit timeout field (`ODSY_FLOWCTL_TIMO`) set to 200 in 100 MHz ticks (2 microseconds) in the 6.5.7 source; what it times is not stated there, so its role is **unknown**. The 6.5.30 kernel builds the same low byte, 0xc8 ([kernel.md](../../software/kernel/kernel.md), `gf_OdsyInitialize`). The doubleword stored to register 0x7f0 (10^9) is a hardware-sync timeout, **established** by the 6.5.7 source (`SYNC_TIMEOUT`, in board clocks, commented as 5 seconds at 200 MHz and "less than 80 seconds"); a wait for a hardware sync is not a wait for operands. **Inferred, weakly:** wait. IRIX can preempt a client between any two of its stores (libGLcore puts no barrier between them), so a command left half sent for a scheduling quantum is routine, and the board is never told. **Unknown:** how the next context's words are kept out of the preempted client's operands. Two readings fit: the save request at +0x118000 captures the front end's partial-command state with the context, or the user stores reach the board in whole bursts. The saved record the kernel replays holds an open primitive's type and vertices ([buzz/README.md](../buzz/README.md) section 4, "Context switch inside a primitive" above), not an operand count. **Test that settles it:** the board's host-interface input logic, or a model of it; neither exists here. A hardware test would be a last resort and goes through the proposal step.
- **Design consequence, for the bug-check handler.** Do not pad or resynchronise. Treat any command in flight as lost and reset the board before drawing (next section). A padding scheme would be built on an unknown, and IRIX never does it. If a miniport can cheaply record how many operands it still owes, padding is harmless on every reading that waits, but it is not a recovery on the readings that do not.

## Taking the board back after a crash or a lost manager

Question: how software takes the head back for a panic or STOP screen, and what IRIX's own console path does. Sources as above, plus the IRIX 6.5.7 kernel sources `irix/kern/os/printf.c` and `irix/kern/io/cn.c` (the panic and console paths), the IP30 `gfx.o` (`GfxUnmanage`, read in full) and the IP30 `htport.o` (the generic text port: `htp_register_board`, `htp_init`, `htp_reinit`, read in full; `htp_write` read to its dispatch).

**The path IRIX takes, established.**

1. `cmn_err` at panic level raises the interrupt level, tells the other processors to spin, and calls `dopromreset(1)`, which calls `cn_init(1, 0)` once (`printf.c`). The text of the panic is then written through `cn_write`, which on a graphics console calls `tpcons_write` ([kernel-textport.md](../../software/kernel/kernel-textport.md)). `console_ready` lets a graphics console print during a panic whether or not the serial port was found.
2. `cn_init` begins with `gfx_earlyinit` (`cn.c`). On IP30 that calls `odsy_earlyinit` and then `mgras_earlyinit` with no test of either result ([kernel-textport.md](../../software/kernel/kernel-textport.md)). A console on serial (first character `d` or `D`) makes `odsy_earlyinit` return at once, so a serial console never resets the board.
3. `odsy_earlyinit` (IP30 `odsy_init.o`, read in full): a second entry while the first has not finished logs "re-entered" and gives up. Otherwise it finds the board and waits (a 200 tick timer and a semaphore, repeated) until a counter in the board record at +28480 falls below 2; the wait is skipped when a panic is in progress, when a board-record flag at +0xb468 is set, when a global flag is set, or when the counter is already below 2. What the counter counts is not read. In panic mode `odsy_earlyinit` also sets the +0xb468 flag. It then calls `odsyReset(0)`, `odsy_tport_lock_init` (which re-initialises the text port's spin lock; **inferred** that this is what lets a lock left held by a stopped CPU be ignored) and `htp_register_board` with the board's pixel size.
4. `odsyReset` is the full reset of [bringup-without-prom.md](../../software/kernel/bringup-without-prom.md) step 3: the 0x100c abort pulse, the widget link reset, the host-chip mask handling, the register zeroing, the memory-configuration word and the display back end set-up with the default timing. It ends with the flow-control clear pulse (+0x1084, below) and zeroes +0x1074 and +0x107c. Whether that is what abandons a half-sent command is the unknown above; IRIX relies on the whole reset, not on one step.
5. `cn_init` then calls `tp_init`. The text port was already chosen, so `tp_init` calls `htp_reinit`, which is `htp_init` (a plain call, same code). `htp_init` calls the board's `odsy_tpinit`, then redraws the whole text port (`txMapcolors`, font set-up, defaults, `txClear`, `txReshape`).
6. `odsy_tpinit` (IP30 `odsy_tport.o`, read in full) is the second half of the recovery: it waits until the FIFO level (+0x106c bits 15:7) reads zero (5 microsecond polls, no limit), pulses +0x1084 as 0, 1, 0, stores 0 to +0x1074 and 1 to +0x107c (flow control off), runs `odsyInitCfifo` (the six FIFO set-up doublewords, the 12,288-word microcode program, the +0x201594 check), runs `odsyInitDBE` twice for the display timing, copies the 4165-word stored command stream into the kernel FIFO port, and sends the textport state words (`ODSY_SET_GC`). A failed set-up repeats `odsyReset` up to six times, then logs and gives up. Every wait in this chain is unbounded.
7. The same chain runs when the board manager (the X server) goes away: `GfxUnmanage` (IP30 `gfx.o`, read in full) runs a thread scan carrying the number 9 (a kill signal, **established** as in `odsy_teardown` above: the same `GfxKiller` callback, `SIGKILL`), calls the driver's release slot (slot +192 of the operation table), then calls `cn_init(0, 1)`. The call is made only on the branch where a word at +24 of the object at +8 of the manager record is zero; what that word says is not read. The 6.5.7 comment in `odsy_init.c` says that when the manager for board 0 dies, `cn_init` re-runs the early init. The case "a client died mid-command" is therefore handled by resetting everything, not by finishing the command.
8. The PROM's console uses the same textport source built standalone: `odsy_stand_tpinit` calls `odsy_earlyinit` and `odsy_tpinit`, then loads a cursor glyph and parks the cursor at x = 1280, off screen (6.5.7 `odsy_tport.c`). [prom-board-handoff.md](../../software/firmware/prom-board-handoff.md) has what that leaves.

**The register facts the chain relies on.**

- **+0x100c is the abort register, with named fields.** The 6.5.7 source (`odsy_init.c`, `odsyReset`) toggles six named bits together and releases them, then separately pulses a DBE soft reset: the names are `dbe_fifo_flush`, `dma`, `copy`, `pio_fmt`, `dma_fmt` and `hw_sync`, with `dbe_sreset` and `ody_flush` as two more fields. **Established** that these fields belong to the register `sys.abort`, whose offset is the +0x100c that the 6.5.30 binary stores to (the source's field set is six names and the binary's constant has six bits). **Inferred:** the bit values follow the order the source sets them, 0x100, 0x40, 0x20, 0x8, 0x4, 0x1 for the six names in that order, because the 6.5.30 binary ORs six constants in that order (`odsyLowLevelReset`, read in full). The values are not in a header held here. The 0x200 form of the 6.5.30 kernel is **inferred** to be `ody_flush` (the source's one-shot board reset; its comment says the reset line has "a huge capacitor", which is why the newer form waits a full second) but 0x200 could also be `dbe_sreset`; no held source gives either value. The 6.5.30 kernel has no separate DBE soft-reset pulse: its only stores to +0x100c are these.
- **+0x1084 is the flow-control clear, not a command FIFO reset, established.** The 6.5.7 source names the register `flow_ctl_clr`, sets it 0, 1, 0 right after waiting for the FIFO level to drain and before writing the flow configuration word, and the kernel's other site (`odsyReset`) does the same. Earlier pages here (`BUZZ.h`, [kernel.md](../../software/kernel/kernel.md)) called it the command FIFO reset, inferred; that reading is withdrawn. What actually empties or restarts the command FIFO's parser is therefore **unknown**: the abort pulse's `copy`, `pio_fmt` and `dma_fmt` names suggest the front end's format state is among the six, but no field is described. The practical recipe (abort pulse, link reset, full set-up) is the one IRIX uses and is established as a sequence, not as a mechanism.
- **The FIFO is 128 KB of board memory with no wrap protection, established (source).** `odsy_flow.h` defines it as 16 tiles of 8 KB at address 0, 32,768 words, with a physical high-water mark that leaves room for the front end's buffering (256 doubleword entries doubled plus 0x40 words, 576 words) and a low-water mark at three quarters of the high mark. These give exactly the values `odsyInitCfifo` stores (0x6b1 = 256 tiles, 0x6b2 = 32192, 0x6b3 = 24144, in the source's order base, tiles, low, high, bypass-off), so the stored values are established as the source's derived constants. The pairing of register ids with those names rests on the exact match of the two formulas (the high mark is the size minus 576, the low mark three quarters of it) and on the store order matching the source's (base, tiles, low, high, bypass-off), so it moves from weak inference to strong inference: 0x6b3 is the low mark and 0x6b2 the high mark. No source held gives the ids. The comment says plainly that the board does not protect against wrapping, so a cut command that is never completed cannot overrun the FIFO by itself; only more words can.

**What a STOP-screen backend should do, design.** The chain above is the proven recipe. Its explicit delays add to about 0.4 s on the 0x16d form (the abort pulse waits 0.2 s, the host-chip mask restore 0.1 s, the widget write 0.1 s, the link reset 1 ms, the memory-configuration stores about 2 ms) and about 1.2 s on the 0x200 form (1 s instead of 0.2 s). The three `odsyInitDBE` runs, the microcode load and the 4165-word stream are not timed here. Run it as one sequence: link reset, abort pulse, `odsyReset` steps 3.2 to 3.9, the +0x106c drain wait, the +0x1084 pulse, the FIFO set-up and microcode load, the timing, the stored stream, the textport state words, then the polled text writes of [kernel.md](../../software/kernel/kernel.md) ("Command words the kernel emits"). Bound every wait, which IRIX does not, and do not take the driver's own locks, semaphores or credit objects. IRIX's own path takes them: `odsyReset` takes the global spin lock when the panic flag is set, `odsyInitDBE` takes the board's semaphore and spin locks (a call count of the object, not a read of each caller), and `odsy_earlyinit_timeout` is a plain `vsema`. Whether a stopped CPU can leave one of those held and hang the panic path is **unknown** and is IRIX's problem, not ours. **Unknown:** whether a lighter path (abort pulse plus FIFO clear and set-up, no link reset or display re-timing) leaves the display intact; nothing shipped tries it. **Test:** a model run, or the proposal step for a board.

**Known console mode after recovery, inferred.** The 6.5.7 library's `odsy_tpinit` (source, read in full) sets 8-bit colour index, the front buffer, window offset zero and the screen mask and scissor to the size of the default or `monitor`-chosen timing; the standalone path parks the cursor off screen at x = 1280. The 6.5.30 kernel's `odsy_tpinit` sends its state through `ODSY_SET_GC` and a stored stream whose words were not decoded for this page, so that the kernel path leaves the same mode is inferred, and the screen size is the timing's, not necessarily 1280 x 1024. The text port's redraw then remaps its colours and clears the screen.
