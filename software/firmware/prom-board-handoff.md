# What the boot PROMs leave on the board

Which parts of the VPro bring-up the IP30 and IP35 boot PROMs run, and what a client that starts after them (a kernel, OpenBSD, an NT driver) can rely on. Release IRIX 6.5.30m, `usr/cpu/firmware/IP30prom.bin` (flash offset = address minus 0xbfc00000) and the inflated BASEIO PROM inside `usr/cpu/firmware/ip35prom.img` (gzip stream at file offset 0x8cbb0, an ELF executable linked at 0x13000000; file offset = address minus 0x13000000). Labels: **established** (code read in full, address given), **inferred**, **unknown**. Disassembly was done with a flat big-endian MIPS64 decode; the PROM text is not committed.

## Short answer

- **established.** Both PROMs carry the same VPro driver source as the kernel: `odsyGatherInfo`, `odsyReset`, `odsyLowLevelReset`, `odsyInitCfifo` (with the microcode load), `odsyInitDBE`, the cursor-table loader and `odsy_earlyinit`. The IP35 PROM is not a bare identifier, which the compressed image's string search had suggested (corrected in [firmware-images.md](firmware-images.md)). Both hold the kernel's 27196-byte microcode array byte for byte (IP30 flash 0xba708; IP35 inflated file offset 0x12df90).
- **established.** The PROM does two separate things. A hardware scan resets every VPro board it finds and nothing more. Installing the graphics console then runs the full start-up: command FIFO set-up, microcode load, timing and scan-out size, cursor tables, stored command stream.
- **inferred.** With `console=d` (serial console on IP30) the scan still runs, so the board is reset and quiet, but the console-install start-up is not run: no microcode, no timing, no scan-out size, so no picture. The scan code has no test of the console variable; the console-install step is a method of the graphics console device, which a serial console does not select. The link from the variable to the method table was not traced to the end (below).
- **established.** A client that runs after a console=g start-up sees: microcode loaded (built-in 2048 instructions), command-FIFO water marks set, flow control off, 1280 x 1024 scan-out with a 60 Hz (or `monitor=72hz`) timing, cursor tables loaded. OpenBSD relies on exactly that and rewrites everything else itself.

## IP30 PROM, in order

All addresses are IP30PROM code addresses.

1. **Hardware start-up reads `diagmode` and `console`** (routine at 0xbfc37364; the two names are the environment strings at flash 0x93328 and 0x93338). A first character 'd' in `console` sets a local flag that selects the plain-text sign-on (0xbfc6df6c with its second argument 0) over the graphics sign-on (second argument 1). Both paths then reach the same call at 0xbfc37414 to the graphics board initialiser at 0xbfc3a3b0. **established** as flow. The flag does not condition that call.
2. **Graphics board initialiser** (0xbfc3a3b0). It asks the enumerator at 0xbfc3a4ec for the board list of every graphics family, and for a VPro board calls the scan at 0xbfc499a8. **established.**
3. **VPro scan** (0xbfc499a8, with `odsyFindBoardAddr` at 0xbfc498dc and the widget finder at 0xbfc49a40). For board numbers 0 and 1 it looks for a crossbar widget with part 0xc013 and manufacturer 0x23, searching widgets 15 down to 9 behind a link test (0xbfc6b0d4). Each board found gets a per-board record of 0x5688 bytes and a call to `odsyReset` (0xbfc488a0). The same scan also runs from `odsy_earlyinit` (0xbfc49d98, which has the same re-entry guard and message as the kernel's but no `console` test). **established.**
4. **`odsyReset`** (0xbfc488a0). The kernel's order ([kernel.md](../kernel/kernel.md), "odsyReset order of operations") with the differences marked:
   1. defaults 1280 x 1024 into the record (+0xe8, +0xea);
   2. `odsyLowLevelReset` (0xbfc48dd4): 0x100c = 0x200 on hosts whose chip word has a revision nibble above 4, else 0x16d, each followed by `us_delay(200000)`; the 0x16d form then stores 0 to 0x100c, runs the widget reset (0xbfc49870) and `us_delay(1000)`; restore of the widget words; 0x1004 = record shadow, then 0x40_0000 (the kernel's master widget 8 shifted left by 19, below);
   3. nothing: the PROM has no store of widget id | 0x4200 to widget +0x24, no `us_delay(100000)` after it and no separate 0x1004 = master id << 19 write; the kernel has all three ([bringup-without-prom.md](../kernel/bringup-without-prom.md) steps 3.2 and 3.3). **established** (no such store in 0xbfc488a0 to 0xbfc48dd4 or in the IP35 copy at 0x1305f130);
   4. `odsyGatherInfo` (0xbfc48384) reads the strap word at +0x106c;
   5. `odsyInitDBE` with quick = 1 (0xbfc491dc): display FIFO writes 0x2b00 = 0 five times and 0x2700 = 0x0006d3e0, I2C ports, option probe, `odsyConfigFb` 1280 x 1024 x 8, then 0x2802 = 0 and 0x2803 = 0 (**inferred** from the kernel's twin; the PROM copy was read for the first step only);
   6. the zeroing of the interrupt and engine registers (0x103c, 0x101c, 0x1044 to 0x105c, 0x1074, 0x107c, 0x108c to 0x10ac, 0x401c to 0x405c, 0x10bc, 0x10cc), the 0x4044 and 0x4014 words, with the master id fixed at 8 (0x80 and 0x800000 where the kernel ORs in id << 4 and id << 20);
   7. the 0x1004 memory-configuration sequence (0xbfc48be8 to 0xbfc48c60): `us_delay(400)`, then bit 5 cleared (wait 400), bit 5 set (wait 400), the same word again (no wait), bit 5 cleared (wait 400). That is four waits and no bit 8 store; both kernels add a bit 8 store and a fifth wait ([bringup-without-prom.md](../kernel/bringup-without-prom.md) step 3.8). The IP35 PROM is the same (0x1305f4ec to 0x1305f560);
   8. 0x34 = 0, 0x1044 = 0, 0x103c = all ones, 0x1074 = 0, 0x1084 pulse 0, 1, 0, 0x101c = all ones, 0x5c = 0.
   **established** for the store list and the delays. The PROM and kernel copies differ in the marked steps and in the 0x100c delay (below).
5. **Timing choice inside `odsyReset`** (0xbfc489a4 to 0xbfc48dd0). The PROM environment variable `monitor` (string at flash 0x96598) is read. A value of "72hz" selects the 72 Hz table at flash 0xc9a00, but only when the board variant flag (record +0x118) is 1; "60hz", or no variable, or any other value, leaves the table at flash 0xc9d90. The pointer sits in the 64-bit variable at flash 0xba700, which also precedes the microcode array at 0xba708; `odsyReset` passes it to the quick `odsyInitDBE` first and then resets it to the 60 Hz table before the `monitor` test. The kernel does the same with its option "monitor" (`driver-functions.md`, default timing). **established** for the PROM; the 72 Hz and 60 Hz tables were not compared with the kernel's built-in ones.
6. **Graphics console install** (method at 0xbfc65328, first word of the ODSY console method table at flash 0xcee80; the sibling at 0xcee40 is the board lookup 0xbfc652a4). It calls:
   1. `odsy_earlyinit` again (0xbfc49d98), which resets any board not yet reset;
   2. the console set-up at 0xbfc64d9c: wait for bits 15:7 of +0x106c to read zero (5 microsecond polls), pulse 0x1084 (0, 1, 0), 0x1074 = 0, 0x107c = 1, then `odsyInitCfifo` (0xbfc48624);
   3. `odsyInitCfifo`: block 0x0854 with 0 and 0x0fffffff, the five doublewords 0x6b0 = 0, 0x6b1 = 0x100, 0x6b3 = 0x5e50, 0x6b2 = 0x7dc0, 0x7b5 = 1, word 0x00010046, `us_delay(2000)`, a read of +0x201594 that must be 0x003d0046 (otherwise it stops and returns 1), then 0x2e008380, 0x2600807f, 0x27008000, the first 2048 instructions of the array at flash 0xba708 as 12288 words, and 0x7f0 = 0x3b9aca00. Identical to the kernel's routine ([kernel.md](../kernel/kernel.md), "start-up FIFO set-up"). **established.**
   4. `odsyInitDBE` twice with quick = 0 (0xbfc491dc): first with the table at flash 0xc9d90, then with the chosen pointer from step 5. Each writes the scan-out size 1280 x 1024 (0x2802, 0x2803) and loads the timing, as the kernel's twin does. That the first call uses the fixed 60 Hz table is **established**; why it loads the 60 Hz table before the chosen one is **unknown**.
   5. the cursor tables (0xbfc64fc8, described in [firmware-images.md](firmware-images.md));
   6. the stored command stream (flash 0xcac30, replayed through 0xbfc6407c; described in [firmware-images.md](firmware-images.md)), and the return of width 1280 and height 1024 to the console layer.

## IP35 PROM

- **established.** The inflated BASEIO PROM has the same routines and strings (`odsy_earlyinit(hw=0x%x) boardnum=%d`, `monitor`, `72hz`, `60hz`, the `odsyReset`, `odsyGatherInfo` and `odsyInitDBE` messages at inflated offsets 0x102718 to 0x1028e8). Its `odsyInitCfifo` is at 0x1305e1d8 (same store list, same 2000 us wait and +0x201594 check, same 2048-instruction load from its own copy of the array, inflated file offset 0x12df90), its `odsyLowLevelReset` store of 0x200 to 0x100c is at 0x1305f0b0, and its graphics console install is at 0x1305fd5c, with the same drain wait, 0x1084 pulse, 0x1074, 0x107c, `odsyInitCfifo` and two `odsyInitDBE` calls at 0x1305f9f8 to 0x1305fb04. The install first calls a board-start routine (0x1305fc14) that, for a board not yet marked as reset, runs the reset (0x1305f130) twice with `us_delay(100)` between; the IP30 start (0xbfc49d98) resets each board once. **established.** Its reset has the same missing widget +0x24 store and four-wait 0x1004 sequence as the IP30 one (above).
- **established.** Its diagnostics ("Graphics diagnostics", "Odyssey board #%d found on nasid %d", the xtalk sanity and Buzz register tests, `diag_gfx`) run before the console install, and they print the strap word ([board-registers.md](../../devices/board/board-registers.md), "The IP35 PROM's board-register diagnostic"). The three IP35 PROM boot transcripts on one published page (PROM 6.210 and 6.211, boards on nasid 0 and 3; https://just.graphica.com.au/tips/sgi-o350-chimera-notes/, a 2021 Origin 350 and Fuel notes page) show the diagnostics, then "Installing Graphics Console..." and "graphics install: searching for pipe 0".
- **established.** The IP35 PROM waits 200000 microseconds after storing 0x200 to 0x100c (0x1305f0a8, with the delay routine at 0x130d5fb8); the IP35 kernel waits 1000000 (`kernel.md`, "odsyLowLevelReset on IP35"). The IP30 PROM waits 200000 on both branches; the IP30 kernel waits 1000000 on the 0x200 branch. Both values work on shipped boards.

## What the NT design should take from this

- **IP30.** If the HAL is allowed to require `console=g`, the PROM state above is what a driver inherits, and OpenBSD shows the minimum a client then adds (below). If the NT loader must also work with `console=d`, the driver needs the whole [bring-up sequence](../kernel/bringup-without-prom.md), because a serial console leaves the board reset but not started.
- **IP35.** The same holds: the PROM's console install does the bring-up the kernel would do, so a loader that starts after a graphics console install inherits the state of the IP30 case. The design's earlier statement that the IP35 PROM leaves bring-up to the driver is wrong for the console-g case.
- **What OpenBSD adds on top.** Its `odyssey_setup` rewrites the sequencer registers 0x20 to 0x35, the two transform tables, the raster blocks, the 32 display-mode words at 0x2900 (all 0x905215a6), the cursor control (0x2581 = 0) and the gamma ramp, so none of those has to be what the PROM left. It loads no microcode and does not write the scan-out size or the timing, so those two and the microcode are the state it depends on. **established** from [buzz/README.md](../../devices/buzz/README.md) section 11 and the PROM reads above.

## Not left, or not known

- **Display mode word.** The kernel's `odsyInitDBE` writes the 32 words at 0x2900 from two stack words the function never sets (`kernel.md`); the PROM copy was not read for this step, so the value the PROM leaves is **unknown**. OpenBSD overwrites it, so nothing depends on it.
- **Scan-out base, pitch, depth.** There is no register a client reads for these. `odsyConfigFb` (called with 1280, 1024 and depth 8) sets 0x2800, 0x2801, 0x2807 and 0x2809 ([pbj/PBJ.h](../../devices/pbj/PBJ.h) section 6); the pitch is in 16-pixel tiles and the frame buffer is only reachable through commands. That the PROM's 8-bit depth code stays in 0x2809 while OpenBSD draws 32-bit pixels is **established** as a pair of facts; how the board reconciles them is **unknown**.
- **Gamma.** The PROM was not read for a gamma-ramp write. **unknown** what it leaves; OpenBSD writes its own.
- **Interrupts.** The PROM zeroes the routing and enable registers and never programs them ([kernel.md](../kernel/kernel.md) step 5). A client that wants interrupts programs them.
- **`console=d` end to end.** The scan reaches the board without the console test, and the console install is a method reached through a table, not a direct call: nothing calls 0xbfc65328 by address. The step from the `console` string (read again at 0xbfc44a94, where any first character other than 'g' is taken as head 0 of the graphics list) to the method was not traced. What would settle it: finding the table entry that holds the method address (flash 0xcee80) in the console-device list and reading the code that walks the list.
