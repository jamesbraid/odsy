# Retrace interrupt and video-sync count in a two-field format: per field or per frame

Question: for a VPro (Odyssey) format with two fields to a frame, such as `1920x1200_30f`, does the board raise its retrace interrupt, and does the counter that `glXGetVideoSyncSGI` returns advance, once per field or once per frame? A model that raised one per field made a 30 frame-per-second clip play at double speed.

Release IRIX 6.5.30m. Kernel objects `usr/cpu/sysgen/IP30boot/odyssey.a(odsy_retrace.o)`, `usr/cpu/sysgen/IP35boot/odyssey.a(odsy_retrace.o)`, `usr/cpu/sysgen/IP30boot/rrm.o`; library `usr/gfx/arch/IP30ODSY64/libGL.so`; X module `usr/lib/X11/dyDDX/odyssey.so`; format file `usr/gfx/ucode/ODSY/vof/1920x1200_30f.vfo`; compiler rules `usr/gfx/ucode/vfc/rules/VPro_Board.def`. The line-table decode is `tools/vfo_line_tables.py`, which reads all 71 files of `usr/gfx/ucode/ODSY/vof/`. Offsets are in the member or image named. Ratings: established, observed, software expectation, inferred, approximation, unknown. Nothing here is observed: no board was read.

## Answers

| # | Answer | Rating |
|---|---|---|
| 1 | `1920x1200_30f` is progressive, not interlaced. It has two fields per frame, each a full 1200-line scan of the same frame-buffer lines. Frame rate 29.8997 Hz, so each field (the monitor's vertical refresh) comes at 59.7994 Hz. | established (file fields, arithmetic); that the field rate is the monitor's refresh is inferred |
| 2a | The video-sync counter that `glXGetVideoSyncSGI` returns is raised once per retrace interrupt, unconditionally. The handler reads no field, frame or parity state. | established |
| 2b | The kernel cannot tell a field interrupt from a frame interrupt, so the interrupt rate is whatever the board's timing program makes it. The compiled tables of all 71 shipped format files carry `VINT` exactly once per frame, never once per field (section 3a). If `VINT` is the retrace interrupt, `1920x1200_30f` raises 29.9 a second and so does the counter, and the interlaced `1920x1080_30i` raises 30, not 60. | established (the pulse count and position); the rate follows only if 2c holds |
| 2c | `VINT` is what raises the retrace interrupt (source 3). The name, the once-per-frame pulse and the VPro guide's per-frame counter agree, and the other once-per-frame output is named for the swap-ready pin. No register write routes a generator output to an interrupt source, and no shipped software or document states the wiring (section 3b). | inferred, weakly; the wiring itself is unknown |
| 2d | `VINT` is bit 0 of the low byte of every timed line-table entry (generator output A14, signal index 14): high from the start of line 1 to the start of line 2 of each frame. | established (arithmetic: the compiled edges match the compiler rules to the pixel) |
| 3 | The two manuals state the counter, not the interrupt. The VPro guide (full frame) agrees with the shipped format rules read as in 2b; the OpenGL guide's generic per-retrace text does not address a progressive two-field format. | software expectation (manuals), inferred (match) |

## 1. What kind of format `1920x1200_30f` is

All values are **established**, read from the format file's name table (table at 0xd38, 180 fields; the container is described in [display-files.md](../../../video/display-files.md)). The three files compared are `1920x1200_30f.vfo`, `1920x1080_30i.vfo` (interlaced) and `1920x1200_60.vfo` (one field).

| Field (value offset in the file) | `1920x1200_30f` | `1920x1080_30i` | `1920x1200_60` |
|---|---|---|---|
| `FormatInfo_Interlaced` (0xd2c / 0x137c / 0xa84) | 0 | 1 | 0 |
| `FieldsPerFrame` (0xbc) | 2 | 2 | 1 |
| `FieldLineCount` (0xc0, count then values) | 1200, 1200 | 540, 540 | 1200 |
| `FieldLineOffset` (0xcc) | 0, 0 | 1, 0 | 0 |
| `FieldLineSkip` (0xd8) | 0, 0 | 1, 1 | 0 |
| `SwapsPerFrame` | 1 (0x198) | 2 (0x1a4) | 1 (0x180) |
| `FieldSwap` (0xe4) | 1, 0 | 1, 1 | 1 |
| `TotalLinesPerFrame` / `TotalPixelsPerLine` | 2592 / 2400 (0x1d8, 0x1dc) | 1125 / 2200 | 1242 / 2616 |
| pixel clock (`FormatInfo_PixelClock`) | 186 000 000 (0xce0) | 74 250 000 | 195 000 000 |
| `FramesPerSecond` and `VerticalRetraceRate` | 29.8997 (0x120, 0x1e0) | 30 | 60.017 |
| vertical front / sync / back porch (lines) | 30 / 6 / 60 (0x3a8 to 0x3b0) | | 3 / 3 / 36 |

- **established.** The 30f file is progressive (`FormatInfo_Interlaced` is 0) and its two fields do not interleave: both start at offset 0 with skip 0 and 1200 lines, where the interlaced file's fields start at 1 and 0 with skip 1 and 540 lines each. So each field repaints the whole frame-buffer image. The frame carries 2 x 1296 lines (1200 active, 30 + 6 + 60 porch and sync); both field-vertical-sync entries (`FormatInfo_F_0_V_Sync`, `FormatInfo_F_1_V_Sync`) are present and equal.
- **established (arithmetic).** 186 000 000 / (2400 x 2592) = 29.8997, the stored `FramesPerSecond`; 186 000 000 / (2400 x 1296) = 59.7994 per field. This is the monitor's vertical refresh, **inferred** from the two per-field vertical-sync entries.
- **established.** `VerticalRetraceRate` equals `FramesPerSecond` in all 71 files of `usr/gfx/ucode/ODSY/vof/`, including every two-field, stereo and interlaced one (a two-field 30i file stores 30, not 60). The compiler's "vertical retrace rate" is therefore a frame rate.
- **established.** The X module treats it that way: `odsyReadVideoFormat..MB` (`odyssey.so`, 0x16b3220) stores `VerticalRetraceRate` at node offset +0x218 (0x16b33f4 to 0x16b33fc) and sets the refresh rate at +0x214 to the same value when the format is interlaced (the branch at 0x16b3404), otherwise to `FieldsPerFrame` times it (0x16b3838 to 0x16b3858, `mul.s`). For the 30f file the refresh rate is 2 x 29.8997 = 59.8 Hz, the field rate.
- **established.** The kernel does not read the field count or the refresh rate: in `gfP_OdsyBRDMGRloadTimingTable` and `odsyLoadTimingTable` (`odsy_brdmgr.o`, IP30) no load touches words 172 (`FieldsPerFrame` as the X module stores it) or 184 (refresh rate) of the 320-byte structure. The frame and line tables carry the whole field structure to the timing generator.

## 2. The kernel side: what the counter counts

**established** (whole routines read; IP30 and IP35 listings compared, identical apart from one per-CPU index constant).

- `odsyRetraceHandler` (`odsy_retrace.o`, IP30 0x1274, 716 bytes; IP35 0x131c, same size): after `mutex_lock` on the retrace mutex it adds 1 to the board record's word at +128 (IP30 store at 0x12b8; IP35 0x1360) and 1 to the word at +124 (IP30 0x12c4; IP35 0x136c) on every entry. Nothing before those stores branches. The only board register the handler reads is +0x10d4 (IP30 0x12f8), the per-window buffer-select word; it reads no flags, status or timing-generator register, so it has no field or parity to test. Both counters therefore rise by one per interrupt. The handler runs only as the handler of interrupt source 3 (`devices/buzz/README.md` section 6).
- Nothing else in `odyssey.a` writes those two record words: a search of every `sw` or `sd` to offsets 124 and 128 in the IP30 objects finds the handler, `RRM_SetVideoSync` and `gfxioctl` (both below) and stores to other records (`odsy_ddrn.o`, `odsy_ctxsw.o`, other `rrm.o` routines; the 8-byte stores in `rrm.o` are a different field).
- `RRM_GetVideoSync` (`rrm.o`, IP30 0x431c; ioctl 1022) copies the word at +128 of the board record to the caller. `RRM_SetVideoSync` (0x4308, ioctl 1021) is the only other writer in `rrm.o`. `gfxioctl` (`gfx.o` 0x2b48, command 106, branch at 0x2dc4) also stores zero to +128 of the record at +40 of its device argument (0x2fe0, in the delay slot of a `splhi` call) before it clears that record's +72 pointer (0x3000), so the counter restarts at zero on that path. The record is the one `RRM_GetVideoSync` reads: **inferred**, since `RRM_Dispatch` is called with that same argument (0x2db4). The shipped binaries hold no sender of 1021 that the scan found, although both manuals say `gfxinit` initialises the counter: **unknown** who sets a nonzero value.
- `glXGetVideoSyncSGI` (`libGL.so` IP30ODSY64, 0x55a995c) sends ioctl 1022 (`li a1,1022` at 0x55a99b0) and returns the second word of the reply unchanged (load at 0x55a99cc, store at 0x55a99d8): no scaling or division.
- `rrmValidateVideoSync` (`rrm.o` 0x44a8; called only from the handler, when the waiter list at +136 is not empty) tests a waiter with `counter mod count == phase`, using +128 when bit 3 of the waiter's flags is set and +124 otherwise. Both counters move together, so `glXWaitVideoSyncSGI` also counts interrupts.

So the question reduces to the interrupt rate: the counter is exactly one per interrupt, and the kernel keeps no per-frame or per-parity state.

## 3. The board side: which timing output could be the interrupt

- **established.** The compiler rules `VPro_Board.def` give the timing generator these outputs (rule text near offset 10836, edge rules from offset 12557): `VINT` on A14, `SWP_RDY_LCK` on A15, `END_OF_FIELD` on A19. The edge rules, in the file's own scope words: `VINT` rises one line into each frame and falls one line later (`within each (frame)`); `SWP_RDY_LCK` pulses for three lines in the first frame only; `END_OF_FIELD` pulses low for 1.75 lines at the start of each field (`within each (frame)` containing `within each (field)`, so the field is the inner unit); `HIF_V_UPDATE_EN` is per field active area. A frame therefore contains all of a format's fields, as the format compiler guide says for multi-field formats (007-3402-003 printed p.20 to 22).
- **established** (fields above): `SwapsPerFrame` is 1 and `FieldSwap` is 1, 0 in the 30f file, so the board takes one swap opportunity per frame, in field 0; the interlaced and stereo files have 2 and 1, 1. Who reads `SwapsPerFrame` is **unknown**: the name sits in a table of format-field names in `odyssey.so` (.sdata, entry at 0x1738e34) whose reader was not traced, and the kernel loader does not read it.

### 3a. Where the compiled table carries VINT

All **established (arithmetic)** unless marked: the table is read from the file and laid against the rules' text, and `tools/vfo_line_tables.py` repeats every check below on all 71 files (exit status 0; with its event rule removed it fails on all 71, so the check can fail).

- **Entry layout.** A line type is a run of 16-bit entries ending at the first one with bit 15 set (the frame table's start positions, in 32-bit words, are half the halfword index). A timed entry has its duration in pixels in bits 14:8. Its low byte is the generator's output levels: bits 0 to 6 are A14 to A20 (`VINT`, `SWP_RDY_LCK`, `END_OF_LINE`, `HIF_V_UPDATE_EN`, `XMP_CBLANK_N`, `END_OF_FIELD`, `REQUEST_SRC`, in the rules' signal order); bit 7 is clear on a timed entry exactly when the next entry is an event, which takes no time. Every line type used by every frame table (1136 line types across the 71 files) then sums to `TotalPixelsPerLine`, and every frame table's repeats sum to `TotalLinesPerFrame`. The B7 to B13 and C0 to C6 outputs are not in the low byte; the event entries are the place left, not decoded (**inferred**). This corrects the earlier reading that bits 0 to 6 were C0 to C6 ([display.md](../../../../devices/display/README.md#which-signal-a-line-table-low-byte-bit-drives-read-2026-11-10)).
- **`1920x1200_30f.vfo`, edge by edge.** Frame of 2592 lines (two fields of 1296: 6 sync, 60 back porch, 1200 active, 30 front porch). `VINT` (bit 0): high from line 1 to line 2, once; only the first field's second line type (line-table start 24) carries it, and the second field's opening types (404 and 428) carry neither it nor `SWP_RDY_LCK`. `SWP_RDY_LCK` (bit 1): high lines 0 to 3, once. `HIF_V_UPDATE_EN` (bit 3): low over lines 66 to 1265 and 1362 to 2561, the two active areas. `END_OF_FIELD` (bit 5): low at lines 0 and 1296, high at pixel 1800 of the next line, which is 1.75 lines in. `XMP_CBLANK_N` (bit 4): rises at pixel 426 and falls at 2346 of each active line, and `REQUEST_SRC` (bit 6) rises at 354 for 64 pixels in every 128, matching the rules' 26 and 98 pixel leads on the active start once the table's pixel 0 is taken as the rules' pixel 28 (the horizontal front porch; that offset is **inferred** from the fit). `END_OF_LINE` (bit 2) is a four-pixel pulse per active line; its edges were not compared with the rules one by one.
- **Initial state.** The first timed entry of all 71 files has bits 6:0 equal to 0x0a (`SWP_RDY_LCK` and `HIF_V_UPDATE_EN` high, the rest low), the rules' state at the frame start. `SignalInitialStateValue` words 14 to 20 are 1, 1, 1, 2, 1, 2, 1 in every file, matching the rules' initial states (`VINT` low, `SWP_RDY_LCK` low, `END_OF_LINE` low, `HIF_V_UPDATE_EN` high, `XMP_CBLANK_N` low, `END_OF_FIELD` high, `REQUEST_SRC` low), so the field's 1 is low and 2 high (**inferred** from that match).
- **All 71 files.** `VINT` is one pulse per frame from the start of line 1 to the start of line 2, whether the file has 1 field (26 files), 2 progressive fields (12 with `SwapsPerFrame` 1, 22 dual-channel `2@` files and 6 stereo files with 2), or interlaced fields (5 files). `END_OF_FIELD` rises once per field (once in the two full-screen-stereo files, as the rules' second branch says). `1920x1080_30i`: 1125 lines, `VINT` once, `END_OF_FIELD` twice, so 30 pulses a second against 60 field edges.

### 3b. Does any write route a generator output to the interrupt

- **established.** `odsyInitInterrupts` (`odsy_init.o`, IP30 listing `software/kernel/ip30/disasm/odsy_init/odsy_init.text.s` from line 2735 to `odsyDisableInterrupts`) was read in full. It stores only to the board words 0x34, 0x3c, 0x5c, 0x1034, 0x1044, 0x104c, 0x1054 and 0x105c, built from the five vector numbers and two target addresses `odsyInitIntr` fetched. It makes no store to the display window and reads no timing-structure word. The retrace vector goes to bits 23:16 of 0x1054 with the other sources' vectors; nothing says which board event sends it. A scan of every store with displacement 4164, 4172, 4180 or 4188 (0x1044 to 0x105c) in the IP30 `odsy_*.o` listings finds only `odsyInitInterrupts`, `odsyDisableInterrupts` and `odsyReset`; it follows constant displacements only.
- **established.** The retrace source has no bit in the flags register (0x1014) or its enable mask (0x1034): `odsyFlagInterrupt` is source 1 and the handler of source 3 reads no flags register (section 2). So no enable bit a driver sets is named for retrace; the three enable bits 18:16 of 0x1044 are not attributed to sources (`devices/buzz/README.md`, section 10).
- **established.** The only software link between the board and the generator is the timing load: structure words 28, 32 and 36 go to display addresses 0x2481 (control), 0x2482 (initial state) and 0x2483 (channel enable), the tables follow, and `odsyEnableVTG` (`odyssey.so`, ioctl 0x6f640020 with 1) starts the generator. In all 71 files `ODY_VTG_ChanEn` is 0x3fffff (bits 0 to 21, so channel 14 is on), `ODY_VTG_InitState` 0 and `ODY_VTG_Control` 0x1f0. That channel-enable bit n gates output n is **inferred**: `odsyBlankScreen` clears bits 0, 1 and 5 of the word to blank, the monitor sync pair and the DAC blank. Every format therefore enables `VINT`; no format-dependent choice routes it.
- **established.** No file under `usr/gfx`, `usr/sbin`, `usr/bin`, `usr/lib`, `usr/lib32`, `usr/diags`, `usr/stand`, `usr/cpu` or `usr/share` of the install contains the string `VINT` except the compiler rules (a recursive byte search; it finds the rules, so it can hit), and `odyssey.so`, `odyssey.a`, `rrm.o`, `gfx.o` and `kernel.o` carry neither `SWP_RDY_LCK` nor `END_OF_FIELD`. The OpenBSD VPro driver never touches interrupts ([buzz/README.md](../../../../devices/buzz/README.md), section 11). The IRIX 6.5.5 and 6.5.7 source trees hold only make-definition files named for the board, no driver. The published manuals (section 4) do not name the interrupt's source.

Taken together, 2c is **inferred**, not read. For: the rules name one output for a vertical interrupt; its compiled pulse is a single line at a fixed place near the frame start in every format; the VPro guide's per-full-frame counter (section 4) together with one counter step per interrupt (section 2) says the interrupt is per full frame, which `VINT` and `SWP_RDY_LCK` are and `END_OF_FIELD` (per field, 59.8 a second for `1920x1200_30f`) is not; and `SWP_RDY_LCK` is named for the swap-ready pin, not an interrupt. Against it, or open: the retrace source may come from a signal inside the display chip that is not one of the 21 compiled outputs, and nothing but the name ties `VINT` to source 3.

## 4. The published sources

Both were read in the Library by document number (`tools/library-pdf text`).

- 007-4271-001 (VPro porting guide), printed p.32, row "SGI video sync": the counter "is incremented upon the completion of the display of each full frame of video data", and for an interlaced monitor this is "typically the rate of displaying both the even and odd fields of a frame". **software expectation**, VPro-titled, per full frame. It matches section 2 (a counter per interrupt) plus section 3 (the interrupt per frame).
- 007-2392-003 (OpenGL on Silicon Graphics systems), printed p.288, "SGI_video_sync": "incremented upon each vertical retrace", and for an interlaced monitor "the synchronization is actually with the field rate instead". **software expectation**, platform-generic text. It does not address a progressive two-field format: counted per vertical retrace as the monitor sees it, `1920x1200_30f` would give 59.8 a second, counted per frame 29.9. The two manuals therefore disagree only if the interlaced sentences are carried over to formats like this one. Neither speaks of the interrupt itself.

## What is unknown, and what would settle it

- **Whether `VINT` drives source 3.** Routes tried, all negative for a routing write: the whole handler, `odsyInitIntr`, `odsyInitInterrupts`, the loader and the generator words, the compiler rules, all 71 compiled tables, strings in the X module and the kernel objects, the OpenBSD driver, the IRIX source trees, the manuals. What would settle it: a capture of the retrace interrupt count against the frame rate on a real board in a two-field format (30f: 29.9 a second if `VINT`, 59.8 if `END_OF_FIELD`; physical reads need the owner's approval, and none is assumed available), or a published datasheet of the display chip's interrupt logic (none held).
- **Where B7 to B13 and C0 to C6 sit in the line table.** Not in the timed entries' low byte (section 3a); the event entries are untested candidates.
- **Per-field activity in interlaced and stereo formats.** `VINT` is per frame there too (section 3a), so a per-field interrupt, if any, would come from `END_OF_FIELD` or another source; the handler's forced-swap repeat count of 2 (`odsyRetraceHandler`, the `sltiu ...,2` test) remains unread.
- **Who initialises the counter** (`gfxinit` per the manuals) and who reads `SwapsPerFrame`: no sender or reader found in the shipped binaries searched.
