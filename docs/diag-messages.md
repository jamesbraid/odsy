# Diagnostic and kernel-driver messages

The table [diag-messages.tsv](diag-messages.tsv) lists every call that prints, in four shipped
targets of IRIX 6.5.30m and its diagnostic installs, one row per call site:

- the compositor test program `usr/diags/compositor/bin/sting`;
- the field diagnostic `odydiags` (Internal Support Tools 2.7, 6.5.15), at
  `root/builds/odydiags-6.5.15/usr/diags/ody/odydiags`;
- the Odyssey kernel driver `odyssey.a` of the IP30 build (`usr/cpu/sysgen/IP30boot/`);
- the same driver of the IP35 build (`usr/cpu/sysgen/IP35boot/`), for Fuel, Tezro and Onyx 350.

The table is generated by `scripts/diag_messages.py`; rerun that script to regenerate it, do not
edit the table. The script imports its helpers from `retools/tools/`. Run it from the repository
root inside the toolchain container (`retools/tools/re-run`). The container does not follow a link
in `root/` that leaves it, so the `odydiags` path must be a real file inside `root/`; where it
does not resolve the script stops with a missing-file error and writes nothing. The `odydiags`
target dominates the run time, because the dataflow pass of `retools/tools/facts.py` takes
minutes on each of its 28 routines of 90 KB to 826 KB: a regeneration took about 70 minutes on one
core.

## Coverage

- **`sting`:** 271 call sites in 54 routines. 161 sites are in the 37 routines the symbol table
  names; 110 are in 17 static routines that only a direct call names (see Method).
- **`odydiags`:** 242 call sites in 66 routines: 125 in 52 named routines and 117 in 14 static
  routines found from direct calls. Of the 242, 126 print (`printf`, `fprintf`, `vfprintf` and
  `perror`), and 116 format into a buffer (`sprintf`, `vsprintf` and `snprintf`).
- **IP30 driver:** 389 call sites in 138 routines of 23 of the 29 members of `odyssey.a`: 381
  `cmn_err`, 6 `printf`, and 2 `sprintf`. The six members with no printing call are not listed.
- **IP35 driver:** 421 call sites in 147 routines of 24 of the 29 members: 413 `cmn_err`, 6
  `printf`, and 2 `sprintf`. The IP35 member `odsy_dvi.o` holds 31 of the printing sites. The IP30
  member of that name is a 1.2 KB object with no code section, so these messages have no IP30
  counterpart in this archive.
- **Not covered:** `kernel.o`, `gfx.o` and `rrm.o` next to the driver. They are shared graphics
  code, not Odyssey code.

## Columns

- `hardware`: `yes` when the printed message names board hardware (register, DMA, interrupt,
  PLL, DAC, I2C, DDC and similar, matched as whole words in the message). `hw_words` lists the
  words. Hardware rows sort first.
- `output`: `printed` for a call that writes text out; `buffer` for a call that formats into
  memory, which prints only if the buffer is printed later (not followed here).
- `severity`: for `cmn_err`, the level from `a0` with its CE_ name: 4 is `CE_WARN`, 1 `CE_ALERT`, 5 `CE_NOTE`, 7 `CE_DEBUG`, 0
  `CE_PANIC`. Flag bits (0x8, 0x10, 0x20 and so on) are masked off and not shown. For `fprintf`,
  the stream when it is a named symbol (`stderr` or `stdout`); `stream not named` when the stream
  is a pointer taken from a structure or an argument.
- `message`: the C string the call passes, with `\n` shown as the two characters. `(not resolved)`
  when the format argument does not trace to a constant in the routine.
- `condition`: what the call's routine has to do before the call runs. A call is gated by a
  conditional branch when it can be reached only through one arm of that branch. The text gives the
  register test that holds on the path, and the branch that makes it. When the branches join before
  the call, no single branch decides it: the text says so, and says whether every return path runs
  the call.
- `grade`: `established` when the format and the severity were read from the instructions and
  the gating comes from a complete flow graph of the routine. `inferred` when the format or the
  stream did not trace, when the routine has an indirect jump the flow graph does not follow, when
  the routine has no symbol (see Method), or when the string is empty in the file.

## Method

The generator takes every routine of the target from the fact sheet
(`retools/tools/facts.py`), finds the calls that name a printing routine, and then:

0. Names the routines the symbol tables leave out. A stripped build keeps only its exported
   routines, so each other target of a direct call in `.text` becomes a routine named `sub_` and
   its address, and ends where the next routine starts, or at the end of `.text`. In a relocatable
   kernel object a direct call to another routine is a relocation, so this adds nothing there. The end of such a routine
   is an estimate, so every row in one is graded `inferred`.

1. Resolves the format argument by walking the instructions back from the call, through the
   delay slot (which runs before the callee). A register set in more than one place is resolved
   only when every incoming path gives the same value. Relocated addresses in the kernel objects
   come from the relocation records: a `gp`-relative load of a `.srdata` slot gives the `.rodata`
   address the slot holds, and the offset in the instruction is taken from the object's `gp`
   base. Linked addresses come from the file image.
2. Reads the C string at that address.
3. Builds the basic blocks of the routine, the edges between them and their dominators. A
   conditional branch gates the call when the call's block is unreachable from the entry once the
   edge along one arm is removed, so the call needs the other arm. A jump register's delay slot
   is treated as the branch's arm. A jump that lands on a branch's delay slot runs that instruction
   and then the next one, not either arm of the branch, so the landing is a copy of the slot's block
   that only falls through.

The fact sheet's argument values are not used for the format. For a relocatable object they drop
the immediate that a delay slot adds to a relocated address, so a format such as `.rodata+128`
reads as `.rodata`. The generator resolves the delay slot itself. That defect is in
`retools/tools/facts.py` and is not fixed here.

## Hardware-facing messages

199 rows name board hardware: 7 in `sting`, 2 in `odydiags`, 86 in the IP30 driver and 104 in the
IP35 driver. Most of the kernel rows come from four groups.

- **Display and clock programming** in `odsy_brdmgr.o`: `odsy_LoadDCD2Regs` (the DCD2 output
  control, horizontal timing, RAMDAC and TMDS control writes, each on a failed write),
  `odsyLoadTimingTable` (the PLL and AMI PLL register writes, the "Reg 0x1" to "Reg 0x5"
  writes), and `odsy_reconfigDCD2FPLD` (reset of register 1 and register 2). Both builds carry
  these.
- **DVI transmitter and FPGA** in the IP35 `odsy_dvi.o` only: 18 of that member's 31 printing
  sites name hardware. They report read and write failures of the transmitter registers, the
  FPGA register and sequence failures, and the CRC and L1-expander messages of `odsy_loadDVIFPGA`.
- **DMA completion checks** in `odsy_dma.o`: `odsyDMAWait` compares the completed operation
  number with the requested one and with the read pointer, and reports outstanding sync DMAs.
  The timeout handlers `odsy_dmawait_timeout` and `odsy_dmawait_harmless_timeout` print an
  alert and a debug line.
- **I2C and DDC** in `odsy_ddc.o` and `odsy_compositor.o`: the reset op-code failure and the
  I2C passthrough enable message.

Each is a single row with its routine, call address and gate in the table.

## What the table does not show

- **Unresolved formats.** 78 rows have `(not resolved)`, graded `inferred`. 34 are `vsprintf` and
  `snprintf` calls in the `dl_output_*` helpers of `sting` and `odydiags`, which format a string
  their caller passes; the literal formats that callers pass are not joined to these rows. 35 are
  `cmn_err` rows in the driver: 14 per build in `odsyRestoreVB`, where the search could not trace
  the format across the routine's joins, and one each in `odsy_hpipe_discover`,
  `gf_OdsyInitialize` and `odsy_ProbeRainier` of both builds, and in `restoreRect` of the IP35
  build. Those were not traced further. The other nine are scattered over static and named
  routines of the two diagnostics.
- **Stream names.** 78 rows have `stream not named`: 50 in `odydiags` (49 `fprintf`, 1
  `vfprintf`) and 28 in `sting` (26 `fprintf`, 2 `fputs`). The stream is a `FILE` pointer that a
  structure or an argument supplies.
- **Flow the table does not follow.** 21 rows sit in routines that have an indirect jump:
  `odsyGatherInfo` (3 rows in each driver build), and in `odydiags` `sdram_xlateToBoardID`,
  `sub_1060e134` and `sub_10537ca0`. Each carries a note, and its condition may be understated. Sixteen `odydiags`
  rows, in `sub_1060e134` and `sub_10537ca0`, sit in code that the followed branches do not reach
  at all; the condition column says so, and does not call it dead code.
- **Static routines called only indirectly.** A routine with no symbol that is reached only
  through a register-held address is not in the table.
- **Routine ends.** The end of an unnamed routine is the next routine start found by a direct
  call. A routine whose code is split by a jump to another routine can be cut short, so its rows
  stay `inferred`.
- **Dead code.** No row is dead code: every call in the table is reached from the routine's entry,
  or has the note above. A call that no branch reaches, in a routine with no indirect jump, is
  marked `dead code` in the condition column.
