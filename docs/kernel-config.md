# Kernel configuration files for the VPro driver

Three small text files under `var/sysgen/` tell the kernel configuration tool how to build the driver in or out. Release IRIX 6.5.30m; every entry is **established** from the whole file, plus the object code named where a tunable's reader was looked for.

- `var/sysgen/master.d/odyssey`: **established.**
  The 127-byte master entry that declares the driver to the configuration tool. Its single line has the flags `sc`, the routine prefix `odsy_`, no soft device number, no device count and the dependencies `gfx,gfxs`, so selecting this driver pulls in the generic graphics object and the graphics support archive. The prefix is why the driver's entry points all begin `odsy_`, such as `odsy_earlyinit` and `odsy_init`.
- `var/sysgen/master.d/odysseystubs`: **established.**
  The 130-byte master entry of the stub object, which is **inferred** to stand in when the driver is not selected (the stub carries the same entry names as the driver). Its one line has the flag `oxu` and no prefix, soft number, device count or dependency, so it belongs to the kernel as a plain object. The object it names, `odysseystubs.a(odysseystubs.o)` in `IP30boot`, holds `odsy_earlyinit` as an eight-byte routine (`jr ra` and a delay slot that zeroes the result at offset 4) and three words in `.sdata`, 1, 100 and 1 (bytes 00000001 00000064 00000001), named `odyssey_dwsupport`, `odyssey_dwcredits` and `odyssey_sw_sync_cacheline_multiplicity`, so a kernel without the driver would still link and `odsy_earlyinit` would return 0 (**inferred**).
- `var/sysgen/mtune/odyssey`: **established.**
  The 1357-byte tunables file. After the licence banner it declares `gfx_odyssey: static` (the driver's graphics-parameter group cannot be changed at run time) and three parameters, each as default, minimum and maximum: `odyssey_dwsupport` 1, 0, 1 (the file's comment says it switches whether the board returns double-word write responses), `odyssey_dwcredits` 100, 84, 256 (graphics flow-control credits counted in double words) and `odyssey_sw_sync_cacheline_multiplicity` 1, 0, 1 (whether software-sync tokens may share a cache line). The defaults equal the three words of the stub object.
  Readers in the 6.5.30m objects: only the IP35 `odsy_init.o` names a tunable at all. In `gf_OdsyInitialize` (starts at 0x15dc) the load of `odyssey_dwsupport` is at 0x1760: a nonzero value stores 0x800000 and zero stores 0x1800000 into the board record word at -31292 (reached by `sw` at 0x1770 and 0x18e4), which then has an interrupt-target field, a credit transaction number and 0xc8 or-ed in and is written to board offset 0x1074. The load of `odyssey_dwcredits` is at 0x185c; it is multiplied by 8 (the `dsll` at 0x186c) and passed to `gfx_flow_alloc` (called at 0x1878) unless `get_chimera_type` (called at 0x183c) returns 5.
  No IP30 object, no `gfxs.a` member and none of `kernel.o`, `gfx.o` or `rrm.o` in either `IP30boot` or `IP35boot` has a reference to any of the three names, and none has one to `odyssey_sw_sync_cacheline_multiplicity`. The IP30 build therefore ignores all three, and the third tunable has no reader in these objects.
