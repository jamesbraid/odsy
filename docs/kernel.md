# Kernel driver notes

Companion to `odsy_kernel/include/odsy_kern.h`. Labels: **established** (read from a binary, with where), **inferred** (reasoned, with the reasoning), **unknown**. IRIX 6.5.30m, IP30 objects (`odsy_init.o` unless named). IP35 was not diffed for anything here: **unknown**.

## Attach and probe

- **established.** `odsy_init` registers the driver with `xwidget_driver_register(0xc013, 35, "odsy", 0)`. **inferred** that 0xc013 and 35 are the crossbar-widget part and manufacturer numbers the board answers to (the call's argument order is not read from a header; the values are what the code passes).
- **established.** `odsy_attach` maps the board with `xtalk_piotrans_addr(dev, 0, 0, 0x401000, 0)` and stores the result as the PIO base (record +824): the board's register window is 0x401000 bytes. It stores the widget id (`xwidget_info_id_get`) at record byte 793 and the master id (`xwidget_info_masterid_get`) at byte 792, reads the word at board +4 and, when its bits 31:28 are 2 or more, registers the board's NIC reader and reads the NIC (serial-number part) with `odsy_set_gfx_mfg_nic_name`; a NULL NIC logs an error. (An earlier version of this line had the test reversed; both builds skip the NIC when the type is below 2: `sltiu` against 2, then a branch past the call. See Pass 14.)
- **established.** `odsyFindBoardAddr` (the early path) obtains the same base with `xtalk_early_piotrans_addr(0xc013, 35, <board>, 0, 0x401000)`, reads the word at widget +0x24 (`lw 36(base)`), and keeps its low nibble in record byte 793.
- **established.** `odsy_earlyinit` (before attach, for the textport) checks the `kopt` string for the console graphics setting (first byte 'd' or 'D'), calls `odsyFindBoardAddr(0)` and `odsyReset(0)`, then registers the textport with `htp_register_board(base, width, height, ...)`; a second `odsy_earlyinit` before the first finished logs "re-entered" and waits.

## odsyReset order of operations

**established** from `odsyReset`, `odsyLowLevelReset`, `odsyLLPReset`, `odsyGatherInfo` (IP30). Offsets are board PIO offsets unless a "widget" word is named. All board registers in the 0x1000 and 0x4000 groups sit at 8-byte spacing with data in the odd word (offsets end in 4 or c); `sync` follows every store.

1. Stop the FIFO timer (`odsyFifoTimer`), mark the record "in reset" (record +816 = 1, +794 = 0), clear the record's name, set the default screen size 1280 x 1024 (record +232, +234) and the default refresh (record +236 = 588 is a record word the code initialises; its use is unknown).
2. `odsyLowLevelReset`: reset the link to the board. If the host's own chip id register (the global at gp-30696) reports a certain revision class (top nibble > 4, host-side, unnamed) it writes board 0x100c = 0x200 and waits 1 s (`odsy_usdelay(1000000)`), clearing only the driver's shadow word and not the register; otherwise writes 0x100c = 0x16d, waits 200000 us, clears it and calls `odsyLLPReset`, which resets the widget through `xwidget_reset` or, when there is none, writes 0 to a host-chip word at 308 + (widget id << 6) after saving word 268, waits 10 ms and restores 268. **inferred** that 0x100c is a board reset control with the high-numbered form for newer hosts; no bit names are known. It also toggles mask bits in the host chip's per-widget words (offsets 268, 276, 316 of the 64-byte-stride widget array) around the reset and restores them afterwards, retrying up to three times (`cmn_err` "retry") when the widget does not come back; their meaning belongs to the host chip, not the board: **unknown**.
3. Write widget +0x24 = (widget id) | 0x4200 and wait 100 ms (`odsy_usdelay(100000)`). Write board 0x1004 = (master id & 0xf) << 19.
4. `odsyGatherInfo(board, 0)` then `odsyMMinit`, `odsyInitDBE` (the I2C ports `odsyInitDBE` names "main" and "opt"), then `odsyGatherInfo(board, 1)`: see `docs/board.md` for what they read.
5. Zero the interrupt and DMA-engine registers, in this order (offsets): 0x103c = 0xffffffff, 0x101c = 0xffffffff, then 0x0 to 0x1044, 0x104c, 0x1054, 0x105c, 0x1074, 0x107c, 0x108c, 0x109c, 0x10a4, 0x10ac, 0x401c, 0x4024, 0x402c, 0x4034, 0x403c; then 0x4044 and 0x4014 are written with a master-id field (bits 7:4 of 0x4044, bits 23:20 of 0x4014) and fixed bits (0x4044 also gets bits 16, 15:14 and 3:2; 0x4014 gets 0x12, bit 18 and bit 24); then 0x404c, 0x4054, 0x405c = 0; 0x10bc = 0, 0x10cc = 0xffffffff.
6. Write the memory-configuration word 0x1004 from the probed bank, CAS-latency and size values and pulse it (`docs/board.md`).
7. Zero 0x34, 0x1044, set 0x103c to 0xffffffff, zero 0x1074, pulse 0x1084 (0, 1, 0, the command FIFO reset in `BUZZ.h`), write 0x101c = 0xffffffff, zero 0x5c, invalidate the hpipe state (`odsy_hpipe_invalidate`), and clear the "in reset" flag. `odsyInitCfifo`, `odsyInitInterrupts` and the DMA set-up follow in `gf_OdsyInitialize`/`gf_OdsyStart` (not read in this pass).

- **inferred.** 0x4004 to 0x405c is a bank of per-engine address and control registers (the context save target 0x4004/0x400c is its first pair); the zeroing in step 5 returns every engine to idle. Their roles, and the fields of 0x4014 and 0x4044, are inferred in `docs/buzz.md` section 10 (pass 12, from the 6.5.30 store values): performance-statistics region, software-sync region and mode, glGet write-back offset, diagnostic region and mode.
- Pass 12 (`docs/buzz.md` section 10): 0x4014 and 0x4044 are decoded, and 0x100c is **inferred** to be the abort register with six abort bits. **unknown** (`docs/open-questions.md`): which abort each 0x100c bit is, the 0x200 form, and widget word +0x24's 0x4200 pattern. On a board it would show in: a trace of the board's reset state (the host-visible status after each write in step 2 and 3), or the crossbar-widget chip documentation for the +0x24 control word. `odsyInitDBE` is read in full in the next section.

## odsyInitDBE (`odsy_init.o`, IP30)

**established** from the disassembly, with the 64-bit constants read from the object's `.lit8` section (the `$gp` loads carry a section-relative displacement: displacement + 30720 is the offset in `.lit8`). The function is about 1150 lines, but nearly all of it is one inlined helper repeated twelve times (below). The signature is `odsyInitDBE(board, timing, quick)`. `odsyReset` calls it with `quick` = 1 and the first built-in timing (step 4 above); the textport start-up and the diagnostic path (`odsy_tport.o`, `odsy_diag.o`) call it with `quick` = 0, choosing either built-in timing. Display FIFO words are the 64-bit stores to board +0x400000 (`DISPLAY.h` and `PBJ.h` give the word format: `0x30000001 | (display address << 14)` in the upper half, the data in the lower half). "Level N" means `odsy_poll_dfifo_level(board, N)` waits until the display FIFO holds N or fewer entries; any timeout abandons the function and returns nonzero.

The inlined helper, **established** as code: unless the record's "initialising" word (-19352) is set, each FIFO write section is bracketed by the display-FIFO semaphore (record +0x8530, `psema`/`vsema`) and a spin lock (record +0x8540); on release the helper flushes the queued pending doubleword (record -31416) and the cursor control word's mirror (0x2581) with the same toggle pattern that `docs/display.md` (cursor section) describes for `odsyGatherInfo` and the genlock handler. Nothing in it writes any other board register. When "initialising" is set (during `gf_OdsyInitialize`) none of it runs.

1. **Quiet the clock register.** Wait for level 10. Write display address 0x2b00 = 0 five times and 0x2700 = 0x0006d3e0 (`PBJ.h` section 6). Wait for level 0.
2. **Read two output-enable words.** Read display addresses 0x2483 and 0x2482 through the read window into record -19496 and -19492 (the shadows `odsyBlankScreen` edits).
3. **I2C ports.** Initialise the "main" port (record +0xb3e0, port 0) and the "opt" port (record +0xb408, port 1) with `odsy_i2c_init_port_handle`. A failure logs "cannot initialize main i2c port" or "opt" through `cmn_err` and returns.
4. **Identify the option card.** Wait for level 15, read 0x2701. If bit 10 is set, skip the probe (`PBJ.h` section 3, bit 10 "no option"). Otherwise, the first time only (record +296 is set to 1): select I2C address 0x1f (stored in record -19416), read register 0 of the opt port; when its low nibble is 3 store 3 in record +298 and read register 7 into record +300. **inferred** (`PBJ.h`): 3 means a dual-channel display option.
5. **Probe the attached parts**, results in record words +700 (compositor), +704 (Denali), +708 (Rainier), +712 (compositor NIC): without the option, `odsy_i2cProbe2b` on the main port fills record +308 when it is zero and +292 is positive; `odsy_ProbeCompositor` reads a compositor register (arguments 171 and 87) and folds its answer into record +700 (bit 0 set, other bits from the register), `odsy_ProbeRainier` finds `rcx` devices through the device graph (not I2C) and writes rcx register 720 = 66 when it finds one, and `odsy_ProbeDenali` probes channel 0 (and channel 1 when the option is present). With the option (+298 = 3): `odsy_DCDResetDone` is polled first, then the opt port's PLL register 0 is written 16, then 32 when record +438 is nonzero and 48 when record +568 is nonzero (the two "DCD" slot flags: what sets them is not read here), then Denali, compositor and Rainier are probed. If a compositor is found with type nibble (bits 31:28 of +700) not 1, `odsy_ReadCompositorNic` reads its serial number into +712. The routines' internals belong to `odsy_compositor.o`, `odsy_rainier.o`, `odsy_denali.o`, `odsy_i2c.o`; the parts' register meanings: **unknown** (`docs/open-questions.md`) of a boot with each part present.
6. **Frame buffer.** `odsyConfigFb` with a 20-byte request on the stack: width 1280, height 1024, depth 8, two zero words (`PBJ.h` section 6 gives its writes). Wait for level 14.
7. **Scanout size.** With `quick` = 0: write display addresses 0x2802 = 1280 and 0x2803 = 1024, then call `odsyLoadTimingTable(board, timing)` (`docs/display.md`). With `quick` = 1: write 0x2802 = 0 and 0x2803 = 0 and leave the timing to a later call. `PBJ.h` section 6 is updated to match.
8. **Mode table.** Write 32 words to 0x2900 to 0x291f, waiting for level 0 before the first and the seventeenth, each with the same data `((X & 0xfe001fff) | 0x004b5e00) & 0xfffffe00`, then 8 words to 0x2920 to 0x2927 with data `Y & 0xffffff00`. X and Y are two stack words the function never stores to (read at stack offsets 64 and 68): **established** as code, so the visible bits are 0x004b5e00 with the low 9 bits clear and 0 in the low byte, and the rest is whatever the stack held (**unknown**; an open question (`docs/open-questions.md`), see below). Wait for level 11, then write 0x2929, 0x292a, 0x292b and 0x292c = 0 (the four mode entries 0x29 to 0x2c).
9. **Finish.** Clear the cursor control mirror (record -19664) and write 0x2581 = 0 with the helper's preamble; initialise a semaphore at record +0xb470 to 1; call `odsyBlankScreen(board, 0)`; release the semaphore (record +0x8530) when it was taken.

- **unknown** (`docs/open-questions.md`). What the 0x2b00 writes do, the meaning of the bits of 0x2700 beyond those in `PBJ.h`, and the mode-table words' values (the stack words above). On a board it would show in: a read-back of display addresses 0x2900 to 0x292c, 0x2b00 and 0x2700 after `odsyInitDBE` on a board, through the read window at board +0x220000 + 8a + 4 (read-only).

## odsyLowLevelReset on IP35

**established** by reading the IP35 object beside the IP30 one (`odsy_kernel_ip35/disasm/odsy_init/`). Same board store, different host handling:

- IP35 has only the 0x100c = 0x200 form: store, `odsy_usdelay(1000000)`, then a zero store to the driver's shadow word (record offset 34216), not to the register. The IP30 branches on the host chip id (0x200 path versus 0x16d path) and the 0x16d path with its `us_delay(200000)`, the six-bit sequence of `ori` stores (0x100, 0x40, 0x20, 0x8, 0x4, 0x1 accumulated on one word, written to the record's shadow and to 0x100c) and the `odsyLLPReset` call do not exist on IP35. IP35 never calls `odsyLLPReset`.
- Both versions clear the same per-widget host-chip mask bits (widget word +0x24 loses bits 5, 2 and 1; word +268 loses bits 1, 3, 4, 5, 6, 7, 8, 16, 17 and 31; the identical immediates appear in both objects; the code also tests bit 31 of +276 and bit 5 of +316), try the reset up to four times (retry counter in steps of 2, stop at 7, `cmn_err` between attempts), restore widget word +0x24 and +268, and end with `odsy_usdelay(100000)`.
- IP35 locates the host-chip widget array from the board's own PIO address (the node field, bits 40:34 of record +824) instead of from the global used on IP30; a host chip's type nibble (bits 31:28 of the word at +4) is compared with 0xd100 in the upper bits, a host-side check **inferred** to separate two host-chip variants. The bits' names belong to the host chip: **unknown**, needs the host chip's documentation.

## Initialise and start (`gf_OdsyInitialize`, `gf_OdsyStart`, `odsyInitDMA`)

**established** (`odsy_init.o`, IP30). Offsets are board record bytes unless "board +" is named; the record word at "-31292" is the record base plus 0x10000 minus 31292.

`gf_OdsyInitialize`:

1. Clears a word at -19352 ("initialising"), and when render nodes are still open (record +28480 nonzero) logs "rnodes still open" and retries up to 11 times, sleeping 500 ticks each time; failure returns -1.
2. Takes the board semaphore (+56) as owner (+72), waits for the busy word (+104) to clear, increments the busy count (+80), unregisters the early textport (`htp_register_board` with zero arguments, **inferred** from the null arguments: the early console driver gives way to this one).
3. When bits 1:0 of the graphics-context word at gfx+4 are set it clears them under `splhi`, and if the flow-control object (+808) is attached detaches it, marking -31288 = 1 and writing 1 to board +0x107c (the flow-off register, `BUZZ.h`). It then frees the flow object.
4. Up to six attempts of: `odsyReset` (above), `gfx_flow_alloc` with the constants 2048 and 10000 (their meaning: **unknown**, the flow object is host-kernel code), wait until bits 15:7 of board +0x106c (the FIFO level) read zero (5 microsecond polls), pulse board +0x1084 as 0, 1, 0, build the flow configuration word `(interrupt target << 17) | 0x800000 | (credit transaction number << 12) | 0xc8` (target from `xtalk_intr_target_get`, number from `gfx_flow_credit_tnum_get`), keep it at -31292 and store it to board +0x1074, then `odsyInitCfifo(board, 1)`. A nonzero result frees the flow object, waits 10 ms and retries; six failures return -1.
5. After success: allocates two 32 KB slots from the board's slot mask (+29952), the second becoming the host-visible sync page (index at -19380, address at -19376, first halfword zeroed), then `odsyInitMM`, `odsyInitDMA`, `odsyInitRetrace`, `odsyInitInterrupts`; sets bit 1 of gfx+4, attaches the flow object and rewrites the flow configuration word with the attached credit number into 0x1074 (clearing -31288 and writing 0 to 0x107c); calls `odsyZeroOut`; clears bit 1; drops the busy count.

`gf_OdsyStart` zeroes the record's mode words (+8, +16, +104, +120, +84, +816), sets +794 = 1 and +820 = 127, calls `odsyInitDrawables`, converts the host buffer at +880 (a zeroed 128 KB host buffer allocated by `odsyInitHwWrRgn` and cut into 16 KB pieces recorded at +29880 and +29888; its allocation error calls it the "sw sync wr/hw shadow cache") with `kvtophys`, keeps the halves at -31248 (upper 16 bits) and -31244 (lower 32), and stores them to board +0x4034 and +0x403c. **inferred** by pairing with the context-save target (+0x4004/+0x400c, `docs/buzz.md` section 4) that these are the high and low halves of the shadow region's physical address; the register names and what the board writes there: **unknown** (`docs/open-questions.md`) (a trace of host-memory writes into the region after a draw).

`odsyInitDMA` sets up the DMA mutex (+5800) and sync variable (+5816), zeroes four words at the board's hw-write record (+888), allocates a 32 KB slot whose host address becomes the tag page (+5824, index +5840, first halfword 0xffff, which is also the initial tag at +5836) and a second slot (+6896, index +6904, first halfword 0xffff), and zeroes the counters (+6880/+6888 retired/issued, +5844/+5848 tag and retire indices, +28448 interrupt list head). **established.**

## IP35 differences in `odsyReset`

**established** by comparing store offsets and calls of `odsyReset` in `odsy_kernel_ip35/` against IP30: every board register store (the list in step 5 and the 0x1004 sequence) is identical in value and order, `odsyGatherInfo` stores the same record offsets, and the reset order is the same. IP35 adds host-hub calls: before the first board access `xwidget_info_get`, `xwidget_info_master_get`, `master_node_get` then `hub_widget_flags_set(node, widget, 1)`; after the register zeroing a `hub_widget_flags_set(..., 2, 16384, chimera type)` call; and `hub_set_piomode(..., 2)` at the end and in the retry path. **inferred** that these set host-hub widget flags and the PIO ordering mode for the board's widget (the names are the host kernel's; their register effects belong to the host chip and are **unknown**). `odsyLowLevelReset` is compared in the section below; IP35 never calls `odsyLLPReset`.

## Host DMA: regions, diagnostic transfers, op ring, wait and finish

Release IRIX 6.5.30m, IP30 `odsy_dma.o` and `odsy_init.o` (disassembly in `odsy_kernel/disasm/`; message strings from `readelf -p .rodata`). Offsets are bytes into the record named. IP35 was not diffed: **unknown**.

### DMA region record (`odsy_NewDmaRegion`, 88 bytes)

**established** from `odsy_NewDmaRegion`, `odsy_DeleteDmaRegion`, `odsy_DmaRegion_Pin/UnPin`, `odsy_DmaRegion_BuildXlatTbl`. The record is zero-allocated; the debug build poisons freed bytes (0x81, 0x83, 0x85, 0x87 on the table and record), which is why the loops walk it byte by byte.

| Offset | Field |
|---|---|
| +0 | pointer to the page list (`generatePageTable` output, `BUZZ.h` pass 3) |
| +8 | page list size in bytes: `((len + 16383) >> 14) * 8 + 40` |
| +16, +24 | the first two creation arguments (opaque to this module; stored, never read here: **unknown** use) |
| +32 | user virtual address of the buffer |
| +40 | length in bytes |
| +48 | creation flag (nonzero: pin at creation) |
| +52 | pinned flag (1 after `useracc(addr, len, 272)` succeeded and the page list was built) |
| +56 to +87 | 32-byte header copied from the caller; copied again to the start of the page list (its contents: **unknown**, the diagnostic ioctl hands it through from user space) |

`odsy_DmaRegion_Pin` repeats the `useracc` and rebuild when the pinned flag is clear; `UnPin` calls `unuseracc`, frees the list and clears +0, +8, +52. Error returns from `odsy_NewDmaRegion` are 12 (out of memory) or the `useracc` / page list error; `generatePageTable` also has a "too many scanlines in dma parameter block" error, whose limit test was not located: **unknown**.

### Diagnostic transfer (`gfP_OdsyDIAGdma`)

**established.** Reads a 48-byte argument block from user space with `copyin` (failure: "bad ptr to dma arg", error 14): +0 user address (8 bytes), +8 length (4 bytes), +12 to +43 the 32-byte region header, +44 the flags word whose bit 2 selects id 0xe03 over 0xe01 in `odsy_DmaRegion_DoTransfer`. The steps: take the board semaphore (record +56, owner at +72), wait with 2 microsecond delays while the word at +104 is nonzero, bump the busy count at +80, build a region, clear bit 11 (DMA_DONE) of the flags register 0x1014 with a read-modify-write (not the clear register 0x101c), kick through `odsy_DmaRegion_DoTransfer`, then poll up to 40 times, 25 ticks apart (`DmaFinishedPollDelay` = `timeout` plus a semaphore), for flags bit 11. On exhaustion it logs "diag dma timeout" and calls `odsy_teardown`. Afterwards it deletes the region and drops the busy count.
The caller is the field diagnostic `odydiags` (IRIX 6.5.15 build, `usr/diags/ody/odydiags`, an N32 executable, which `root/` holds). Its routine `diag_do_dma` (0x1053d000, 176 bytes) runs `diag_validate_config` (0x1053cc10), then calls `ioctl(descriptor of board diag_current_board, 0x6f64002e, argument)` (the call goes through local GOT slot 187, which is dynamic symbol 289, `ioctl`); a nonzero result is reported through `dl_output_error` with code 26 and returned. Everything below was read in `diagdma` (0x1052f440, 2248 bytes) and its three `diag_do_dma` calls (0x1052f944, 0x1052f9d0 and 0x1052fc70). **established**, from the code and the tool's own strings:
- The tool's DMA test is a host-to-board-memory write, a read-back and a compare. Its parameter file names the direction `HOST_TO_SDRAM`, `SDRAM_TO_HOST` or `HOST_TO_SDRAM_TO_HOST` ("sdram" is the tool's name for the board's memory), the pattern sent to board memory (`dma_pat`), the origin, a swap and an expansion flag, the image size, an output-format code (`the I/O output Odyssey driver requests*`, 57 distinct names in the help text, such as RGBA8 to RGB565), a storage size per pixel of 1, 2, 4, 6, 8, 16 or 32 bytes (`the I/O input Odyssey driver requests*`) and the host data type and pixel format. With no file it defaults to `HOST_TO_SDRAM_TO_HOST`, RGBA8 to RGBA8, 4 bytes a pixel, unsigned bytes in RGBA order. Its failure messages say "dma from host to sdram failed", "dma from sdram to host failed" and "dma comparison failure". So the data path is an ordinary image transfer through the board's pixel path, not an engine loop-back: the write sends a host buffer, the read returns what the board stored, and the host compares.
- `diagdma` builds one 48-byte argument for each direction on its stack. The first (sp+64) is the write: it is sent when bit 0 of the request's word at +56 is set. The second (sp+112) is the read-back, sent when bit 1 of that word is set. Before the read-back the tool calls a helper with its comparison buffer, the word 0xbaaddada and a length of 0x800000, which reads as a fill of the receive buffer (**inferred** from the arguments; a read that transfers nothing would then fail the compare). The compare, `dc_compare_images`, runs when the request's word at +52 is nonzero (the parameter file's `do_compare`, default 1).
- The kernel's flags word (argument +44) is 3 in the write and 2 in the read-back, with bit 2 (value 4) added to both when the tool's global `asyncdma` is nonzero (the code at 0x1052f4c0 to 0x1052f4f4 and 0x1052f760 to 0x1052f7c8); `asyncdma` is the option whose help text is "Do an asynchronous DMA". So **the kick id 0xe03 is the one the tool selects for its asynchronous-DMA option, and 0xe01 for the default synchronous one**. Bit 0 is set only on the write and bit 1 on both transfers; the kernel reads neither (it tests bit 2 only), so their board-side meaning is **unknown**. That 0xe03 is what makes the transfer asynchronous on the board is **inferred**, from the option's name and help text alone: the kernel waits for the same done flag after either kick.
- When the tool's `do_corrupt_data_bus` option is set and `read_only` is clear, a third transfer is sent between the write and the read-back (0x1052fc70), with bit 6 (0x40) ORed into the header word at stack offset 88. Its purpose (a deliberate bad-data test for a data-bus fault) is **inferred** from the option's name.
`sting`, the compositor tool, forms one ioctl command constant with the 0x6f64 prefix (0x6f640025, in `ody_comp_reg_access`), so it has no caller for this path. **unknown:** what the board does differently for 0xe03, and what bits 0 and 1 of the flags word select.

### Op ring and sequence numbers (`odsyDMAOp`, `odsyDMADone`)

**established.** Per-board fields: `+28440` an 8-bit op-slot counter into 256 op records of 80 bytes starting at +7960; `+6888` issued count and `+6880` retired count (64-bit, wrap at 2^61, compared as modular differences); `+5844` the 7-bit tag counter; `+5848` the retire index; `+5856` the 128-entry ring of op pointers. Per `odsyDMAOp`: take the next op record (zeroed with `bzero`), set +8 = 1 (pending; bit 1 is added when the op is queued on the interrupt completion list at record +28448, and `odsyDMAWakeup` / `odsyDMAIrptWakeup` clear it; where bit 0 is cleared was not located), optionally create a per-op sync variable at +32 (9th argument bit 1), record the owner context at +40, and for an owner with a lock request allocate a context-set id (+48, -1 when none) and keep the user range (+56 address, +64 length). The page list goes to +16 with its size at +24. Space check: if issued minus retired plus 2 does not fit in 128 minus the entry count the routine drops the mutex, calls `odsyDMAWait(board, 0, 0, 0)` to drain and retries. The op's number (+72) is the issued count before the increment; the tag sent with block 0x5a is `0x5a00 | (old +5844 & 0xff)`. The flags clear register 0x101c gets 0x800 once per op before the kick (`BUZZ.h`).
After issue the owner context stores the op number at +256 or +248 depending on a flag word `odsyDMAOp` zeroes on entry: nonzero would select id 0xe03 and slot +256. **established:** no store in `odsy_dma.o` sets that flag nonzero (it is cleared at entry and only read later), so every op the driver issues itself uses id 0xe01 and slot +248; only the diagnostic path reaches 0xe03. **established:** the kick id does not carry the transfer direction. Reads and writes both reach `odsyDMAOp` through `gfP_OdsyMMxfr` and `odsyDMAOps` with the flag clear, so both go out as 0xe01; the direction travels in header word 7 instead (the `MMxfr` section below). 0xe03 is used only by the diagnostic ioctl when its caller sets flag bit 2. What 0xe03 asks of the board: **unknown** (`docs/open-questions.md`) (the diagnostic transfer of a known buffer with flag bit 2 set and clear, and the board memory it touched).
`odsyDMADone(op)` frees the page list (poison 0x91), clears +16 and +24; with no owner (+40 = 0) it broadcasts and destroys the sync variable, with an owner and a held range (+64 nonzero) it only broadcasts, with an owner and no range it does nothing.

### `odsyDMAWait`, `odsyDMAFinish`, `gfP_OdsyMMwaitXfr`

**established.** `odsyDMAWait(board, ctx, mode, &opnr)`: returns 9 while the board is torn down (+816 nonzero). Mode 0 waits for any ring progress: it arms a 1500-tick `timeout` (`odsy_dmawait_harmless_timeout`, which logs at severity 7 and broadcasts the retire sync variable at +5816; the 3 stored beside the arm is the wait kind, not a tick count, read from the IP35 object where `li a2,1500` sits in the delay slot shared by both modes) and sleeps interruptibly on it; interrupted returns 22. Mode 1 waits for op number *opnr (-1 = none, returns 0): if the number lies outside [retired, issued] it is already done; else it must lie within 128 of the retired count and match the ring entry's +72 ("too many outstanding sync dmas", "low sync opnr != readp opnr", "dma op nr != requested op nr", return 22), then it arms a 1500-tick fatal `timeout` (`odsy_dmawait_timeout`, which prints the issued and retired counts, the last sync write value (+5832), the tag read back from the host page (+5824) and the shadow (+5836) and calls `odsy_teardown`) and sleeps on the op's sync variable (+32) while its pending word (+8) is nonzero. On return *opnr = -1. With a context, it then frees every completed op in the context's set (page list, `unuseracc`, set id). A word at record +0x10000-19328 holds the active wait kind (3 harmless, 1 fatal) so `odsy_teardown` can report it.
`odsyDMAFinish(board, ctx)` sets the word at record +0x10000-19324 to 1, waits for both stored op numbers (ctx +248 then +256), clears it, then under the mutex frees and destroys the context's remaining set (poison 0x97; warns when the board is not torn down but an op was still pending). `gfP_OdsyMMwaitXfr` copies in an 8-byte op number and calls `odsyDMAWait` in mode 1 with the caller's context (error 1 with no context, 14 on a bad pointer); **inferred** from its argument that it is the ioctl user code uses to wait for one transfer (the caller was not read).
### 128-byte entries, the op header and the tag (`ConstructTftchWarList`, `odsyDMAOp`)

**established** (IP30 `odsy_dma.o`; constants resolved from the object's `.lit8`/`.data`). Each call of `odsyDMAOp` turns one request into a list of 128-byte table entries in kernel memory (op record +16 the table, +24 the entry count) and kicks each entry's physical address with the pair in `BUZZ.h`.

- `ConstructTftchWarList` first decides how many entries a request needs. A request whose byte length is at most 0x24000 (147456) is one entry. A longer one is cut into bands of `floor(0x24000 / row_bytes)` rows, where `row_bytes` is the header's row length (+20) plus its 20-bit extension (+24 bits 19:0); a row longer than 0x24000 is an error ("too many scanlines" family message, return 1). **inferred** that 0x24000 bytes is the most the board's fetch can cover per entry: the entry's 96-byte page list holds 12 pairs, which covers 0x24000 (nine 16 KB pages, plus slack for misalignment) but not much more.
- Entry layout, **established** from `odsyDMAOp`: bytes 0-31 are the caller's 32-byte header (eight words, `bcopy`), edited per entry: word +4 low half = the entry's x, high half = its y; word +12 low half = its width, high half = its height; word +24 bits 19:0 = bytes per pixel times the width (the row length); the other words pass through. The bytes-per-pixel table is `.data` offset 0 of the object, indexed by header word +28 bits 18:16: 2, 4, 8, 16, 12, 1, 6, 3 (**inferred** as bytes per pixel from its use as a row-length multiplier). **established** for libGLcore's image-move senders: they fill bits 18:16 with `__glOdysseyImageCalcPixelModeFields(...) & 7` (`ody_image_move.c`, decompiled lines 2257 and 2952), and that routine (`ody_image_move.s`, N32 0x0d9bf070-0x0d9bf1d3) returns 1 on every path, so their transfers always use code 1, four bytes a pixel. **inferred** that the word they fill is header word 7, because its top byte is the one `gfP_OdsyMMxfr` rewrites (below). Which senders use the other codes: not read here (the X module's image paths). Bytes 32-127 are the page list `generatePageTable` writes (`BUZZ.h`, eight bytes a page, up to 12 pages).
- If header word +28 bit 24 is set, the last entry's word +28 gets bit 31 set and the op is appended to the interrupt completion list (record +28448) with op bit 1 set. **inferred:** bit 31 asks the board to interrupt after that entry; the interrupt is the completion the second wake-up (below) waits for.
- Before the first kick `odsyDMAOp` takes the DMA mutex (record +5800), waits (`odsyDMAWait` mode 0, drops the mutex while it sleeps) while the ring cannot hold this request: outstanding + 2 must be below 128 minus the pieces still to come. It then stores the issue count and the tag counter into the hw-write record (+888) and the ring slot (record +5856 + 8 x tag counter), writes 0x800 to the flags-clear register 0x101c and kicks.
- After the last kick, a request with header word +28 bit 27 set sends `0x00014001` and the three settle groups (`BUZZ.h`); otherwise a request with the op argument's bit 1 clear sends block 0x258 (`0x00010658`) with operand `0x00120000` (the word the X module sends before a rectangle copy, `docs/opengl.md`). With the op argument's bit 1 set (the last op of a request) the op ends with class-1 block 0x05a (`0x00010a5a`, COUNT 2): operand 0 = record word +5840 | 0x8000, operand 1 = the tag `0x5a00 | (counter & 0xff)`; the driver also stores the tag in record halfword +5832.
- **established, the board's side: unknown.** The tag page: `odsyInitDMA` makes the page whose first halfword is 0xffff; **inferred** that the board writes the tag of the last finished op into it (see `odsyDMAWakeup`) and that block 0x05a operand 0 names the page.

### Wake-up logic (`odsyDMAWakeup`, `odsyDMAIrptWakeup`)

**established.** `odsyDMAWakeup` (called from the sync-source interrupt, `BUZZ.h`) takes the DMA mutex and does nothing when issued equals retired. Otherwise it reads the first halfword of the tag page (record +5824). When its high byte is 0x5a it is the board's latest tag and is remembered at +5834; when it is not (the initial 0xffff) the code uses the remembered tag plus one, masked to seven bits. The number of finished ops is `((tag + 1) & 0x7f) - retire index (+5848) + 128` masked to seven bits; a count above the outstanding total logs a "tag" error and returns. For each finished op it advances the retired count, empties the ring slot (an empty slot logs an error), advances the retire index, clears the op's pending bit 0, copies the op's +72 value into the hw-write record (+888, offset 8), and when no bit remains set calls `odsyDMADone` and broadcasts the retire sync variable (+5816). `odsyDMAIrptWakeup` (the DMA interrupt vector) takes the same mutex, pops the head of the interrupt completion list (+28448), clears the op's bit 1, and when no bit remains calls `odsyDMADone` and broadcasts. An op is therefore finished only when the tag has reached it and, when it asked for an interrupt, the interrupt has come. **inferred** that the tag page is written by the board's DMA engine, since no host code stores 0x5a00 values into it.

### The `MMxfr` request (`gfP_OdsyMMxfr`, ioctl `0x6f640006`)

**established** from the kernel handler (`odsy_pmm.o` .text 0x1fa8-0x2633, `copyin` and `copyout` of 80 bytes) and its two libGLcore senders, `__glOdysseyAssignToPMObj` (the Odyssey GL driver pixmap object assembly unit, N32 0x0d9c6d20-0x0d9c6e73) and `__glOdysseyReadFromPMObj` (0x0d9c6e80-0x0d9c6fa7):

| Offset | Content |
|---|---|
| 0 | 0 |
| 4 | memory group id |
| 8 | halfword entry index within the group |
| 16 | user buffer address (zero-extended 32-bit) |
| 24 | length in bytes |
| 28-59 | the 32-byte transfer header (the caller's, with word 5 masked to 17 bits) |
| 60 | flags: bit 0 set by the write sender (`AssignToPMObj` ORs in 1) and clear from the read sender; bit 1 makes the kernel wait for the transfer (`odsyDMAWait` mode 1) before replying; bit 3 the unclipped and bit 4 the clipped path of `odsyDMAOps`; bits 23:16 stored into byte 18 of the memory object |
| 64 | a caller word passed through |
| 72 | reply: the op number of the last operation (libGLcore keeps it for a later `MMwaitXfr` unless it asked for the wait) |

- **established.** Before calling `odsyDMAOps` the handler rewrites the top byte of header word 7 (request offset 56) to `0x32 | (bit 0 of +60 clear ? 0x01 : 0) | (old bit 27) | (old bit 30)`, keeping bits 23:0. So bits 29, 28 and 25 are always set, bit 24 is set for a read (board to host) and clear for a write, and the caller controls only bits 27, 30 and 23:0. Because the entries copy the header, bit 24 is also the read bit the entry section above says makes the last entry request a completion interrupt: reads finish on an interrupt, writes on the tag alone.
- **established.** The image-move senders in libGLcore (`ody_image_move.c` lines near 2607 and 2703 of the decompiled source) pass flag words of the form `1 or 3 or 9 or 0xb`, optionally `| 0x10`, `| 8`, with a per-object byte in bits 23:16.

### `odsyDMAOps`, the pixel-transfer request (`odsy_dma.o`)

**established.** `odsyDMAOps(board, ?, ctx, req, win)` turns one pixel-transfer request into a series of `odsyDMAOp` calls. `req` is read at these offsets: +16 user address, +24 length, +28 to +59 the eight-word header the entries are built from (word +28 flags: bit 29 selects the window origin, bit 24 requests a completion interrupt, bit 27 the 0xcf80a92f path, bits 18:16 the pixel-size code; word +32: x in the low 16 bits and y in the high 16, sign-extended from bit 15; +40: width and height halves), +56 (the header's word 7; bits 30 and 27 are tested) and +60 (bit 4 and bit 3 select the clipped and the unclipped path), +72 the result (set to -1, filled with the last op number). `useracc(addr, len, 272)` locks the buffer first; a nonzero result returns 12. On the way out the buffer is unlocked here only on an error; on success the op that ends the request owns the unlock (op +56 and +64), done in `odsyDMADone`.

1. Send block 0x258 (`0x00010658`, operand `0x00120000`).
2. **Plain path** (header word 7 bit 27 clear): one `odsyDMAOp` for the whole buffer; return its result.
3. **Transform path** (bit 27 set). The prologue, sent once before the first op of the request, is the ten-operand block `0xcf80a92f`, then the primitive begin `0x00014400` operand 10, then a Vertex2 word `0x8080c800` with operands 0, 0; then each op kicks its entries. The block's ten operands are the context's hardware-state mirror (context +176, then +6988) words 0, 1, 2, 3, two computed words, mirror word 6, two computed words, mirror word 9.
   - With +60 bit 3 clear the mirror words are sent unchanged (all ten, in order) and the whole buffer goes in one op.
   - With +60 bit 3 set the request is cut along y into chunks that end on a multiple of 64 rows when the board's variant flag (record +280) is 0 and of 128 when it is 1 (any other value reads an uninitialised stack word: **established** as code, never seen to occur). The destination is first clipped against the window rectangle (`win` +20/+24 origin, +32/+36 size) and the window origin (zero, or from the context's window record at +224 -> +128 words +104/+108 when header bit 29 is set); each chunk is one op, then the header's x, y and height are advanced for the next. The four computed words are floats the code builds by software normalisation of integers (sign, exponent = top-bit position + 127, 23 mantissa bits); **inferred** that they are the chunk's clipped destination extents relative to the window origin, the y pair derived from the mirror's float words +20 and +32 truncated to integers. Before the first chunk, when the context's settle flag (+7352) is set, the driver sends the first settle group and block 0x041 (`0x00010841`) with operands 0 and context +112; after the last chunk it sends that settle group again and block 0x041 with context +108 and +112, restoring the first operand. **inferred** that block 0x041 is clip state (the kernel's clip push also sends 0x040 and 0x041, `docs/buzz.md`) and the transfer zeroes its first operand while it runs.
4. **Clipped path** (+60 bit 4 set, the window query at context +224 -> +120 -> +144 reads zero and the context's clip count at +40 is nonzero): header bit 27 is cleared, so no prologue is sent, and the destination is intersected with up to four clip rectangles (context +44, +60, +76, +92: four-entry integer arrays of left, top, right and bottom). Each non-empty intersection goes out as its own op with its header adjusted.
5. **Error.** A failing intermediate op logs "dmaops: failed intermediate dma operation #n", then drains: block 0x044 (`0x00010444`, operand 0), block 0x05a with the tag-page operand `record +0xb44c | 0x8000` and the word 0xd0a, `odsyDMAWait` mode 1 for the failed op, and `unuseracc`; the op's error is returned.

- **unknown** (`docs/open-questions.md`). The two operands of block 0x05a beyond the tag page (the second operand's 0xd0a on the error path), what block 0x258 and its operand 0x00120000 select, the board-side meaning of the pixel-size codes, and which of the transform path's computed words the board uses as the destination extent. On a board it would show in: a command-FIFO trace (or a write-back of the board's registers) around one glDrawPixels and one glReadPixels of known size and format, together with the direction bit above.
- **unknown** (`docs/open-questions.md`). What the board does with bit 31 of an entry's word +28 and the page list's end marker. On a board it would show in: the interrupt line and the descriptor memory of one request with the interrupt bit set.

## RRM retrace and video-sync callbacks

**established** (`rrm.o`, IP30). These are the rendering resource manager's wake-ups that `odsyRetraceHandler` calls (`docs/buzz.md` section 6). Rendering node (RN) record: +4 halfword of wanted flags, +6 halfword of valid flags, +48 sync variable, +104 spinlock.

- `rrmValidateRetrace(rn)`: under the lock sets bit 4 of the valid flags (+6) and signals the RN's sync variable. It is the per-event retrace callback.
- `rrmValidateMyRetrace(gfxproc, rn)`: under the lock, when bit 4 is wanted and not yet valid, sleeps on the RN's sync variable (priority 25) until `rrmValidateRetrace` sets it; else returns.
- `RRM_WaitForRetrace`: fault check, `rrmInvalidateRN(rn, 16)` (clears the retrace bit), then calls slot +152 of the driver's operation table (**inferred** to be the retrace-event scheduler, `gf_OdsySchedRetraceEvent`, because that is the function queueing RN events for `rrmValidateRetrace`; the table was not resolved against its relocations) and unmaps the graphics pages.
- `RRM_WaitVideoSync` / `rrmWaitVideoSync(count, phase)`: requires 0 <= phase < count (else 22), queues the waiter on the board list (head at record +136, next at waiter +160) with the count at +144 and phase at +148, and sleeps interruptibly (priority 30); returns -1 when interrupted. `RRM_SetVideoSync` stores a value at record +128 and `RRM_GetVideoSync` returns it.
- `rrmValidateVideoSync(board)`: for each queued waiter, picks the counter at record +128 (when bit 3 of the waiter's RN flags is set) or +124 (otherwise), and when `counter mod count == phase` stores the counter in the waiter (+152), unlinks it and signals. A second list (head +168, linked through +168 of each waiter, retrace counter at record +164) holds buffer-swap waiters: `RRM_SwapBuf` puts a window's swap on it through `rrmSwapWait` when the swap interval (+24 of the window's swap record) is nonzero and `counter + 1` is below the swap target at +28, and `rrmValidateBuffer` sets that target to interval + counter when swap-interval mode (record +160) is on. `rrmValidateVideoSync` releases every entry whose target is at or below `counter + 1`. **established** from `RRM_SwapBuf`, `rrmValidateBuffer`, `rrmValidateVideoSync`. **inferred** that +124 counts vertical retraces and +128 counts a video-sync (genlock-relative) counter, by pairing with the handler's two increments; confirming which board event raises each is an open question (`docs/open-questions.md`); on a board it would show in a capture of the retrace interrupt against the display timing.

## Pass 14 (2026-10-31): what a DMA wait depends on, the NIC at attach, and the start-up FIFO set-up

IRIX 6.5.30m, IP30 `odsy_dma.o`, `odsy_intr.o`, `odsy_retrace.o`, `odsy_init.o` and the IP35 builds of the same objects. Written to explain a boot on a Tezro model (model evidence only) where the X server starts and the kernel later logs a DMA wait timeout. Labels as above.

### Who sleeps on one operation

- **established.** `odsyDMAWait` mode 1 (kind 1 stored while the watchdog is armed) is called from: `gfP_OdsyMMxfr` when the request flag word has bit 1 set (the X module's synchronous senders use flag 2 for reads and 3 or 0xb for writes); `gfP_OdsyMMwaitXfr`; `odsy_mm_obj_destroy` (for the object's stored operation number at +96, -1 returns); `odsy_mm_obj_xfr_bs` and the eviction helper `odsy_mm_jettison_freerun_bs` (call present, exact condition not traced); `odsyDMAFinish` (called by `gf_OdsyDestroyDDRN` and `gf_OdsyExit`); and `odsyDMAOps`' error drain after "failed intermediate dma operation". The submit routine's own space wait is mode 0 (kind 3).
- **established.** The IP35 watchdog `odsy_dmawait_timeout` logs "odsy board %d: DMAWAIT timeout" (severity 1) then, at severity 5, four lines whose text has no "odsy" in it: `last_issued_val : 0x%x` (halfword at +5832), `sync_hw_wr->val : 0x%x` (the halfword read through the pointer at +5824, the tag page), `shadow_sync_hw_wr.val : 0x%x` (+5836) and the outstanding count; then `odsy_teardown`. A syslog filtered on "odsy" drops those four lines; `sync_hw_wr->val` reads `0xffff` when the board never wrote the tag and `0x5aNN` when it did.

### The tag check runs from two interrupts

- **established.** `odsyDMAWakeup` is called from `odsySsyncInterrupt` and from the end of `odsyRetraceHandler` (both branches: with and without video-sync waiters, `jal odsyDMAWakeup` at IP35 `odsy_retrace.o` text, after `rrmValidateRetrace`/`rrmValidateVideoSync`). IP30 `odsy_retrace.o` has the same call. No other caller; `odsyDMAWait` has no poll loop.
- **established.** Fallback: when the halfword at +5824 has a high byte other than 0x5a (the initial 0xffff), `odsyDMAWakeup` takes `((+5834 & 0xff) + 1) & 0x7f | 0x5a00` as the tag. With +5834 = 0 after `odsyInitDMA`, the first call retires operations 0 and 1 whether or not the board wrote the page. A later operation, or one with pending bit 1 (entry interrupt requested), still waits. The IP35 routine is instruction-for-instruction the IP30 routine.
- **inferred.** A board with no vertical-retrace interrupts and a lost softsync interrupt never reaches the tag check, so the wait runs to its 1500 ticks (15 s at 100 ticks per second, **inferred**).
