# Firmware and standalone images

Three shipped files carry code that runs before IRIX or outside it: the IP30 boot PROM image, the IP35 boot PROM image and the standalone diagnostic monitor of the IP30. Release IRIX 6.5.30m. **Established** is what was read in the file; **inferred** is marked. The standalone driver the first and third carry is read from the binaries only.

- `usr/cpu/firmware/IP30prom.bin`: **established.**
  The flash image of the IP30 boot PROM, 879312 bytes of big-endian MIPS64 code with no header: the first word is a jump to 0xbfc003c0 (the reset vector `j` at +0x0) and the second a jump to 0xbfc003e0, followed by exception-vector jumps (0xbfc005d4) that fill the rest of the first page. Code addresses are the flash offset plus 0xbfc00000 (the image is also seen at 0x9fc00000 in the cached window, which is how its code builds addresses with `lui`).
  The board support is the standalone VPro driver, named in the error texts it prints: 50 strings begin with `odsy` between 0x96470 and 0xa0a40 and the text "ODYSSEY" appears twice, at 0x96590 and 0x96698 (the second as "SGI-ODYSSEY").
  The routines identified by their messages are `odsyGatherInfo` (reports an invalid BUZZ revision type, an unknown SDRAM CAS latency and an unknown number of banks; its code starts at flash offset 0x48384 and holds the three string references at 0x483d8, 0x484a4 and 0x485fc), `odsyReset` (invalid bank count, latency or size in MB), `odsyInitDBE` (cannot initialise the main or the option two-wire port) and `odsy_earlyinit` ("re-entered. Init code probably paniced!").
  The same image prints the texts of the two-wire monitor-agent routines (`odsy_i2c2abReset`, `odsy_i2c2abAttention`, `odsy_i2c2abIDRequest`), of `odsy_initDCD2DAC` ("failed to disable flash") and of `odsy_reconfigDCD2FPLD` (failures while reprogramming an FPGA).
  Where each of these routines starts, other than `odsyGatherInfo`, was not located.
- `usr/cpu/firmware/IP30prom.bin`, flash layout and what is compressed: for the headers, by inference for the audio reading.
  Two 256-byte headers carry the magic word "PROM" (0x50524f4d): one at 0x2ff00 (version word 0x409, data length 0x23efe) and one at 0x30000 (version word 0x411, data length 0xa69d0). The version words split into a major and a minor byte (24-bit major, 8-bit minor is **inferred** from the banners), and they match the banners "SGI Version 6.5 Rev 4.9 IP30" at 0x190f8 and "SGI Version 6.5 Rev 4.17 IP30" at 0x930f0. The second header's data starts at 0x30100, and 0x30100 plus 0xa69d0 is 0xd6ad0, the file size. So the file is a three-segment boot part (0 to 0x2ffff, header in its last 256 bytes) followed by one image that fills the rest, with no compressed container around either.
  The earlier note that the image is "partly compressed" came from byte entropy alone. The high-entropy span between about 0xa3e00 and 0xb1c00 is boot-tune audio, not compressed code. Decoding the span as 4-bit ADPCM with the standard 89-entry step table gives slowly varying 16-bit samples, with a mean absolute step between samples of mostly 250 to 1,600 over 1,024-sample windows, that fade to near zero (below 20) three times, at about 0xab200, 0xb0200 and 0xb1a00. The same decoder on code or random bytes gives 9,000 to 18,000. Three runs ending in silence match three tunes. The block at about 0xb1e00 to 0xb3a00 (entropy about 7.1 bits per byte, no text) is also audio, **inferred**: decoded with the same 4-bit ADPCM decoder in either nibble order, 512-sample windows give a mean absolute step of 11 and 39 at the start, then 890 to 2200, falling through 800 to 500 and ending at 132 and 63, a smooth envelope from silence to silence. The same decoder gives 17,000 to 18,000 on random bytes and 6,000 to 8,000 on code (`objdump`-readable spans at 0x8fb00), so neither explains the block. An earlier test counted opcode-like top bits and a smoothness test on single windows only, which is why it missed this. It is a fourth tune or a longer one; which sound it is stays **unknown** and only a listen to the decoded samples or a read of the routine that plays the tune table would say. The code spans decode as ordinary MIPS (`objdump -D` over 0x8fb00 to 0x8fc40 gives prologues, calls and returns), so the strings listed above are the whole of the PROM's board text that a string search can reach (text built at run time would not show).
  Strings of the hardware-listing region (0x925f0 to 0x926c0): `xbow(rev 1.%d):`, `xbow(rev 2.%d):`, `bridge(rev %c): `, `ioc3(rev %d): eaddr %s `, `   xtalk 0x%x `, `HQ4: ` and `ODSY: `. The listing routine's Xbow revision arithmetic (`1.<n-1>` up to n = 5, `2.<n-5>` above) is not read here; when the `ODSY: ` branch was added is **unknown**, and a read of the same routine in the older PROM images would settle it.
  The printing code (read from 0xbfc33c90 to 0xbfc34198, flash 0x33c90, the PROM's hardware lister). It reaches its strings through one base, the cached address 0x9fc921c0 (`lui 0x9fc9`, `daddiu 8640`), and an offset per string, which is why no instruction formed a string's own address: `ODSY: ` is base + 1232 (0xbfc3402c), `HQ4: ` base + 1224, `bridge(rev %c): ` base + 1200, `   xtalk 0x%x ` base + 1184 and the unknown-widget text base + 1240. For each widget number from 14 down to 9 (the counter starts at 14 at 0xbfc33fa4 and the loop exits at 8) it calls a link test at 0xbfc6b0d4 with the crossbar window 0x9000000010000000 and the number, and for a live link prints `   xtalk 0x<number> `, then reads the widget's identity word at window +4 (window = 0x1n000000 for widget n, as `docs/buzz.md` has it for Linux) and takes bits 27:12 as the part number. Part 0xc002 prints `bridge(rev %c): ` with the revision letter (the word's top nibble plus 0x40) and then the identity string read from window +0xb4; part 0xc003 prints `HQ4: ` and reads its identity string at window +0x11098 (the offset is formed as `lui 1`, `ori 0x1098` at 0xbfc34114 to 0xbfc3411c); part 0xc013 prints `ODSY: ` and reads the identity string at window +0x10dc; any other part prints `unknown widget partno=0x%x`. Each identity read is a call to 0xbfc6de58 (register address, buffer) followed by the printer at 0xbfc33b28. So for the VPro board the PROM prints the label and that identity string only: no revision letter, no memory size and no strap word. The helper at 0xbfc6de58 and the register at +0x10dc are read (PROM image, flash offset = address minus 0xbfc00000). **Established:** the helper clears the first byte of the buffer, then calls the routine at 0xbfc6dd44 with the register address and the buffer. That routine sets up a reader state on its stack (0xbfc6cb40) and calls the fragment routine at 0xbfc6d868 repeatedly until it returns non-zero; each call appends text to the buffer. The routine at 0xbfc6cb68 packs 64 sampled bits (one per byte of the reader state, gathered by 0xbfc6c7dc, not read here) into eight bytes, runs a byte-wise table CRC over them (the 256-entry table at flash 0xd5328 starts `00 5e bc e2 61 3f dd 83`, the table of the 8-bit CRC with reflected polynomial 0x8c used by one-wire serial-number parts) and returns 3 when the residue is not zero; on success it returns the family byte, the six serial bytes and the check byte. The fragment routine dispatches on a seven-way jump table on that read's result and builds a record of the shape `Part:..;Name:..;Serial:..;Revision:..;Group:..;Capability:..;Variety:..;Laser:..` (fragment strings at flash 0x9d7f8 to 0x9d850). When the part cannot be read it stores one of six fixed fall-back strings instead, for example `NIC:Not present on interface;Laser:unreadable;` and `NIC:CRC failure reading interface;Laser:unreadable;` (0x9d860 to 0x9d968). The PROM's own error text names the same family of routines (`nic_match_rom: couldn't see presence pulse`, `nic_read_one_page`, `nic_read_mfg`, strings at 0x9d5ee to 0x9d6b0). **Inferred:** the register at +0x10dc is therefore the board's manufacturing serial-number part, the same part the kernel hands to its NIC reader (`docs/kernel.md`, "The manufacturing NIC at attach"), and the printed identity is that part's manufacturing record. The bridge and HQ4 paths use the same helper at other offsets. **Established** (PROM image, flash offset = address minus 0xbfc00000; the port routine at 0xbfc6d72c, the bit and byte wrappers from 0xbfc6c7dc to 0xbfc6c958 and the reader set-up at 0xbfc6cb40 read in full): the reader state holds a port-routine pointer and the register address (0xbfc6cb48 and 0xbfc6cb58), and the helper at 0xbfc6de58 passes the cached address 0x9fc6d72c, which is that routine. The port routine stores the 32-bit word `(a1 << 10) | (a2 << 2)` to the register (0xbfc6d72c to 0xbfc6d740), reads the register until bit 1 is set (0xbfc6d748 to 0xbfc6d750), calls the PROM's calibrated delay at 0xbfc6c574 with a3 and returns bit 0 of the last read. The wrappers pass (a1, a2, a3): reset (0xbfc6c7dc) 520, 65 and 500; write of a 1 bit (0xbfc6c808) 6, 110 and 0; write of a 0 bit 80, 30 and 0; read of a bit (0xbfc6c848) 6, 13 and 100. A byte goes out least significant bit first (0xbfc6c874) and comes in the same way (0xbfc6c8f0). After the reset the caller (0xbfc6c988 to 0xbfc6c9a0) goes on when the level is 0 and returns code 4, the one behind `couldn't see presence pulse`, when it is 1, so a low level read back after the reset means a part answered. **Inferred:** a1 is the time the line is driven low and a2 the time from the end of that pulse to the sample or the end of the slot, both in microseconds, because the four pairs are the usual reset, write-0, write-1 and read slots of a one-wire serial-number part (a 520 reset pulse, a presence sample at 65, 6 microsecond pulses for a 1 and a read, 80 for a 0); the clock that counts a1 and a2 in the hardware, and the unit of a3, are not shown by the PROM. **Unknown:** the part numbers and names a real board returns. A posted boot of a V6 to V12 Octane2 that prints an `ODSY: ` line would show them (one Library search of the Usenet archive for the label found none).
- `usr/cpu/firmware/IP30prom.bin`, the stored start-up command image at flash 0xcac30: **established** for the comparison and the counts of blocks 0x043, 0x046, 0x019, 0x018, 0x050 and 0x258, **inferred** for what the settle pattern does.
  The kernel's textport object holds a 16660-byte data object, `buzz_init`, at `.data` offset 0 of `odsy_tport.o`; `odsy_tpinit` writes 4165 of its words to the command FIFO (`docs/driver-functions.md`). The PROM carries the same words at flash offset 0xcac30. Compared word by word, the first 3265 words are identical. At word 3265 the PROM has a primitive-begin word (0x00014400, end word 0x00014001 at 3279; repeated at 3398, 3531 and 3678) where the kernel's image has a settle group, and the two differ after that; the kernel's image has its only later begin at word 3633. Read as class-1 words (id in bits 9:0, operand count in bits 13:10), both images are one sequence of drain groups, state blocks and copy blocks, so the PROM does not send the text-port set-up as a series of constants: it replays a stored stream, as the kernel does. The stream's block values are in `docs/tokens.md` (block 0x015 = 0xa, 0x04a = 0x80 and 0x80, 0x022 = 3 and 0x024 = 3, 0x04b first maximum 0x4ff3ff).
  What the two images add about the blocks `docs/open-questions.md` listed as only stored, counted over the PROM image up to word 4212 (the kernel's image to word 4165 gives the same counts, 155, 427, 36 and 1, for blocks 0x043, 0x046, 0x019 and 0x018): block 0x043 is sent 155 times and only ever with operand 250 (101 times) or 150 (54 times); block 0x046 427 times and block 0x019 36 times, each with no operand. They come in runs, each ending at a state block or raw words: 33 runs read 0x043 with 250, two 0x046, 0x019, 0x043 with 150, four 0x046, 0x043 with 250, two 0x046; 14 start at the 0x043 with 150; 10 are only the last three blocks (0x043 with 250, two 0x046); the other six are variants (three are the last three blocks followed at once by the full run). Every run is followed by a state block or raw words, though not every state block follows a run (**inferred**: a wait, a pad and a flush, matching `BUZZ.h`). Block 0x018 is sent once with no operand, between block 0x006 and block 0x01c of the zero-state group, bracketed by two drain groups; its effect is **unknown**. Block 0x258 is sent 19 times in the PROM image: once with operand 0x00110000 (word 2818, ahead of a primitive-begin group) and 18 times with 0x00120000, the first ahead of a run of register-write words at word 2905 and the other 17 ahead of rectangle-copy sequences whose size words begin at 0x00040004 and end at 0x02000500, mostly with one half or the other doubling from one copy to the next (0x00040008, 0x00040010, 0x00030020, 0x00030040, 0x00040080 and so on; 0x00040200 is followed by 0x00040100 and 0x00040500) (the words after the block are the copy sequence of `docs/opengl.md`). The operands 0x110000 and 0x120000 equal the offsets of the two command-word windows in `docs/registers.md`; whether the block's operand selects a window is **unknown**, since the copies are written through the 0x110000 port in both cases. Blocks 0x044 and 0x170 appear in neither image; block 0x050 appears once in both, at word 2834, with operands 0xf and 0. Block 0x022 is already the logic operation (`docs/tokens.md`). The PROM code that selects the length of the replay was not located (no instruction forms the flash address), so the PROM's stop word is read only from the image.
- `usr/cpu/firmware/IP30prom.bin`, the cursor set-up: **established** for the stores and the table contents, **inferred** for the control-word fields.
  The routine at 0xbfc64fc8 (flash 0x64fc8 to 0x65284) copies three tables from flash: 512 bytes (128 words) from 0x9c2f0, 256 bytes (64 words) from 0x9c4f0 and 180 bytes (45 words) from 0x9c5f0. It writes them to the display FIFO window at board +0x400000, two words to a doubleword, with type-3 headers 0x39400080 (address 0x2500, 128 words), 0x39700040 (0x25c0, 64 words) and 0x3964000f (0x2590, 15 words). The first 64 words of the first table and the first 32 of the second hold the glyph and alpha arrays, and the rest of both tables is zero; the 15 colour entries are entry 0 0x00,0xff,0x00; entry 1 0xff,0,0; entry 2 0x00,0xff,0xff; the rest zero. Each entry word is red shifted left by 22, green by 12 and blue by 2 (instructions at 0xbfc6516c to 0xbfc65190).
  The last store (0xbfc65254 to 0xbfc65278) writes address 0x2581 with header 0x39604001 and a word read from stack offset 952 with bits 4:2 cleared (mask -29) and bits 1:0 set (the OR with 3). Nothing in the routine initialises that stack word, so bits 31:5 are whatever the stack held. So two fields sit in bits 1:0 (set) and three in bits 4:2 (cleared). What each field is, and which bit of each set belongs to which, is **unknown** from the binaries read here; a read of the cursor-control writers in `odyssey.so` for the same bits would settle it. The X module's own reading of bits 0, 1, 4 and 5 (`docs/odyssey-so-reads.md`, `odsyInstallCursor`) is a separate inference and is not corrected here.
- `usr/cpu/firmware/ip35prom.img`: **established.**
  The flash image of the IP35 boot PROM, 1480360 bytes. The first 63 bytes are zero, byte 63 is 0xd2 and the text `JFKSWCSM` fills bytes 64 to 71, then come the words 0x6 at +76 and 0x1696a8 at +84, which equals the file size in bytes.
  It has no VPro bring-up code of its own: the strings `odsy` and `ODYSSEY` occur once in all of it, the single `odsy` being an entry of a short table of graphics board names (`kona`, `mgras`, `odsy` and `unknown_gfx`) at flash offset 562048, next to the warnings "Warning: Unknown GFX board (0x%x) at Module %M Slot %d" and "Note: Found gfx widget with unknown subsystem".
  So the IP35 PROM only identifies a VPro board by its widget identity and leaves the initialisation to the kernel driver's IP35 build, which is **inferred** from the absence of `odsyReset`, `odsyGatherInfo` and the other driver messages that the IP30 image holds.
  This reading rests on the image alone.
- `sbin/stand/ide.IP30`: **established.**
  The IP30 standalone diagnostic monitor, an N64 executable of 1594880 bytes whose entry point is 0xa8000000208a8410 (a link address in the standalone window) with `.text` from 0xa800000020800180 and `.rodata` from 0xa8000000208f0000. It reaches the board itself, through the same code as the PROM, not through IRIX.
  Its strings include the VPro driver's error texts (`odsyGatherInfo: Invalid buzz rev type`, `odsyReset: invalid sdram size`, `odsyInitDBE(): cannot initialize main i2c port`, `odsy_earlyinit re-entered`) and the monitor-agent and option-card messages of `odsy_i2c2abReset`, `odsy_i2c2abAttention`, `odsy_i2c2abIDRequest`, `odsy_initDCD2DAC` and `odsy_reconfigDCD2FPLD`, the same set as in `IP30prom.bin`.
  It also carries the text "odsy: frame buffer/fullscreen accum config causes oversubscription of sdram.", which the board-manager code prints when a framebuffer and accumulation configuration would exceed the board memory.
  A search of its strings for `odsy` and `ODYSSEY` finds only the driver's own messages above and no test-command names.

## Transform microcode images

Two data files hold the program of the board's transform engine. Both are tables of 96-bit instructions (12 bytes each, big-endian) in the format of `ucode/buzz_isa.md`; every statement here is **established** by comparing the two files and the loaders named.

- `usr/gfx/ucode/ODSY/buzz_xform.bin`: **established.**
  The full program as the install ships it: 33528 bytes, exactly 2794 instructions, starting with the instruction bytes 04a400000120c00000080000 and ending with a zero instruction word and the word 1e167204.
  It reaches the board in two steps: `gfxinit` (`odsy_init` at 0x1000e2c4 in `usr/gfx/gfxinfo`) maps the file read-only and sends it with ioctl 0x6c, and the kernel's `gf_OdsyDownload` (offset 0x130 in `odsy_ucode.o`, 840 bytes) hands it to `odsyDownloadUcode`, which writes each instruction as six 16-bit FIFO words after an address word.
  Against the kernel's built-in copy it has 99 more instructions inserted at record 792 and 429 appended after the copy's end.
- `usr/gfx/ucode/ODSY-kernel/buzz_ucode_ip30.bin`: **established.**
  The array the kernel itself carries, written out unchanged by the extraction script: 27196 bytes, which is 2266 instructions of 12 bytes plus a four-byte trailer of 0xffffffff (the file's last four bytes). It begins with the same instruction bytes as the full program.
  The kernel sends it from `odsyInitCfifo` (offset 0x230c in `odsy_init.o`, 860 bytes) at board start-up, loading only the first 2048 instructions into the sequencer RAM, before any program from `gfxinit` replaces it.
  The IP35 kernel's copy is byte-identical (`ODSY-kernel/buzz_ucode_ip35.bin` has the same bytes, so the inventory folds it into this row).

## Other releases and patch copies of the microcode

These are the transform microcode and PROM images that a 6.5.22 install or a VPro patch ships with, compared with the 6.5.30m files above by SHA-256 of their bytes. **Established** for every hash and every match below, since each comparison reads the bytes.

- The kernel array is byte-identical in all six copies: the IP30 and IP35 kernels of 6.5.30m, of 6.5.22, and VPro patches 4103 and 4104 (IP30 kernel only). Each copy is the `buzz_ucode` object of the `odsy_init.o` member of its `odyssey.a`, 27196 bytes, SHA-256 `9955bc1bad614a4d`. **Established.** The same bytes are `ODSY-kernel/buzz_ucode_ip30.bin` above.
- The object that carries the array changes around it. `odsy_init.o` differs from the 6.5.30m member in every copy: IP30 6.5.22 `44bff539`, patch 4103 `99796766`, patch 4104 `d3172ec3` (6.5.30m IP30 `3a57d1f9`); IP35 6.5.22 `daad6f16` against 6.5.30m IP35 `ff0614b4`. So the releases and patches changed the kernel code around the microcode, not the microcode itself. **Established** for the hashes; why the code changed is **unknown**.
- Sibling rows: the six copies are siblings of the `buzz_ucode_ip30.bin` row, but none is a row of its own. The array is part of each `odsy_init.o` member, and the inventory lists whole members, not arrays inside them. The 6.5.22 `odyssey.a` builds are not in the inventory's build list at all. The patch 4103 and 4104 `odsy_init.o` members are listed, as members, in `docs/inventory/binaries.tsv`.
- Changed microcode images: none. Every microcode image present in two releases matches, so this comparison adds nothing to the reading queue.
- Kernel objects that match exactly across releases: of the 6.5.30m IP30 members, 6.5.22 holds `odsy_dvi.o` (`a1f4b5c2b48a`) and `odsy_idbg.o` (`67dd60f94fc9`) byte for byte. The VPro patch archives hold 24 members, against 29 in 6.5.30m: they lack `odsy_compositor.o`, `odsy_denali.o`, `odsy_dvi.o`, `odsy_hpipe.o` and `odsy_rainier.o`. The 6.5.22 IP30 archive lacks only `odsy_rainier.o`. These are kernel objects, not images, and their code is not compared here.
- Not compared, because no other copy of these files is in the trees read: `usr/gfx/ucode/ODSY/buzz_xform.bin` and `ODSY/vof/*.vfo`, and `usr/cpu/firmware/IP30prom.bin` and `ip35prom.img`. The 6.5.22 install tree has its kernel objects and sysgen files but no `usr/gfx` or `usr/cpu/firmware`, and each patch build holds the IP30 `odyssey.a` and the `libGL.so` and `libGLcore.so` of the three IP30ODSY arch directories, with no `usr/gfx/ucode` or firmware. See the open question on the 6.5.22 transform image and PROM in [open-questions.md](open-questions.md).
- The 6.5.15 diagnostic transform image `diagxform.bin` (SHA-256 `dd27f727`) is a different program from `buzz_xform.bin` (`a0201d88`), not a release copy of it, so it is outside this comparison.
