# Board registers, one entry each

Release IRIX 6.5.30m, IP30 kernel objects (`odyssey.a` members) unless a row says otherwise. Every row starts with a board offset, the number the kernel adds to the PIO base it keeps at board record +824. The access column gives the width the code uses. The labels are **established** (read from the instruction stream, with the function) or **inferred** (a reading, with its reason). Offsets that end in 4 or c are the low word of an 8-byte register, which is why the FIFO-level register is loaded at 0x106c. The IP35 objects store the same offsets in the same order (`docs/kernel.md`).

Bit-level detail of the flags and status words is in `BUZZ.h`; the display-side registers behind the display FIFO are in `docs/pbj.md`.

## Crossbar widget header (0x00 to 0x5c)

The layout of this block is published in the shipped header the Odyssey stack header 6 (6.5.30) and in the public Linux IP30 port's asm/xtalk/xwidget.h. The board follows it.

| Offset | Access | Role and derivation |
|---|---|---|
| 0x4 | load 32 bits | **established.** Widget identification word. `odsyGatherInfo` (`odsy_init.o`) takes bits 31:28 as the revision type, stores it at record +264 and dispatches on it through a 16-entry jump table; the part number 0xc013 and manufacturer number 35 that `odsy_init` registers for this widget are the other fields of the same word, by the xwidget.h layout. |
| 0xc | load 32 bits | **established.** Widget status word, loaded first by `odsyXtErrorInterrupt` (`odsy_intr.o`) on every crossbar error interrupt. It tests bit 8 (logs "Response Time-out Error"), then bit 7 ("Address Error", the only case that tears the board down), then bit 6 ("Packet Format Error"), and logs a catch-all message when none is set. |
| 0x14 | load 32 bits | **established.** Upper error-address word. Only the address-error branch of `odsyXtErrorInterrupt` (`odsy_intr.o`) loads it; the handler masks it with 0xffff0000 and prints the result as the "hi error" value, while the "hi addr" it prints is a constant 0. By the xwidget.h layout its low 16 bits would be address bits 47:32, which the handler discards. |
| 0x1c | load 32 bits | **established.** Lower error-address word. The address-error branch of `odsyXtErrorInterrupt` (`odsy_intr.o`) prints it unmodified as "lo addr", next to the header from 0x44 and the 0x14 word. |
| 0x24 | load and store 32 bits | **established.** Widget control word. `odsyReset` (`odsy_init.o`) reads it into a record shadow before each step that resets the link, among them `odsyLowLevelReset`, and stores the shadow back afterwards, because the link reset clears it (31 sites). Its final store is the widget id (record byte +793) OR 0x4200: by xwidget.h that sets bit 9 (big-endian system) and the value 4 in the crossbar credit field, bits 15:12. |
| 0x2c | not accessed by any kernel object | **established** that no IP30 or IP35 `odyssey.a` member loads or stores it (the widget-block scan above lists 0x4, 0xc, 0x14, 0x1c, 0x24, 0x34, 0x3c, 0x44 and 0x5c only). xwidget.h places the request-timeout word here (the low word of the 8-byte slot at 0x28). The IP35 PROM's crossbar sanity diagnostic reads it as `XT_REQ_TIMEOUT`, a 20-bit register, and published PROM transcripts print `0x000fffff`: [The IP35 PROM's board-register diagnostic](#the-ip35-proms-board-register-diagnostic-6210). What the value times, and its unit: **unknown: no shipped software depends on it**. |
| 0x34 | store 32 bits | **established.** Upper half of the widget's interrupt destination (`odsy_init.o`), written by `odsyInitInterrupts` and again by `odsyDisableInterrupts`. Value: error-source vector in bits 31:24, bits 23 to 21 set, crossbar target number from `xtalk_intr_target_get` in bits 19:16, address bits 47:32 in 15:0. `odsyDisableInterrupts` clears bit 21, so that bit is the source's enable (inferred from the pair). |
| 0x3c | store 32 bits | **established.** Lower half of the same interrupt destination: `odsyInitInterrupts` (`odsy_init.o`) stores address bits 31:0 of the error source, the 64-bit value kept at record -19688, here right after the 0x34 word. By xwidget.h this is the interrupt-destination lower-address slot. |
| 0x44 | load and store 32 bits | **established.** Error command word. `odsyXtErrorInterrupt` (`odsy_intr.o`) loads it before anything else, prints it as "xt header", and ends every call by storing 0 to it; the "Fatal widget error (header = ...)" message of the two non-address cases repeats it. The xwidget.h layout splits it into destination, source, packet type and transaction fields. |
| 0x5c | store 32 bits | **inferred.** Crossbar interrupt configuration word, by its position beside the 0x34 and 0x3c destination words; the Linux `xwidget.h` header stops at 0x54. `odsyInitInterrupts` (`odsy_init.o`) builds it as bit 13 set, bits 12 to 8 cleared, then bits 12 to 10 and the low byte set, and `odsyReset` zeroes it as the last of its interrupt-state stores. |

## System block (0x1000 to 0x10d4)

| Offset | Access | Role and derivation |
|---|---|---|
| 0x1004 | store 32 bits | **established.** SDRAM configuration word, written only by `odsyReset` (`odsy_init.o`): first the master widget id in bits 22:19, then banks (bit 2), CAS latency (bit 1) and size code (bits 4:3) from the strap read at 0x106c, then bit 5 cleared, set, written and cleared again with 400 us waits, and bit 8 last. |
| 0x100c | store 32 bits | **inferred.** Abort and reset register. `odsyLowLevelReset` (`odsy_init.o`) writes 0x200 on newer host chips and then waits, never writing 0 back to the register, otherwise the six single bits that add up to 0x16d, waits, and then writes 0 to the register. |
| 0x1014 | load and store 32 bits | **established.** The flags register. `odsyFlagInterrupt` (`odsy_intr.o`) reads it; `odsyHiwaterInterrupt` stores 0x200 to it when the status word still shows the command FIFO below the low-water mark, and `gfP_OdsyDIAGdma` clears bit 11 with a read-modify-write. |
| 0x101c | store 32 bits | **established.** Flag-clear register, write-one-to-clear: `odsyReset` stores all ones, `odsyHiwaterInterrupt` stores 0x200 (the command FIFO low-water flag) before it re-arms, `odsyDMAOp` (`odsy_dma.o`) stores 0x800 (the DMA-done flag) before each transfer, and the flag interrupt handler stores the pending bits it has just served. |
| 0x1034 | load and store 32 bits | **established.** Flag interrupt-enable mask. `odsyFlagInterrupt` (`odsy_intr.o`) loads it and ANDs it with the flags; `odsyInitInterrupts` stores the start-up mask built by read-modify-write, the high-water handler stores the shadow with bit 9 set, and `odsyLoadTimingTable` sets bit 31 before it writes the genlock word. |
| 0x103c | store 32 bits | **established.** Interrupt-enable clear register: `odsyLowaterInterrupt` (`odsy_flow.o`) stores 0x200 here to turn the low-water interrupt off, and `odsyDisableInterrupts` and `odsyReset` store all ones. |
| 0x1044 | store 32 bits | **established.** Interrupt control, high half for the flag, DMA, retrace and sync sources, written by `odsyInitInterrupts` (`odsy_init.o`) and zeroed by `odsyReset`: crossbar target number in bits 28:25, bit 29, bits 24 to 22, bit 19 and bits 18 to 16 set, and address bits 47:32 of the flag-source destination in 15:0. `odsyDisableInterrupts` clears bits 18 to 16. |
| 0x104c | store 32 bits | **established.** Low half of the shared interrupt destination: `odsyInitInterrupts` (`odsy_init.o`) stores the 32 low bits of the address the crossbar allocator returned for the flag source (record -19680), and `odsyReset` zeroes it. |
| 0x1054 | store 32 bits | **established.** Four interrupt vectors packed one per byte: flag source in bits 7:0, DMA source 15:8, retrace source 23:16 and sync source 31:24, each taken from the number `xtalk_intr_vector_get` returned. |
| 0x105c | store 32 bits | **inferred.** Interrupt packet header word, three identical ten-bit groups with one group per interrupt source, laid out under the table. `odsyInitInterrupts` (`odsy_init.o`) builds each group from a barrier bit, a destination id of 7 and the 4-bit crossbar target number it copies from the shadow of the 0x34 word, and `odsyReset` zeroes the register between the vector word and the flow configuration. The kernel fills the three groups identically, so no shipped code ties a group to a source. |
| 0x1064 | load 32 bits | **established.** Status word 0, read by `odsyHiwaterInterrupt` (`odsy_flow.o`), which tests bit 17 (command FIFO below low-water) to decide whether to raise the low-water flag by hand, and printed by `odsyPrintRegs` after a fatal error. |
| 0x106c | load 32 bits | **established.** Levels and straps, loaded 23 times by IP30 kernel driver members and 6 times by IP35 ones, plus the PROM and `ide.IP30` readers listed under [the 0x106c readers](#the-0x106c-readers). Bits 31:24 are the strap byte that `odsyGatherInfo` decodes once; bits 6:0 are the display FIFO level in doublewords (**established** from the waits in `odsy_brdmgr.o`, section below) and bits 15:7 a command-side level, **inferred**; no binary compares bits 15:7 with anything but zero. Which queue the command-side count covers is **unknown** in the section below the table. |
| 0x1074 | store 32 bits | **established.** Flow-control configuration. The attach sequence inlined in many kernel routines, for example `gfP_OdsyClearBuffer` (`odsy_clip.o`), stores a word whose bits 16:12 are the credit target number from `gfx_flow_credit_tnum_get`; `odsyReset` zeroes it. |
| 0x107c | store 32 bits | **inferred.** Flow-control off switch: stored 0 when a process attaches to flow control and 1 just before `gfx_flow_detach_me` in `odsyInitCfifo` (`odsy_init.o`), which is why a 1 is read as "flow control disabled". |
| 0x1084 | store 32 bits | **established.** Flow-control clear: a clear-set-clear pulse stored by `odsyReset` (`odsy_init.o`); `gf_OdsyInitialize` repeats the three-store shape after it has waited, in 5 us steps, for the command FIFO level to reach 0. |
| 0x10b4 | store 32 bits | **inferred.** Per-window buffer-swap trigger, one bit per window id (32 ids). `odsySwapBuffer` (`odsy_retrace.o`) stores the ids whose driver buffer shadow (record +28528) differs from the wanted buffer word (record +28572), and `odsyRetraceHandler` stores the bit of a window whose swap has waited too many retraces. |
| 0x10bc | store 32 bits | **inferred.** Per-window swap-timing select, one bit per window id: `odsyReset` stores 0, `gf_OdsySchedSwapBuf` stores the mask of the swap group, and `odsySwapBuffer` (`odsy_retrace.o`) stores the same mask minus the windows it has finished. |
| 0x10c4 | store 32 bits | **inferred.** Buffer-B select set register: `odsySwapBuffer` (`odsy_retrace.o`) and `gf_OdsySetDisplayMode` store the window ids whose new front buffer is B here, and the complementary ids to 0x10cc; it is the set twin of the clear register that follows. |
| 0x10cc | store 32 bits | **established.** Buffer-B select clear register: `odsyReset` (`odsy_init.o`) stores all ones to put every window id on buffer A; `odsySwapBuffer` stores the ids whose front buffer goes back to A. |
| 0x10d4 | load 32 bits | **inferred.** Read-back of the buffer select each window currently shows: `odsyRetraceHandler` (`odsy_retrace.o`) loads it once per retrace and XORs it with its record copy at +28528 to find the windows whose buffer changed. |

0x105c bit layout: the groups sit at bits 9:0, 19:10 and 29:20. In each group bit 0 is set, bits 5:3 hold 7 and bits 9:6 hold the target number, so the word is the target number at bits 9:6, 19:16 and 29:26, ones at bits 0, 10 and 20, and 7 in bits 5:3, 15:13 and 25:23 (read from the `ori`, shift and mask sequence at the end of `odsyInitInterrupts`, `odsy_init.o` text 0x2938 to 0x299c).

The four registers between the flow group and the swap group are each stored once, with zero, by `odsyReset`, and never read:

0x108c: role **unknown**. `odsyReset` stores 0 to it once, after a record shadow store at -31276, and no other shipped kernel object, library or tool touches that offset. The status word's scan-done bit suggests a scan unit exists and that this is the first of four registers for it (0x108c to 0x10ac, **inferred** from position and that bit), and reset leaves it idle. The register's bit fields are an open question in `docs/open-questions.md`; routes tried: the offset scan of every in-scope binary, the strings of the diagnostic tool, which name no scan register, and the patch copies of the driver.

0x109c: role **unknown**, **inferred** to be the upper half of a host address for scan output (by position after 0x108c). `odsyReset` stores 0 to it once, shadow at -31272, and it is read nowhere. The kernel does keep a scan buffer for a diagnostics client: `gfP_OdsyDIAGallocScanbuf` (`odsy_diag.o`) returns the buffer's physical address to user space, the value an address pair would carry, but nothing in the shipped kernel stores it to the board. Which address bits the board keeps is an open question; routes tried: the offset scan, the driver's reset path and the three kernel builds' `odsy_diag.o`.

0x10a4: role **unknown**, **inferred** to be the low word that completes the address begun at 0x109c (by position). `odsyReset` stores 0 to it once, shadow at -31268, and it is read nowhere. Its alignment rules are an open question; routes tried: the binary scan and the shipped Linux xwidget.h header, which stops at 0x54.

0x10ac: role **unknown**, **inferred** to start a scan (by position last of the four, with the status word's scan-done bit). `odsyReset` stores 0 to it once, shadow at -31264, directly before the performance-statistics base registers, so no scan is pending after reset. No shipped code starts a scan. Which value starts one is an open question; routes tried: the binary scan, that reset path and the diagnostic-register candidates at 0x109c.

## Context-save and statistics group (0x4000 to 0x405c)

| Offset | Access | Role and derivation |
|---|---|---|
| 0x4004 | store 32 bits | **established.** High 16 bits of the physical address of the context-save buffer: `gf_OdsyPcxSwap` (`odsy_ctxsw.o`) converts a record's buffer with `kvtophys`, stores bits 47:32 here and the low word at 0x400c, then calls `odsyMMvalidatePcxSwap`. |
| 0x400c | store 32 bits | **established.** Low 32 bits of the same context-save buffer address, stored by `gf_OdsyPcxSwap` (`odsy_ctxsw.o`) right after 0x4004 and followed by a `sync` before the save request goes to 0x118000. |
| 0x4014 | store 32 bits | **established.** Master-id control word of the 0x4000 group, written once by `odsyReset` (`odsy_init.o`): bits 15:0 set to 0x12, bit 18 and bit 24 set, bits 19:16 otherwise clear, and the widget master id (record byte +792) in bits 23:20. Its twin with the id in a different place is 0x4044. |
| 0x401c | store 32 bits | **established.** High half (bits 47:32) of the physical address of the 16 KB statistics region: `odsyInitPfRgn` (`odsy_diag.o`) writes it after converting the buffer address, `odsyDestroyPfRgn` and `odsyReset` write 0. Each write is followed by a sync. That the board writes into the region is inferred from the pin-and-map step. |
| 0x4024 | store 32 bits | **established.** Low half (bits 31:0) of the statistics region address, written by `odsyInitPfRgn` (`odsy_diag.o`) after the 0x401c store and cleared with it; the same hi/lo split as the shadow-region pair at 0x4034 with its low word 0x403c. |
| 0x402c | store 32 bits | **established.** Statistics control word built by `gfP_OdsyPerfStat` (`odsy_diag.o`) from a 24-byte user argument: bits 3:0 and bits 4 to 6 from argument bytes 16 to 19, bits 10:8 from byte 21, bit 7 cleared, and bit 31 plus bit 27 always set. `odsyReset` zeroes it. |
| 0x4034 | store 32 bits | **established.** High half of the physical address of the hardware-shadow cache region: `gf_OdsyStart` (`odsy_init.o`) converts the 128 KB host buffer at record +880 and stores bits 47:32 here, `odsyReset` stores 0. The pairing with the context-save pair at 0x4004 makes it an address the board writes through (inferred). |
| 0x403c | store 32 bits | **established.** Low half (bits 31:0) of the shadow cache region address, stored by `gf_OdsyStart` (`odsy_init.o`) straight after the 0x4034 word and zeroed by `odsyReset`. |
| 0x4044 | store 32 bits | **established.** Master-id word of the second control pair, written once by `odsyReset` (`odsy_init.o`): the master widget id (record byte +792) in bits 7:4, bit 16, bits 15:14 and bits 3:2 set, and every other bit cleared by the 0x1ffff mask. Compare 0x4014, which carries the id in bits 23:20. |

0x404c: role **unknown**, **inferred** to be the upper diagnostic region address (by position, and because the status word's diagnostic-history bit beside its statistics bit points to a host region for history like the one at 0x401c). `odsyReset` stores 0 to it once, shadow at -31236, the first store after the glGet offset register at 0x4014. Which address bits the board keeps is an open question; routes tried: the offset scan of every in-scope binary.

0x4054: role **unknown**, **inferred** to be the low half of the address begun at 0x404c, as 0x4024 completes 0x401c. `odsyReset` stores 0 to it once, shadow at -31232, and it is read nowhere. The region's alignment is an open question; routes tried: the offset scan.

0x405c: role **unknown**. `odsyReset` stores 0 to it once, shadow at -31228, and no shipped binary reads it. Its bit positions are an open question; routes tried: the offset scan.

## FIFO ports and windows

| Offset | Access | Role and derivation |
|---|---|---|
| 0x110000 | store 32 bits or 64 bits | **established.** Command FIFO port: every FIFO word the kernel sends (the textport routines of `odsy_tport.o`, `odsyInitCfifo`) is a 32- or 64-bit store at this offset from the PIO base, and `gf_OdsyMapGfx` maps the page at client offset 0x10000 for privileged clients. |
| 0x118000 | store 64 bits | **established.** Context-save request port: `gf_OdsyPcxSwap` and `gfP_OdsySaveHwShadow` (`odsy_ctxsw.o`) store one doubleword here, (7 << 40) OR (slot << 16) OR 1, slot 127 meaning a save with no switch, after announcing the incoming record at 0x4004 plus 0x400c. |
| 0x120000 | store 32 bits or 64 bits | **inferred.** Second command-word window, mapped at client offset +0x4000 for every client by `gf_OdsyMapGfx` and never touched by the kernel. The `libGLcore` builds of both patches, in all three ABIs, store class-1 command words to it, 25126 constant-address sites in six binaries, for example at 0xda80774 in `AddConvolutionBorders`. The only other access is a 32-bit load at +0x4004 through a register that discards its result, straight after a tag word reaches the FIFO. Details are under [the 0x120000 window](#the-0x120000-window). |
| 0x201594 | load 32 bits | **inferred.** Identification or ready word that `odsyInitCfifo` (`odsy_init.o`) checks before it loads microcode: after storing the class-1 word 0x00010046 (block 0x046, no operands) to the command FIFO and waiting 2000 us, it loads the word from the 0x200000 window that `gf_OdsyMapGfx` hands to privileged clients and compares it with 0x003d0046, whose low half repeats the block id. A match enters the 12288-word microcode load (which opens with the header word 0x2e008380); a mismatch takes the branch at `.L00002584`, which clears a flag bit, detaches flow control and skips the load. Both hosts compare the same constant and no other routine reads the word. Its field split and the rest of the window are open questions in `docs/open-questions.md`; routes tried: every access with displacement 0x201594 in both kernels and byte searches of both microcode images. |
| 0x400000 | store 64 bits | **established.** Display FIFO port: 64-bit stores only, one per update, from 32 routines including `gf_OdsySetDisplayMode` (`odsy_retrace.o`) and `odsyBlankScreen`. Each doubleword is a header (type, address) and a data word for the display back end (`PBJ.h`, `DISPLAY.h`). |

## The 0x120000 window

Patch 4103 and patch 4104 `libGLcore` builds of IP30, all three ABIs, read with the instruction listings and `retools/tools/facts.py`. The 6.5.30m `libGLcore` builds of IP30 and IP35, in all three ABIs, have no store with displacement 16384 from a zero base; they send through a pointer.

- **established.** The patch O32 libraries address the window as the absolute constant 0x4000 with a zero base register: 4101 stores in each of the two builds (32-bit integer and single-precision float stores, and 64-bit float-register stores). The patch N32 and N64 libraries do the same, with 4231 stores in each of the four builds (3093 `sw`, 1085 `swc1` and 53 `sd`, the same split in the N32 and the N64 builds of both patches); the 6.5.30m libraries reach the command FIFO window through a pointer instead (no store with displacement 16384 from the zero register in any of the three IP30 builds). `AddConvolutionBorders` (0xda7e098) sends 0x10443 with operand 0xfa, 0x10046 twice and 0x10422 at 0xda80774 to 0xda80790; `ApplyMaterialF` opens with the same settle words, then 0x13c4d and the material words.
- By inference: The window is a second entry for the command stream, not a separate register file: the words are the settle words and block headers that go to the FIFO window, and the odydiags drawing streams use the +0x100000 window the same way. Whether it aliases the FIFO or feeds its own queue is an open question in `docs/open-questions.md`; routes tried: the three library ABIs' stores, the kernel mapping code.

## The 0x106c readers

Release 6.5.30m, IP30 and IP35 objects, both PROMs, `ide.IP30` and the user-space libraries. Every board load at offset 0x106c was found by disassembling every member of both `odyssey.a` files and each binary below with `mips64-linux-gnuabi64-objdump -d` and matching a load at displacement 4204 (and 0x106c as an immediate); each hit was read in context.

- **established. The kernel members that load 0x106c.** In the IP30 `odyssey.a`: `odsy_clip`, `odsy_ctxsw`, `odsy_ddrn`, `odsy_drawable`, `odsy_flow`, `odsy_init`, `odsy_map`, `odsy_retrace`, `odsy_sched`, `odsy_tport` and `odsy_ucode` hold 23 board loads. In the IP35 one, `odsy_flow`, `odsy_init` and `odsy_tport` hold 6. `IP30prom.bin` and `ide.IP30` hold the drain-loop loads described below; four further loads in IP30 `odsy_ctxsw.o` and one in IP35 read the context's shadow copy, not the board.
- **Units of bits 6:0: doublewords.** The board-manager waits for `24 - 9` before the nine-operand mode write and `24 - 12` before the cursor, blank-screen and mode writes (`odsy_brdmgr.o` and `gf_OdsySetDisplayMode` in `odsy_retrace.o`; not the buffer swap, whose routines call no level poll: `rrm.o`, `gf_OdsySchedSwapBuf` and `odsySwapBuffer` were disassembled), and the kernel waits for 15 and 12 (`odsy_flow.o` +0x40 callers; docs/kernel.md). Those constants read as free-entry counts against a display queue of 24 doublewords, **inferred** from the arithmetic. No shipped code compares bits 15:7 with a nonzero value, so the binaries cannot fix the command-side unit; it is **unknown**, and a doubleword count is only a guess. A read of the body of the level-poll routine would settle the sense of both fields.
- **unknown. What the count in bits 15:7 covers.** 9 bits reach 511 units; the memory FIFO is 32768 words (`odsyInitCfifo`, register id 0x6b1 = 256), so if the unit is a doubleword the field cannot be that FIFO's fill. Whether the count includes the memory FIFO is **unknown**; routes tried: all IP30 and IP35 readers (none uses a nonzero level) and the status register's empty and water-mark bits.
- **Drain waits.** Three kinds of loop wait for bits 15:7 to read zero with `us_delay(5)` and no iteration limit, then pulse 0x1084 as 0, 1, 0: `gf_OdsyInitialize` (`odsy_init.o` +0x13c0 IP30, +0x1728 IP35), `odsy_tpinit` (`odsy_tport.o` +0x16a8 IP30, +0x1634 IP35) and, on IP35 only, the reset path in `odsy_flow.o` +0x1e8 (after `gfx_flow_detach_me`, `odsy_teardown`; symbol `odsy_flow_await_returned_credits` covers it in the object's symbol table, but the code stores 0x107c and calls `gfx_flow_reset`, so the symbol's extent is suspect). `IP30prom.bin` has one drain loop at flash +0x64de4 and `ide.IP30` one at 0xa8000000208c58d8.
- **Detach read-backs.** Each detach stores 1 to 0x107c, pushes it, then loads 0x106c into a local that is never used. IP30 has 19 such sites (the other 18 besides make-current: `gfP_OdsySaveHwShadow` 2, `gf_OdsyPcxSwap` 2, `gf_OdsyValidateClip` 1, `gfP_OdsyClearBuffer` 1, `gfP_OdsySetDrawBuffer` 1, `gf_OdsyInitialize` 2, `odsyInitCfifo` 2, `gf_OdsyUnMapGfx` 1, `gf_OdsySchedSwapBuf` 1, `gf_OdsySuspend` 1, `gf_OdsyReleaseGfxSema` 1, `gf_OdsyDownload` 2, `gf_OdsyDestroyDDRN` 1). The make-current one is `gfP_OdsyMakeCurrent`, `odsy_drawable.o` +0xc4c: when `gfx_flow_am_i_attached` says the thread's flow control is attached, set the driver's detach flag, store 1 to 0x107c, `sync`, load 0x106c into a register, spill it, and call `gfx_flow_detach_me(flow, ctx)`. `gfx_flow_detach_me` (IP30 `gfxs.a(gfx_flow.o)` +0x620, IP35 +0x6b4) reads `a0` only, so the value is dead (the caller only spills it to its frame): the read orders the 0x107c store. IP35 reads 0x107c back in its make-current (`odsy_drawable.o` +0xc90), set-draw-buffer (+0x640) and most other detach sites, and 0x106c only in `odsy_fc_detach` (`odsy_init.o` +0x2030). The read-back as a store flush is by inference (from the position after `sync` and the dead result).
- **established. No other readers.** The IP35 PROM, `libGLcore` N32, O32 and N64, `odyssey.so`, `glx.so`, `libgl.so`, `libfm.so`, `odydiags` and `sting` contain no board load at 0x106c: their `4204` and `0x106c` hits are zero-base dispatch loads before an indirect call, enumerant immediates in a call table, and stack or context fields. `ide.IP30` also has a load and a store at 0x1068 in a diagnostic helper (0xa8000000208bcdc and 0x208bd0c) that is not a read of 0x106c.

## The IP35 PROM's board-register diagnostic (6.210)

Release: IRIX 6.5.30m `usr/cpu/firmware/ip35prom.img`. The image holds a gzip stream at file offset 0x8cbb0 that inflates to the BASEIO PROM, a 64-bit big-endian executable linked at 0x13000000. Its graphics start-up prints "Running Odyssey xtalk sanity diag..." and "Running Odyssey Buzz registers diag...". Both diagnostics walk a table of 40-byte records: an 8-byte register slot offset, a 32-bit bit count, a 32-bit mask, then the register's name as a string at +16. The two tables sit at file offsets 0xf4180 (four records) and 0xf4300 (thirteen records) of the inflated PROM. **established**: every slot, count, mask and name below is read from those bytes. The routine that walks them (around 0x130ba308) reads each register into a saved copy, stores two pass patterns built from the mask and bit count, and writes the saved values back; the code that prints "Error in reg ... Expected ... Actual" and the pass-by-pass compare were not located, so what the board returns for the patterns is **unknown**.

The table slots are 8-byte aligned. What this settles, each **inferred** unless marked:

- **XT_REQ_TIMEOUT is a 20-bit register.** The mask 0xfffff is the whole of the value `0x000fffff` that the PROM prints for it (below).
- **The names the PROM gives the registers the kernel only zeroes.** 0x108c, 0x109c, 0x10a4 and 0x10ac are, in the PROM's words, scan configuration, scan address high, scan address low and scan go: a scan facility of unknown function, of which a software-visible part is 13, 28, 32 and 14 bits wide. 0x107c is the flow-control detach bit (1 bit). 0x10bc is "swap enable select" and 0x10c4 "swap buffer B select set". **established** that these are the PROM's labels; what the hardware does with a scan go is **unknown: no shipped software depends on it**.
- **0x100c has ten bits.** Both pulse values the kernel writes (0x16d and 0x200) fit in that width.
- **0x1004 has thirty bits.** The kernel builds bits 22:19, 8, 5, 4:3, 2 and 1 only.
- Which registers read back is **unknown**: the diagnostic restores saved values, which suggests a read-modify-restore on every register of both tables, but no compare was traced.

Published output of the first diagnostic. Three PROM transcripts in two public pages (the IRIXNet forum thread "Tezro IO9/Configuration Oddities" and https://just.graphica.com.au/tips/sgi-o350-chimera-notes/) print, before any IRIX driver runs, `XT_REQ_TIMEOUT = 0x000fffff`, `XT_INTR_DST_HI = 0x00000000`, `XT_INTR_DST_LO = 0x00000000` and, in the IRIXNet transcript, `FLCTL_CONFIG = 0x0001c000`. Whether `0x000fffff` is a reset value or something the host chip or the PROM programmed before the print: **unknown**. No IP30 print was found, and the IP30 PROM image's uncompressed part carries none of these strings.

`FLCTL_CONFIG = 0x0001c000` has the value 28 in bits 16:12, the field that the kernel's 0x1074 word fills with the credit target number (`docs/kernel-flow-control.md`).
