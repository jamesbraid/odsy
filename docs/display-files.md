# Display-table files of the VPro install

Three kinds of file under `usr/gfx/ucode/` describe display timing, and every row below is read from the file it names by `scripts/display_files.py` (rerun it to regenerate the tables). All three share one container, a big-endian symbol database: version word 4, the tag `sdb `, a description string at +28, the field count at +128 and the name table's offset at +136, the values from +144, and a name table of (name length, name padded to four bytes, type, array length, value offset) entries. The types are integer (2 and 7), boolean (10), string (15), float (16) and double (17); an array stores its element count first. Every value is **established** from the file contents of the 6.5.30m install. What a field does in hardware is a separate question: the chip-level meaning of the clock and timing-generator words is in [display.md](display.md), and the 320-byte structure the X module builds from a file for the kernel is described there.

The readers are in the shipped programs. The X module `odyssey.so` reads the video formats of the VPro board and the combinations (its strings name both directories and the fields `OdsyFmtName` and `CmpFmtName`); the compositor test program, `sgcombine` and `dmconf` carry the same combination field names; `setmon` reads the video formats directory.

## Video formats of the VPro board

One row per `.vfo` file under `usr/gfx/ucode/ODSY/vof/`, written by the format compiler for the target `ODY_VTG`. Columns: active and total raster, frame rate (`FramesPerSecond`; a field-sequential or two-field file counts frames, so a stereo file at 96 fields a second says 48), pixel clock (`FormatInfo_PixelClock` in MHz), the display-controller porches in pixels (`DCDHorizontalFrontPorch`, `DCDHorizontalSync`, `DCDHorizontalBackPorch`) and the vertical ones in lines where the file stores them (stereo and interlaced files do not, and show dashes), scan and stereo flags from `FormatInfo_Interlaced` and `FormatInfo_Stereo`, field count, channels from `FormatInfo_DualHead`, the clock part's feedback divider (`ODY_PLL_FdBkDiv0`) and oscillator divider (`ODY_PLL_Osc_Div`), the timing generator's control word (`ODY_VTG_Control`), where the name table starts and how many fields the file has. The words are the values the X module hands to the board's clock and timing generator; their bit layout is **unknown** here.

## How the clock-part words give the pixel clock

Checked over all 71 files of the table above (`scripts/clock_words.py` reads each file's `ODY_PLL_*`, `ODY_AMI_PLL_0x0` to `0x4`, `ICS_AchievedFrequency`, `AchievedFrequency` and `FormatInfo_PixelClock` fields and exits nonzero on any mismatch); the compiler's own rules are in [video-format-sources.md](video-format-sources.md).

- **established (71 of 71 files, no mismatch).** The first clock part's words give the file's `ICS_AchievedFrequency` as 12 MHz x (`ODY_PLL_FdBkDiv0` + 8 + 256 x `ODY_PLL_FdBkDiv1`) / (`ODY_PLL_Osc_Div` - 126). The divider and oscillator columns of the table above are the low byte of the feedback word and the whole oscillator byte; the feedback word's upper four bits are `FdBkDiv1`, which the table omits (it is 0 to 6 in the shipped files). The 640x480 file: 55 + 8 = 63 over 156 - 126 = 30 gives 25.2 MHz. The 1920x1200 60 Hz file: 191 + 8 + 256 = 455 over 28 gives 195.0 MHz. The compiler's search allows a reference divider of 3 to 129, which is oscillator values 129 to 255 under this rule, and a feedback word of 12 to 4103, which is `FdBkDiv0` + 256 x `FdBkDiv1` + 8 with a four-bit upper field, so the two readings agree on both ranges.
- **established (71 of 71).** `ODY_PLL_LoopControl` bits 5:4 hold the post scaler (0 for 2, 1 for 4, 2 for 8, 3 for 16) and the loop oscillator, 12 MHz x feedback / reference x post scaler, lies between 196.6 and 499.2 MHz across the shipped files, inside the compiler's 125 to 500 MHz window; the phase-detector input, 12 MHz over the reference divider, lies between 0.093 and 0.48 MHz, inside its 0.008 to 0.5 MHz window. `ODY_PLL_InputControl` is 1 and `DPAControl`, `DPAOffset` are 0 in every file, `OutputEnables` is 1; only `LoopControl` varies (2, 18, 34 and 50, the four post scalers with the other bits fixed at 2).
- **established (71 of 71).** The second clock part's words give `AchievedFrequency`: 12 MHz x (`ODY_AMI_PLL_0x4` x 256 + `ODY_AMI_PLL_0x3`) / (`ODY_AMI_PLL_0x1` x 256 + `ODY_AMI_PLL_0x0`), and `FormatInfo_PixelClock` is that same frequency in hertz, rounded to the nearest integer. So the pixel clock column above is the second part's figure and the file's first-part setting reaches the same clock to within the rounding of its smaller dividers, at most 0.036 MHz apart across the shipped files (for example 64.9565 MHz against 64.9558 MHz for 1024x768 at 60 Hz); a board of revision 0 uses the first part and later boards the second ([display.md](display.md), clock parts), so the achieved clock of a given board differs from the column by no more than that.
- **inferred.** The 12 MHz is the clock input of both parts: the compiler fixes it, and every file reproduces its achieved value from it. Which board crystal or oscillator supplies it is **unknown: no shipped software or published source depends on it** beyond the compiler's constant. The part's own register numbers for `FdBkDiv0` to `OutputEnables` follow the structure order given in [display.md](display.md); the meaning of `InputControl`, `DPAControl`, `DPAOffset` and `OutputEnables` beyond their constant values is unknown, because no file varies them.
