# Interrupts, command FIFO credits and reset: graded readings

Release IRIX 6.5.30m. Builds: the IP30 and IP35 `odyssey.a` (`odsy_init.o`, `odsy_intr.o`, `odsy_flow.o`, `odsy_retrace.o`, `odsy_tport.o`, `odsy_ctxsw.o`), the IP30 boot PROM image, the IP30 standalone diagnostic monitor, and the published documents named per entry. Every offset is in the member or image named. **Established** is a whole routine or whole sequence read; **inferred** is a reasoned reading, with the reasoning; **unknown** has the routes tried, so that an emulator author can choose a value and document the choice.

The entries answer one question each, so an emulator author can tell which part of a behaviour rests on software and which part is a free choice.

## Interrupts

### The flags handler: one pass, acknowledged at the board

- `odsyFlagInterrupt` (`odsy_intr.o`, offset 0x1ac, 916 bytes, IP30 and IP35 alike): **established.** It loads the flags word at +0x1014 and the enable word at +0x1034 once, ANDs them, runs the low-water routine first when bit 9 is set, tests the remaining bits in a fixed order (logging or acting on each), and as its last step before returning stores the pending set to +0x101c. It contains no loop and no re-read of +0x1014, and it makes no access to any host-interrupt register. So the handler acknowledges at the board, once, and it relies on the board to raise a new delivery for anything that becomes pending afterwards.
- **Inferred:** the board must deliver one interrupt for each rise of (flags AND enables) from zero. The reasoning is the single pass above; nothing in the shipped code shows what the board does on the way down.
- **Unknown: whether the board sends anything when (flags AND enables) falls to zero.** Routes tried: both builds of the handler, the low-water and high-water routines, the reset and disable routines (all of them only store to the board), and the PROM and standalone images (they never enable a flag). Whether the host interrupt controller's pending bit needs a clearing write from the board depends on who clears it first, which no Odyssey object shows. An emulator that sends a set write on each rise and a clearing write on each fall is making a choice; nothing in the software depends on the clearing write.

### Flags raised while their enable is clear

- **Inferred:** a flag raised while its enable bit in +0x1034 is clear is held in +0x1014, and enabling it afterwards raises the interrupt. Two readings give this. First, the handler's teardown test is made on the raw flags word, before the enable mask is applied (`odsyFlagInterrupt`, the test against 0x39f02587 after the per-bit chain), which only makes sense if masked flags stay latched. Second, the high-water routine (`odsy_flow.o` `odsyHiwaterInterrupt`, offset 0xcc) clears flag 9, and when status bit 17 is already set it stores 0x200 into +0x1014 itself, then enables flag 9 through +0x1034, then returns. The low-water routine that wakes the sleeping writer runs only from that interrupt, so the enable of an already-set flag has to interrupt.
- **Unknown, the three routed sources (bits 18:16 of +0x1044): whether a source raised while its enable bit is clear is dropped or held.** No shipped code writes one of the three bits alone, in the kernel, the PROM or the standalone monitor (see the next section), so no shipped path raises a source in that state. An emulator that drops it is approximating.

### Bits 18:16 of +0x1044: the PROM images

Earlier readings of these bits did not scan the PROM images. Both IP30 images carry a copy of the driver's reset routine: the PROM at flash offsets 0x48830 to 0x48cc0 and the standalone monitor at 0xbfc40 to 0xbfed0. **Established** by reading both sequences in full: each stores +0x1044 exactly twice, both stores of zero (the PROM at flash 0x48a0c and 0x48c70; the monitor at 0xbfc58 and 0xbfebc), and neither image sets a bit of the register. The PROM text console takes no interrupts. So no shipped code of any kind writes one of bits 18:16 alone, so no shipped code of any kind writes one of bits 18:16 alone. A routed source is silenced only by the all-clear store.

- **The assignment, unknown:** which of bits 18:16 enables the retrace, DMA-done and software-sync sources is not shown by the binaries read here; the three handlers are numbered 3, 2 and 4 in `docs/buzz.md` section 6, and a guess that the bits run in the order retrace, DMA, software sync from bit 18 down has no evidence behind it. A read of the enable path of each handler in `odsyInitInterrupts` would settle it.
- **Unknown from the shipped binaries, which bit is which.** No binary separates the bits (all three are set together, cleared together). What would settle it is the same as before: a board with one bit cleared at a time.

### The retrace handler and +0x10d4

- `odsyRetraceHandler` (`odsy_retrace.o`, 716 bytes in both builds): **established.** Once per retrace interrupt it loads the 32-bit word at +0x10d4, XORs it with the driver's kept copy (record +28528) to get the set of window ids whose bit changed, then walks window ids 0 to 31. It stores the swap mask to +0x10b4 and 0 to +0x10bc (under a driver state flag), forces a swap that has waited more than 300 retraces, wakes video-sync waiters, and finishes by running the DMA tag check. It acknowledges nothing at the board.
  Build: `6.5.30-media/usr/cpu/sysgen/IP30boot/odyssey.a(odsy_retrace.o)`.
- **Inferred:** a set bit i of +0x10d4 says window id i is showing the second buffer, and the bit toggles when the board latches a pending swap for that id at a vertical retrace. The basis is the pairing with the set port +0x10c4 and clear port +0x10cc and the XOR against a kept copy. Which polarity is the first buffer rests on that pairing only.
- **Unknown:** what starts the retrace interrupts (the timing generator's start is the last write of the timing load, +0x2481 = 1, but no code shows the board's reaction), whether one arrives for every frame, and the jitter. A retrace source that is latched at the emulator's own frame callback is a model choice with that limit.

## Command FIFO and credits

### FIFO depth and level unit

- **Inferred (shipped values): the depth is 32,768 words (128 KB).** The five stored registers are inferred to be the FIFO's base, its size in 2-bytes-per-pixel tiles, a low-water mark, a high-water mark and a bypass switch. The shipped values fit that reading exactly: `0x6b1` = 256 tiles of 128 words is 32,768 words; `0x6b2` = 32192 is 32,768 - 576; `0x6b3` = 24144 is exactly three quarters of 32192 (4 x 24144 = 3 x 32192 = 96,576). The arithmetic is the only support: no 6.5.30 code reads the registers back, so the roles stay inferred. The two builds and the IP30 PROM's copy of the set-up (flash 0x486a8 to 0x48700; the standalone monitor loads the same constants at 0xbf8f4 to 0xbf940) send the same values.
- **Unknown:** whether the depth is the same on every board. The diagnostic reference (108-0314-003, memory tests) says the FIFO's data normally resides in SDRAM, so its size is a share of board memory. The porting guide (007-4271-001, "Command FIFO and Context Switching") says only that the FIFO holds about a millisecond of commands.
- **Inferred, level unit:** words. The diagnostic reference's error text "Timed out waiting for CFIFO level to drop below <num> words" names the unit, and the marks above are in words. That a doubleword store counts two follows from the host credit unit (one credit is an 8-byte doubleword, established in `gfx_flow.o`).
- **Established, arithmetic:** the host credit window is at most 256 credits (2048 bytes, 512 words) on both builds (`gfx_flow_alloc`), and the high-water poll and the hold work in credits, not in FIFO fill. A FIFO of 32,768 words is 64 times the window, so the window, not the FIFO, limits a writer that the board keeps up with.

### Credit return: when, and the 64-store rule

- **Inferred, the hardware shape:** a credit returns when the board takes a word into its FIFO, not when it has run the work. The FIFO holds about a millisecond of commands (published) and the window is 100 to 256 doublewords, so on a real board the window, not the FIFO, limits the writer, and a credit waits only for the store and its acknowledgement to cross the interconnect. No published figure gives that round trip. An emulator whose board thread is slower than the real board still has to return credits at FIFO entry, with a FIFO deeper than the window, and withhold credits only from the high-water mark (32,192 words) until the level falls below the low mark, if it wants the writer held only when the board has genuinely fallen behind.
- **Approximated, the 64-store rule:** crediting only the oldest 64 queued stores and holding the rest owed is a back-pressure device for a slow software board. It is not hardware behaviour and no software requires it. It is not a contract; it must carry its limitation (a slow board, not the FIFO, sets when the writer is held) and a test that fails without it.
- **Reconciliation with a model that has no credit flow at all:** a model that never holds the writer (credits are never owed, the counter never falls below the driver's bias) is the same as crediting at entry into an unbounded FIFO. It agrees with the inferred hardware shape whenever the real FIFO is deeper than the window, which the arithmetic above makes certain for the shipped drivers. It differs only in not holding a writer that outruns a slow board, which is a timing difference and invisible to IRIX except through guest-clock ratios.

### Full FIFO

- **Inferred:** software avoids filling the FIFO by credits and descheduling; a board-side overflow is a flagged fatal error (flag 27, and the teardown mask 0x39f02587 contains bit 27).
- **Unknown: what a store to a full FIFO does** (is it refused, held in the interconnect, or lost). Routes tried: the two kernels, the PROM and the diagnostic reference. The host processor interface's hold on a store when credits run short is described in the interface's own header comments (write-ready withdrawn below the bias); that is a host-side mechanism, not a board one.
- **Approximated:** an emulator that refuses a store when its own ring is full and lets the processor retry is not modelling the board's FIFO; it is modelling its ring.

### Water marks, status bit 15 and flag 25

- **Established:** the register names of status bit 15 ("above high water"), bit 17 ("below low water"), bit 16 (empty), flag bit 25 and flag bit 9 are in the driver's decode tables (`odsy_init.o` data tables). The kernel never tests bit 15 and masks flag 25 at start-up (`odsyInitInterrupts`, IP30 offset 0x275c, the enable chain clears bit 25).
- **Inferred:** `0x6b2` is the physical high-water mark and `0x6b3` the physical low-water mark, both in words of FIFO fill, and bit 15 and flag 25 compare the fill against the high mark, bit 17 and flag 9 against the low mark. Basis: the arithmetic above and the status-bit names. The 576-word margin below the FIFO's size would be room for words already in flight when the high mark is reached; that reading rests on the arithmetic only, and no shipped code tests it. What the board does at the marks (the comparison it makes, level or edge) is **unknown**.
- **Inferred, what follows for the host:** because the low mark (24,144 words) is far above anything the host window can queue, status bit 17 reads set whenever the board is keeping up. The high-water routine's path then finds bit 17 already set, raises flag 9 itself and enables it, and the low-water routine releases the hold at once. The writer sleeps for real only when the board has fallen 24,144 words behind.
- **Unknown:** hysteresis between the marks, whether flag 25 and flag 9 are level or edge, and the interrupt latency.

### FIFO set-up registers and 0x7f0

- **Established, value, order and count:** `odsyInitCfifo` stores, in this order, `0x6b0 = 0`, `0x6b1 = 256`, `0x6b3 = 24144`, `0x6b2 = 32192`, `0x7b5 = 1` (IP30 `odsy_init.o` 0x230c, IP35 0x2bc8; the pool of doublewords is read from the code), then the doubleword `0x7f0 = 1000000000` after the microcode load. The IP30 PROM's FIFO set-up (flash 0x48620 to 0x4882c) builds and sends the same six doublewords in the same order, with the memory-protect command in front, `0x7f0` last (flash 0x487f0). So the values are the same in the kernel, the PROM and both hosts.
- **Established:** nothing reads back any of the six registers, in the kernels, the PROM or the monitor.
- **Inferred, `0x7f0`:** a hardware sync timeout counted in board clocks, 10^9 clocks; its expiry raises flag bit 1 (named SYNC_TIMEOUT in the driver's flag table, which is in the teardown mask). Basis: the flag name and the value alone. **Unknown:** the board clock rate and what a sync that times out does besides the flag. A model without a timer cannot raise the flag; that is a choice, and the stock drivers never sync for long enough to need it.
- **Unknown, `0x7b5`:** the value 1 is stored last in the set-up; its role (leaving a bypass mode) is a reading of the value alone. Whether any 6.5.30 path stores it with another value: none stores `0x7b5` but the set-up.
- **Established, what a stored-only model must accept:** the PROM's text console and the kernel's textport both draw after these stores with no read-back, so a board that merely stores them keeps both working. The kernel's flow-control attach follows the stores and is independent of them: its bias and window are fixed per platform.

## Reset and initialisation

### The widget request timeout, offset 0x28 (+0x2c as a 32-bit access)

- **Established, no shipped writer:** neither `odsyReset` (IP30 `odsy_init.o` 0x1c04; IP35 0x23e0) nor the IP30 PROM's copy (flash 0x48830 to 0x48cc0; the helpers it calls for the clock and memory set-up and for the 0x100c pulse were not scanned) nor any other member of either `odyssey.a` stores to widget offset 0x28 or 0x2c. The scan covered every load and store through the board's register base in all members of both archives for constant displacement 40 and 44; none exists. Generic crosstalk code in the kernel was not scanned.
- **Established, a value was read from a real board:** a published verbose boot of a four-processor deskside Tezro with a V12 (forum post "Tezro IO9/Configuration Oddities", 22 July 2022, https://forums.irixnet.org/thread-3613.html) prints, from the base-I/O PROM's Odyssey sanity diagnostic and before any kernel runs, `XT_REQ_TIMEOUT = 0x000fffff`, `XT_INTR_DST_HI = 0x00000000`, `XT_INTR_DST_LO = 0x00000000` and `FLCTL_CONFIG = 0x0001c000`.
- **Inferred, as a reset value:** 0x000fffff. Nothing shipped writes the register, and the same 20-bit all-ones default is the documented reset value of the request timeout of other crosstalk widgets. The register is read-write: the diagnostic reference (108-0314-003, "Register Test") says its walking-zero and walking-one test covers `XT_REQ_TIMEOUT` (printed pages 11 and 12). That only the low 20 bits are writable is **inferred** from the width of the value and the sibling widgets.
- **Unknown:** what the timeout does (no code reads it) and the register's state after a link reset.
- Cross-reference: the same capture names `FLCTL_CONFIG` with the value 0x0001c000. The print does not give the offset. The driver's flow-control configuration word is at +0x1074 and carries the credit target number in bits 16:12; 0x1c in those bits is the transaction number the driver packs into the interrupt words. Which offset the name stands for is left to the entry that owns +0x1070 and +0x1074.

### The kernel's and the PROM's reset sequences

`odsyReset` and the PROM's copy store, in this order after the clock and memory set-up: +0x103c = all ones, +0x101c = all ones, then zero to +0x1044, +0x104c, +0x1054, +0x105c, +0x1074, +0x107c, +0x108c, +0x109c, +0x10a4, +0x10ac, +0x401c, +0x4024, +0x402c, +0x4034, +0x403c; then +0x4044 and +0x4014 with the master widget id; zero to +0x404c, +0x4054, +0x405c, +0x10bc; all ones to +0x10cc; and at the end zero to +0x34, +0x1044, all ones to +0x103c, zero to +0x1074, the pulse 0, 1, 0 on +0x1084, all ones to +0x101c, zero to +0x5c. **Established**, both images read in full. The reset never stores to +0x1034 (the enables are cleared through +0x103c), +0x1014 (the flags are cleared through +0x101c), +0x28, any command-FIFO word, or any drawing register.

### Board reset pulse, +0x100c

- `odsyLowLevelReset` (`odsy_init.o`, IP30 build, 980 bytes): **established.** One form stores 0x200 to the register (offset 0x1acc), waits 1,000,000 microseconds and never writes 0 back to the register: the zero stores at 0x1ab4 and 0x1ae4 go to the driver's shadow word in the board record (record offset 34216). The other stores 0x16d (built as 0x100, 0x40, 0x20, 0x8, 0x4, 0x1; the store is at 0x1b0c), waits 200,000 microseconds and does write 0 to the register (0x1b24). The form chosen depends on a field of the host chip's identity word (a revision above 4 takes the 0x200 form). The IP35 build has only the 0x200 form. This replaces the earlier statement that the timings were not re-checked.
  Build: `6.5.30-media/usr/cpu/sysgen/IP30boot/odyssey.a(odsy_init.o)`.
- **Established:** `odsyLowLevelReset` is called at the start of `odsyReset`, which then stores every register listed above and sends no drawing state. So a driver run does not depend on any state surviving the pulse.
- **Unknown:** which state a pulse clears. A model that clears all board state on a pulse is consistent with the driver; one that keeps state is too.

### Reset values of drawing state

For each item the software reads below, the point is the same: the board's reset value is unknown, and the shipped software sends the state before any drawing that depends on it.

- **Draw mask (block 0x024, 0x10424).** **Unknown** reset value. the kernel's textport sends the mask before every primitive (the text-port state set-up routine, `odsy_tport.o` 0x30: the word 0x10424, then the context's mask word, 12 or the caller's value), the buffer-select push (`odsy_drawable.o` 0x744) sends it and is run by the bind and the swap path, and the kernel's state replay after a lost context sends block 0x024. By inference, the X server sends it before the first draw, because its per-screen copy is compared against the new value and an all-zero copy never equals a real mask (3, 12 or 15); the copy's initial value was not traced. So no shipped code draws on the reset mask.
- **Colour mode (the select words 0x22008000 / 0x23008002 for RGB and 0x22008001 / 0x23008003 for index).** **Unknown** reset value. **Established:** the kernel textport's colour routine sends the index form before every fill (`odsy_color`, `odsy_tport.o` 0x9b8), and the public OpenBSD console driver sends the RGB form before its fill. **Inferred** from the X server's constant sites that its fill routines send one or the other before drawing. No shipped path relies on the reset mode. The four select words and their register numbers and values are in `BUZZ_DECODE.h` (`BUZZ_SEQ_WORD_COLOUR_*`).
- **Current colour index.** **Unknown** reset value. No shipped path draws in index mode without an index word, and the hardware shadow's initial content is whatever the kernel's reset leaves in host memory. An emulator's initial index is a choice; GL's own initial index is 1.
- **Depth function, write masks, clip rectangles.** **Unknown** reset values. The kernel's drawable bind pushes the clip words (block 0x204b with the full and empty rectangles) and the context restore replays the depth function and masks; the library validates its state before the first draw. A reset value of these is unobservable to IRIX.
- **First switch-in after board start replays everything.** `gf_OdsyStart` (`odsy_init.o`, IP30 build, 144 bytes) stores 127, the "no context" slot, into the board record's current-slot word at +820, and `gf_OdsyPcxSwap` (`odsy_ctxsw.o`) takes its full-replay path when that word is 127 or 0, or when the incoming context's saved word at +564 is zero: it calls `odsyRestoreXform`, `odsyRestoreRaster`, `odsyRestoreGfe` and `odsyRestartContext` in that order (labels 0x908 and 0x90c). **Established**, both routines read in the paths named. So the first context the kernel switches in sends the transform, raster and geometry-engine state wholesale, and no shipped path relies on the board's reset values of that state.
  Build: `6.5.30-media/usr/cpu/sysgen/IP30boot/odyssey.a(odsy_init.o)`.
- **Lighting constants and geometry program memory.** **Unknown** reset content. **Established:** the program memory is loaded before use, by the 12,288-word program of `odsyInitCfifo` and later by the microcode download, and the library loads lighting constants before a lit draw.
- **Depth plane contents.** **Unknown**; the depth-clear word is unknown (grades table). Nothing reads depth before a clear in the shipped software, so an emulator's fill is a choice.
- **Back-end entries (display tables, colour map, cursor, DAC, clock).** **Unknown** reset values. **Established:** the kernel writes every display mode, the cursor control word and the scanout entries itself during board start; the cursor's own reset is graded separately.

## Context switch inside a primitive

- The context switch and restart routines (`odsy_ctxsw.o`): **established.** `gf_OdsyPcxSwap` and `odsyRestartContext` both test the saved primitive type, the low four bits of the saved word at +128, against 11 (`andi 0xf; sltiu 11`): a type below 11 is an open primitive, which `gf_OdsyPcxSwap` drops with the words 0x10444 and 0; a type of 11 or more means none, and `odsyRestartContext` then uses 15. The member also holds eleven restore walkers, named `restorePoints`, `restoreLines`, `restoreLineLoop`, `restoreLineStrip`, `restoreTriangles`, `restoreTriStrip`, `restoreTriFan`, `restoreQuads`, `restoreQuadStrip`, `restorePolygon` and `restoreRect`, one for each type 0 to 10.
- **Inferred:** the board saves an open primitive of every type 0 to 10 (points through polygon and the rectangle form), because the kernel has a replay path for each; the order of the walkers matches the OpenGL primitive numbering used by the library. A model that reports an unsupported switch and saves "idle" for polygon and rectangle forms refuses behaviour the hardware has; it is a limitation of the model, not a board rule. Which of the saved words the board writes for each type is **unknown** (see the attribute replay entry in the datasheet).
