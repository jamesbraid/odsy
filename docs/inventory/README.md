# Inventory

Every file in this directory is generated by `scripts/inventory.py`. Do not edit them by hand: change the docs, the headers or `scripts/inventory-config.json`, then regenerate. The script is the same in every graphics workspace; what belongs to one graphics family (the files in scope and their roles, the register windows and how code reaches them, the token sources, the microcode images, the specification tables) is in the config. The same inputs give byte-identical tables.

Run it from the repository root with `root/` populated (`IRIX_FILES.md`), inside the toolchain environment of `AGENTS.md` section 5:

    python3 scripts/inventory.py

It also rewrites the block between the `inventory:begin` and `inventory:end` markers at the top of [../coverage.md](../coverage.md). Regenerate in the same commit as any doc or header change.

## Tables

Every table except `summary.tsv` ends with the same three columns:

- `status`: one of the five statuses below.
- `doc`: where the best mention is, `file#anchor` for a markdown page and `file:line` for a header.
- `section`: the heading of that page section, or the section banner of that header.

A table that does not apply to this family is still written, with its header row and no rows.

### binaries.tsv

One row per distinct file content in scope. An archive contributes one row per member; byte-identical files and members are read once.

| Column | Meaning |
|---|---|
| `binary` | install path under `root/`, with `(member)` for an archive member |
| `group` | the config group that put it in scope |
| `role` | `board-` or `shared-` followed by what it is: `kernel`, `library`, `x-module`, `x-server`, `tool`, `diagnostic`, `firmware`, `microcode` or `data`. `board-` means it serves this family only |
| `kind` | `object`, `executable`, `shared-object` or `data` |
| `abi` | `o32`, `n32`, `n64`, or `-` for data |
| `bytes` | size |
| `sha256` | first 16 hex digits of the content hash |
| `copies` | the other paths with the same content |
| `functions` | rows this binary has in `functions.tsv` |
| `access_sites` | register access sites resolved to an offset |
| `unresolved_sites` | register access sites whose offset could not be traced |

The status of a binary comes from its file or member name, written in backticks.

### functions.tsv

One row per (binary, function symbol). A function present in several distinct binaries has one row in each; `summary.tsv` also counts distinct names.

| Column | Meaning |
|---|---|
| `binary`, `role`, `abi` | as in `binaries.tsv` |
| `elf_section` | the section holding the code |
| `address` | the symbol value (0 when only a name is known) |
| `size` | the symbol size; when the symbol has none, the distance to the next function in the section |
| `name` | the symbol |
| `source` | where the name came from: `symtab`, `dynsym`, `mdebug` (o32 procedure table), `funcnames` (`.debug_funcnames`), `dwarf`, or `strings` (names found by pattern in a raw image) |
| `code_sha` | first 12 hex digits of the hash of the function's bytes, empty when they could not be read. A name with the same `code_sha` in two binaries has the same code there |

### mmio.tsv

One row per register offset the code reaches, in a window of the config.

| Column | Meaning |
|---|---|
| `window` | the register window, or the named region of one |
| `offset` | offset from the window base |
| `name` | the register a specification table puts at this offset, if any |
| `access` | `r` or `w` and the width in bytes, for each kind seen; `alias` marks an access through an alias the config folds back |
| `sites` | instructions or accessor calls that reach it |
| `binaries` | how many binaries reach it |
| `functions` | the functions that reach it, the first six by name |
| `evidence` | how the base was known: a constant address, a pointer field, a global, an argument, an accessor, `caller argument` (every call site passes the same window) or `callee return` (the callee always returns it) |
| `example` | the first `binary:function` by name |

### tokens.tsv

One row per command token or constant command word.

| Column | Meaning |
|---|---|
| `kind` | `token` (a named host command), `word` (a constant stored to a command register or FIFO), or a group the config defines over words, such as `block` |
| `value` | the token or word |
| `name` | the names the token tables give it |
| `register` | the register the word was stored to, for families whose words are register-specific |
| `detail` | fields of the word, or what a token table says about the token |
| `sources` | the tables and code scans that list it |
| `sites`, `binaries`, `example` | as in `mmio.tsv`, for words found in code |

### ioctls.tsv

One row per ioctl number a kernel dispatcher handles or user code sends.

| Column | Meaning |
|---|---|
| `number`, `hex` | the request number in decimal and hex |
| `table` | the dispatcher table that serves it, or the number range it falls in |
| `handler` | the kernel functions that handle it |
| `evidence` | `table` (a dispatch table entry), `handled` (a constant the dispatcher compares against), `boundary` (a compare boundary of a binary search, next to a case but not always one), `sent` (a constant argument of an ioctl call), `constant` (a constant of the family's ioctl pattern built anywhere) |
| `senders` | the functions that send it |
| `binaries`, `example` | as in `mmio.tsv` |

### ucode.tsv

One row per microcode routine, label, symbol or dispatch entry.

| Column | Meaning |
|---|---|
| `program` | the microcode image |
| `kind` | what the row is, from the config (`symbol`, `label`, `dispatch slot`, `host entry` and so on) |
| `address` | address, record number or slot index |
| `name` | the symbol or label, if the image has one |
| `detail` | sizes, handlers, flags |

### spec-registers.tsv

One row per register a specification or a shipped register table lists.

| Column | Meaning |
|---|---|
| `spec`, `table`, `page` | where the register is listed |
| `window`, `offset` | where it sits, in the windows of `mmio.tsv` |
| `name` | its name there |
| `count`, `stride`, `width`, `rw` | array length, array stride in bytes, width in bits, access |
| `reached_in_code` | `mmio.tsv` rows inside it |

### summary.tsv

One row per table, plus `functions (distinct names)`, which counts each function name once at its best status, and then one row `functions in <binary>` per binary that has functions.

| Column | Meaning |
|---|---|
| `table`, `rows` | the table and its row count |
| `understood`, `located`, `named_only`, `undocumented`, `no_software_dependency` | rows at each status |
| `understood_distinct` | different sentence skeletons behind the understood rows |
| `templated` | rows held at `located` because their entry's skeleton is over the template cap |
| `pct_understood` | understood rows as a percentage |
| `pct_located_or_better` | understood, located and no-software-dependency rows as a percentage |
| `pct_mentioned` | every row except `undocumented`, as a percentage |
| `pct_done` | understood and no-software-dependency rows as a percentage |
| `unresolved_sites` | for `mmio`: register access sites whose offset could not be traced |

## Status

A mention is not understanding. The status of an item is the best of the entries that mention it, and an entry earns its status only for its subject. An entry is one table row (its own cells only, never the header), one list item with its continuation lines, one paragraph, or one header comment paragraph with the definition it sits on. A fenced listing restates its subject and never earns more than `named-only`.

- `undocumented`: no entry mentions it.
- `named-only`: mentioned, but the entry does not reach `located` for it. This covers a bare mention; an item the entry only mentions because its subject is another item; a mention on a line that names more than three items (distinct identifiers, plus numbers written as a list), because a list documents none of its members; an entry with no citation of its own; an entry with a citation but no label; an index file (`AGENTS.md`, `README.md`, `IRIX_FILES.md`, `docs/coverage.md`, `docs/open-questions.md`); a committed table; and a fenced listing.
- `located`: the entry carries a citation of its own and says the behaviour is `unknown`, and gives where the item is (an address, offset or size, records, callers or sites). Identity and location are established, what it does is not. A subject whose entry is templated (below) is at most this.
- `understood`: the entry has a label (`established` or `inferred`), at least six plain words, which is the floor for stating a role and a hardware effect, a citation of its own, and no `unknown` anywhere in it. The words are not read for meaning: check the cited section.
- `no-software-dependency`: the paragraph says "no shipped software or published source" depends on the fact (`AGENTS.md` section 6) and names the routes tried (the word "routes" or "tried"). The row is finished. Like every other status it goes to the entry's subject only.

A row is done when it is `understood` or `no-software-dependency`. The repository is finished when every row of every table is done.

### Subject

An entry credits one item, its subject:

- a table row: the first identifier in the first cell that holds one. An identifier is a backticked span, a code-like word (an underscore, a digit or an inner capital) or a hex number. A plain decimal counts only in a column headed ioctl, entry, record, routine, slot or request, so that a row-number column is skipped. The header row has no subject;
- a list item or paragraph: the identifier it starts with, after any bullet and emphasis. When it starts with prose, the first identifier of the heading above it;
- a header definition: the name it defines and its value, for the comment above it and the one beside it. A comment on a line of its own has no subject.

Every other identifier, number or file name in the entry is a mention and stays `named-only`. One exception: a command word stored to a register is a pair, so the entry whose subject is the register credits the word it states.

### Citation

A derivation citation must tie the entry to its own item. Each of these counts, and none counts when it is the subject itself:

- an offset (`+0x1a4`, "offset 0x40"), or a hex address after "address", "at", "entry", "record" or `@`, or a hex number alone in a column headed offset, address, entry or record;
- a callee or caller written in code (`calls` or `called from` followed by a backticked name);
- a source file or a path with at least two slashes (`odsy_init.c`, `libglcore/asm/ODYSSEY/x.s`);
- a binary or object file name (`odsy.o`, `libGLcore.so`) together with a backticked routine of it other than the subject.

A release or patch number (`6.5.30m`, `patch 4103`), a binary name alone, and a link to another page are not citations: every item of a build shares them.

### Templated entries

Mask the identifiers, file names, numbers and punctuation of an entry and lower-case what is left: that is its sentence skeleton. When more than 5 entries (`TEMPLATE_CAP` in the script) share one skeleton, counting table rows, list items, paragraphs and header comments across every document read, all of them grade at most `located`. One sentence pattern repeated over many names is bulk, not a separate derivation for each. `summary.tsv` counts the rows this capped in `templated`. Two entries that differ by a word of prose have different skeletons, so the cap catches mechanical repetition, not paraphrase; read the `understood_distinct` column for that.

### Builds of one function

A function row exists once per binary. When a name is defined with different code in several binaries, an entry credits it only in the binary the entry names: by its path as `binaries.tsv` spells it, from any directory down (`usr/gfx/arch/IP32CRM/libGLcore.so`, or just `libGLcore.so` when no other binary has that name), or for an archive member by `gfxs.a(gfx_flow.o)` or the member alone. The name must pick out one binary: a path that matches several builds with different code names none of them. Builds with the same `code_sha` for that name have the same code and share the credit. Every other build is at most `located`. A name that has the same code wherever it is defined needs no citation of a binary. `summary.tsv` has one row, `functions in <binary>`, per binary with functions.

### Distinct counts

`understood_distinct` in `summary.tsv` is the number of different sentence skeletons behind a table's understood rows. A table whose understood rows rest on few skeletons is templated bulk even when no skeleton is over the cap.

How a mention is found:

- Names: an identifier in backticks or a code block, any identifier that looks like code (an underscore, a digit or an inner capital) anywhere in a line, and any identifier in a header. A short or all-lower-case name (`save`, `window`) also reads as English, so for those only backticks, code blocks, header code and the call form `name()` count. Write the name exactly as the binary spells it.
- Register offsets: a header definition of the value, `+0xOFFSET`, the full physical address, or a bare hex value on a line or under a heading that says what it is (register, offset, field, FIFO, command and so on), in the docs the config lists for that window. A register a specification table names, whose name is documented, takes that status for the offsets inside it.
- Decimal numbers: a context word (the config's list, or for ioctls "ioctl") within the three words before the number or the one after it, or, for a table cell holding only the number, in the column heading. A number elsewhere on the line, or in the section heading, does not count.
- Tokens and words: the token's names; for a word stored to a register, its value within two lines of the register's offset or name; for other words, the value on a line or under a heading that says what it is.
- Ioctls: the handler names, and the number (decimal, or hex) in the config's ioctl docs on a line or under a heading that mentions ioctls.
- Microcode: the symbol or label; a routine that has no name, by its record number with "entry", "routine" or "record" next to it, as above.

The status measures what an entry claims and cites, not whether it is right: read the cited section. Generated listings, disassembly and verbatim dumps of a binary's own tables restate the binary and are not read.

## How register accesses are found

Each function of every ELF file in scope is disassembled and replayed over its basic blocks to a fixed point. A register or a stack slot keeps a value across a join only when every path into the join agrees; when the paths agree on the window but not the offset, it keeps the window with an untraced offset. Constants are followed through `lui`, `ori`, `addiu`, shifts, adds and loads from read-only data, literal pools and the GOT. A value becomes a register window base when the config says so:

- `constant`: an address in a fixed range (a physical window, a kernel segment address of one, or a fixed user mapping);
- `field`: a load from a given displacement, the pointer field a structure keeps the base in;
- `global`: a load from a given offset of a named global;
- `argument`: a register on entry to a named function;
- `return`: the value a named function returns.

The replay then learns two more sources inside each file: a function whose every call site passes the same window in an argument register starts with it, and a call to a function that always returns a window base yields it. An accessor (a function that takes a register address in an argument) counts as an access at that address.

A load or store through a window base is a site. When its offset is a constant it is a row of `mmio.tsv`; when the base is a window but the offset could not be traced (an index, a loop counter, a value passed in from elsewhere) it is counted as unresolved, per binary and window, and the headline in `coverage.md` gives the share. A loop's first iteration still yields its offsets, and the site is counted as unresolved as well, since the later iterations are not placed.

## What the scan does not see

- An access through a pointer the config does not name, and that is not passed in or returned by a function in the same file, is neither a row nor an unresolved site. A register window reached that way is missing from the count altogether, so add the pointer to the config when a reader finds it.
- Calls through function pointers are not followed, so an ioctl sent that way is missed.
- Functions that no symbol table names (stripped local functions) have no row in `functions.tsv`; a stripped binary's code is still scanned, in pieces between its exported symbols.
- Token words built from variables are not rows.
