An entry that exhausts all five is relabelled "unknown: no shipped software or published source depends on it" in its owning file, with the routes listed, and removed here.

## Published sources, route tried (2026-10-29)

Patents, SGI manuals and white papers were searched for every open entry below; [published-sources.md](published-sources.md) holds the identity and facts of each. Result by entry, so no later reader repeats the route. Every patent fact is inferred, because no patent names the chip.

- [software now] **Colour interpolation arithmetic** (Raster rules): the patents describe perspective-corrected barycentrics from reciprocal-area-scaled edge distances, an interpolated 1/w correction, 12-bit bilerp modules and a recursive 4K x 4K subdivision. None gives widths or rounding. A numeric rebuild of the first `blend.SUM` panel with the weights, denominator, reciprocal, plane slopes or a uniform error rounded at 8 to 24 bits left the residue unchanged or worse (no variant below 1,082 of about 1,100); the stored bytes run high more often than low. Not yet tried: 12-bit colour modules and subdivision-order evaluation. Same question as the raster-rules colour entry below.
- [software now] **Texture arithmetic**: the quad level of detail is the base-2 logarithm of the larger diagonal difference of s and t (inferred). Filter-weight and sub-texel widths are in no published source. Same question as the BUZZ texture arithmetic entry below.
- [software now] **Remaining operation codes**: the patents' scalar stage has an inverse square root, a negate, an exponent and an arc-sine; three of those match codes already read. Which table function codes 3 and 0xb are stays open: the exponent or the arc-sine.
- [software now] **Value-3 marks and the loop entries**: the patents say the transform engine has no run-time branch and runs fragments chosen from a program table. A mark deciding between two entries is more likely a table-building step. Not established. Same question as the microcode value-3 entry below.
- [hardware only] **Raster tie rule on a shared edge**: a patent says each shared subpixel has exactly one owner, decided by consulting the neighbouring pixels of the quad; which side is not stated. Recorded, not scheduled: no shipped stream or stored frame draws a shared edge with a tie, and an emulator run shows only the emulator. Silicon test: with depth test, blending, antialiasing and dithering off and a one-colour 8-bit window, clear the window to black; draw two triangles that share an edge passing exactly through pixel centres, with every vertex on a half-integer window coordinate (rectangle corners at x.5, y.5 split by its diagonal; also one split by a vertical and one by a horizontal edge through centres), each filled by logic-op XOR with a white constant so a pixel drawn twice returns to black and a pixel never drawn stays black. Read the window back with `glReadPixels`. A pixel on the shared edge that is white was drawn once; black means a hole or a double hit, and the count of holes against doubles is told apart by repeating with ADD blending at 50% grey (grey 128 once, 0 for a hole, 255 for a double). Repeat with the two triangles drawn in the opposite order and with each triangle's vertex order reversed. Which neighbour owns an edge pixel (left against right, top against bottom, and whether it depends on the vertex order) is read off the white pixels of the four runs.

- [software now] **How the board packs and reads an ICC texture level** (indices 48 and 49, [texture-formats.md](texture-formats.md), "How an ICC level's texels are packed"): the packing of a texel in a booked 2- or 4-byte element, the order of texels in it, whether the half-width primary-level pitch and the full-width detail-level pitch describe the same density, and what the host-conversion fallback writes for host data in the published block layout.
