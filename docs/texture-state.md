# Texture state the library sends: level table bounds, wraps, environment words, colour table, 3D levels

Release IRIX 6.5.30m, `usr/gfx/arch/IP30ODSY32/libGLcore.so` (N32); addresses are N32. The o32 and 64-bit builds and the IP35 builds were not re-read for these entries, so each is for the N32 IP30 build and the other builds are **inferred** the same (the four format routines of [texture-formats.md](texture-formats.md) are identical in all of them, which says nothing about the routines below). Names are the routine names of the N32 library's debug information. Every entry says what the library sends. What the board does with it is a separate statement, and where no software shows it the entry says **unknown** and names what would settle it.

## Level table: which entries and which bits the library writes

The level table is 64 entries of three words, sent as blocks `0x0e80` + i (context shadow +31968 + 12 i; [texture-formats.md](texture-formats.md) names the fields of word 1).

**Entries written.** *Established.* `__glOdysseyTextureActivate` (0xd9d1f90 to 0xd9d2540) writes primary entries `level - base level`, one for each level from the base level up to the last level (the loop index is formed at 0xd9d2134 to 0xd9d213c), and, for a detail magnification filter, entries `64 - n` to 63 (the loop at 0xd9d2410, n the negated detail level, at most 15). The level number is limited before it reaches the table: `CheckTargetLevel` (0xd9d3a60 to 0xd9d3b18) returns the invalid-value error for a level below 0 or above the context word at +3732, and context creation stores 15 there (0xd96f4c0). A primary level count is therefore at most 16, entries 0 to 15, and detail entries sit at 49 to 63; the two ranges cannot meet and no entry above 63 is written. Entries 16 to 48 are never written by activation. So the model's refusal of an entry past the table is a model rule: no library state reaches it.

For a 3D target the last level is replaced by the base level before the table is filled (the `movz` pair at 0xd9d1fe0 to 0xd9d1fec compares the target with `GL_TEXTURE_3D`, 0x806f), so only entry 0 is filled; see "3D textures" below.

**Bits written.** *Established* for the three routines that store the level words, each read for its stores to the three words:

| Routine | Word 0 | Word 1 | Word 2 |
|---|---|---|---|
| `__glOdysseyTextureActivate` | bits 28:0 (0xd9d2160) | bits 25:20 (0xd9d217c), 31:30 (0xd9d2194), 11:0 (0xd9d2108) | bits 11:0 (0xd9d2130) |
| `DownsampleTextureThruHW` (0xd9d11a0), descriptor 60 only | bits 28:0 (0xd9d1468) | bits 31:30, 28:26 and 25:20 (0xd9d14cc), 11:0 (0xd9d14ec) | bits 11:0, cleared (0xd9d14dc) |
| `__glOdysseyImageMovePixelsTexture` (0xd9bbff0), descriptor 60 only (stores at 0xd9bc1b8 to 0xd9bc36c) | bits 28:0 | bits 31:30, 28:26, 25:20 and 11:0 | bits 11:0, cleared |

Every store is a read-modify-write with a mask, so bits the routine does not name keep their previous value. A search of the whole N32 library assembly for stores to word 1 at its context offsets (`sw`, `sd` and `sh` with an offset of 31972 + 12 i) finds only these three routines. Therefore bit 29 and bits 19:12 of word 1 are **established** as never written by these routines and **inferred** never written by any code of the library: a store through a pointer formed another way would not show, and the context's creation was not traced for a nonzero initial table (**inferred** zero). Bits 28:26 are written only by the move and the mipmap builder, from the texture-offset code of the buffer (0 or 2). What the board does with a set bit 29, set bits 19:12 or a level descriptor past entry 63 is **unknown: no shipped software or published source depends on it**. Routes tried: the writers above, the kernel's context-restore replay (plain loads and stores, no mask), the X module (no level descriptor), the published patents (texture cache and tile sizes only), the porting guide. What would settle it: a board's behaviour with those bits set, which no software here shows.

One value is written differently: when the row in 16-texel units comes out as exactly 4096, activation stores 1 in the pitch field instead (0xd9d20fc, 0xd9d21e0 to 0xd9d21e8). A texture 65,536 texels wide would be needed, and `IsLegalRange` (below) stops at 32,768, so the case is **established** as unreachable from a texture the library accepts.

## Wrap modes are independent per axis

*Established.* `__glOdysseyTextureSetSWrap` (0xd9d5bc0), `...SetTWrap` (0xd9d5c70) and `...SetRWrap` (0xd9d5d20) each take one enumerant and write one axis, with no look at the other two:

| Enumerant | Word 4 field (S bits 13:12, T 11:10, R 9:8) | Size word bits 23:18 of that axis |
|---|---|---|
| `GL_REPEAT` (0x2901) | 0 | 0 |
| `GL_CLAMP` (0x2900) | 2 | 0 |
| `GL_CLAMP_TO_EDGE_SGIS` (0x812f) | 1 | 1 |
| `GL_CLAMP_TO_BORDER_SGIS` (0x812d) | 3 | 63 |

Any enumerant outside the four raises GL error 0x500. The R setter reads `GL_REPEAT` for the sampler unless the target is 3D (the stored value is kept at object +36, the value the sampler gets at +40). So the library sends every combination of repeat, clamp, clamp to edge and clamp to border on the three axes, and a mixed state (for example S clamp, T repeat) reaches the board as the two fields and nothing else. What the board does with a combination the stock programs do not send is **unknown**: the diagnostic simulator frames of [raster.md](raster.md) use one wrap on every axis, and the demos seen draw one wrap on all axes. What would settle it: a mixed-wrap drawing on a board.

## Texture environment block `0x141b`

The block is five words from context +31920, sent at 0xd9684bc; the mode word is the first and the colour is words 1 and 2.

- *Established* (`__glOdysseyTextureSetOp`, 0xd9d7ad0 to 0xd9d7d38, read in full). Bits 2:0 of word 0 are set to 1 for `GL_REPLACE` (0x1e01) and `GL_REPLACE_EXT` (0x8062), 2 for `GL_MODULATE` (0x2100), 3 for `GL_DECAL` (0x2101), 4 for `GL_BLEND` (0x0be2) and 5 for `GL_ADD` (0x0104); any other enumerant raises 0x500. No format test: decal is accepted for every base format, so a decal of an alpha, luminance or intensity texture reaches the board (GL leaves the result undefined, so what the board shows is **unknown**). The other bits of the word are never written by the setter (texture driver initialisation sets bits 2:0 to 2, modulate, at 0xd9cf8e4 to 0xd9cf8fc).
- *Established.* `GL_ADD` writes 0xfff to the four environment colour channels (0xd9d7b60 to 0xd9d7b88). `GL_TEXTURE_ENV_COLOR` converts four floats to 12 bits per channel through the 12-bit converter (`floatTo12`, 0xd9cfa20) and stores them in words 1 and 2.
- *Established* that words 3 and 4 of the block (context +31932 and +31936) are always zero for GL texturing: the texture driver initialisation stores zero to both (0xd9cf8dc, 0xd9cf8e0) and no setter of `ody_texture.c` stores to either; the only other writers are the image-chain routines that save and restore the whole block (`__glOdysseyImageSaveUserBuzzRasterState`, `__glOdysseyImageLoadBuzzRasterState`, `RenderFunc_PixelTexture`), which copy it from the saved block, itself a copy. Their meaning is **unknown: no shipped software or published source depends on it**.
- `GL_PHASE_SGIX` (0x832a) is not an environment mode. It is a minification or magnification filter: the filter setters (0xd9d5e40, 0xd9d61a0) store filter code 1 and set bit 17 of the sampler word 4 whenever either filter is 0x832a, as [libglcore-odyssey-reads.md](libglcore-odyssey-reads.md) records. What the board does with bit 17 is **unknown**.

## Wider limits the library applies

- *Established.* A level's size less twice its border must be zero or a power of two no larger than 0x8000 (32,768), else `GL_INVALID_VALUE`; a border other than 0 or 1 makes the check return false with no error raised there (`IsLegalRange`, 0xd9d3070 to 0xd9d30e8, read in full). The ceiling is the library's, not a board measurement, and the board's memory bounds a real texture lower. Compare "textures up to 32,768 on a side if they fit" in the published white paper ([published-sources.md](published-sources.md), source 6) and "32K (up to board memory size)" in the porting guide, which agree.
- *Established* (library, from the setters read for [texture-formats.md](texture-formats.md)). The minimum and maximum LOD words are limited to -15 to 15 before they are written, so the library never sends a value in the 16 to 31 range that the 14-bit field could hold. What the board does with such a value is **unknown: no shipped software or published source depends on it**.

## Texture colour table and the 0x3e00 and 0x3e10 uploads

`GL_SGI_texture_color_table` is in the library's extension string ([opengl.md](opengl.md)), and the porting guide lists "12-bit RGBA post-interpolation tables" (007-4271-001 printed page 18) and the extension (page 31).

- *Established* (`__glOdyim_ColorTableSGI`, 0xd98d560 to 0xd98da70). For target `GL_TEXTURE_COLOR_TABLE_SGI` (0x80bc) and its proxy (0x80bd) a width of 0 or a power of two up to 256 is accepted; above 256 the real target raises `GL_TABLE_TOO_LARGE` (0x8031, 0xd98d6f4) and the proxy reports 0. The other color-table targets accept 4096. The application's table is first loaded into the library's own colour table through a context call (the slot at context +12720, 0xd98d72c), then the lookup builder `__glOdysseyStoreLUT` (0xd9c3c50, kind 1 for 0x80bc; called at 0xd98d8e0) builds the board table, and the routine copies the record's 512 words over the context shadow at +0x8d7c (the loop at 0xd98d960), sets bits 22:20 of the sampler word 4 (context +0x7cd4) from the record's code (0xd98da08 to 0xd98da28) and raises dirty bits 0x400000 and 0x200 (0xd98da2c to 0xd98da3c). Validation sends the shadow as the `0x3e00` and `0x3e10` uploads on dirty bit 0x400000 (`__glOdysseyValidateHardware`, the loop at 0xd968c20 to 0xd968d38: sixteen words to `0x3e00 + i` from context +0x8d7c, then sixteen to `0x3e10 + i` from +0x917c, for i = 0 to 15), the same uploads the pixel lookup step sends. So the table behind the first two upload blocks is **established** as the texture colour table, shared with the pixel colour-map lookup (the lookup builder's other kinds write the same shadow).
- *Established.* The record's code is the table's component set, the same numbering as the texture class: `StoreLUT` stores 1 for alpha (internal format 0x1906), 2 for luminance (0x1909), 3 for luminance-alpha (0x190a), 4 for intensity (0x8049), 5 for RGB (0x1907) and 6 for RGBA (0x1908, the default) (stores at 0xd9c437c to 0xd9c4430). Sampler word 4 bits 22:20 are therefore the table's component class, and bit 0 is the enable: `glEnable(GL_TEXTURE_COLOR_TABLE_SGI)` sets it (the case at 0xd957520 of `__glOdyim_Enable`, 0xd956bc0) and disable clears it (the case at 0xd95e6f0 of `__glOdyim_Disable`, 0xd95dc70), and texture validation keeps both fields from the context (`__glOdysseyValidateTextureState`, 0xd9d2cc4 to 0xd9d2cd8, which merges the object's word with the context's bits 22:18 and 0). The colour-chain lookup step sets the same bit for pixel maps (`RenderFunc_Lut`, 0xd990eb0; see [pixel-paths.md](pixel-paths.md)). That bit 0 enables the table and bits 22:20 say how to read it is the library's use of the fields (**established**); that the board does so is **inferred**: nothing else reads them. Bits 19:18 are not written by this routine and their source was not traced.
- *Established* (`__glOdysseyStoreLUT`, the 256-entry branch at 0xd9c41b4 to 0xd9c42dc, read in full). The order of the 256 entries in the upload words: the record holds two 256-word tables back to back, the first with word n = (red lane of entry n in bits 23:12, green lane in bits 11:0) and the second with word n = (blue in 23:12, alpha in 11:0); bits 31:24 of each word are kept from the record. Upload `0x3e00 + i` is words 16 i to 16 i + 15 of the first table and `0x3e10 + i` the same words of the second, so entry n sits in upload i = n >> 4 at word n & 15 of both blocks. Each lane is the 12-bit value `ResizeLUTData` made. After its 512 data words the record holds the entry-count code (1 for 256 entries, 2 otherwise, stored at 0xd9c3d64) and then the component code (stored at 0xd9c437c to 0xd9c4430). The branch for a 4096-entry table (0xd9c3d70 to 0xd9c3ed8) uses a different, tiled order and was not read in full; it is not the texture table.
- *Established* (`ResizeLUTData`, the format branches at 0xd9c48c0 to 0xd9c4c4c). A table whose format lacks a component gets an identity ramp in that lane, not zero: for an alpha table the red, green and blue lanes are the ramp and the alpha lane the table; for luminance red, green and blue are the table and alpha is the ramp; for RGB alpha is the ramp; for luminance-alpha red, green and blue are the luminance and alpha is the table's alpha; for intensity all four lanes are the table; RGBA takes four elements. The ramp is `trunc(0.5 + 4095 i / (n - 1))` for n entries, with i the first output index of the run that shares one table element (the quotient is computed once a run, at 0xd9c4878 to 0xd9c4890, so for a table narrower than n the ramp is a step function too). That is the pass-through a lookup applies to a component the table does not supply.
- *Established.* The board never receives fewer than 256 entries from a texture colour table. `ResizeLUTData` (0xd9c4440, the colour-table branch at 0xd9c47c8) expands a table of w entries (w a power of two up to 256) to 256 on the host: it steps `256 / w` and fills output entries from the previous end up to `trunc(sum + 0.5)` with the table's value, so entry k covers outputs `[256 k / w, 256 (k + 1) / w)`; the value of each channel is `trunc(4095 x + 0.5) & 0xfff`. So a table narrower than 256 is a step function by replication, done by the library; whether the board interpolates between its 256 entries or truncates the index is **unknown: no shipped software or published source depends on it**. Routes tried: the lookup builder and every sender of the table, the patent's texture look-up tables (it names the unit and gives no index rule).
- *Established.* The library does not look at the texture target when it enables the table or sends it, so a volume texture is sent with the same two fields as a 2D one. What the board does for a 3D texel lookup is **unknown**.
- `0x3e20` (dirty bit 0x040000) and `0x3e30` (0x080000). A scan of every store to the dirty word (context +26976, all N32 `ODYSSEY` objects) resolved the stored value through `lui`, `li` and `ori` chains where the chain was in the same routine, and found no store that includes either bit (the one all-ones store, +26980 at context creation, is a different word). Stores whose value arrives through other registers were not resolved. The upload code for both tables exists (0xd968618 for `0x3e20`, 0xd9686b8 for `0x3e30`), so the tables are sent only if the dirty word holds the bit. **Inferred** that no code of the library sets either bit; the dirty word's initial value was not traced (**inferred** zero). What the two tables hold, and whether a board expects them, is **unknown: no shipped software or published source depends on it**.

## 3D textures and the level table

*Established.* Activation fills one level-table entry for a 3D target, the base level (0xd9d1fe0 to 0xd9d1fec: the last level is replaced by the base level when the target is 0x806f), and the filter setters do not read the target: `__glOdysseyTextureSetMinFilter` (0xd9d5e40) writes the filter and its code for 3D as for 2D. So a 3D texture whose application asked for a mipmap filter reaches the board with a mipmap filter code in word 4 and a single entry in the level table, which is the state the captured `0x40` and `0xa0` filter fields show. The library does not change the filter to nearest or linear, and no software fallback is taken by the setters.

What the board does with a mipmap filter on a one-entry table is **inferred** to be a plain nearest or linear read of level 0: the porting guide says "Mipmapping is not supported with 3D textures. Applications which supply a mipmap pyramid and request a `*_MIPMAP_*` mode will automatically use NEAREST or LINEAR" (007-4271-001, printed page 18), and the texture-tree patent says 3D mipmapping is not implemented and no level of detail is computed for 3D. Two published statements and the library's one-entry table agree, and no source shows a board reading entries above 0 for a 3D texture. Any model that derives further volume levels from slice spacing is going beyond what the library names.

## Colour-index mode

*Established.* The texture code of the library (`ody_texture.c`) and the hardware validation (`__glOdysseyValidateHardware`, 0xd968180) contain no branch on the colour-index visual flag (context byte +3221, which the library tests elsewhere, for example in buffer set-up, fog and lighting; none of the tests is in the texture file), and the internal-format check (`CheckInternalFormat`, 0xd9d3240 to 0xd9d3648) compares the alpha, luminance, intensity, RGB and RGBA families and the two ICC formats and no colour-index internal format (**inferred**: its enumerant constants were listed, not every branch followed). So the library sends texture state and the textured primitive the same way in a colour-index window as in an RGBA one. What the board does with a textured fragment bound for a colour-index buffer is **unknown: no shipped software or published source depends on it**. What would settle it: a board drawing, which no software shows. An emulator that refuses or ignores texturing in colour-index mode is making a model choice.

## Routines read for this chapter

Binary `builds/6.5.30-media/usr/gfx/arch/IP30ODSY32/libGLcore.so`; each routine was read in full for the stores and compares named above, except the two lookup-table routines, which were read for the branches named.

- `__glOdysseyTextureActivate` (`builds/6.5.30-media/usr/gfx/arch/IP30ODSY32/libGLcore.so`, 0xd9d1f90, 1448 bytes): **established.**
  Fills the level table and the sampler words from a texture object (level-table writes in the first table above). For a 3D target it replaces the last level by the base level before the loop, so one entry is written.
- `CheckTargetLevel` (`builds/6.5.30-media/usr/gfx/arch/IP30ODSY32/libGLcore.so`, 0xd9d3a60, 184 bytes): **established.**
  Returns the invalid-value error for a negative level or a level above the context word at +3732 for the texture targets; the invalid-enumerant error for any other target.
- `IsLegalRange` (`builds/6.5.30-media/usr/gfx/arch/IP30ODSY32/libGLcore.so`, 0xd9d3070, 120 bytes): **established.**
  Accepts a size less twice its border when it is zero or a power of two up to 0x8000, with a border of 0 or 1.
- `__glOdysseyTextureSetSWrap` (`builds/6.5.30-media/usr/gfx/arch/IP30ODSY32/libGLcore.so`, 0xd9d5bc0, 176 bytes): **established.**
  Writes the S wrap code into bits 13:12 of the sampler word 4 and the S value into bits 23:18 of the first size word, from the four wrap enumerants; any other enumerant raises the invalid-enumerant error.
- `__glOdysseyTextureSetOp` (`builds/6.5.30-media/usr/gfx/arch/IP30ODSY32/libGLcore.so`, 0xd9d7ad0, 616 bytes): **established.**
  Sets the environment mode in bits 2:0 of the first word of the environment block; for the add mode it also writes ones to the four colour channels.
- `__glOdysseyStoreLUT` (`builds/6.5.30-media/usr/gfx/arch/IP30ODSY32/libGLcore.so`, 0xd9c3c50, 2020 bytes): **inferred.**
  Read for the dispatch, the 256-entry branch and the code stores only.
  Reformats a resized table into the board record: for a 256-entry table entry n goes to word n of two 256-word tables, the first holding the red and green lanes (bits 23:12 and 11:0) and the second the blue and alpha lanes; it stores the table's component code 1 to 6 in the record.
- `ResizeLUTData` (`builds/6.5.30-media/usr/gfx/arch/IP30ODSY32/libGLcore.so`, 0xd9c4440, 2380 bytes): **inferred.**
  Read for the colour-table kind (1) and the format branches only.
  Resamples an application table to 256 or 4096 entries by replication and converts each channel to `trunc(4095 x + 0.5) & 0xfff`; a component the table's format lacks gets the identity ramp `trunc(0.5 + 4095 i / (n - 1))` (i the first index of the run sharing one element).
- `__glOdyim_ColorTableSGI` (`builds/6.5.30-media/usr/gfx/arch/IP30ODSY32/libGLcore.so`, 0xd98d560, 1296 bytes): **established.**
  Checks the width (a power of two, at most 256 for the texture target), builds the board table through the routines above and, for the texture target, copies the record over the 512-word shadow at context +0x8d7c and merges the table's code into bits 22:20 of the sampler word 4.
