# Board memory and board configuration

Labels: **established**, **inferred**, **unknown**. IRIX 6.5.30m, IP30 `odsy_init.o` (`odsyGatherInfo`, `odsyReset`). A fact about IP35 is **unknown** unless named.

## The strap word at board +0x106c

- `odsyGatherInfo(board, 1)` reads the 32-bit word at +0x106c (the FIFO-levels register of `BUZZ.h`, whose bits 15:0 are FIFO levels) and decodes its top byte as board configuration:

| Bits | Decoded | Stored in record | Values | Grade |
|---|---|---|---|---|
| 31:30 | SDRAM size code | +252 (MB) | 0 -> 32, 1 -> 64, 2 -> 128, 3 -> 33 | **established** (`odsy_init.o` `.text` 0xbdc to 0xc18, with the value stores at 0xc98 to 0xcbc) |
| 29 | SDRAM banks | +260 | 0 -> 2, 1 -> 4 | **established** (same routine, 0xc38 to 0xc5c, with the 2-bank store at 0xcac) |
| 28 | CAS latency | +256 | 1 -> 2, 0 -> 3 | **established** (same routine, 0xc18 to 0xc38, with the latency-2 store at 0xca4) |
| 27:24 | board revision | +292 | raw nibble; 0 selects the first clock part, 1 or more the second (`docs/display.md`, clock parts) | nibble and its store at 0xbf8 **established**; the link to the clock part is **inferred** (below) |

Grade covers the bit positions and the decoded values read from the kernel's attach code. What each field means on the board is graded separately in the paragraphs that follow.

- **established.** The decoded values are checked in `odsyReset`: banks other than 2 or 4, latency other than 2 or 3 and size other than 32, 33, 64 or 128 log "invalid sdram banks", "invalid sdram casl" or "invalid sdram size %dMB". The strings in `odsyGatherInfo` name the same fields ("unknown sdram casl setting", "unknown number of sdram banks").
- **inferred.** The word's top byte is a strap or ID field set by the board (no driver code writes it and the same register's other bits change at run time). The value 3 for size, recorded as 33, selects the same register code as 128 in step below; why the board distinguishes it: **unknown**. **Test that settles it:** a published verbose boot or board-memory datasheet of a 32 MB (V6 or V10) board showing the memory configuration programmed for strap size 3, compared with code 2. Both shipped programs were read in full and treat code 3 as 32 MB while writing the 128 MB register code, so no further shipped read settles it. "33" is the driver's own marker, not a size in MB.
- **inferred.** The bank count and CAS latency are what "board inventory reports" carry, because the driver stores them in the record that `odsyGatherInfo` fills and prints.

## How the IP35 PROM labels the strap fields

Release: IRIX 6.5.30m IP35 PROM (`usr/cpu/firmware/ip35prom.img`, 6.210), the inflated BASEIO segment, board-information routine near 0x130ba480. **established** (read from the code): it loads the word at +0x106c, splits it the way `odsyGatherInfo` does and keeps the results in a record: bits 31:30 select 32, 64, 128 or 33 (stored at record +12); bit 28 stores 2 when set and 3 when clear (+16); bit 29 stores 2 when clear and 4 when set (+20); bits 27:24 are stored raw (+52). It prints them with the strings "On board sdram size: %d Mb" ("On board sdram size: 32 Mb" has its own string), "Cas latency: CAS %d", "%d banks by sdram module" and "Board version %d - Buzz revision %d%s", and the error strings "Unknown sdram size", "Unknown sdram cas latency setting" and "Unknow number of sdram banks". The print routine's choice of record field for "Board version" was not traced, so the nibble as the printed board version is **inferred**.

What the published prints add (three PROM transcripts, see [the PROM's board-register diagnostic](registers.md#the-ip35-proms-board-register-diagnostic-6210)): "Board version 1", "128 Mb", "CAS 3", "4 banks" on V12-class boards. Through the decode above that gives bits 31:30 = 2, bit 29 set, bit 28 clear and bits 27:24 = 1 (**inferred**: no raw strap word of any board was published). So the labels "banks" and "CAS latency" for bits 29 and 28 are the PROM's own, **established** as labels; what the hardware does with them is still **inferred** to be SDRAM controller configuration, because the kernel copies the decoded values into bits 2 and 1 of the +0x1004 configuration word.

Size code 3 is a 32 MB board to both programs. **established** (read from both): the PROM stores 33 and prints its fixed string "On board sdram size: 32 Mb" for it (any other value goes through "%d Mb"); the kernel programs bits 4:3 of +0x1004 with 2, the code it uses for 128 MB, and rewrites its record to 32 in that branch (`odsy_init.o` near .text 0x2254 to 0x22dc, `sw` of the register holding 32 at the end of the size-33 path). Which boards present code 3 and why the controller code differs from code 0: **unknown: no shipped software or published source depends on it**. Routes tried: both PROM and kernel paths, the published V6, V8, V10 and V12 prints (none shows a size other than 32 or 128).

`odsyReset` validates the decoded banks, CAS latency and size before programming +0x1004. **established** for CAS latency and size (the banks branch was not re-read): a value outside the accepted set prints "invalid sdram casl" or "invalid sdram size" and execution falls through to the next step with that field's bits left clear; the reset does not abort.

## The board revision word at board +0x04

- **established.** `odsyGatherInfo(board, 0)` reads +0x04 and takes bits 31:28 as a buzz revision type, stored in record +264, then dispatches through a 16-entry jump table (`odsy_init.o` `.rodata` offset 0x238):

| Value | Record +264 | Record +280 | Grade |
|---|---|---|---|
| 1, 2, 3 | the value | 0 | established |
| 9 to 15 | value - 8 (1 to 7) | 1 | established |
| 0, 4 to 8 | error "Invalid buzz rev type %d" | | established |

- **established.** After a valid type it reads the word at +0x23380c, keeps bits 2:0 in record +268, and returns.
- **inferred.** Bit 31 (record +280) is a variant flag, the low three bits the BUZZ revision. **established** (`docs/pbj.md`, items 3 and 4): +0x23380c is display address 0x2701, the register whose bits 2:0 `gfxinit` prints as "PB&J version"; `odsyGatherInfo` stores them in record +268. `+0x233804` is the clock-programming word read by `odsyLoadTimingTable` (`docs/display.md`), a neighbour in the same block. The meaning of bits 31:3 of 0x2701: **unknown**, `odsyInitDBE` tests bit 10 (`PBJ.h` section 2); a read-back of the whole word on a real board with known revisions would settle the rest.

### The revision nibble, the letter and the inventory name

- **established (6.5.30 kernel).** The nibble selects the buzz type by the jump table above: values 1 to 3 are the first type (record +280 = 0), 9 to 15 the second (+280 = 1, with 8 taken off the stored value), and 0 and 4 to 8 are errors. The inventory state word that `odsyInitBoardGfx` forms carries that type in its top byte (0x01 and 0x02) and the memory size in the byte below, and the 6.5.30 `hinv` names the board from that word (the next section's list). The letters "Rev A" and "Rev B" as names of the two types are **unknown** from the binaries read here; the V6, V8, V10 and V12 names are the 6.5.30 `hinv` strings.
- **inferred.** So the letter that `gfxinit` prints is the type the revision nibble selects, not a per-nibble letter: nibbles 1 to 3 print A and 9 to 15 print B. With the printed number as the revision minus 1 (`docs/vpro-tool-functions.md`), the published V12 sample whose raw revision is 10 prints B.1, which fits (10 gives type B, revision 2, printed 1); a nibble of 2 would print A.1, the letter and number the published V6 and V8 captures show, so those boards would carry nibble 2 (type A stores the nibble unchanged), if the report's revision word is the record's +264 word, which was not traced. Linux's names (nibble 1 "A", nibble 2 "B", `xwidget.h`) are a coarser labelling and do not agree with the IRIX one for nibble 2. Whether a B.1 board is nibble 10 and a B.2 board nibble 11 is likewise inferred from the same rule. Routes tried: the 6.5.30 binaries (the printed number rests on that reading), Linux, the published `hinv` and `gfxinfo` captures of [published-sources.md](published-sources.md). No published capture pairs a raw widget revision with the printed letter except the one V12 sample, so the nibble of an A.1 board is not confirmed by any capture.

## Memory configuration word at board +0x1004

- **established.** `odsyReset` builds a word in a record copy and stores it to +0x1004 (a 400 us delay after each store):
  - bits 22:19 = the widget master id (`xwidget_info_masterid_get`), stored first, at step 3 of `docs/kernel.md`.
  - bit 2 set for 4 banks, clear for 2 banks.
  - bit 1 set for CAS latency 2, clear for 3.
  - bits 4:3: 0 for 32 MB, 1 for 64 MB, 2 for 128 MB and for the size code 3 (the driver rewrites its record to 32 in that case).
  - Then bit 5 is cleared, set, written, cleared again (three stores, 400 us apart) and bit 8 is set last.
- **inferred.** +0x1004 configures the board's SDRAM controller (banks, CAS latency, size) and bit 5 pulses an SDRAM initialisation; bit 8 enables it. Reason: the field values are exactly the three probed properties and the pulse is the driver's standard reset shape. Not confirmed by hardware.
- **unknown.** Organisation and addressing of the memory, timing beyond CAS latency, and the width of any other field of 0x1004. **Test that settles it:** a published board memory datasheet or parts list for the V6, V8, V10 or V12 naming the SDRAM parts and their mode registers; the kernels and libGLcore's memory-manager calls were read and carry sizes only.

## Strap word and configuration register fields (pass 12)

Positions come from the 6.5.30 binaries above.

- **established.** The top byte of +0x106c holds the board's straps, read once. Size is the top two bits, bank count the next, CAS latency the next, and the low nibble is stored as the board revision (decode above). Whether that low nibble is a board version in the hardware's sense, and the register's own name, are **unknown** from the binaries read here; a read of the remaining readers of +0x106c in `libGLcore` and `odyssey.so` would settle the nibble. The size field has three legal codes (32, 64, 128 MB) in the 6.5.30 kernel and code 3 is handled as above (recorded as 33, programmed as 128 MB). Why: **unknown: no shipped software or published source depends on it** beyond that branch. Routes tried: both 6.5.30 kernels and the strings of both.
- **inferred.** The board revision selects the pixel-clock part: revision 0 boards use the first part (I2C 0x26), later boards the second (I2C 0x58); the 6.5.30 kernel's choice is the variant word at +292 (`docs/display.md`), and that this is the strap nibble is inferred.
- **established.** +0x1004 is written by `odsyReset` as listed above: SDRAM bank count, CAS latency, size, an SDRAM reset bit (the bit 5 pulse: written 0, then 1 twice, then 0, 400 us apart) and the host widget id (bits 22:19, the master id). Bit 8, which 6.5.30 sets last, has no known role: **unknown**. **Test that settles it:** a memory-controller or board-memory datasheet for the VPro board that names the bit, or a trace of the board's memory traffic taken with the bit clear and set (the only way to show it is on hardware; no shipped program reads it back, so no further binary read can). Any other field of 0x1004 is **unknown** from the binaries read.
- Memory organisation: chip count, data width and the address map are **unknown** (`docs/open-questions.md`). Routes tried: both 6.5.30 kernels and libGLcore's memory-manager calls. Not tried: board photographs (route 3). **Test that settles it:** a photograph of a V10 or V12 board with the memory chips' part markings legible, whose datasheet gives the width and capacity (count them, compare with 32 and 128 MB), plus the diagnostic's chip numbering (0 to 15, below) to place each chip in an address range.

## Board numbering and the two-board case (6.5.30 kernel)

- **established (6.5.30 kernel, [driver-functions.md](driver-functions.md)).** The board number comes from the attach order, not from a port scan: `odsy_attach` takes the next value of `OdsyBoardEnum` under `GfxBoardInitSema`, and `odsy_earlyinit` looks only for board 0 with `odsyFindBoardAddr`. The numbering therefore follows the order in which the crossbar layer calls the attach routine for matching widgets. That layer is not part of the driver and its order was not read, so whether a second board gets the higher or the lower port number first is **unknown** from the driver; the published `hinv -m` captures list the boards at `/hw/node/xtalk/11` and `/hw/node/xtalk/9` (the higher port first), which says nothing about the attach order.
- **unknown.** What makes a pair of boards one two-head system, and how a board becomes master or slave. The strings of the 6.5.30 kernel carry no text of such a check ("Illegal" and "master" appear only in unrelated routines) and its code was not searched for one. A search of the 6.5.30 kernel for reads of the display back end's host-interface status register after every board is initialised would settle whether it classifies boards at all, and by which bits.

## What stays unknown, and what would settle it

Pass 8. IP35 `odsyGatherInfo` stores to the same record offsets as IP30 and IP35 `odsyReset` writes the same 0x1004 sequence (`docs/kernel.md`), so the findings above hold for both hosts. **established:** no kernel object reads 0x1004 (every access with displacement 4100 in the disassembly of `odsy_kernel/` and `odsy_kernel_ip35/` is a store in `odsyReset`; the user-space libraries were not scanned: **unknown** whether they map the register), so nothing in the software says how the word's other bits behave.

- **unknown** (`docs/open-questions.md`). Memory organisation (chip count, data width, address map). The software only sees size, banks and CAS latency from the strap word. On a board it would show in: a read of the SDRAM controller's own configuration after reset on a known board, or a board photograph naming the memory parts with their datasheets.
- **unknown** (`docs/open-questions.md`). What bit 5 (the pulse) and bit 8 (the last set) do in hardware, and bits 0, 7:6 and 21:9 of 0x1004. On a board it would show in: a bus-level trace of the SDRAM command lines during the 400 us after each store, or a read-back of 0x1004 before and after `odsyReset` (it is not known whether the register reads back: **unknown**).
- **unknown** (`docs/open-questions.md`). Why size code 3 is distinct from code 2 (the driver records 33 and then writes the 128 MB code). On a board it would show in: the strap word's size code on a board with a known memory population.

## Published board facts (guides, datasheets and the revision-003 diagnostic reference)

Labels here are **established (published)** unless marked: an SGI manual says it. Page numbers are printed pages; identities and hashes are in [published-sources.md](published-sources.md) sources 8 to 14. These are statements about shipped products, not reads of the driver.

- **Board sizes and texture share.** V6 and V10 carry 32 MB of which up to 8 MB can be texture; V8 and V12 carry 128 MB of which up to 104 MB can be texture (the Octane2 datasheet, the Fuel datasheet and the May 2001 product table agree, and the porting guide gives the V6 and V8 figures). The Fuel datasheet gives 80 MB of texture on a V12 when the dual channel option is used; the reason is **unknown**, and **inferred** to be that the second output takes board memory. **Test:** compare an `odydiags -getinfo` or `gfxinfo` dump from a dual-channel V12 with one from a single-channel V12 for the reported texture memory, and look for a dual-channel memory split in the diagnostic reference (108-0314-003). The strap word's size field ([The strap word](#the-strap-word-at-board-0x106c)) is the only software view of the 32 versus 128 MB split; the guides add no organisation.
- **Second source for the strap decode.** An `odydiags -getinfo` sample from a V12 reads "buzz revision is 10", 128 MB, 4 banks, CAS latency 3, board version 1 and PB&J version 1 (108-0314-003 p. 23). Those are the fields of the decode above: 128 MB is size code 2, 4 banks is bit 29, latency 3 is bit 28 clear, and raw type 10 falls in the 9-to-15 row (value 2, variant flag 1). **inferred** that `gfxinit` prints it as BUZZ B.1, from its letter and number rule in `docs/pbj.md`.
- **Tile arithmetic.** 32 MB is more than 65,000 tiles in the diagnostic's address-unique test (p. 16). Exactly 65,536 tiles of 512 bytes, a 16 x 16-pixel tile at 2 bytes per pixel, is the same figure and the tile of the memory manager above (**inferred**; the text does not give the tile size). The same pages say a tile is 16 pixels wide and strides are counted in tiles (Table 7, p. 31).
- **Memory chips.** Chips are numbered 0 to 15 for diagnostic software and named by bank and letter ("SDRAM Bank 2_A"); a 4-byte pixel has components 0 and 1 in one chip and components 2 and 3 in another (pp. 31 and 35). Chip width, count per board and the address map are still **unknown** (same settling test as the memory organisation item in the strap section above: a legible board photograph and the chip's datasheet).
- **Ports.** A V6, V8, V10 or V12 board on an Octane2 has a 13W3 monitor port with a DDC variant, a genlock port, a StereoView port and a swap-ready port (007-4210-003 pp. 30-33). Fuel and Tezro boards have one DVI-I port with analog and digital video instead, plus the same three small ports (007-4480-001 p. 35, 007-4643-003 p. 32); the swap-ready feature is "not functional at this time" on the Fuel. A V12 in a V-brick has two DVI-I ports, a blocked 13W3 connector, genlock, swap-ready and stereo (007-4264-002 pp. 56-57). The dual channel option is a daughterboard under the main board that adds two DVI-I ports (007-4209-003; 007-4480-001 p. 35).
- **Host requirements.** V10 and V12 need a Crossbow of revision 1.4 or later; the power supply must be part 060-0035-00x for an Octane taking its first VPro; V6 and V8 need PROM 4.0 and V10 and V12 PROM 4.5 (007-4210-003 pp. 2-6). IRIX 6.5.8 is the first release to name VPro support (007-3897-007).
- **Part numbers.** The Fuel diagnostic reference gives the Fuel field-replaceable boards: V10 013-3513-00x, V12 013-3416-00x and the dual channel board 030-1713-00x (108-0350-002). Octane2 board part numbers are not in the guides read.
- **V-brick.** Each V12 takes two of four slots, and the brick midplane has an Xbridge ASIC joining its two 800 MB/s ports to the boards (007-4264-002 pp. 52-56). **unknown:** which Crosstalk widget a V12 answers at in a V-brick. No manual or capture says; the candidates 8 or 12 (first pipe) and 9 or 13 (second) are **inferred** from the IP35 kernel's X-brick slot map (slot 1 widget 8, slot 2 widget 12, slot 3 widget 9, slot 4 widget 13) if the V-brick midplane is wired like an X-brick's, which is not shown; widgets 10 and 11 are the cable connectors. The V-brick cables straight to a C-brick (one node, one XIO connector), so there is no "node 1" attach point, and its L1 identity (the type letter `V` is the CG-brick) is unknown. Settling test: `hinv -vm` and the PROM `hinv -v` of an Onyx 3000 with a V-brick. Grading: the chips repository's Onyx 3000 graphics-brick topology page.

## Board kinds seen by software (checked against the recollection leads)

Release 6.5.30m, IP30 and IP35 builds. Each item carries its label.

- **established.** `odsyInitBoardGfx` (`odsy_init.o`, 0x904) forms the board's inventory state word from two inputs: the memory size word at record +252 (32 gives 0x10000, 64 gives 0x20000, 128 gives 0x30000, anything else 0) ORed with 0x1000000 when the variant word at +280 is 0 or 0x2000000 when it is 1, and hands it to the inventory routine with class 7 and type 21. A second entry (class 17, type 3, state 0) follows when the halfword at +296 is nonzero and the halfword at +298 is 3. So software distinguishes only a memory size and an A or B variant. **established (6.5.30 `/sbin/hinv`, read 2026-11-10):** the `Graphics board: ` line of the 6.5.30 `hinv` picks its name from that word. It tests the top byte first (0x01 type A, 0x02 type B, anything else prints no name here), then the size byte (0x01 for 32 MB, 0x03 for 128 MB, any other value including the 64 MB code 0x02). Type A prints `V6` for 32 MB, `V8` for 128 MB and `VPRO` for any other size; type B prints `V10` for 32 MB, `V12` for 128 MB and `VPRO+` for any other size. The six strings sit together in the program's read-only small-data, so the 64 MB code that the kernel can form has a generic name in `hinv` even though no published capture shows a 64 MB board. The mapping V6 (32 MB, A), V8 (128 MB, A), V10 (32 MB, B) and V12 (128 MB, B) is therefore established for the software, as is the generic `VPRO` and `VPRO+` fallback; that these are the marketing products is the published captures' evidence. The same program prints an Xbow line `Xbow ASIC: Revision 1.%d` with a revision number minus 1 when that number is below 6, and `Xbow ASIC: Revision 2.%d` with it minus 5 otherwise (the code at 0x100045e0 to 0x10005788; where the number comes from was not traced, so which widget field it is stays **unknown**; the test is to read the code that fills the global it loads). The one published V6 sample that reports B.1 (published-sources.md, Higher Intellect entry) does not fit that mapping and is **unresolved**.
- **established.** The BUZZ A.1 test in `odyssey.so`. The module's board record is the kernel's board-information record shifted by 0x28: its compositor word is at +0x1cc where `gfxinfo` reads +500, and its option-card halfword is at +0x3a where `gfxinfo` reads +0x62. The two words the module compares, +0x18 and +0x28, are therefore information words +0x40 and +0x50: the BUZZ revision (printed minus 1) and the variant (0 prints A). Revision 2 with variant 0 is "A.1", and the module prints that board as "Buzz A.1" (string 0x0172d7d8 in `odsyLdFmtByName`, 0x0165efc0). On that kind, and only on it, the module: (1) refuses a video format whose pixel clock lies strictly between 109.0 and 194.0 MHz (doubles at 0x0172c9b8 and 0x0172c9c0 in `odsyReadVideoFormat`, 0x016b3220), and also refuses 108.0 and 107.2512 MHz when the screen record's word +0x10 is 3 (0x0172c9c8, 0x0172c9d0); (2) refuses depth 16 with a format name beginning `1280x1024_60` (`odsySetFBConfig`, 0x016081e0, and `odsyLdFmtByName`); (3) defaults to `1280x720_72`, and to depth 8 for monitors whose default would be `1280x1024_60` (`odsyValidateBoardConfig`, 0x016f2230). The list of formats under rule (1) is in [display.md](display.md).
- **inferred.** Rule (1) and (2) keep a first-generation board away from pixel clocks it cannot generate cleanly. No shipped text states the cause; the format compiler rules give two clock-part searches with different loop oscillator ranges (125 to 500 MHz and 40 to 230 MHz, [video-format-sources.md](video-format-sources.md)), and the kernel picks the clock chip by the variant (0 the classic part at two-wire address 0x26, above 0 the second chip at 0x58, `odsyLoadTimingTable`, [driver-functions.md](driver-functions.md)). That the variant-A board is the one with the classic chip and the window is a limit of that chip is a reading, not a read.
- **established.** What software sees of the board identity is the `gfxinfo` text, which prints "BUZZ version", the variant letter and the revision minus 1, "PB&J version %d", "%dMB memory" and "Banks: %d, CAS latency: %d" (`_odsy_info`, [vpro-tool-functions.md](vpro-tool-functions.md)). The diagnostic reference's V12 sample reads revision 10, 128 MB, 4 banks, CAS latency 3 (p. 23), which that routine prints as B.1.
- **established.** What the board kind changes in the X module (read 2026-11-10, [display.md](display.md), "Which visuals a board offers"). The module takes memory (information word +0x34) and variant (+0x50) from the same record `gfxinfo` prints. Below 128 MB it drops the four 12-bit-component visual lists (entries 49 to 52 of the visual table) and refuses accumulation type 1 (24-bit components, `odsyReadTTfilename`); at 128 MB the variant selects which of those four are listed (variant A: 49 and, with the 16 configuration, 51; other variants: 49, 50 and, with the 16 configuration, 52). A 32 MB board of either variant is offered the same 35 or 41 visuals. With the **inferred** product mapping above, V6 and V10 offer the same visuals, V8 and V12 add the 12-bit ones, and the variant matters only on 128 MB boards.
- **established (6.5.30 `var/inst/machfile`, read 2026-11-10).** The install tool's graphics-board selector (`GFXBOARD`) takes the value `ODYSSEY` from the hardware inventory entry of class 7 and type 21, the same class and type `odsyInitBoardGfx` registers. Its machine table then lists `ODYSSEY` as the board for IP30 (Octane2) and for IP35 (Onyx3 InfinitePerformance and Fuel), beside `MGRAS` for the older Octane and `KONA` for the InfiniteReality systems. So the install selector does not distinguish V6, V8, V10 and V12.
- **established.** `ide.IP30` (6.5.30m) recognises the board by widget part number 0xc013 and prints that Odyssey diagnostics are not supported in `ide` and that the Unix `odydiags` tool is the one to use. The kernel registers manufacturer 35 and part 0xc013 under `odsy_` in both builds.
- **unknown: no shipped software or published source depends on it.** Whether the refusal of pixel clocks from 109.0 to 194.0 MHz on a first-generation board guards a hardware fault that shows with several contexts. Software shows only the refusal range; routes tried are `odyssey.so`, the format compiler rules and the diagnostic reference. Silicon test: on a board that prints the first-generation revision, drive one format at a time with a pixel clock inside the refused window from a patched timing file, with a single context drawing a full-screen black and white 1-pixel grid, and capture the output with a pixel-accurate grabber for 1,000 frames; repeat with 2, 4 and 8 clients each holding a different context and switching at every swap. Count frames with a wrong pixel or a lost sync. A nonzero count that grows with the number of contexts and is zero on a later-revision board settles that the refusal guards a hardware fault; zero on the first-generation board says the refusal is conservative. Log the board's flag and status words (`ODSY_BOARD_FLAGS`, `ODSY_BOARD_STATUS0`) once a frame during the run.
- **established.** The format compiler rules derive the display-bus clock divider from 266.0 MHz divided by 8, 16, 32 and 64 (`VPro_Board.def`, `ODY_DCBClockSpeed`); the same rules cap the pixel clock at 202.6 MHz and the DAC clock at 240 MHz.

### Board NIC and the manufacturing name (V6 to V12)

Full note, with grades and open questions: `docs/questions/v12-nic.md` in the chips reverse-engineering repository.

- **established.** The board NIC is a Dallas 1-Wire (MicroLAN) memory part, not I2C. The driver passes the host `board + 0x10dc` and the host's generic one-wire code bit-bangs a 32-bit IOC3-style control register there (pulse bit 10, sample bit 2, done bit 1, level bit 0; done is polled without a limit). Host reads family 0x0B (IP35 also 0x09): ROM search, Match ROM, status read of the redirection map at 0x0100, two 32-byte pages each ending in an inverted CRC-16, ROM CRC-8.
- **established.** The IP30 PROM drives the same register with the word `(low time << 10) | (sample time << 2)` and the values reset 520 and 65, write 1 6 and 110, write 0 80 and 30, read 6 and 13, each followed by a software wait of 500, 0, 0 and 100 units; the units are inferred to be microseconds ([firmware-images.md](firmware-images.md), "The printing code").
- **established.** The page layout the host turns into text is `Part:...;Name:...;Serial:...;Revision:...;Group:..;Capability:..;Variety:..;Laser:<rom serial>;`; Name is page B bytes 16 to 29 (14 characters). `odsy_set_gfx_mfg_nic_name` splits that text on `:` and `;` and takes the token after `Name`.
- **established.** The host label routine stores the text even when the bus read fails (a "not present" or CRC-failure text), so a failed read never gives the NULL that triggers the "NULL nic_info" alert. NULL means the label was not stored: allocation or label add failed, or (IP35, host class 4 or chimera type nonzero) the node-EEPROM registration ran instead of the board NIC.
- **unknown.** Which cause applies on a given boot, and what a real V12's ROM and memory bytes hold beyond the published board name and part (`ODY128VERSIONB`, `030-1611-001 rev C`).
