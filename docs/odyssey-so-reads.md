# X module (`odyssey.so`) functions read in full, one entry each

Release IRIX 6.5.30m, `usr/lib/X11/dyDDX/odyssey.so` (N32, `$gp` resolved with `ghidra/scripts/IrixGp.java` before reading). Each entry names the function, its address in the module and its size in bytes. Labels are **established** for functions whose whole listing was read next to the decompilation, and **inferred** for anything less. The role lists of the whole module are in [odyssey-so-functions.md](odyssey-so-functions.md). Offsets such as +0x1b4 in a screen record are the X server's own `ScreenRec` and window-record fields; the module keeps two screen-private slots, the board record (`odsyScreenPrivateIndex`) and the video-control record (`vcScreenPrivateIndex`).

## Timing and format-file routines

- `odsyLoadTimingTable..CC` (`usr/lib/X11/dyDDX/odyssey.so`, 0x170a7f0, 5308 bytes): **established.**
  Builds the 320-byte video timing structure of the kernel's timing-table request from a video format file and loads it (arguments: screen, format-file handle, format record, a flag to enable the timing generator afterwards, genlock source; result 1 on success, 0 on any failure). Read as the whole 1327-instruction listing next to the decompilation, `$gp` = 0x173a9c0. The names below are resolved through the module's constant-pool slot at 0x17339b8 (base 0x172acc0); each is read from the file with `SDBgetSymbolValueScalar` into a stack word and every miss prints "odsyGetScalar: unable to find %s" with `ErrorF` and returns 0, after freeing the two table buffers. The structure is the stack block at sp+0x28, offsets below are from its start.
  Set-up. The routine keeps the file descriptor from the screen's second-level record (the pointer at +0x74, word +100) and the board record from the screen private slot `odsyScreenPrivateIndex`. It clears the structure with `bzero(…, 0x140)`, stores the caller's genlock source at +220, the refresh rate (the float at format-record +0x110, truncated) at +184 and the fields-per-frame word (format-record +0x12c) into +172, and clears the flag word at +200. The format record is the 312-byte block that `odsyBuildFmtInfoArray..HB` copies out of each format-list node, with the format name in its first 255 bytes. First it reads `AchievedFrequency` into +192, then `ODY_I2CClockSpeed` into +216, `ODY_DDCClockSpeed` into +212 and `ODY_DCBClockSpeed` into +208.
  Dual-head fields. `TTL_Sync` is read into a local and +264 becomes 0xf0 when it equals 3 and 0 otherwise. `DCDHorizontalFrontPorch`, `DCDHorizontalSync`, `DCDHorizontalBackPorch` and `ActivePixelsPerLine` are read in that order into locals; +268, +272, +276 and +280 receive each one halved (round toward zero, the `srl 31`, add, `sra 1` idiom at 0x170a998 to 0x170aa14). Before `DCDTotalPixelsPerLine` is read, its slot is preset to the sum of the four values; the file's value replaces it when the read succeeds. `TotalLinesPerFrame` and `FramesPerSecond` (a double) follow.
  Clock divider search. The pixel clock is lines times total pixels times frames per second divided by 1,000,000 (the double at pool offset 0x2560). A word at +260 is 0xbb when that exceeds 165 MHz and 0xff otherwise (the doubles 165.0 and the codes at 0x170aafc to 0x170ab1c). The search then walks three four-entry tables in the module's data at 0x1731258, 0x1731268 and 0x1731278 (values 1, 2, 4, 8; 1, 3, 5, 4; 1, 3, 5, 4), outermost loop over the third table, innermost over the first, and takes the first combination whose product times the pixel clock lies strictly between 69.0 and 230.0. The result is the code (outer index << 4) | (middle index << 2) | inner index at +292. The low byte of the total pixels per line goes to +296 and bits 13:8 of it to +300. The product's range selects +304: 3 at 140 or above, 0x13 from 80 up to 140 and 0x12 below 80. Words +308 (0x8e) and +312 (0) are constants. +252 is 1 when the halfword at +0x3a of the board's own record (the pointer at +0x5c of the private record) equals 3, else 0. When no combination fits, `ErrorF` prints "Timing invalid for DCD board" and the routine goes on: +292 stays 0, and +296 to +312 are computed from the last product tried (the range test reads the double saved at sp+0x350).
  Plain fields. `ODY_PLL_DPAControl`, `DPAOffset`, `FdBkDiv0`, `FdBkDiv1`, `InputControl`, `LoopControl`, `Osc_Div` and `OutputEnables` fill +96 to +124, `ODY_AMI_PLL_0x0` to `0x7` fill +128 to +156 and `GEN_AMI_REG1`, `REG2`, `REG5` and `REG6` fill +236 to +248. `FormatInfo_FullScreenStereo`, `Stereo`, `FieldSequential` and `Interlaced` set bits 3, 2, 5 and 0 of the flag word at +200; when interlaced is set and the first word of the field table that the pointer at format-record +0x130 names (the first field's line offset) is nonzero, bit 1 is set as well. `FormatInfo_DualHead` sets bit 4 and stores 1 in the halfword at +0x3e of the board record, or stores 0 there when the value is zero. Then `ODY_VTG_Control`, `ODY_VTG_InitState` and `ODY_VTG_ChanEn` fill +28, +32 and +36, `ODY_DAC_Cntrl` fills +160 and `ODY_DP_Cntrl` +164, and bit 1 of the DAC control value is stored in the screen private record at +0x7c (the word `odsyQryCntrl..JD` returns for control 5). `ODY_SM_Cntrl` fills +168, `FrameBufferHeight` +180 and `ActivePixelsPerLine` +176.
  Tables. For `FrameTab` and then `LineSeqTab` it asks `SDBgetSymbolElementCount`, allocates that many halfwords with `calloc(count, 2)` and fills them with `SDBgetSymbolValueArray`; the frame table pointer and count go to +0 and +8 and the line table pointer and count to +16 and +24. A failed allocation or read prints "Couldn't allocate frametable", "Couldn't get frametable", "Couldn't allocate linetable" or "Couldn't get linetable" with the routine's name and returns 0.
  Generator words. The screen private record's word at +0x88 is copied into +224 first and then chooses the source. When it is nonzero, the ten words at private +0x10c to +0x130 are copied into +40 to +76, bit 1 is ORed into +28, `ODY_GEN_CONTROL` fills +88 (a miss returns 0 at once) and `GEN_Control_mask` is read and ORed into +88; a miss of the mask is recorded and the routine returns 0 before the two reads below. When it is zero, +40 to +76 come from `ODY_GEN_lPFD`, `hPFD`, `lPFD_HI`, `hPFD_HI`, `lPFD_LO`, `hPFD_LO`, `lPSD`, `hPSD`, `lHMASK` and `hHMASK`, and `ODY_GEN_CONTROL` fills +88; a miss there is recorded and the routine returns 0 before the two reads below. In both cases `ODY_GEN_BP_CLAMP` fills +84 and `ODY_GENLOCK` +80 afterwards.
  External genlock. When the genlock source argument is -2 the routine reads `VTG_Control_mask`, `VTG_ChanEn_mask`, `GEN_Control_mask` and `VTG_ChanDisable_mask`, ORs the first into +28, ORs the third into +88, and sets +36 to (+36 OR the second) AND the fourth. It then reads `GEN_PLL_InputControl` into +228 and `GEN_PLL_Osc_Div` into +232; a miss of the latter prints the message and returns 0 after the reads.
  Load. `ioctl(fd, 0x6f64001f, structure)` loads the timing; a negative result prints "ODSY_LOAD_TIMING_TABLE Failed '%s'" with `strerror(errno)` and returns 0. When the enable flag is nonzero, `ioctl(fd, 0x6f640020, {1})` enables the timing generator; its failure is reported ("odsyEnableVTG: ODSY_BRDMGR_VTG_CONTROL Failed") and ignored. Finally the byte at +0x138 of the private record decides on a Denali reset: a value of 3 or more is reduced by 2 and the routine returns 1; 0 returns 1 at once; 1 or 2 sends a 48-byte two-wire request with `ioctl(fd, 0x6f640021, …)` (command 16, a write to the DM5 chip, port 1, 8 bytes of value 0xa4 flagged at +6, acknowledge mode 1) whose payload words are 3 and 10 when the byte is 1 and 1 and 9 when it is 2. A failure prints "Error resetting dm5". The byte is cleared and the routine returns 1.
  The kernel source's timing-information structure names its fields for the clock-speed, width, height and refresh words, which fits +208 to +216, +176, +180 and +184. The dual-head and divider fields have no counterpart there. Callers: `odsyAttachXvc` (enable 0, genlock -1), `odsyLdFmtByName..OC` and `odsyLoadAndFree` (enable 1, genlock source from the video-control record at +0x18).

- `odsyReadVideoFormat..MB` (`usr/lib/X11/dyDDX/odyssey.so`, 0x16b3220, 6292 bytes): **established.**
  Opens a `.vfo` video format file, fills a 600-byte format node from it and answers whether the format can be shown on this screen (arguments: screen, file path, node, mode 0, 1 or 2; result 1 when usable, 0 when not or on any error). Read as the whole listing next to the decompilation (the stack saves and restores were skimmed). `SDBreadOpenDatabase` failing prints "Failed to open %s", frees the node's field table (the pointer at node +0x234) and returns 0; the database is closed with `SDBcloseReadDatabase` on a success.
  Reads. The names come from the file with `SDBgetSymbolValueScalar`; a miss prints "odsyGetScalar: unable to find %s" and returns 0. `FormatName` is copied (255 bytes) to node +4 with a terminator at +0x102, or +4 is cleared when it is absent. `VfoVersion` zero prints "Illegal timing file '%s' specified" and returns 0. The format block at node +0x104 (312 bytes) is cleared; then `FieldsPerFrame` goes to +0x230, `FormatInfo_Interlaced`, `FormatInfo_FullScreenStereo`, `FormatInfo_Stereo` and `FormatInfo_FieldSequential` to locals, `AchievedFrequency` (a double) and `VerticalRetraceRate` (double) to locals. `VerticalRetraceRate` is stored as a float at +0x218; the float at +0x214 (the refresh rate) is the same value when the format is interlaced and fields per frame times it otherwise, and +0x240 is 1 for interlaced and 0 for progressive. The stereo word at +0x238 is 0 without stereo, 1 with stereo and 4 with stereo plus full-screen stereo, with bit 1 added for a field-sequential format. `ScreenHeight`, `ActivePixelsPerLine`, `TotalLinesPerFrame`, `TotalPixelsPerLine`, `FormatInfo_PixelClock`, `FormatInfo_H_BackPorch`, `H_Sync`, `H_FrontPorch` and `H_Active` fill +0x204, +0x208, +0x20c, +0x210, +0x21c, +0x220, +0x224, +0x228 and +0x22c.
  Dual-head files. `FormatInfo_DualHead` (a local), `FormatInfo_DigitalSkew` (stored at +0x254, the read's own failure is ignored) and `DCDSupport` (+0x250) follow. With dual-head set, +0x23c is 1, total lines (+0x20c) is halved, `DCDHorizontalBackPorch`, `DCDHorizontalFrontPorch` and `DCDHorizontalSync` replace +0x220, +0x228 and +0x224, the original total pixels per line is kept in +0x248 and `DCDTotalPixelsPerLine` replaces +0x210 and is copied to +0x24c. With dual-head clear but digital skew set, +0x23c is 0, +0x254 is forced to 1 and the same four reads are made. With both clear, +0x23c is 0 and +0x248 and +0x24c copy +0x210. Failures in the DCD reads are collected and the routine returns 0 after the last of them. The horizontal blanking sum (sync plus back plus front porch) goes to +0x244.
  Field table. With zero fields per frame the table pointer is cleared; otherwise it is `calloc(fields, 36)` and four temporary word arrays (`calloc(fields, 4)`) are filled from `FieldLineOffset`, `FieldLineSkip`, `FieldColor` and `FieldEye`; an allocation failure prints its own message and returns 0. Each 36-byte field entry is: word 0 line offset, word 1 line skip, words 2 to 6 the five vertical timing values (back porch, sync, sync pulse, front porch, active; from `FormatInfo_F_0_V_BackPorch`, `V_Sync`, `V_SyncPulse`, `V_FrontPorch` and `V_Active`), word 7 colour and word 8 eye. For a plain file the five values are read directly. When the file is dual-head or has a digital skew, the sync pulse is not read; the values come from the same names but are scaled by the `DCDTotalPixelsPerLine` value over the file's total pixels per line, truncated to an integer in the quotient before multiplying, and the sync value is stored in both word 3 and word 4. A zero divisor traps.
  Usability. The routine calls `odsyCanLoadOptionHW` with the screen and a flag that is 1 for a dual-head file and 0 otherwise (a zero result returns 0). The mode, taken from the fourth argument, then selects the test; a mode other than 0, 1 or 2 returns 0 here, after all the reading. Mode 1 (formats for the current screen): on a board whose halfword at +0x3e is zero (single head) the format must fit the screen (width at screen +8, height at +10) and not be dual-head; with the halfword set the format's width must be at most half the screen width, it must fit the height and be dual-head. Mode 2 (formats the current screen cannot hold): rejected when the stereo word is 4; on a single-head board it is rejected when it fits the screen and is not dual-head; with the halfword set the same width, height and dual-head conditions as mode 1 reject it when all hold. Mode 0 rejects only a stereo word of 4.
  Board and monitor tests (shared by the modes). With the option card present (halfword +0x3a of the board record equal to 3) the format is usable only when `DCDSupport` is nonzero, the pixel clock in `AchievedFrequency` is between 60.0 and 180.0 MHz (at most 220.0 when the module's global at 0x173aa10 is nonzero), it is not interlaced and has neither stereo bit 2 nor bit 4; when the global is zero, the format is not dual-head and has no digital skew, it also needs the blanking sum to be at most 500 times total pixels over DCD total pixels (as integers). A 1600 by 1024 format is refused when either of two monitor identity slots in the board record (valid word +0xc6 with bytes +0xd0 to +0xd3, valid word +0x148 with bytes +0x152 to +0x155) holds the bytes 0x4c, 0xf8, 0x41, 0x06. Without the card the format is usable when it is not dual-head (mode 1 and 0) or dual-head (mode 2) and has no digital skew. On a board whose word at +0x28 is zero and whose word at +0x18 is 2, a pixel clock strictly between 109.0 and 194.0 is refused, and 108.0 and 107.2512 are refused when the screen private record's word at +0x10 is 3. A refused format frees the field table, clears the pointer and returns 0.

## Gamma ramp routines

The gamma ramp the module keeps for a screen sits behind the video-control record: the word at +0x24 points to a record whose first word is the sample count (0x1000), whose second is 10, and whose word at +0xc points to three tables of 0x600 16-bit entries, red at +0, green at +0xc00 and blue at +0x1800. Entry n of a table stands for a range of the 4096 input samples: entries 0 to 0x1ff are samples 0 to 0x1ff, entries 0x200 to 0x2ff are every second sample from 0x200, and entries 0x300 to 0x5ff are every fourth sample from 0x400 (the compressed index that `odsyLoadGamma0` also walks). The board takes the ramp as 0x600 colour-map entries at index 0x1a00 + n, each the three 16-bit values reduced to 10 bits and packed as red 29:20, green 19:10, blue 9:0.

- `odsyStoreGamma16` (`usr/lib/X11/dyDDX/odyssey.so`, 0x158f900, 872 bytes): **established.**
  Replaces selected channels of the gamma ramp with a 16-bit ramp and sends the result (arguments: screen, channel mask, unused, sample count, ramp pointer). The mask selects red (bit 0), green (bit 1) and blue (bit 2). The sample count must equal the ramp's first word or "the size of the ramp passed doesn't match the gamma size" is printed and nothing changes. It reserves a 0xf8a0-byte stack block as a colour-load request (count 0x1f00, entries at +0x10; a zero from the reservation prints "couldn't allocate memory"). For each of the 4096 samples the first loop uses the compressed index above, so it visits 0x600 samples: the next ramp value is copied into the selected channels' tables at that index (the stores guarded by mask bits 1, 2 and 4) and an entry (index 0x1a00 plus the table index, packed colour from all three tables) is written. The resource-manager client keeps one record per screen (the screen-private slot `rrmScreenPrivateIndex`) and one record per window (the window-private slot `rrmWindowPrivateIndex`). ## The three constants built after `sqrt` in `odsyInitDefaultHW..N`

- `odsyInitDefaultHW..N` three stored constants (`usr/lib/X11/dyDDX/odyssey.so`, calls at 0x15c67e0, 0x15c6804 and 0x15c6820, conversions at 0x15c67e8, 0x15c680c and 0x15c6844): **established.**

## Clip-identifier stealing, buffer swap, plane clears and PIO image upload

The resource manager keeps a per-screen table of clip identifiers (the record at screen-private index `rrmScreenPrivateIndex`): word 0 is the number of identifiers, the entries are 0x24 bytes each from +0x98 (+0x98 and +0x9c first and last window of the entry, +0xa0 and +0xa4 two mask words, halfword +0xa8 flags, halfword +0xaa the visual class, +0xac a use count), and word +0x84 is a round-robin cursor.

- `StealID` (`usr/lib/X11/dyDDX/odyssey.so`, 0x1563dc0, 5016 bytes): **inferred** (the decompilation was read in full and the branch structure is as stated; the names of the policies are my reading of what the branches do).

## Symbol-database open, close and read routines and the format-file readers

The symbol database is an XDR-encoded file: a header (identification string of 4 bytes, two version numbers at +4 and +8, a 100-byte name at +0xc, the symbol count at +0x70, the stream position of the header at +0x74, the position of the symbol table at +0x78, ten spare words from +0x7c; 0xa4 bytes in memory) followed by data and, at the end, a table of 0x2c-byte entries sorted by name. A write handle is 0x14 bytes (XDR stream pointer, `FILE`, header, table, a zero word); a read handle is 0xb0 bytes with the header inline from +8, the symbol count at +0x78 and the table pointer at +0xac. Memory comes from the interface table `_SDBmemface` (calloc at +4, free at +0xc). Everything below is read from the listing; the three statics named by address are `FUN_0154e9ec`, `FUN_0154efd4` and `FUN_0154f08c`.

- `SDBopenNewDatabase` (`usr/lib/X11/dyDDX/odyssey.so`, 0x154edf8, 356 bytes): **established.**
  Opens a database for writing (arguments: path, two values handed to `SDBsetHeader`). The path "-" means standard output (`__iob` + 0x10, which is never closed); any other path is opened with `fopen` in mode "w", and a failure sets `errno` to 2. ## Invert, clear and set loops with a mask

These four are the long forms of the loops above: the constant and complement operations get a software-pipelined main loop with loads issued ahead of the stores. All take (source, destination pointer, destination end pointer) and the mask loops add the mask as a fourth argument; the source is never read. A run whose destination is at or past the end does nothing. The same two-path shape appears in all four: a head loop for the leading words with a store prefetch 0xfc bytes ahead, then, when at least one full block remains, a prefetch 0x100 bytes ahead, a main loop that loads the next block while storing the previous, and a plain block loop used instead when fewer than one block lies below the end.

- `nfb10RopLoop..KH` (`usr/lib/X11/dyDDX/odyssey.so`, 0x1611b30, 1436 bytes): **established.**
