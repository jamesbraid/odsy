# PB&J notes

Companion to `PBJ.h`. Labels: **established** (read from a binary, with where), **inferred** (reasoned, with the reasoning), **unknown**. IRIX 6.5.30m, IP30 kernel objects unless IP35 is named; `usr/gfx/gfxinit` (N32, stripped, from the same install).

## How the chip was identified

1. **established.** No kernel object, `odyssey.so`, `Xsgi` or libGLcore contains the string "PB&J" or "PBJ". The only binary in `root/` that does is `usr/gfx/gfxinit`, at file offset 0x228c8 (`"\tPB&J version %d\n"`), next to `"\tBUZZ version "`, the memory size and the SDRAM bank and CAS-latency lines.
2. **established.** The gfxinit routine at VA 0x1000e03c prints those lines from a structure: "BUZZ version" then a letter chosen by word 80 (0 `A`, 1 `B`, 2 `N`), then `.%d` of word 64 minus 1; "PB&J version %d" from word 68; memory from word 52; banks and CAS latency from words 60 and 56; "Dual Channel Display option" when the halfword at 98 is 3.
3. **established.** The kernel side of that structure is `gf_OdsyInfo` (`odsy.o`), which copies at most 588 bytes from board record +200. Record +252, +256, +260, +264 and +280 are the size, CAS latency, banks, BUZZ revision and variant flag that `docs/board.md` traced in `odsyGatherInfo`, so the gfxinit words line up with them at record offset = word + 200. Word 68 is record +268, which `odsyGatherInfo` sets to bits 2:0 of the word at board PIO +0x23380c.
4. **established.** Board PIO +0x220000 + 8 * a + 4 returns display address a (the read-back test in `PBJ.h` section 2). +0x23380c is display address 0x2701.
5. **inferred.** PB&J is the chip behind the display FIFO: its version sits in that address space, among the timing generator, colour maps, cursor, display modes and I2C controllers, while BUZZ's revision is BUZZ's own PIO register +0x04. The kernel names that side the DBE (`odsyInitDBE`, flag `DBE_OFLOW_INTR`). Nothing ties the strings "PB&J" and "DBE" together directly.

## Method for the address list

- **established.** Every 64-bit `.lit8` constant in every IP30 and IP35 `odsy*.o` whose high word decodes as a display-FIFO header (type 3 or 7, address 0x2000 and up) was listed; the two hosts use the same set: 0x2481-0x2483, 0x2580, 0x2581, 0x2600, 0x2680, 0x26c0, 0x2700, 0x27c0-0x27cc, 0x2800-0x2807, 0x2809, 0x2929-0x292c, 0x2b00. Headers built in registers add the colour map (index << 14), the display-mode table (0x2900 + id), the cursor image and colour blocks, the line and frame tables, and the I2C register pairs.
- **established.** A base-register scan of the IP30 disassembly (loads of the PIO base from record +824, followed through constant adds) lists every read of the window: 0x232414, 0x23241c (`odsyInitDBE`), 0x233604 (`odsyBlankScreen`, `odsySetDACGain`), 0x233804 (`odsyLoadTimingTable`, `odsy_i2cProbe2b`, the Denali read and write), 0x23380c (`odsyGatherInfo`, `odsyInitDBE`), 0x233e64 and 0x233e6c (`odsyGenlockInterrupt`), plus the I2C routines' computed addresses. The IP35 scan gives the same list.
- The scan follows a base only within straight-line code and misses bases passed in as arguments (the textport's `odsy_mapcolor`), so the list is complete for constant offsets only.

## Genlock clock values

`odsyGenlockInterrupt` names its two branches in its error messages ("(lost)" and "(got)") and the clock registers it writes ("pll_input_control", "pll_osc_div", "ami_pll_0x1".."0x6", "gen_ami_pll_0x1".."0x6"). `PBJ.h` section 5 gives the sequence. The values are not constants: they come from the timing structure the X server loads (`docs/display.md`), words 132-152 for free running and 236-248 for genlock, so the clock part's PLL settings for each video format live in the `.vfo` files, not in the kernel. For the part at I2C address 0x26 the driver itself sets register 0 to 0x01 (lost) or 0x11 (got) and toggles bit 7 of register 7. **established.**

The register names in `odsyLoadTimingTable`'s messages for the 0x26 part are DPA Control, DPA Offset, FdBkDiv0, FdBkDiv1, Input Control, Loop Control, OscDiv and Output Enable, and the genlock code fixes two of them by number (0 Input Control, 7 OscDiv). Which number carries each of the other six: **unknown** (the order of the messages suggests 5, 4, 2, 3, 0, 1, 7, 6 as in the write order, which agrees with the two known ones, but the error paths were not tied one by one).

## Open questions

- What PB&J stands for: **established (published)**, "pixel blaster and jammer", and the diagnostic reference calls it one ASIC, the display back-end chip of the board (`docs/sources/manuals/108-0314-003-vpro-odyssey-diagnostic-reference.pdf`, introduction p. 1 and glossary p. Glossary-2; `docs/published-sources.md` source 8). The same document names the BUZZ-to-PB&J control path the display control bus, an 8-bit bidirectional bus (glossary p. Glossary-1; the bus test writes walking patterns to a PB&J register, p. 18), which is **inferred** to be the path the DCB clock-speed field of display address 0x2b00 times. How pixels reach PB&J stays **unknown** (below).
- How PB&J reads pixels: no host-visible DMA; the scanout base and pitch registers (0x2800, 0x2801, 0x2807, 0x2809) name BUZZ memory locations in tile units. The link between the two chips: **unknown**.
- Reset: the board-level reset (`odsyLowLevelReset`, `docs/kernel.md`) is the only reset; no PB&J-specific reset register was found. `odsyInitDBE` starts by writing 0x2b00 = 0 five times, which may be a reset or a flush of that register's function: **unknown**.
- Bits of 0x2482, 0x2483, 0x2600, 0x2680, 0x27c0-0x27cb, 0x2b00 beyond what `PBJ.h` names: **unknown**.
- Whether the I2C registers return data in both halves of the read slot: **unknown**.

## What the binaries cannot settle (pass 8)

Each item below is **unknown** after a full read of the paths that touch it, with the measurement that would settle it. The measurements are single-register reads or a timed observation, not a sweep of the display address space. The absence claims rest on the address scans under "Method for the address list", which cover constant offsets only.

- **How PB&J fetches pixels from BUZZ memory.** No kernel path moves pixel data to or from PB&J except by PIO (`PBJ.h` section 7); scanout is set by base, pitch and depth registers in tile units. Needs the link's description: a bus trace of traffic between the two chips during scanout, or the chip's own datasheet. The software gives no view of it.
- **What raises GEN_LOCK, DBE_OFLOW and the retrace interrupt.** The handlers (`odsyGenlockInterrupt`, the flags handler's DBE_OFLOW message, `odsyRetraceHandler`) react to the flags bits and name them; their enables are bits of the BUZZ-side mask at 0x1034 (`docs/buzz.md` section 6), and the earlier passes found no PB&J register that arms them other than the genlock clock registers (0x27cc/0x27cd); the scan is of constant offsets only, so a register reached through a passed-in base is **unknown**. Needs the flags register (0x1014) read at the instant each fires: retrace against the display timing's vertical blank on a scope or a timestamped read, genlock by applying and removing a reference signal, DBE_OFLOW by overfilling the display FIFO (its depth is also **unknown**; the level field is 7 bits wide, **inferred** upper bound of 127 entries, `BUZZ.h` section 5).
- **Display FIFO word types other than 3 and 7, and whether type 7 is "apply at the next vertical blank".** The kernel only ever builds headers of those two types (`PBJ.h` section 2), so other values are unreachable from software. The type 7 reading rests on which registers use it: the X server colour-map load is the user that would tear if applied mid-frame, so type 7 as "apply at the next vertical blank" is **inferred** from that pairing (`PBJ.h` section 2). Bits 29:28 as a per-BUZZ target field are **unknown**: both are set in both types. What the part does with a type nibble no code sends: **unknown: no shipped software or published source depends on it**. Routes tried: every writer in both IP30 and IP35 kernels.
- **Any PB&J-specific reset, the 0x2b00 writes, and bits of 0x2700 other than 14:12, 17:15 and 18.** `odsyInitDBE` writes 0x2b00 = 0 five times then 0x2700 = 0x0006d3e0 and nothing reads 0x2b00 (address scans). Needs a read-back of display addresses 0x2b00 and 0x2700 immediately after power-on and again after `odsyInitDBE`, through the read window at board +0x220000 + 8a + 4 (read-only).
- **Bit fields of the display registers, and the top of the colour map.** **established** (pass 9, `odsy_brdmgr.o` and `odsy_init.o`, IP30): every address the kernel writes is listed in `PBJ.h` section 3 and each has a known source. 0x2600, 0x2680, 0x27c0 to 0x27cb, 0x27cc, 0x2802 to 0x2806, 0x2929 and 0x2b00 are written only by `odsyLoadTimingTable` from the 320-byte timing structure's words (the table in `docs/display.md`) and, for 0x2b00 and 0x2929 to 0x292c, zeroed by `odsyInitDBE`, which also writes 0x2802 and 0x2803 (`docs/kernel.md`); 0x26c0, 0x2482 and 0x2483 only by the blanking and gain routines. The kernel passes colour-map indices to the display FIFO as addresses masked to 14 bits (`gfP_OdsyBRDMGRsetColors`) and applies no upper bound; the largest map any X visual declares is 4096 entries (PseudoColor 12), and 0x2000 is the line table, so the map ends at or below 0x1fff. **unknown** (`docs/open-questions.md`): what each bit of those registers does. The top of the map is **established (published)**: the diagnostic reference's colour-map pattern test steps the red, green and blue index from 0 to 8191 and calls that the maximum size of the maps (108-0314-003 p. 19), so entries 0 to 0x1fff exist and the map ends exactly where the line table at 0x2000 begins. On a board it would show in: read-backs through the window at board +0x220000 + 8a + 4 of every listed address while a known timing is loaded (the values should equal the structure words), then of colour-map indices 0xfff, 0x1000 and 0x1fff after writing a pattern to them (read-only apart from the pattern).


## Display-address registers, one entry each

Release IRIX 6.5.30m, IP30 kernel objects. The offset starting each row is a display address: the number in the header word the kernel sends through the display FIFO (board +0x400000) or reads back at board +0x220000 + 8 x address + 4. That ordering is the pairing, so each name is **inferred** while the write itself is **established**.

| Offset | Access | Role and derivation |
|---|---|---|
| 0x2481 | store 64 bits | **established.** Video timing generator control word: `odsyLoadTimingTable` (`odsy_brdmgr.o`) sends timing-structure word 28 ORed with 0x42 here, first of the generator's three words, and a second store of 1 follows the clock programming. |
| 0x2482 | load 32 bits | **established.** Generator initial-state word. `odsyInitDBE` (`odsy_init.o`) reads it back through the window at +0x232414 and keeps the value as the driver's shadow that `odsyBlankScreen` clears bit 5 of; the writer is `odsyLoadTimingTable`, from structure word 32. |
| 0x2483 | load 32 bits | **established.** Generator channel-enable word. `odsyInitDBE` (`odsy_init.o`) reads it back at +0x23241c into a shadow, `odsyBlankScreen` clears the three bits of mask 0x23 in it to blank and sets them again to unblank, and `odsyLoadTimingTable` writes structure word 36 with the driver's own bit 5 kept. |
| 0x2581 | store 64 bits | **established.** Cursor control word. `odsyInitDBE` (`odsy_init.o`) ends by clearing its record mirror and sending 0 here, and every cursor request rewrites it from that mirror with a toggled bit 5 (`docs/display.md`). |
| 0x2600 | load 32 bits | **inferred.** Display-chip control word of unknown role: `odsyLoadTimingTable` (`odsy_brdmgr.o`) writes timing-structure word 164 here, setting bit 7 when bit 6 is set, and `odsyBlankScreen` reads it back at +0x233004. What the word controls is **unknown** from the binaries read here; a read of the display-chip registers' other users in `odyssey.so` would settle it. |
| 0x26c0 | load 32 bits | **established.** DAC control: `odsyBlankScreen` (`odsy_brdmgr.o`) sets bit 0 here to blank, `odsySetDACGain` sets or clears bit 1 with a read-modify-write through +0x233604, and `odsyLoadTimingTable` writes structure word 160. |
| 0x2700 | load 32 bits, store 64 bits | **established.** Host-interface control register of the display chip: bits 14:12 take the clock-select field of timing word 212, bits 17:15 that of word 216, bit 18 is held clear while the clock is programmed and set after a 100 ms wait, and `odsyInitDBE` (`odsy_init.o`) first writes 0x0006d3e0. |
| 0x2701 | load 32 bits | **established.** Identification word of the display chip, read by `odsyGatherInfo` (`odsy_init.o`) at +0x23380c, which stores bits 2:0 at record +268, and by `odsyInitDBE`, which skips the option-card probe when bit 10 is set. |
| 0x27cc | load 32 bits, store 64 bits | **established.** Genlock control register: `odsyLoadTimingTable` (`odsy_brdmgr.o`) writes timing word 88 here after setting bit 31 of the 0x1034 mask, and `odsyGenlockInterrupt` (`odsy_intr.o`) continues only when bit 6 is set.
| 0x27cd | load 32 bits | **inferred.** Genlock status, read only: `odsyGenlockInterrupt` (`odsy_intr.o`) loads it, and bit 1 selects the "got" or "lost" message and the 0x2481 update.
| 0x2802 | store 64 bits | **established.** Scan-out width in pixels: `odsyConfigFb` and `odsyInitDBE` (`odsy_brdmgr.o`) store zero in the quick form and 1280 otherwise, `odsyLoadTimingTable` stores timing word 176, which holds 1280 in the built-in timing. |
| 0x2803 | store 64 bits | **established.** Scan-out height in lines, written beside 0x2802 by `odsyConfigFb` and `odsyInitDBE` (`odsy_brdmgr.o`): 0, or 1024 in the full-size form; `odsyLoadTimingTable` stores timing word 180. |
| 0x2929 | store 64 bits | **inferred.** Written by `odsyInitDBE` (`odsy_init.o`) with 0, first of four consecutive stores (0x2929 to 0x292c) after the mode table, and `odsyLoadTimingTable` stores bit 5 of timing word 200 here, the same flag it stores to 0x2806. What the register controls is **unknown** from the binaries read here; the grouping with the next three is from their store order. |
| 0x292a | store 64 bits | **inferred.** Second of the four zero stores `odsyInitDBE` (`odsy_init.o`) makes from 0x2929; what it controls is **unknown**. |
| 0x292b | store 64 bits | **inferred.** Third of the four zero stores `odsyInitDBE` (`odsy_init.o`) makes from 0x2929; what it controls is **unknown**. |
| 0x292c | store 64 bits | **inferred.** Last of the four zero stores `odsyInitDBE` (`odsy_init.o`) makes after the mode table; what it controls is **unknown**. |
| 0x2b00 | store 64 bits | **inferred.** Back-end interface configuration register: `odsyLoadTimingTable` (`odsy_brdmgr.o`) stores bits 2:0 of timing word 208 here, and `odsyInitDBE` first clears it five times. What the three bits select is **unknown** from the binaries read here. |
