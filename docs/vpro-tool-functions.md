# VPro tool functions, one entry each

Release IRIX 6.5.30m. Each entry starts with the function, then the shipped binary, its address in that binary and its size in bytes. Labels are **established** (the whole body was read in the Ghidra decompilation and the listing, with the `$gp` fix-up and jump-table scripts of `ghidra/scripts/` applied first) or **inferred**. An entry speaks for the binary it names. Driver-side numbers are in `docs/ioctls.md` and `docs/driver-functions.md`.

## Dual-channel confidence test, `usr/sbin/Confidence/dualchannel`

A confidence program for the dual-channel display option card: it draws patterns in a GL window, switches the card between its pass-through, multiplexed and test modes over a two-wire bus, and reads back one status bit per test. It supports two hosts through one code path, selected by the board name the kernel reports: a `CRM` board uses the bus ioctl 0x560b on the graphics device (the `crime_i2c_*` routines) and an `ODYSSEY` board uses private ioctl 0x6f640021 (the `odsy_i2c_*` routines). Control byte format of the card, from `dc_disp_mode`, `load_testmode` and `init_pass`: the card is addressed at 0x7e for a write and 0x7f for a read; every written byte after the address has 0x70 in its high bits and the 8-bit control register in the low bits (bits 1:0 display mode, bit 2 shift clock, bit 3 data or strobe); a read returns one byte whose bit 4 is the pass bit of the last test.

- `main` (`usr/sbin/Confidence/dualchannel`, 0x403520, 3664 bytes): **established.**
  Whole-program driver read in full. It opens the graphics device (flags 0x802), asks the board name with ioctl 0x66 (a 16-byte request into a 40-byte buffer) and compares it with `CRM` (host type 1) and `ODYSSEY` (host type 2); any other name prints "Dual channel display is not supported on %s graphics" and exits 1. For each host it copies a preset timing-file path (`/var/X11/Xvc/Crm0_TimingTable` or `/var/X11/Xvc/Odyssey0_TimingTable`) and a default format name (`2@1280x1024_75` for CRM, `2@1280x1024_72` for ODYSSEY) into globals. A first argument `-probe` runs `probe_dcd` and prints `+OK MANUAL dualchannel ConfidenceErrors dualchannel` when the card is present; a first argument `-test` sets the confidence flag and calls `set_timing(1)`. The options are `v:r:p:cfsib`: -v verbosity, -r retest count (the failure limit is half of it), -p first pattern, -c continuous, -f stop and wait after each failure, -s single step, -i the endless bus write test, -b a bus-check flag that no routine reads. It then opens an X connection, insists on a 32-bit GL visual (otherwise it prints "Dual Channel confidence test requires 32 bit frame buffer configuration"), makes a full-screen undecorated window with an empty cursor titled "Dual Channel Diagnostic", attaches the board with ioctl 0x67 (a word of 0 and 0x02000000), installs `clean_up` for SIGINT, SIGQUIT and SIGHUP, optionally runs the endless bus test, and on the first expose event calls `reshape`, `runPattern`, `runDiagnostic` and `clean_up`. In the listing the body calls `setlocale` at 0x4035a0 and `setcat` at 0x4035b4.
- `runDiagnostic` (`usr/sbin/Confidence/dualchannel`, 0x404458, 624 bytes): **established.**
  Runs the test loop and reports. It resets the bus (`crime_i2c_reset` or `odsy_i2c_reset`), reads the control register once into `dc_ctlreg` with `dc_read`, then repeats `DatapathTest` and `DramTest`, counting runs. A run without failures prints the catalogue text `uxconfidence:245`, "Dual Channel tests passed", behind the `+MESSAGE ` prefix when verbosity is 0 and plainly when it is not; a failing run prints "** Runs: %d, Errors: %d **". With the continuous flag set the loop restarts after clearing the test counter; otherwise it ends with `dc_disp_mode(3)`, restores the display timing through `set_timing(0)` when the confidence flag is set, and exits 0. The listing shows calls to `crime_i2c_reset` (site 0x4044a8) and `odsy_i2c_reset` (site 0x4044c8), in that order.
- `clean_up` (`usr/sbin/Confidence/dualchannel`, 0x4046c8, 184 bytes): **established.**
  Signal handler and common exit. It resets the bus for the detected host, puts the card in mode 3 with `dc_disp_mode(3)`, runs `set_timing(0)` when the confidence flag is set and exits 0; `print_failure` and `runBusCheck` also finish through it. Read against the listing: `crime_i2c_reset` is called at 0x4046f8, `odsy_i2c_reset` at 0x404718.
- `reshape` (`usr/sbin/Confidence/dualchannel`, 0x404370, 232 bytes): **established.**
  Sets up a pixel-exact 2D view: viewport over the whole window, an orthographic projection of width by height, and a 0.375 pixel translation (the float 0x3ec00000) in x and y on the model-view matrix, so `glDrawPixels` and `glRasterPos2i` hit pixel centres. Two of its callees, `glViewport` at 0x4043a0 and `glMatrixMode` at 0x4043b4, mark the steps described.
- `runPattern` (`usr/sbin/Confidence/dualchannel`, 0x40529c, 2224 bytes): **established.**
  Fills the window-sized RGBA buffer with one of seven patterns chosen by the pattern number modulo 7, draws it with `glDrawPixels`, flushes and waits 60 frames with `FrameSync(60)` before the next one. The patterns are: 0 a black-to-white ramp that adds one to the grey level every 5 pixels; 1, 2 and 3 solid red, green and blue; 4 alternating white and black pixels; 5 two white and two black pixels in turn (its message text is the same as pattern 4's, "1 Pixel Black/White Stripes", although the stripes are two pixels wide); 6 a pulse and bar, with a single white pixel at a quarter of the width and white from half the width on, black elsewhere. Alpha is 0xff throughout. With a nonzero starting pattern the routine shows one pattern and decrements the number, otherwise it runs 7. The decompiled body and the listing agree on the calls `fprintf` at 0x4052f4 and `glRasterPos2i` at 0x405aa8.
- `DatapathTest` (`usr/sbin/Confidence/dualchannel`, 0x406160, 1516 bytes): **established.**
  Tests every bit of the 24-bit pixel path through the card. For bit i from 0 to 23 it sets mode 0, clears the window to the colour 1 << i (red, green and blue taken from bits 23:16, 15:8 and 7:0), flushes, and runs `run_test` with test words i | 0xc0, i | 0xe0 in mode 0 and i | 0x80, i | 0xa0 in mode 1; it then clears to the complement and runs i | 0x40, i | 0x60 in mode 0 and i, i | 0x20 in mode 1. In test words bit 5 picks the low or high pixel of the pair, bit 6 the left or right path, bit 7 the expected value and bit 8 the DRAM test (not set here). With verbosity set it follows with the even-odd select check: a window of alternating white and black pixels drawn in mode 2, then 24 tests each on the paths with words i | 0x60, i | 0xc0, i | 0x20 and i | 0x80. The two `diagnose_` calls at the ends do nothing. Checked in the listing: it reaches `fprintf` at 0x4061c4 before `dc_disp_mode` at 0x4061f4.
- `DramTest` (`usr/sbin/Confidence/dualchannel`, 0x406ed8, 544 bytes): **established.**
  Tests the card's frame memory with two images. It builds a buffer whose every pixel in row r has grey level r (low 8 bits, alpha 0xff), calls `checkDRAM`, then inverts the colour bytes of the whole buffer with 0xff and calls `checkDRAM` again; `diagnose_dram` is called with 0 and 1 after the two passes and does nothing. Callees seen while reading: `fprintf` at 0x406f10, `checkDRAM` at 0x406fc8.
- `checkDRAM` (`usr/sbin/Confidence/dualchannel`, 0x4070f8, 356 bytes): **established.**
  Writes the current buffer through the card and reads the DRAM-test bits back. It selects mode 2, draws the buffer with `glDrawPixels`, flushes, waits 3 frames and then runs `run_test` for the 24 bits i in mode 1 with words i | 0x140 and i | 0x160, and in mode 0 with i | 0x100 and i | 0x120; bit 8 of every word selects the memory comparison and bit 5 chooses between the low and high pixel of the pair. The first two calls of the body go to `dc_disp_mode` at 0x407120 and `glRasterPos2i` at 0x407138.
- `run_test` (`usr/sbin/Confidence/dualchannel`, 0x406828, 1000 bytes): **established.**
  Runs one test word. It loads the word with `load_testmode`, waits 1 frame (2 for the memory tests whose bit 8 is set), reads the card status and takes bit 4 as pass. On a failure it retests as many times as the retest option says (each retest reloads the word, strobes `init_pass` and, for the memory tests, flips the display mode twice), counts the failed retests and, when that count is above the failure limit, adds one to the failed-test count and calls `print_failure`, waiting for a keypress when the stop flag is set. A pass with the single-step flag waits for a keypress as well. The test counter goes up by one at the end. Instruction sites tie the description to the code: `load_testmode` is called at 0x406854 and `FrameSync` at 0x40687c.
- `load_testmode` (`usr/sbin/Confidence/dualchannel`, 0x405d3c, 720 bytes): **established.**
  Sends a nine-bit test word to the card's serial shift register. After the address byte 0x7e it clocks bits 0 to 8 of the word out one at a time: it clears the data and clock bits of the control register, puts the bit in bit 3, writes the byte with 0x70, raises the clock (bit 2) and writes it with 0x74; it ends with a strobe of bit 3 (high, then low). With verbosity above 2 it prints the word as " (%3d) Test mode: bit=%2d, lopix=%d, leftpath=%d cmpval=%d, lvsr=%d". Both host variants are in the same routine. Both the call to `fprintf` at 0x405db4 and the call to `crime_i2c_start` at 0x405e00 appear in the listing.
- `init_pass` (`usr/sbin/Confidence/dualchannel`, 0x40600c, 340 bytes): **established.**
  Sends the strobe alone: address byte 0x7e, the control register with bit 3 set and written with 0x78, then with bit 3 cleared and written with 0x70. The tests use it to restart the comparison after a mode change without shifting a new word. The body's callees include `crime_i2c_start` (at 0x40603c) and `crime_i2c_sendbyte` (at 0x406050).
- `dc_read` (`usr/sbin/Confidence/dualchannel`, 0x405b4c, 236 bytes): **established.**
  Reads the card's status byte: a start, the address byte 0x7f, a one-byte receive into the caller's buffer and a stop, on the bus of the detected host. Matching the description to the code: calling `crime_i2c_start` at 0x405b7c and `crime_i2c_sendbyte` at 0x405b90.
- `dc_disp_mode` (`usr/sbin/Confidence/dualchannel`, 0x405c38, 260 bytes): **established.**
  Sets the card's display mode. It replaces bits 1:0 of the control register with the argument's low two bits and sends it (start, 0x7e, register OR 0x70, stop). The tests use 0 and 1 for the two datapath views and 2 for the memory test, and the exit paths write 3. Verified against the disassembly, which shows `crime_i2c_start` called at 0x405c80 and `crime_i2c_sendbyte` called at 0x405c94.
- `FrameSync` (`usr/sbin/Confidence/dualchannel`, 0x40674c, 220 bytes): **established.**
  Waits a number of video frames: it reads the video-sync counter with `glXGetVideoSyncSGI`, then blocks in `glXWaitVideoSyncSGI` with divisor 2n and remainder (n + counter) mod 2n, so the wait is n frames of the 2-field counter; with verbosity above 3 it prints the start and end counts. The disassembly puts the calls to `glXGetVideoSyncSGI` at 0x40676c and to `fprintf` at 0x4067a0.
- `print_failure` (`usr/sbin/Confidence/dualchannel`, 0x406c10, 712 bytes): **established.**
  Reports a failed test word. With verbosity 0 it prints `+MESSAGE ` and a catalogue text, `uxconfidence:246` "Dual Channel DRAM test failed" when bit 8 of the word is set and `uxconfidence:247` "Dual Channel Datapath test failed" otherwise, then calls `clean_up`. Otherwise it prints "* Failure (Total: %3d) *" and the detail: for the datapath "Mux/Demux: " with "Left  Datapath" when bit 6 is set and "Right Datapath" when it is not, "Low  Pixel" for bit 5 set or "High Pixel" for clear with the bit number from the low five bits, and "Expected %d, Found %d" with bit 7 and its complement; for the memory "DRAM: " with "Right DRAM" when bit 6 is set and "Left  DRAM" when it is not (the opposite sense to the datapath text), then the pixel and bit number. In the listing the body calls `gettxt` at 0x406c98 and `strcat` at 0x406cb0.
- `runBusCheck` (`usr/sbin/Confidence/dualchannel`, 0x40725c, 788 bytes): **established.**
  Diagnostic that walks the datapath bits by pixel value: for each of 24 single-bit colours and then their 24 complements it clears the window to the colour in mode 0, waits 2 frames and calls `check_bus` in mode 0 and again in mode 1, then calls `clean_up`. No function of the binary calls it: the -b option sets a flag that nothing reads. The listing shows calls to `fprintf` (site 0x407298) and `dc_disp_mode` (site 0x4072c0), in that order.
- `check_bus` (`usr/sbin/Confidence/dualchannel`, 0x407570, 504 bytes): **established.**
  Prints one line of the bus check for a pixel value: "Pixel: %6x," then "Left:  |" or "Right: |" by the current mode (nonzero mode means the left label), and for the two pixels of a pair in turn the 24 bits from bit 23 down to bit 0 as '1' (pass bit clear) or '0' (pass bit set), loading each test word from the bit number, the pixel select and the path select, with a space every 8 bits and "|" between the pixels. Read against the listing: `fprintf` is called at 0x4075cc, `load_testmode` at 0x407660.
- `probe_dcd` (`usr/sbin/Confidence/dualchannel`, 0x407768, 288 bytes): **established.**
  Looks for the option card in the hardware inventory: it walks `getinvent` entries until one has class 17 and type 3, prints "Found dual channel display board" and the class and type when verbosity is above 1, and returns 1; when the list ends it prints "Did not Find dual channel display board" and returns 0. Two of its callees, `setinvent` at 0x407788 and `getinvent` at 0x407798, mark the steps described.
- `set_timing` (`usr/sbin/Confidence/dualchannel`, 0x407888, 536 bytes): **established.**
  Switches the display timing for the test and back. With 1 it saves the gamma value from `/etc/config/system.glGammaVal` (default "1.7"), sets gamma 1.0 with the local gamma routine, reads the current timing name from the timing file chosen by `main` (default format when the file cannot be read) and runs `/usr/gfx/setmon -n 2@1280x1024_60`; with 0 it restores the saved gamma and runs `setmon -n` with the saved timing name. The decompiled body and the listing agree on the calls `open` at 0x4078b0 and `read` at 0x4078d0.
- `FUN_00407ab8` (`usr/sbin/Confidence/dualchannel`, 0x407ab8, 428 bytes): **established.**
  Builds a gamma table: for a table of n 16-bit entries it stores floor(65535 * (i / (n - 1))^(1/g) + 0.5) (negative results as 0xffff), with an allocation message "gamma: could not allocate memory." on failure. Checked in the listing: it reaches `malloc` at 0x407afc before `fprintf` at 0x407b20.
- `FUN_00407c60` (`usr/sbin/Confidence/dualchannel`, 0x407c60, 608 bytes): **established.**
  Applies a gamma value through the X video-control extension: the value from `atof` must lie strictly between 0 and 20 (otherwise "gamma: gammavalue %f out of range [0., 20.]."), it opens the default display, checks `XSGIvcQueryVersion` and `XSGIvcQueryScreenGammaMaps` (messages "gamma: XSGIvc extension not supported." and "gamma not supported on this screen."), queries the first channel's map and its size, builds the table with `FUN_00407ab8` and stores it with `XSGIvcStoreGammaColors16`. Callees seen while reading: `atof` at 0x407c7c, `XOpenDisplay` at 0x407ccc.

## Display-format and timing tool, `usr/gfx/setmon`

- `odysetmon` (`usr/gfx/setmon`, 0x1000d864, 2252 bytes): **established.**
  The ODYSSEY path of `setmon`: it never talks to the kernel driver directly but through the X video-control extension and a timing file. Argument checks first: framebuffer depth must be 0, 8, 16 or 32 ("setmon: Invalid framebuffer depth") and the accumulation-buffer type -1, 0 or 1 ("setmon: Invalid accumulation buffer type"). With the write flag it requires root ("setmon: root privileges needed to save timing"), checks that the format's `.vfo` file can be opened (path from `odyGetVOFpath`), then stats `/var/X11/Xvc/Odyssey%d_TimingTable` (pipe number) and writes it as three lines: the format name, the colour-buffer depth (8 when 0) and the accumulation-buffer value (0 when -1), re-reading the old depth lines from an existing file when the options leave them out. With the change flag it opens the display for the pipe, then applies in order: the framelock target (`odyDoFramelock`, or a zeroed 260-byte parameter 3 when no framelock is wanted), the master or slave sync setting (-c m prints "Setmon is turning ON csync_en" and sets parameter 2 to 0, -c s prints "Setmon is turning OFF csync_en" and sets it to 1; any other letter prints "setmon: use -c m|s"), the external or internal genlock source (`XSGIvcSetScreenInputSyncSource` with -2 or -1), and the video format itself. For the format it parses `%dx%d_`; the sizes 1280x492 and 1280x984 and the type codes 0xf, 0x1b and 0x1c (stereo formats) switch the stereo mode (`XSGISetStereoMode` with the values 492 and 532 and mode 1 for 0x1b or 2 for 0x1c) and build the name `1280x492_120s` or `1280x492_114s`, the latter when two words of the info structure (at +0x28 and +0x18 from the record at the first argument plus 0x28) are 0 and 2; every other format first turns stereo off when it is on and copies the name. The name then goes to an unnamed helper at 0x1000c8bc with the display, the screen and the verbose flag, which loads the format; the splitter option calls another unnamed helper, 0x1000cbc8, in its place. The DAC-gain option ends the routine with `XSGIvcSetOutputGain` and a value of 5. Both the call to `fprintf` at 0x1000d8e0 and the call to `exit` at 0x1000d8ec appear in the listing.

Each failed route lowers the result by one. Last it records the value in `CHIC_regs` for 0xd4 or `CCX_regs` for 0xaa.
- `readReg` (`usr/diags/compositor/bin/sting`, 0x1002bdec, 1312 bytes): **established.**
  Reads a compositor register by the same routes (arguments: chip address byte, register, output bytes, count; result 0, or a negative count of failed routes). Without a two-wire route it calls `readReg_no_i2c`. For the read addresses 0xab and 0xd5 and the same flags it uses platform parameter 7: a 12-byte block is sent with `XSGIvcSetPlatformParameter`, read back with `XSGIvcQueryPlatformParameter` (a zero reply counts as failure), flushed, and the value is cut into bytes with `int2Bytes`; on the `odyssey` route it calls `ody_comp_reg_access` and on the `voyager` route `agp_comp_reg_access` for register 0x57 and `usb_comp_reg_access` otherwise. ## Compositor test program (`usr/diags/compositor/bin/sting`): the two-wire master

Release IRIX 6.5.30m, N32. **Established** here means the decompilation was read in full and the listing was checked at the addresses cited. The routines drive the two-wire master that sits inside the compositor chip block `CCX`. Two unnamed helpers carry the register traffic: the helper at 0x1002d3f4 reads the master's status word by calling `readReg_4Bytes` (0x1002c73c) with chip address byte 0xab and the register number held in the byte at 0x1005586d, and the helper at 0x1002d444 writes the control word with `writeReg_4Bytes` (0x1002c30c) and chip address byte 0xaa and the register number in the byte at 0x1005586c. `selectI2C` fills those two bytes: bus 0 uses control register 0x55 and status register 0x58, bus 1 uses 0x56 and 0x59. Bits of the control word, from the routines below and their own log texts: bits 7:0 data or slave address byte, bit 9 the transfer bit (the log of `i2c_recvbyte` calls 0x200 "xfer_bit"), bit 10 set on the last byte of a receive (**inferred** from the callers that set it on the final byte only), bit 11 stop (the log calls 0x800 the stop bit), bit 12 send, bits 14 and 13 the force-stop and force-idle pair (the log calls 0x6000 "f_stop & f_idle"), and bit 8 together with send and transfer in the start word 0x1300 (**inferred**, no log names it). In the status word bit 8 is the slave's acknowledge and is active low (the log of `i2c_start` says "ACK_BIT is ... (active low)" and "Received ACK for start by slave"), bit 22 is the busy bit (`i2c_sendbyte` logs "found busy_bit=0, aborting") and bits 21:20 flag a failed read (`i2c_recvbyte` logs "Read transaction failed!").

- `i2c_api_reset_bus` (`usr/diags/compositor/bin/sting`, 0x1002cde8, 100 bytes): **established.**
  Returns the selected bus to idle by calling `i2c_stop` at 0x1002ce18 (no arguments; result 0, or the negative stop result unchanged). It logs the call at level 7 first. `readReg` and `writeReg` call it before every raw transfer.
- `i2c_start` (`usr/diags/compositor/bin/sting`, 0x1002d48c, 504 bytes): **established.**
  Begins a transfer by writing the slave address byte (argument: the address byte; result 0, or -18). It reads the status word once for the log, writes the control word with the address in bits 7:0 and 0x1300 (send, transfer and start), then polls the status word until bit 8 (the active-low acknowledge) is clear, sleeping one second between reads for at most 0x80 reads (the compare against 0x80 after the `usleep` call). A timeout logs "Timeout!" and returns -18; bit 8 still set after the loop logs "Failed to receive ACK from slave" and returns -18, and a clear bit logs "Received ACK for start by slave" and returns 0.
- `i2c_stop` (`usr/diags/compositor/bin/sting`, 0x1002d684, 328 bytes): **established.**
  Ends a transfer and clears the bus (no arguments; no result). It reads the status word, writes 0x800 (the stop bit) to the control register, reads the status again, then writes 0x6000 to the control register 0x80 times in a loop and reads the status a last time. Each step logs the status at level 8.
- `i2c_sendbyte` (`usr/diags/compositor/bin/sting`, 0x1002d7cc, 568 bytes): **established.**
  Sends one data byte (arguments: byte, last-byte flag; result 0, or -18). It then writes the control word with the byte in bits 7:0, 0x1200 and bit 11 when the flag is nonzero, and polls status bit 8 as `i2c_start` does, with the same one-second sleeps and the limit of 0x80.
- `i2c_recvbyte` (`usr/diags/compositor/bin/sting`, 0x1002da04, 272 bytes): **established.**
  Receives one data byte (arguments: output pointer, last-byte flag; result 0, or -18). - `i2c_api_write` (`usr/diags/compositor/bin/sting`, 0x1002ce4c, 320 bytes): **established.**
  Writes a packet to a slave and ends with a stop (arguments: slave address byte, packet pointer, data byte count; result the number of data bytes sent, -17 when the start fails). A null packet fails the assert "mes!=NULL" in `i2c_api.c` at line 0x7d. After `i2c_start` it sends count plus one bytes with `i2c_sendbyte` (the packet's first byte is the register number) and sets the last-byte flag only when the byte index equals the count; a failed byte logs the byte and its index and ends the loop. - `i2c_api_write_no_stop` (`usr/diags/compositor/bin/sting`, 0x1002cf8c, 276 bytes): **established.**
  Writes the first half of a combined transfer without a stop (arguments: slave address byte, packet pointer, byte count; result the number of bytes sent, -17 when the start fails). - `i2c_api_read` (`usr/diags/compositor/bin/sting`, 0x1002d298, 348 bytes): **established.**
  Reads bytes from a slave after writing a command (arguments: write address byte, read address byte, command pointer, command length, output pointer, byte count; result the number of bytes read, -16 when the command write is short, -17 when the second start fails). The assert on "mes!=NULL" is at line 0xe0. The command goes out through `i2c_api_write_no_stop` and must be sent in full; `i2c_start` is then called with the read address and `i2c_recvbyte` is called once per byte with the last-byte flag 1 each time; a failed byte ends the loop and returns the count so far. `readReg` passes the register as the command.
- `i2c_api_read_all` (`usr/diags/compositor/bin/sting`, 0x1002d0a0, 504 bytes): **established.**
  Reads a block that carries its own length (arguments: write address byte, read address byte, command pointer, command length, output pointer; result the byte index reached, -16 or -17 on failure). The command goes out with `i2c_api_write_no_stop` and the read address is started as in `i2c_api_read` (the assert on "mes!=NULL" is at line 0xb2). The first received byte is the sender's address (the failure text is "Failed to read source address") and is discarded, the second is the length ("Failed to get a valid length") and is stored at the output's first byte as the count n, and then up to n more bytes are received into the following positions; the last-byte flag is raised once the position counter reaches n minus 1 and stays raised for the final receive, so the last two data bytes carry it. `i2c_stop` runs at the end and a failing stop returns -17.

## Compositor test program (`usr/diags/compositor/bin/sting`): the CRC checks

The video tests compare a signature the compositor chips compute in hardware with one the program computes from the frame it drew. The signature is a 16-bit linear feedback register with feedback mask 0xb400 (shift right by one; when the bit shifted out, exclusive-ORed with the next data bit, is 1, the mask is exclusive-ORed in), fed one data bit at a time in index order. The four `crc16...` routines are that register unrolled for a fixed number of data bits per call; **established** by reading all 16 output expressions of each routine and checking that the data-bit columns form one chain under the register step starting from 0xb400 and that the state part equals the register stepped that many times. Each routine was also run in a MIPS interpreter on 40 random old-register and data-bit sets (register bit i in word i, data bits in index order): every result equals the register stepped bit by bit, and one 1 followed by 23 zeros from a zero register gives 0x5b14 through `crc1624`.

- `crc1624` (`usr/diags/compositor/bin/sting`, 0x10025f74, 1604 bytes): **established.**
  Advances the signature register by 24 data bits in one call (arguments: old register as 16 separate 0/1 words, 24 data bit words, new register as 16 words). Each of the 16 outputs is an exclusive-OR of 5 to 11 terms of the old register and the data; the first 16 data bits enter with the same terms as the register bits, and the last 8 enter alone. Its one caller is `sw_crc_ctx_output` at 0x10024ec4.
- `crc1648` (`usr/diags/compositor/bin/sting`, 0x10025048, 3884 bytes): **established.**
  The same register stepped by 48 data bits per call, which is six input bytes. It is called by `sw_crc_ccx_input` at 0x10024a68 only.
- `crc1696` (`usr/diags/compositor/bin/sting`, 0x100265b8, 7452 bytes): **established.**
  The same register stepped by 96 data bits per call (twelve bytes), called by `sw_crc_ctx_input` at 0x10024d68 only.
- `crc16120` (`usr/diags/compositor/bin/sting`, 0x100282d4, 9052 bytes): **established.**
  The same register stepped by 120 data bits per call (twelve 10-bit values), called by `sw_crc_ccx_output` at 0x10024c0c only.
- `sw_crc_ccx_input` (`usr/diags/compositor/bin/sting`, 0x10024908, 540 bytes): **established.**
  Computes the signature the compositor chip CCX should see on its input from a frame buffer (arguments: bytes, byte count). It splits each byte into 8 bits, low bit first, collects 48 bits and calls `crc1648` (0x10024a68), copying the new register back with `array_copy` (0x10024a7c); the result is the 16 register bits packed into one word. When the parameter `use_sw_hack` is set it leaves out the first six bytes of every 0xf00-byte block. The count of RGB components processed is logged at level 3.
- `sw_crc_ccx_output` (`usr/diags/compositor/bin/sting`, 0x10024b24, 348 bytes): **established.**
  Computes the expected signature at the chip's output from words of pixel data (arguments: word array, word count). Each word contributes its low 10 bits, low bit first; every 120 bits it calls `crc16120` (0x10024c0c) and copies the register back (0x10024bb0). It returns the register packed into one 16-bit word.
- `sw_crc_ctx_input` (`usr/diags/compositor/bin/sting`, 0x10024c80, 348 bytes): **established.**
  Computes the expected input signature for the transform chip: each byte of the data contributes its 8 bits low bit first, and every 96 bits `crc1696` (0x10024d68) steps the register, which `array_copy` copies back at 0x10024d0c. The result is the packed 16-bit register.
- `sw_crc_ctx_output` (`usr/diags/compositor/bin/sting`, 0x10024ddc, 348 bytes): **established.**
  Computes the expected output signature of the transform chip with 24 bits per step: the same bit loop over bytes, with `crc1624` called at 0x10024ec4 after every 24 bits and the register copied back by `array_copy` at 0x10024e68. `sw_atpg_crc` calls it at 0x10023dc4.

## Compositor test program (`usr/diags/compositor/bin/sting`): clock, timing and format download

Same conventions as above. The clock chain of the compositor is a pixel-clock synthesizer on the two-wire bus (write address 0x4c, read address 0x4d), a digital transmitter (0x70 and 0x71), the video timing unit in CCX (registers 0 to 0x50 of chip address byte 0xaa) and the master reset in CHIC.

- `freq_check` (`usr/diags/compositor/bin/sting`, 0x1002df1c, 180 bytes): **established.**
  Checks that a format's pixel clock is in the range the compositor supports: it logs the frequency in MHz at level 2 and returns 0 for 100 MHz up to but not including 210 MHz, otherwise logs "Only pixel frequencies between 100 and 210 MHz supported." and returns -1. `run_vofprog` calls it at 0x1002ee58 and `cmp_cmb_dnld` at 0x1002f648.
- `load_clock_settings` (`usr/diags/compositor/bin/sting`, 0x1002e018, 368 bytes): **established.**
  Writes the clock-count word of the compositor's video timing unit, `CCX_VTC_CLK_CNT` (register 1 of chip address byte 0xaa), with 0x1c31 for a pixel clock from 100 up to 210 MHz and 0x31 for one below 100 MHz (after an error text saying only 100 to 210 MHz is supported and "Continuing anyway.."). A clock of 210 MHz or more logs "Aborting.." and returns -1 without writing. `run_vofprog` calls it at 0x1002eeb4 and `cmp_cmb_dnld` at 0x1002f6b8.
- `program_pll` (`usr/diags/compositor/bin/sting`, 0x1002e188, 680 bytes): **established.**
  Programs the pixel-clock synthesizer, a two-wire device at write address 0x4c (argument: the pixel clock in Hz). It searches reference dividers from 3 to 129 against a 12 MHz reference, needing the phase detector input 12/divider between 0.008 and 0.5 MHz, takes the feedback divider floor(f x divider / 12), and keeps the divider pair whose output differs least from the wanted clock while the output times a post factor (4 below 40 MHz, 2 from 40 MHz) lies between 100 and 500 MHz. It then writes eight registers with `writeReg_1Byte`: register 0 gets 0x41, 6 gets 1, 7 gets the reference divider minus 2 with bit 7 set, 1 gets 1, 2 and 3 get the low and high bytes of the feedback divider minus 8, 4 gets 0x80, 5 gets 0 and 8 gets 0x50, and any failed write makes it return -1. The search and the register packing are the first clock-part rules of `usr/gfx/ucode/vfc/rules/VPro_Board.def` (`docs/video-format-sources.md`). `run_vofprog` calls it at 0x1002eee0.
- `short_program_pll` (`usr/diags/compositor/bin/sting`, 0x1002e430, 184 bytes): **established.**
  Reprograms the same synthesizer for an external sync source after genlock is chosen: it writes 0x5e to register 0, 0 to register 7 and 0 to register 4 of device 0x4c, three single-byte writes, and returns -1 if any fails. `run_vofprog` calls it at 0x1002f0fc and `cmp_cmb_dnld` at 0x1002f9f4.
- `program_tmds` (`usr/diags/compositor/bin/sting`, 0x1002e4e8, 260 bytes): **established.**
  Turns on the digital transmitter, a two-wire device at write address 0x70: it writes 0 to register 0xe, 0x3d to register 8, 0x21 to register 9, 0x80 to register 10 and 0x89 to register 0xc and returns -1 if any write fails. `run_vofprog` calls it at 0x1002ef0c and `cmp_cmb_dnld` at 0x1002f710.
- `reset_clocks` (`usr/diags/compositor/bin/sting`, 0x1002e9c4, 72 bytes): **established.**

- `last_write_to_vid_cntl` (`usr/diags/compositor/bin/sting`, 0x1002ea54, 196 bytes): **established.**

## Compositor test program (`usr/diags/compositor/bin/sting`): tile registers and tile images

The tiling unit of the CCX chip (chip address bytes 0xaa write, 0xab read) holds four rectangles, "f0" to "f3", one per compositor input port, and a background selector. The eight registers 0x23 to 0x2a are `CCX_TILE_F0_X` to `CCX_TILE_F3_Y` in the table of `docs/compositor-registers.md`. Every function below was read in full in the 6.5.30m decompilation with the strings resolved through the global offset table. The tile description the test code passes around is a 0x48-byte record: byte +0 the background selection (0 to 3), bytes +1 to +4 an enable flag for tile 0 to 3, words +0x08 to +0x24 the x begin and x end of tiles 0 to 3 (begin at +0x08, +0x10, +0x18, +0x20), words +0x28 to +0x44 the y begin and y end (begin at +0x28, +0x30, +0x38, +0x40). The register layout below is **established** from `hw_tile_set` and `sw_get_tile_regs`; what the rectangles mean on the output (a tile's pixels replace the background where they overlap) is **inferred** from `which_tile` and `frame_concat`.

- `hw_tile_set` (`usr/diags/compositor/bin/sting`, 0x100359d8, 4184 bytes): **established.**
  Programs the tiling unit from a tile record (arguments: record, force flag). A failed write logs error 0x59ec "FAILED to WRITE ALL MEMORIES". It finishes by restoring auto-config mode and reports a pass when the error count is 0.

## Compositor test program (`usr/diags/compositor/bin/sting`): format print, external-device and PROM tests

Registers named here are the entries of the three tables in `docs/compositor-registers.md`. None of the four tests below has a direct caller in the binary: they are reached through the function pointers in `testList` (`docs/diagnostics-and-libgl-functions.md`, "Test table"), which is **established** by the table's contents and the lack of any direct call or global offset table load of them.

- `TEST_format` (`usr/diags/compositor/bin/sting`, 0x1000c498, 1296 bytes): **established.**
  Test 1200, "Print the VOF format structure". It sets access mode 2 and calls `cmp_cmb_dnld`, prints thirteen blank lines, then tries `fillStruct` on "1280x1024_60", "1280x1024_72", "1280x1024_75", "1280x1024_96s" and "1920x1200_60" in turn (each failure logs error 0x28 "Could not read file" and ends with a failed result; the code reaches the print only when the last read succeeds, since every attempt is nested in the previous one succeeding, so the printed structure is the last format, 1920x1200_60). It prints the format's state count, frames per second, fields per frame, total and active lines and pixels, swaps per frame, the horizontal active, back porch, sync and front porch in pixels, three vertical sections with each value in pixels and lines (pixels divided by total pixels per line) and the line count of each of 32 states. It ends with a pass result.
- `fillStruct` (`usr/diags/compositor/bin/sting`, 0x1002dd14, 520 bytes): **established.**
  Reads one video format file into a 0x558-byte format record (arguments: format name, record). It zeroes the record, calls `vfmtReadCmp1Format` and turns its result into text: 1 logs "could not open file", 2 "has invalid data" and 3 "illegal path", each as error 0xbcc and a -1 return. On success it logs at debug level 3 the total lines per frame (+0x1e4), total pixels per line (+0x1e8), active lines (+0x1ec), the frame rate as a double at +0x1d8, and the pixel frequency, computed as frame rate times total lines times total pixels divided by 1000000.0. `TEST_format` calls it at 0x1000c5b0 and four more places; `cmp_vfo_dnld` calls it at 0x1002dc70 and `run_vofprog` at 0x1002edf0.
- `TEST_extDiscover` (`usr/diags/compositor/bin/sting`, 0x1000e704, 2768 bytes): **established.**
  Test 980, "External discovery test": checks that the identification registers of the devices around the compositor read as expected. It sets access mode 2, downloads the format (`cmp_cmb_dnld`) and then reads: the CTX identity register 0 of chip 0xad as two bytes, which must be 0x86b7 (error 0xbba on a failed read); the clock generator's version register 0x10 (chip address 0x4d, one byte), which must be 0x17, and its revision register 0x11, which must be 0x01 (error 0xbbd); then it initialises the TMDS transmitter by writing 0x3d, 0x21, 0x80, 0x89 and 0x00 to registers 8, 9, 0xa, 0xc and 0xe of address 0x70 (error 0xbbe on failure ends the test), and reads the transmitter's registers at address 0x71: vendor identity low (0) must be 0x01 and high (1) 0x00, device identity low (2) 0x08 and high (3) 0x00, revision (4) 0x01. Finally it writes 0x6b and then 0x94 to register 0x15 at address 0x70 and reads each back from 0x71 to prove the register holds a written value. Every mismatch logs error 0 with the expected value and counts; the result is a pass only when the count is 0. The register numbering of the clock generator and the transmitter comes from the strings of this function (`CHIP_VERSION`, `CHIP_REVISION`, `VEND_IDLO`, `VEND_IDHI`, `DEV_IDLO`, `DEV_IDHI`, `DEV_REVISION`, `WR_AN_1`); the part numbers behind the addresses are **unknown** from this binary.
- `TEST_extDev` (`usr/diags/compositor/bin/sting`, 0x1000c9a8, 7516 bytes): **established.**
  Test 981, "External device test": a write and read-back test of the same three devices. After access mode 2 and the format download it checks the CTX identity (0x86b7 at register 0 of chip 0xad); then writes 0x5be9 to CTX register 5 (`CRC_INPUT`, write address 0xac) and reads it back from 0xad, writes 0x14f8 to register 6 (`CRC_OUTPUT`) and reads it back, checks that register 5 still holds 0x5be9 after the second write, writes 0x7ae3 to register 5 and checks that register 6 still holds 0x14f8, writes 0x973c to register 6 and checks it, and finally re-reads register 0 (0x86b7) and register 5 (0x7ae3). For the clock generator it checks the version (0x17) and revision (0x01), then writes 0x19, 0x3d and 0x01 in turn to the output-enable register 6 (write address 0x4c) and reads each back from 0x4d. For the transmitter it initialises it with the same five writes as `TEST_extDiscover`, then writes the eight authentication-value registers 0x15 to 0x1c at address 0x70 with 0x9e, 0xf1, 0xac, 0x44, 0x90, 0xb2, 0x13 and 0x5d and reads them back from 0x71; the first seven reads are compared with the written values and the last (register 0x1c) is compared with 0x6f, not the 0x5d that was written. Errors use the codes 0xbba (CTX), 0xbbd (clock generator) and 0xbbe (transmitter); the pass line is "External Device Test FINISHED SUCCESSFULLY". The expected 0x6f for the last register, against 0x5d written, is read from the code (**established**); why the expected value differs from the written one is **unknown**.
- `load_data` (`usr/diags/compositor/bin/sting`, 0x100109dc, 816 bytes): **established.**
  Parses one FPGA configuration text file into the software image (arguments: stream, line count, image array, starting word index). It reads the stream one character at a time with `fscanf` and runs a five-state machine: state 0 waits for a newline at the end of a line header; state 1 skips eight characters; state 2 reads hexadecimal digits, eight to a 32-bit word with the first digit in the top nibble, adding each word into the array (rejecting a non-hex character with "Invalid char (%c) at line %d" and an index of 0x7ffff or more with "SW array boundary exceeded", both error 0xbcc); after 32 digits state 3 waits for the newline; state 4 is the end of the file. After every 0x42 words (0x41 steps) the index skips 0x3f words, so the image is laid out in 0x80-word pages with 0x42 words used per page. It returns the number of words stored or -1. `TEST_PROMread` calls it at 0x10011110 and 0x10011168.
- `read_compare_flash` (`usr/diags/compositor/bin/sting`, 0x10010250, 1932 bytes): **established.**
  Reads a stretch of the configuration flash through the CHIC chip and compares it with the software image (arguments: byte start address, word count, image array, fast flag, chip flag 0 = CCX and 1 = CTX). Every register transaction is retried up to 1000 times (error 0xbbb, message "I2C/USB transaction failed! Retrying..(n)") and a stuck one returns -17. The sequence on the CHIC write address 0xd4 is: write 0 to register 2 (`CHIC_FLASH_STOP`); write the start address to register 0 (`CHIC_FLASH_START_ADDR`); poll register 5 of read address 0xd5 (`CHIC_STATUS`) until bit 3 is set ("Waiting for Flash to become available", return -552 after 1000 tries); write 0 to register 4 of 0xd4, which starts the read (the table lists register 4 only as the read-data register, so this write number is not named in it); then for each word, unless the fast flag is set, poll status bit 4 until the word is ready ("Waiting for Flash word to become ready", error 0xbbb and -552 after 1000 tries) and read register 4 of 0xd5 for the word. A word that differs from the image is a miscompare (error 24000 "Miscompare of data at Flash address %#x: exp %#x got %#x", counted in `miscomp_ccx_cnt` or `miscomp_ctx_cnt`). On the first pass a mismatch whose read value `corrupted_data` flags as bus noise is only marked: it sets `marked_words` for the word and `marked_pages` for its flash page and the function returns -553 afterwards so the caller re-checks those pages; on later passes only marked words are reported. After 0x42 words it skips ahead 0x3f image words, matching the layout `load_data` builds. It logs progress every 1024 words, writes 0 to register 2 again to stop the controller, and returns 0, -1 when miscompares were counted, or -553 when words were marked.
- `TEST_PROMread` (`usr/diags/compositor/bin/sting`, 0x10010d0c, 2948 bytes): **established.**
  Test 825, "PROM readback test": reads back the flash that holds the CCX and CTX configuration and compares it with the configuration files. It sets access mode 2, takes the file names from `CCX_CONFIG_FILE` and `CTX_CONFIG_FILE` (defaults are string-table names the decompiler left unresolved) and the start addresses from `CCX_CONFIG_FILE_START` (default 0) and `CTX_CONFIG_FILE_START` (default 0x188000), counts the lines of each file, loads both into one 0x80000-word software image with `load_data` and then calls `read_compare_flash` for CCX and for CTX. Unless `extensive` is given, only the first 0x26ac CCX words and 0x7bc CTX words are compared (a parameter selects the fast read). When the first pass marks pages (return -553) it clears the first-pass flag and re-reads each marked page of 0x42 words ("Double checking page"), and an aborted test (returns -17, -16 or -552) is reported as such. The report lines give the miscompare count over the words checked and "configuration readback SUCCESSFUL" or "FAILED" per chip; the test passes only when neither chip failed and both miscompare counts are 0.
