# VPro tool functions, one entry each

Release IRIX 6.5.30m. Each entry starts with the function, then the shipped binary, its address in that binary and its size in bytes. Labels are **established** (the whole body was read in the Ghidra decompilation and the listing, with the `$gp` fix-up and jump-table scripts of `ghidra/scripts/` applied first) or **inferred**. An entry speaks for the binary it names. Driver-side numbers are in `docs/ioctls.md` and `docs/driver-functions.md`.

## Dual-channel confidence test, `usr/sbin/Confidence/dualchannel`

A confidence program for the dual-channel display option card: it draws patterns in a GL window, switches the card between its pass-through, multiplexed and test modes over a two-wire bus, and reads back one status bit per test. It supports two hosts through one code path, selected by the board name the kernel reports: a `CRM` board uses the bus ioctl 0x560b on the graphics device (the `crime_i2c_*` routines) and an `ODYSSEY` board uses private ioctl 0x6f640021 (the `odsy_i2c_*` routines). Control byte format of the card, from `dc_disp_mode`, `load_testmode` and `init_pass`: the card is addressed at 0x7e for a write and 0x7f for a read; every written byte after the address has 0x70 in its high bits and the 8-bit control register in the low bits (bits 1:0 display mode, bit 2 shift clock, bit 3 data or strobe); a read returns one byte whose bit 4 is the pass bit of the last test.

- `main` (`usr/sbin/Confidence/dualchannel`, 0x403520, 3664 bytes): **established.**
  Whole-program driver read in full. It opens the graphics device (flags 0x802), asks the board name with ioctl 0x66 (a 16-byte request into a 40-byte buffer) and compares it with `CRM` (host type 1) and `ODYSSEY` (host type 2); any other name prints "Dual channel display is not supported on %s graphics" and exits 1. For each host it copies a preset timing-file path (`/var/X11/Xvc/Crm0_TimingTable` or `/var/X11/Xvc/Odyssey0_TimingTable`) and a default format name (`2@1280x1024_75` for CRM, `2@1280x1024_72` for ODYSSEY) into globals. A first argument `-probe` runs `probe_dcd` and prints `+OK MANUAL dualchannel ConfidenceErrors dualchannel` when the card is present; a first argument `-test` sets the confidence flag and calls `set_timing(1)`. The options are `v:r:p:cfsib`: -v verbosity, -r retest count (the failure limit is half of it), -p first pattern, -c continuous, -f stop and wait after each failure, -s single step, -i the endless bus write test, -b a bus-check flag that no routine reads. It then opens an X connection, insists on a 32-bit GL visual (otherwise it prints "Dual Channel confidence test requires 32 bit frame buffer configuration"), makes a full-screen undecorated window with an empty cursor titled "Dual Channel Diagnostic", attaches the board with ioctl 0x67 (a word of 0 and 0x02000000), installs `clean_up` for SIGINT, SIGQUIT and SIGHUP, optionally runs the endless bus test, and on the first expose event calls `reshape`, `runPattern`, `runDiagnostic` and `clean_up`. In the listing the body calls `setlocale` at 0x4035a0 and `setcat` at 0x4035b4.
- `runDiagnostic` (`usr/sbin/Confidence/dualchannel`, 0x404458, 624 bytes): **established.**
  Runs the test loop and reports. It resets the bus (`crime_i2c_reset` or `odsy_i2c_reset`), reads the control register once into `dc_ctlreg` with `dc_read`, then repeats `DatapathTest` and `DramTest`, counting runs. A run without failures prints the catalogue text `uxconfidence:245`, "Dual Channel tests passed", behind the `+MESSAGE ` prefix when verbosity is 0 and plainly when it is not; a failing run prints "** Runs: %d, Errors: %d **". With the continuous flag set the loop restarts after clearing the test counter; otherwise it ends with `dc_disp_mode(3)`, restores the display timing through `set_timing(0)` when the confidence flag is set, and exits 0. The listing shows calls to `crime_i2c_reset` (site 0x4044a8) and `odsy_i2c_reset` (site 0x4044c8), in that order.
- `clean_up` (`usr/sbin/Confidence/dualchannel`, 0x4046c8, 184 bytes): **established.**
  Signal handler and common exit. It resets the bus for the detected host, puts the card in mode 3 with `dc_disp_mode(3)`, runs `set_timing(0)` when the confidence flag is set and exits 0; `print_failure` and `runBusCheck` also finish through it. Read against the listing: `crime_i2c_reset` is called at 0x4046f8, `odsy_i2c_reset` at 0x404718.
- `reshape` (`usr/sbin/Confidence/dualchannel`, 0x404370, 232 bytes): **established.**
  Sets up a pixel-exact 2D view: viewport over the whole window, an orthographic projection of width by height, and a 0.375 pixel translation (the float 0x3ec00000) in x and y on the model-view matrix, so `glDrawPixels` and `glRasterPos2i` hit pixel centres. Two of its callees, `glViewport` at 0x4043a0 and `glMatrixMode` at 0x4043b4, mark the steps described.
- `runPattern` (`usr/sbin/Confidence/dualchannel`, 0x40529c, 2224 bytes): **established.**
  Fills the window-sized RGBA buffer with one of seven patterns chosen by the pattern number modulo 7, draws it with `glDrawPixels`, flushes and waits 60 frames with `FrameSync(60)` before the next one. The patterns are: 0 a black-to-white ramp that adds one to the grey level every 5 pixels; 1, 2 and 3 solid red, green and blue; 4 alternating white and black pixels; 5 two white and two black pixels in turn (its message text is the same as pattern 4's, "1 Pixel Black/White Stripes", although the stripes are two pixels wide); 6 a pulse and bar, with a single white pixel at a quarter of the width and white from half the width on, black elsewhere. Alpha is 0xff throughout. With a nonzero starting pattern the routine shows one pattern and decrements the number, otherwise it runs 7. The decompiled body and the listing agree on the calls `fprintf` at 0x4052f4 and `glRasterPos2i` at 0x405aa8.
- `DatapathTest` (`usr/sbin/Confidence/dualchannel`, 0x406160, 1516 bytes): **established.**
  Tests every bit of the 24-bit pixel path through the card. For bit i from 0 to 23 it sets mode 0, clears the window to the colour 1 << i (red, green and blue taken from bits 23:16, 15:8 and 7:0), flushes, and runs `run_test` with test words i | 0xc0, i | 0xe0 in mode 0 and i | 0x80, i | 0xa0 in mode 1; it then clears to the complement and runs i | 0x40, i | 0x60 in mode 0 and i, i | 0x20 in mode 1. In test words bit 5 picks the low or high pixel of the pair, bit 6 the left or right path, bit 7 the expected value and bit 8 the DRAM test (not set here). With verbosity set it follows with the even-odd select check: a window of alternating white and black pixels drawn in mode 2, then 24 tests each on the paths with words i | 0x60, i | 0xc0, i | 0x20 and i | 0x80. The two `diagnose_` calls at the ends do nothing. Checked in the listing: it reaches `fprintf` at 0x4061c4 before `dc_disp_mode` at 0x4061f4.
- `DramTest` (`usr/sbin/Confidence/dualchannel`, 0x406ed8, 544 bytes): **established.**
  Tests the card's frame memory with two images. It builds a buffer whose every pixel in row r has grey level r (low 8 bits, alpha 0xff), calls `checkDRAM`, then inverts the colour bytes of the whole buffer with 0xff and calls `checkDRAM` again; `diagnose_dram` is called with 0 and 1 after the two passes and does nothing. Callees seen while reading: `fprintf` at 0x406f10, `checkDRAM` at 0x406fc8.
- `checkDRAM` (`usr/sbin/Confidence/dualchannel`, 0x4070f8, 356 bytes): **established.**
  Writes the current buffer through the card and reads the DRAM-test bits back. It selects mode 2, draws the buffer with `glDrawPixels`, flushes, waits 3 frames and then runs `run_test` for the 24 bits i in mode 1 with words i | 0x140 and i | 0x160, and in mode 0 with i | 0x100 and i | 0x120; bit 8 of every word selects the memory comparison and bit 5 chooses between the low and high pixel of the pair. The first two calls of the body go to `dc_disp_mode` at 0x407120 and `glRasterPos2i` at 0x407138.
- `run_test` (`usr/sbin/Confidence/dualchannel`, 0x406828, 1000 bytes): **established.**
  Runs one test word. It loads the word with `load_testmode`, waits 1 frame (2 for the memory tests whose bit 8 is set), reads the card status and takes bit 4 as pass. On a failure it retests as many times as the retest option says (each retest reloads the word, strobes `init_pass` and, for the memory tests, flips the display mode twice), counts the failed retests and, when that count is above the failure limit, adds one to the failed-test count and calls `print_failure`, waiting for a keypress when the stop flag is set. A pass with the single-step flag waits for a keypress as well. The test counter goes up by one at the end. Instruction sites tie the description to the code: `load_testmode` is called at 0x406854 and `FrameSync` at 0x40687c.
- `load_testmode` (`usr/sbin/Confidence/dualchannel`, 0x405d3c, 720 bytes): **established.**
  Sends a nine-bit test word to the card's serial shift register. After the address byte 0x7e it clocks bits 0 to 8 of the word out one at a time: it clears the data and clock bits of the control register, puts the bit in bit 3, writes the byte with 0x70, raises the clock (bit 2) and writes it with 0x74; it ends with a strobe of bit 3 (high, then low). With verbosity above 2 it prints the word as " (%3d) Test mode: bit=%2d, lopix=%d, leftpath=%d cmpval=%d, lvsr=%d". Both host variants are in the same routine. Both the call to `fprintf` at 0x405db4 and the call to `crime_i2c_start` at 0x405e00 appear in the listing.
- `init_pass` (`usr/sbin/Confidence/dualchannel`, 0x40600c, 340 bytes): **established.**
  Sends the strobe alone: address byte 0x7e, the control register with bit 3 set and written with 0x78, then with bit 3 cleared and written with 0x70. The tests use it to restart the comparison after a mode change without shifting a new word. The body's callees include `crime_i2c_start` (at 0x40603c) and `crime_i2c_sendbyte` (at 0x406050).
- `dc_read` (`usr/sbin/Confidence/dualchannel`, 0x405b4c, 236 bytes): **established.**
  Reads the card's status byte: a start, the address byte 0x7f, a one-byte receive into the caller's buffer and a stop, on the bus of the detected host. Matching the description to the code: calling `crime_i2c_start` at 0x405b7c and `crime_i2c_sendbyte` at 0x405b90.
- `dc_disp_mode` (`usr/sbin/Confidence/dualchannel`, 0x405c38, 260 bytes): **established.**
  Sets the card's display mode. It replaces bits 1:0 of the control register with the argument's low two bits and sends it (start, 0x7e, register OR 0x70, stop). The tests use 0 and 1 for the two datapath views and 2 for the memory test, and the exit paths write 3. Verified against the disassembly, which shows `crime_i2c_start` called at 0x405c80 and `crime_i2c_sendbyte` called at 0x405c94.
- `FrameSync` (`usr/sbin/Confidence/dualchannel`, 0x40674c, 220 bytes): **established.**
  Waits a number of video frames: it reads the video-sync counter with `glXGetVideoSyncSGI`, then blocks in `glXWaitVideoSyncSGI` with divisor 2n and remainder (n + counter) mod 2n, so the wait is n frames of the 2-field counter; with verbosity above 3 it prints the start and end counts. The disassembly puts the calls to `glXGetVideoSyncSGI` at 0x40676c and to `fprintf` at 0x4067a0.
- `print_failure` (`usr/sbin/Confidence/dualchannel`, 0x406c10, 712 bytes): **established.**
  Reports a failed test word. With verbosity 0 it prints `+MESSAGE ` and a catalogue text, `uxconfidence:246` "Dual Channel DRAM test failed" when bit 8 of the word is set and `uxconfidence:247` "Dual Channel Datapath test failed" otherwise, then calls `clean_up`. Otherwise it prints "* Failure (Total: %3d) *" and the detail: for the datapath "Mux/Demux: " with "Left  Datapath" when bit 6 is set and "Right Datapath" when it is not, "Low  Pixel" for bit 5 set or "High Pixel" for clear with the bit number from the low five bits, and "Expected %d, Found %d" with bit 7 and its complement; for the memory "DRAM: " with "Right DRAM" when bit 6 is set and "Left  DRAM" when it is not (the opposite sense to the datapath text), then the pixel and bit number. In the listing the body calls `gettxt` at 0x406c98 and `strcat` at 0x406cb0.
- `runBusCheck` (`usr/sbin/Confidence/dualchannel`, 0x40725c, 788 bytes): **established.**
  Diagnostic that walks the datapath bits by pixel value: for each of 24 single-bit colours and then their 24 complements it clears the window to the colour in mode 0, waits 2 frames and calls `check_bus` in mode 0 and again in mode 1, then calls `clean_up`. No function of the binary calls it: the -b option sets a flag that nothing reads. The listing shows calls to `fprintf` (site 0x407298) and `dc_disp_mode` (site 0x4072c0), in that order.
- `check_bus` (`usr/sbin/Confidence/dualchannel`, 0x407570, 504 bytes): **established.**
  Prints one line of the bus check for a pixel value: "Pixel: %6x," then "Left:  |" or "Right: |" by the current mode (nonzero mode means the left label), and for the two pixels of a pair in turn the 24 bits from bit 23 down to bit 0 as '1' (pass bit clear) or '0' (pass bit set), loading each test word from the bit number, the pixel select and the path select, with a space every 8 bits and "|" between the pixels. Read against the listing: `fprintf` is called at 0x4075cc, `load_testmode` at 0x407660.
- `probe_dcd` (`usr/sbin/Confidence/dualchannel`, 0x407768, 288 bytes): **established.**
  Looks for the option card in the hardware inventory: it walks `getinvent` entries until one has class 17 and type 3, prints "Found dual channel display board" and the class and type when verbosity is above 1, and returns 1; when the list ends it prints "Did not Find dual channel display board" and returns 0. Two of its callees, `setinvent` at 0x407788 and `getinvent` at 0x407798, mark the steps described.
- `set_timing` (`usr/sbin/Confidence/dualchannel`, 0x407888, 536 bytes): **established.**
  Switches the display timing for the test and back. With 1 it saves the gamma value from `/etc/config/system.glGammaVal` (default "1.7"), sets gamma 1.0 with the local gamma routine, reads the current timing name from the timing file chosen by `main` (default format when the file cannot be read) and runs `/usr/gfx/setmon -n 2@1280x1024_60`; with 0 it restores the saved gamma and runs `setmon -n` with the saved timing name. The decompiled body and the listing agree on the calls `open` at 0x4078b0 and `read` at 0x4078d0.
- `FUN_00407ab8` (`usr/sbin/Confidence/dualchannel`, 0x407ab8, 428 bytes): **established.**
  Builds a gamma table: for a table of n 16-bit entries it stores floor(65535 * (i / (n - 1))^(1/g) + 0.5) (negative results as 0xffff), with an allocation message "gamma: could not allocate memory." on failure. Checked in the listing: it reaches `malloc` at 0x407afc before `fprintf` at 0x407b20.
- `FUN_00407c60` (`usr/sbin/Confidence/dualchannel`, 0x407c60, 608 bytes): **established.**
  Applies a gamma value through the X video-control extension: the value from `atof` must lie strictly between 0 and 20 (otherwise "gamma: gammavalue %f out of range [0., 20.]."), it opens the default display, checks `XSGIvcQueryVersion` and `XSGIvcQueryScreenGammaMaps` (messages "gamma: XSGIvc extension not supported." and "gamma not supported on this screen."), queries the first channel's map and its size, builds the table with `FUN_00407ab8` and stores it with `XSGIvcStoreGammaColors16`. Callees seen while reading: `atof` at 0x407c7c, `XOpenDisplay` at 0x407ccc.

## Display-format and timing tool, `usr/gfx/setmon`

- `odysetmon` (`usr/gfx/setmon`, 0x1000d864, 2252 bytes): **established.**
  The ODYSSEY path of `setmon`: it never talks to the kernel driver directly but through the X video-control extension and a timing file. Argument checks first: framebuffer depth must be 0, 8, 16 or 32 ("setmon: Invalid framebuffer depth") and the accumulation-buffer type -1, 0 or 1 ("setmon: Invalid accumulation buffer type"). With the write flag it requires root ("setmon: root privileges needed to save timing"), checks that the format's `.vfo` file can be opened (path from `odyGetVOFpath`), then stats `/var/X11/Xvc/Odyssey%d_TimingTable` (pipe number) and writes it as three lines: the format name, the colour-buffer depth (8 when 0) and the accumulation-buffer value (0 when -1), re-reading the old depth lines from an existing file when the options leave them out. With the change flag it opens the display for the pipe, then applies in order: the framelock target (`odyDoFramelock`, or a zeroed 260-byte parameter 3 when no framelock is wanted), the master or slave sync setting (-c m prints "Setmon is turning ON csync_en" and sets parameter 2 to 0, -c s prints "Setmon is turning OFF csync_en" and sets it to 1; any other letter prints "setmon: use -c m|s"), the external or internal genlock source (`XSGIvcSetScreenInputSyncSource` with -2 or -1), and the video format itself. For the format it parses `%dx%d_`; the sizes 1280x492 and 1280x984 and the type codes 0xf, 0x1b and 0x1c (stereo formats) switch the stereo mode (`XSGISetStereoMode` with the values 492 and 532 and mode 1 for 0x1b or 2 for 0x1c) and build the name `1280x492_120s` or `1280x492_114s`, the latter when two words of the info structure (at +0x28 and +0x18 from the record at the first argument plus 0x28) are 0 and 2; every other format first turns stereo off when it is on and copies the name. The name then goes to an unnamed helper at 0x1000c8bc with the display, the screen and the verbose flag, which loads the format; the splitter option calls another unnamed helper, 0x1000cbc8, in its place. The DAC-gain option ends the routine with `XSGIvcSetOutputGain` and a value of 5. Both the call to `fprintf` at 0x1000d8e0 and the call to `exit` at 0x1000d8ec appear in the listing.
